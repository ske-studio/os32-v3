## 0. なぜ「構造を組み直す」なのか

2026-09-17 に**カーネル帯域 1MB が 17KB 足りない**状態を踏んだ
([`../../archive/kernel_v21/TASK_KSTACK_USER.md`](../../archive/kernel_v21/TASK_KSTACK_USER.md))。共有メモリ帯が
カーネルスタックを飲み、**スタックが設計の 16KB ではなく 4KB しかなく**、
**余裕は 224 バイト**しか残っていなかった。誰も気づいていなかった。

応急処置で余裕は **34.4KB** に戻したが (2026-09-17 時点、カーネル本体 433.6KB / 予算 468KB)、カーネル本体は育ち続けている。
**v2.1 の時点 (2026-09-29) では予算を 596KB に広げたうえで 583.0KB を使い、残りは 13.0KB** — 数字の正典は
[`../../02_memory.md`](../../02_memory.md) §2-1 の生成ブロック (`tools/gen_memmap.py`、`make check` が照合)。ここの数字は写しなので、使うときは向こうを読む。
そしてこの先に積みたいものが、どれも小さくない (§3)。

**帯の中で削るのは延命でしかない。** v3 は「機能を足す」前に「入れ物を作り直す」。

## 1. 順序 (これは動かさない)

| 順 | やること | なぜその順か |
|---|---|---|
| 1 | **規約を C11 へ** (変数は**固定長を維持**) | `_Static_assert` は定数式でなければ**コンパイルエラー**。今の自作 `STATIC_ASSERT` は定数式でないと**黙って無効化される** (`kernel/shm.c` の 2 本が毎ビルド警告を出しながら何も検査していなかった)。**再配置を検査なしでやらないため** |
| 2 | **メモリマップの全体再配置** | §2。**ドライバの置き場とアプリへの払い出しを最初から勘定に入れる** |
| 3 | **ドライバの動的読み込み** | §3 |
| 4 | **PCI の列挙** | [`../realhw/PLAN.md`](../realhw/PLAN.md) §6 |
| 5 | **Intel 82557 のドライバ** | 同 §5 |

1 と 2 を**同時に動かさない**。どちらも全ファイルに触れるので、壊れたときに
**どちらが原因か切り分けられない**。この領域は静かに壊れる (§0 の 224 バイトがそれ)。

## 3. ドライバの動的読み込み (ユーザー指摘 2026-09-17)

### なぜ要るか — 数字

| | 大きさ |
|---|---|
| カーネル本体 | 583.0KB (2026-09-17 は 433.6KB) |
| 残り予算 | **13.0KB** (予算 596KB、v2.1 時点。2026-09-17 は 34.4KB / 468KB) |
| 現在のドライバ群 | 約 89KB (`drivers/` 70KB + `net/` 19KB) |
| これから足したいもの | PCI (数 KB) + 82557 (十数 KB) + …… USB は**単独で 100KB 超** |

**34KB (2026-09-17) でも足りず、v2.1 の時点では 13KB しか残っていない。** 静的リンクのまま積めば、2026-09-17 と同じことが必ず起きる。

### 土台は半分ある

`kernel/shlib.c` (12.4KB) が共有ライブラリを `0x400000` の 1MB 帯へ起動時に読み込む。
**ヘッダの値だけで配置を決め、番地を直書きしていない。**
**再配置とジャンプ表という一番面倒な部分は既に動いている。**

### ただし 3 つ違う

| | 共有ライブラリ | ドライバ |
|---|---|---|
| 特権 | CPL=3 のアプリ向け。USER で載る | **カーネル権限**。ポート I/O と割り込み |
| 呼ぶ向き | アプリが呼ぶ | **カーネルが呼ぶ** |
| 置き場 | アプリ空間 (`0x400000`) | **カーネル帯。そこが今まさに満杯** |

必要なのは KernelAPI とは別の**内側向けの取り決め** (ドライバが実装すべき口と、
カーネルが提供する口)。

### 設定は手動でよい (ユーザー、2026-09-17)

自動検出も依存解決も要らない。**起動時に一覧を読んで順に載せるだけ**で足りる。
一覧はファイルに持たせる (試験ランナーの `guest_tests.txt` と同じ考え方)。
これで実装がかなり軽くなる。

### 決めること

- カーネル帯のどこに置くか (**§2 と同時に決める**)
- 内側向けの取り決めの形。**KernelAPI の [ABI2] 追記のみの規則をここにも効かせるか**
- 読み込みに失敗したドライバをどう扱うか (**起動を止めるのか、その機能だけ諦めるのか**)
- どのドライバを外に出すか。**全部は出さない** — ブートに要るもの (IDE / コンソール) は
  静的のままでよい

## 3-1. HAL の棚卸し (ユーザー問い 2026-09-23: PCI を載せる前にどの層が要るか)

**層がある**: ポート I/O と CPU 原始命令 (`include/io.h` → `arch/x86/` + `platform/pc98/`、`check_arch_asm.py` が直書きを禁止) /
ブロックデバイス (`Device` の `blk_read/write` + CHS 変換、FDD/IDE/ATAPI/loop が同じ表) / FS (`VfsOps` 22 本) /
画面 (gfx バックエンド 3 本を probe 順に選ぶ) / コンソール出力 (`console` + `con_sink`) / マウス (バス / シームレス) /
PCI バス (列挙まで、2026-09-22)。

**予定がある**: NIC 境界 (`net/nic.h`、TASK_LAN_82557 L-C) / 音源バックエンド (§5-5 P3) / ドライバの動的読み込み (§3) /
ISA 非依存化の仕分け (arch_port §3 の 3)。

**無くて PCI の前に要る (提案、82557 = L-B の直前に 1 票、合計 3〜5KB)** → 設計票 [`TASK_HAL_WIRING.md`](TASK_HAL_WIRING.md) (2026-09-23):

| 欠けている層 | いまの状態 | 要る理由 |
|---|---|---|
| 割り込みの動的登録 | `isr_stub.asm` が装置ごとに固定の C ハンドラを `extern` で結ぶ (`fdc_irq_handler`、`irq_stub_nic_3/5/6`…) | PCI は BIOS が IRQ を割り当て、共有し得る。`irq_register(irq, handler, arg)` と共有時のチェーン (各ハンドラが「自分の割り込みか」を答える) |
| 8237 DMA の共通部 | `dma_setup` が `drivers/fdc.c` に閉じる (ch2 決め打ち) | CS4231 (#1/#3) が 2 つ目。チャネル・バンク・境界モード・`0439h` を 1 か所に |
| DMA 可能メモリ | 静的配列 + 整列 | PCM リング 16KB、82557 の CB/RFD。`dma_alloc(size, align, limit)` = 物理連続・64KB を跨がない・16MB 以下・物理番地を返す |
| PCI デバイスの結線 | 列挙表だけ | `pci_find` → BAR・IRQ を渡して `probe()` を呼ぶ最小の登録表。§3 の「内側向けの取り決め」と同じ形にしておき、後で外部モジュールにも開く |
| 時計 | `tick_count` 100Hz のみ | `sys_time_us()` (PIT ラッチ) と 1kHz tick (§5-5) |

シリアルは 2 系統目 (16550 の 2nd CCU / PCI シリアル) が要るまで層にしない — 要らない抽象は増やさない。

> 2026-09-23: カーネル本体の予算は KHEAP の切り直し (320 → 192KB) で 596KB に。帯の切り直しは [`TASK_MEMMAP_V3.md`](TASK_MEMMAP_V3.md)。

## 5. 温めているアイデア (ユーザー、2026-09-17) — **計画ではない**

**まだ決まっていない。** 形になっていないものを計画表に混ぜると順序が狂うので、

### 5-1. ネットワーク越しのホストを仮想メモリとして使う

386 はページングを持ち、ページフォルトを捕まえられるので、**原理的には成立する**。
Host Services のワイヤ (`net/link.c`) も既にある。

**ただし確かめるべきことが多い。**

- **待ち時間**。LAN の往復はミリ秒単位。**ディスクのスワップより速いとは限らない**
- **再入**。ページフォルトを処理する最中に NIC ドライバを呼ぶ。**その NIC ドライバが
  触るメモリがスワップアウトされていたら詰む**。ここの切り分けが設計の核心
- **どのページを対象にするか**。カーネル帯は当然除外。アプリ帯のどこまでか
- **落ちたときの答え方**。ネットワークが切れたらどうなるのか

**先に測るべき**: 実機の LAN でページ 1 枚 (4KB) を往復させたとき何ミリ秒かかるか。
**それがディスクより遅ければ、この案は成立しない。**

### 5-2. V86 の装置要求をホストへ逃がす (ユーザー、2026-09-17)

**狙い**: 実機に C バスなどで挿さないと動かない装置を、**ホストが機能を提供して
仮想的に見せる**。**86 ボードを実機に用意しなくても互換性を出せるのではないか**、という発想。

**土台は既にある。** `kernel/v86_io.c` が V86 ゲストの I/O ポートを
**素通しにするものと、捕まえて仮想化するものに分けている** (観測モードもある)。
**「ホストへ逃がす」は、既にある仕組みの行き先を 1 つ増やす形**に収まる。

具体例として挙がったもの:

- **EMS (EMM386 のような要求) をネットワークへ逃がす** — 5-3
- **実機のレガシー VRAM をホストへ転送する** — 5-4
- **86 ボードなどの装置をホストに演じさせる** — 本項

#### PM の最初の見立ては **2 点で誤っていた** (ユーザー指摘で訂正、2026-09-17)

PM は「読み出しは返事を待つから往復が要る」「DMA は捕まえられない」として
86 ボードを難しいとした。**どちらもホストとゲストが対等だという前提に立っていた。**
**ホストは圧倒的に速い**という指摘を受けて訂正する。

| PM の当初の見立て | 訂正 |
|---|---|
| 状態の読み出し (`in`) は 1 回ごとに往復が要る | **要らない。** 「まだ処理中か」はホスト側では**常に準備完了**。遅いハードウェアだから待ち合わせが要ったのであって、**値が予測できるなら手元で答えられる**。ホストから先回りして状態を押しておけばよい。往復が要るのは**本当に予測できない値だけ** |
| DMA は命令ではないので捕まえられない | **言い過ぎだった。** データの移動は捕まえられないが、**DMA コントローラの設定はポート I/O なので捕まえられる**。転送元の番地と長さが分かるなら **OS32 が自分でゲストのメモリを読んでホストへ送れる**。実際に DMA を起こす必要は無い (エミュレータが普段やっていることと同じ) |

#### 残る難しさ — **ホストの速さでは解決しないもの**

1. **揺らぎ。** 音は一定の間隔で届かないと破綻する。往復時間は平均が速くても
   **ばらつく**。対処は先読みして貯めることだが、**貯めた分だけ遅れる**。
   音楽の再生なら問題にならないが、**操作に対する反応が要る場面 (ゲームの効果音) では
   聞こえる遅れになる**。
2. **切れたときの答え方。** 演奏の途中でネットワークが落ちたらどうなるのか。
   **DOS プログラムは装置が消えることを想定していない。**

**どちらも致命的ではなく設計で扱える範囲**だが、**先に決めておかないと後で効く**。

#### 別の切り口 — 実現性も価値も高いほう

**「実機に無い装置を、あると見せかける」こと自体が使える。** 例えば実機に無い
プリンタを DOS に見せて、実際の出力はホストのファイルに落とす。これは
**Host Services で既にやっていること** (`lpr` がホスト側で印刷する) を
**V86 の DOS からも使えるようにする**話になる。

**86 ボードの互換性より先にこちらのほうが、実現性も価値も高い** (PM 見解)。

### 5-3. V86 の EMS 要求をネットワークへ逃がす (ユーザー、2026-09-17)

**EMS は、ネットワーク越しの記憶に合う唯一の形をしている。**

| | 一般的な仮想メモリ (5-1) | **EMS** |
|---|---|---|
| いつ転送するか | ページフォルトで**予測不能に**起きる | プログラムが**明示的に**バンク切り替えを要求する |
| 再入の危険 | ページフォルト処理中に NIC を呼ぶ → **NIC が触るメモリが退避済みだと詰む** | **無い。** 割り込みの外で、通常の文脈で処理できる |
| 単位 | 4KB を細かく | **16KB を粗く**。往復あたりの効率が良い |
| 遅さの許容 | 遅いと全体が止まる | **元々バンク切り替えは遅い**。DOS 側が織り込み済み |

**5-1 で PM が「設計の核心」と呼んだ再入の問題が、EMS には最初から存在しない。**

**現状**: INT 67h は捕まえていない (`kernel/v86.c:238` の `0x67` は**命令の前置バイト**で別物)。
V86 で BIOS 呼び出しを捕まえる仕組みは動いているので、**INT 67h を 1 本足す形**に収まる。

### 5-4. 実機のレガシー VRAM をホストへ転送する (ユーザー、2026-09-17)

**これは [`../realhw/PLAN.md`](../realhw/PLAN.md) §4 の穴を直接埋める。**
実機には画面を取る手段が無い — 今の道具はすべてエミュレータのデバッグ機能に依存していて、
スクリーンショットの口も実機には無い。**画面が見えないまま実機を触ることになる。**

| 対象 | 番地 | 量 |
|---|---|---|
| テキスト VRAM | `0xA0000` から | **数 KB**。CUI の確認はこれで足りる |
| グラフィック面 | `0xA8000` / `0xE0000` から | 640×400×16 色で 128KB |

**テキストだけなら数 KB で、100BASE-TX なら一瞬。** CUI の開発中はこれで十分で、
**試験ランナーが今やっている「画面を読んで確かめる」がそのまま実機でできる。**
グラフィックは重いので必要なときだけ 1 枚送る形になる。

### 5-5. ソフトウェア 86 互換音源 (ユーザー提案 2026-09-23) — **候補、v3 後半** (C11 移行 (§1 の 1) と動的読み込み (§3) の後)

**提案**: CS4231 (MATE-X PCM) のような PCM 再生があり CPU が十分速い機械では、**PC-9801-86 (YM2608 = FM 6 声 + SSG 3 声 + リズム 6 声 + ADPCM、86 型 PCM) をソフトで合成して PCM に流す**。
OS32 のアプリ (`snd` エンジン) からも、**V86 の DOS ゲスト** (0188h〜018Fh / A460h 系のポートをトラップ) からも使えるようにする。

**PM の見立て (2026-09-23)**: 成立する。根拠と段取り:

| 段 | 内容 | 検証 |
|---|---|---|
| P1 | **CS4231 の PCM ドライバ** (設計票 [`TASK_PCM_CS4231.md`](TASK_PCM_CS4231.md)、2026-09-23): `0F40h` で DMA #1 (or #3) と INT を選び、8237 の DMA リング (64KB 整列、二重バッファ、半分ごとの割り込み)、16 ビットステレオ 22.05/44.1kHz。KAPI で「次のブロックを書く」 | **NP21/W が CS4231 を再現している** (`src/cbus/cs4231io.c`、`cs4231.enable`) ので**エミュレータで開発できる**。実機は Ra266 |
| P2 | **合成器の核は Rust (`no_std`、C ABI の staticlib)** で書く (ユーザー提案 2026-09-23、PM 同意): 既存の Rust ワークスペース (`userland/rust/`、ターゲット `i686-os32-none`) と同じ流儀で、`extern "C" fn opna_render(state, out, n)` の形。割り当てもパニックも無し。同じクレートをホスト (x86_64、std) でも組めるので**波形の md5 を NP21/W の出力と突き合わせるホスト試験がそのまま書ける**。移植元は NP21/W の `fmgen` (C++、OPNA 2,166 行、cisc の MIT 互換) か元 NP2 の C 版。Rust を選ぶ理由: FM 合成の移植で一番多いバグは位相・エンベロープの**回り込み演算と表の添字**で、`wrapping_*` と固定長配列 + マスク添字で明示できる。LLVM なので生成コードは C と同等。**アセンブラは最初は書かない** — kstring と同じ手順で実機 (Ra266) で測り、演算子ループが目標 (44.1kHz で CPU 1 割) を超えるときだけ、その 1 か所を asm にする。先に効くのは (a) i686 向けのコード生成 (カーネルは `-march=i386` だが、このモジュールは速い CPU でしか載せない)、(b) ブロック単位の描画、(c) 表の事前計算。**カーネル予算 (残り 21KB) には入らない** → v3 §3 の動的読み込みの最初の顧客の 1 つ (82557 の次)。**V86 のゲストが CPU を握っている間も鳴らす**ため、描画は PCM の DMA 割り込み (カーネル文脈) から呼ぶ — ユーザランド常駐では V86 中に走れない。ゲストのポート書きはカーネルがトラップして時刻つきのレジスタ列に積み、割り込みごとに描画側が消費する | ホスト試験: 既知のレジスタ列 → 波形の md5 を NP21/W の出力と突き合わせ。実機で CPU 使用率を実測 |
| P3 | **OS32 側の口**: `snd_engine` (YM2203 のレジスタ書き) の下にバックエンドを 2 つ (実 OPN / ソフト OPNA → P1 のリング)。実 FM の無い Ra266 でも既存の BGM が鳴る | NP21/W (実 OPN あり) と実機 (無し) の両方 |
| P4 | **V86 への提供**: `kernel/v86_io.c` は今 0188h〜018Fh を素通し (実 OPN を明け渡す設計)。トラップ側へ倒し、レジスタ書きを P2 へ、86 型 PCM の FIFO (A460h〜A46Ch) も演じ、FIFO 割り込み (INT5) を `v86_pic.c` 経由でゲストへ。ゲストが割り込み禁止のまま長く走る DOS ゲームでは PCM が途切れうるので、リングは 100ms 以上 | 実機で DOS ゲーム (FM 曲) |

**設計の前提 (ユーザーと合意、2026-09-23)**:

| 項目 | 決めたこと | 理由 |
|---|---|---|
| レート / 精度 | **44.1kHz / 16 ビット** (CS4231 の上限は 16 ビット)。内部は 24 ビット固定小数点で混ぜて最後に丸める | 当時の標準と CD-DA との整合 |
| リサンプラー | FM / SSG は fmgen と同じく**出力レートで合成** (位相増分を合わせる) なので不要。**PCM 系 (86 型 PCM の FIFO、ADPCM) だけ線形補間** | 86 の PCM は元が 12 ビット相当 |
| バッファ | DMA の**半バッファ 2048 サンプル (46ms) × 2 = 16KB**、下限 1024。**描画の粒度は 256** (割り込み 1 回で 256 × 8) | 埋める側が FDC の DMA 待ちなどで数十 ms 止まり得る。256 は描画単位であってバッファではない |
| 時刻 | レジスタ書きに **µs の時刻**を付け、描画側がブロック内のサンプル位置で順に反映。時刻は **`sys_time_us()` = `tick` + PIT ch0 のラッチ読み** (0.4〜0.5µs、割り込み不要、386 でも使える。TSC は使わない) | 半バッファ単位に丸めるとキーオンが 46ms の範囲で揺れる |
| 事象 (タイマ A/B、テンポ) | **IRQ0 を 100Hz → 1kHz** に (発想の逆転: `tick_count` は 10 回に 1 回進めて 10ms の意味を保ち、既存コードは無変更。新しい `tick_ms` を足し、100Hz で動かしている `snd_tick` / `link_tick` は分周)。10kHz は割り込みだけで 386 の 2〜3 割を食うので不可 | OPN タイマ B は 1 ステップ ≒ 0.58ms、±1ms のジッタで足りる |
| 対象 | 0188h〜018Fh の **OPN (26K) / OPNA (86) 互換口**。VX 世代のゲームは大半が 26K 駆動 (PMD / FMP 系、タイマ B のテンポ)、OPNA は上位互換なので 1 つの合成器で両方 | OS32 自身の `snd` も YM2203 前提 |

順序は (1) `sys_time_us()` (小さく単独で価値がある。v1.x でも可)、(2) IRQ0 1kHz (実機と NP21/W で割り込み負荷を実測してから既定に)、(3) 合成器のタイマ A/B は (2) の上で。

**CPU の勘定**: NP2 は P100 級のホストで PC-98 全体 (CPU 命令エミュを含む) を回しながら OPNA を合成していた。合成だけなら 266MHz で 22kHz は数 % 台、44.1kHz でも 1 割程度の見込み (実測は P2 で取る)。V86 のゲスト自身は 386/486 向けに書かれているので余裕はある。

**順序の理由**: P1 は単独で価値がある (PCM 再生) ので先に。P2〜P4 はカーネル外に置く前提 (v3 §3 の後)。§5-2 の「86 ボードをホストに演じさせる」案は、この案が**ホスト無しで**同じ目的を達するので置き換える。

### 5-6. ネットワーク越しの CD (ホストサービスが CD 装置を演じる) でインストールする (ユーザー提案 2026-09-24) — **候補、v3 のかなり後**

**狙い**: PC-9821 の内蔵 LAN 搭載機 (Ra266 の Intel 82557) では、CD を焼かずにホストの ISO からインストールできるようにする。
**仕組み**: ホストサービス (`tools/host_agent.py` の延長) が ISO を**読み取り専用のブロック装置**として出し、ゲストはそれを **CD 装置** (`VFS_DEV_CD`) として登録する。`fs/iso9660.c` は CD 装置しかマウントしないので種別で出すのが鍵。`/cd0` にマウントすれば **`cdinst` は無変更**で動く。

- 要求は「LBA・数 → データ + CRC」の 1 種類。読み取り専用なので再送に副作用が無く、SerialFS (TASK_SERIAL_HOSTFS) の応答キャッシュや番号ずれの隔離がほぼ要らない。
- 100BASE-TX なら ISO (約 7.5MB) は数秒〜数十秒 (シリアル 115200 では 10 分以上)。
- **起動は FD のまま** (内蔵 LAN の BIOS 起動は無い見込み、未確認): FD 起動 → ネットワーク CD をマウント → `cdinst`。
- 前提: 82557 ドライバ (TASK_LAN_82557 の L-B) とゲスト側の Host Services のリンク。
- **対応機種は「内蔵 LAN 搭載機」と宣言しつつ、設計はリンクの上 (NIC 非依存)** に置く (PM 提案) → LGY-98 / NP21/W で開発・試験できる。同じ「読み取り専用の CD 演技」はシリアル越しでも動かせる (LAN の無い機種の逃げ道、遅い)。
- **試験の経路は既存**: NP21/W の ai-debug フォークは LGY-98 の模擬を **TAP 無しの socket バックエンド** (`NP2NETSOCK=127.0.0.1:8026`、状態は `/api/net`) でホストの `tools/host_agent.py` に繋ぐ (EtherType 0x88B5、リンク層 L0〜L3、Host Services のクリップボード / 印刷が合格済み、POLICY_DEBUG §4-45)。ネットワーク CD はこの上に読み取り専用のブロック要求を 1 種類足すだけで、エミュレータで開発・試験できる。実機は 82557 → ノートの `tools/lan_bridge.py` → `host_agent.py`。

### 5-7. HostDrv を Host Services 経由でも使える経路にする (ユーザー、2026-09-24) — **候補**

今の `/host` は NP21/W の HostDrv (ハイパーコール) 専用で、実機には無い。ユーザー: 「ホストドライブはホストサービス実装後に使える経路にしたい」。Host Services (LAN のリンク層、実機は 82557) の上にホストのファイルを出す FS を置き、`/host` を実機でも使えるようにする。名前の規則 (Win32 の禁止文字・正しい UTF-8、TASK_VFS_FD_PATH のラリー 3) はこの経路でもそのまま使う。§5-6 (ネットワーク CD) と同じ土台。SerialFS (TASK_SERIAL_HOSTFS) は LAN の無い機種の同じ役。
