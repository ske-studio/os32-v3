## 1. 役割の細則

| 役 | できること | してはいけないこと |
|---|---|---|
| **PM** | 分解・受入判定・git 操作・[D1]〜[D3] の承認取得・エミュレータの**観測** (`gui_gate.py` 等の PM 所有ツール)・着地のときの `make all` + `make check` (§0) | 実装。手を動かし始めたら分解に戻る |
| **コーダー** | 実装 + ホスト TDD (`tools/tests/`、新挙動ごとの RED→GREEN の記録)、`make check-fast` / `make check-changed` | 配備・エミュレータ操作・`main` への取り込み (コミットは自分の worktree のブランチまで) |
| **レビュアー** | 独立レビュー、所見の列挙 (§5) | — (PM はレビューを自分で代行しない) |
| **テスター** | 配備 (`os32-cycle deploy`)・回帰・台本つきの実機操作の実行 | 合否の判断。台本にない操作。ini |

触る前に、ゲスト側の設定 (`gfxmode` など) で足りないかを先に確かめる (ini の変更より先)。

## 2. 起動

```bash
# PM — 対話セッションで /model claude-opus-5-5

# コーダー — Claude Code の Agent tool
#   model: "opus" (Codex の P1 を含む修正は "fable")、worktree は PM が明示的に切って渡す
#
#   **基点の確認 (2026-09-15 追加、2 度踏んだ)**:
#     - PM は依頼文に**期待する基点の SHA** を書く。
#     - コーダーは最初に `git log --oneline -1` を実行し、**その出力を報告の先頭に書く**。
#       期待と違えば `git checkout <SHA>` で合わせる (`--hard` は使わない)。git が
#       ガードで弾かれて確かめられないなら**その旨を報告し、推測で書かない**。
#     - PM は着地前に worktree の `git log -1` を自分で確認する。
#     - 参照すべき文書やファイルが「無い」と報告されたら、PM はまず基点を疑う。

# レビュアー — PM が直接依頼する (§5)。Bash の run_in_background で:
timeout 1500 codex exec -s read-only "<依頼文>" < /dev/null > review.txt 2>&1
#   代行 (Codex が astra でないとき): Agent(model: "fable")、読むだけ・編集禁止

# テスター — 単発 / 定型回帰 / ログ確認
python3 tools/emu_agent/agent.py run "<タスク>"
python3 tools/emu_agent/agent.py suite tools/emu_agent/tasks/regress.txt
python3 tools/emu_agent/agent.py tail
```

テスターへの投げ方と結果の読み方はスキル **`os32-local-ai`**、何を確かめるべきかの選択は
スキル **`os32-build-verify`** が正典。

厳格版が要る操作 (GUI 入力など、誤操作が実機を壊す経路) は `tools/emu_agent/playbook.py` を使う。
承認済み JSON 台本と操作・引数・順序が完全一致したものだけを実行し、既定は dry-run。

**FLM のモデルは、ユーザーがロード済みのものだけに投げる。**
`/v1/models` に並んでいることはロード済みを意味せず、未ロード名を投げると自動ダウンロードが始まる。

## 3. 規約 (3 行)

1. **PM が止まってよいのは 4 つだけ** — [D1]/[D2]/[D3] の承認、仕様の分岐、スコープ拡大、
   そして**独立レビューが要る地点** (§5 の書式でユーザーに報告して渡す)。
   それ以外は承認済みスコープを最後まで進める。各ステップの終わりに「次に進んでよいか」を訊かない。
2. **ブロックできるのは到達可能な反例を伴う所見だけ**。現契約の違反はブロック、将来要件は別ゲートに落とす。
   反例を示せない指摘で、正しいコードを変えない。誤検出はレビュー記録側を訂正する。
3. **エミュレータは同時に 1 オペレータ**。コーダーは触らない。共有ファイルの編集は PM が直列化する。

## 4. 合否の判定

テスターの `RESULT: ok` は**自己申告**として扱う。合否は PM が
`tools/emu_agent/logs/<session>/steps.jsonl` の `obs` を読んで決める。
配備の反映確認は [08_build.md §8-4](../../08_build.md#配備3経路) の経路と、
`os32-cycle deploy` のゲスト側サイズ照合による ([V1]/[V4])。

## 5. レビュー依頼の出し方

現行のレビュアーと代行の規則は §0。**Codex は過去にハングした**ので、依頼は対象ファイルを列挙して範囲を絞り、
`timeout` を付け、判定は `## 判定` を `rfind` で拾う。起動は Bash の `run_in_background` で直接行い、完了通知で読む
(`&` で投げて `pgrep -f "codex exec"` で待つと、待機ループ自身のコマンド行に一致して永久に待つ)。

依頼文 (Codex でも代行の Fable でも同じ) には次の 5 点を揃える。PM は自分でレビューを代行して「問題なし」と結論づけない
(P3 だけの直しの確認は §0 のとおり PM が差分を読んで着地してよい)。

| 項目 | 内容 |
|---|---|
| 対象 | コミット SHA か `git diff` の範囲、主なファイル |
| 変更の要旨 | 何を、なぜ変えたか (3 行以内) |
| 見てほしい観点 | 正しさ / C89・[C1]〜[C4] 準拠 / ABI / 資源回収 など、絞って挙げる |
| 判定基準 | **到達可能な反例を伴う所見だけがブロック要因**。将来要件は別ゲート |
| 既知の未確認 | ゲスト未検証の範囲、呼び出し元が無い API など |

所見が返ってきたら、**鵜呑みにせず自分で反例の到達可能性を確かめてから**着手する
(2026-09-09 の PEGC 回帰は、実機で `sys_frozen_hot` を読んで確定させてから直した)。
誤検出だった場合はコードではなくレビュー記録側を訂正する。

**2026-09-12 ユーザー決裁**: Codex (`codex-cli`、`gpt-6-astra`) のクォータが回復したので、設計票・実装の独立レビューは
**PM が `codex exec -s read-only` で自動的に依頼し、所見の反例を確かめて票を直し、承認が出るまで往復する** (枯渇したら
ユーザー経由に戻す)。起動は `codex exec -s read-only "<依頼文>"` (読むだけ、コードは直さない、リポジトリは trusted 登録済み)。
依頼文には対象の票と参照コードのパス、求める出力の書式 (判定 / blocker と到達可能な反例 / 非 blocker) を書く。
**往復は 3 回まで**: 3 回のレビューで Approve に至らなければ、争点を整理してユーザーに判断を求める (ユーザー指示 2026-09-12)。
**網羅性の要求 (ユーザー指示 2026-09-13)**: T9 の実装レビューで往復ごとに別領域の blocker が 1 件ずつ出て 5 往復しても
収束しなかった。依頼文には必ず「**今回の往復で見つかる到達可能な欠陥をすべて挙げる** (1 件見つけて止めない)。
対象の経路を列挙し (例: CPL=3 に持ち込んだコードが呼ぶ KAPI 全部、カーネル帯のポインタを渡す箇所全部、
端末モデルに依存する出力全部)、経路ごとに見た / 見ていないを明記する。次の往復で新しい領域の指摘を出すなら、
今回なぜ見えなかったかを書く」を入れる。往復数を数える単位は「指摘の集合」であって「1 件」ではない。

#   これを踏み、後者は「HEAD は 086bda5」と**確かめずに**報告した。規則:
#     - PM は依頼文に**期待する基点の SHA** を書く。
#     - コーダーは最初に `git log --oneline -1` を実行し、**その出力を報告の先頭に書く**。

#       ガードで弾かれて確かめられないなら**その旨を報告し、推測で書かない**。
#     - PM は着地前に worktree の `git log -1` を自分で確認する。
#     - 参照すべき文書やファイルが「無い」と報告されたら、PM はまず基点を疑う。

# レビュアー — 起動コマンドは無い。PM がレビュー依頼をまとめてユーザーに報告し、
