## 0. 現行の体制

| 項目 | 現行 |
|---|---|
| **PM** | Claude Code の対話セッション、**Opus 5.5** (`claude-opus-5-5`)。分解・依頼パック・統合・受入判定・git 操作・[D1]〜[D3] の承認取得・エミュレータの操作 |
| **実装者** | **Codex**、worktree 隔離。既定は `gpt-6.1-sol` (手順が明確な実装)。**`gpt-6-astra` (上位) を使うのは**: 設計票の起草 (下の行)、レビューが重大 (P1 / major) と判定した指摘の修正、判定ロジックの作り直しや組合せ検証など難しい依頼、往復が止まったとき。**sol が同じ仕事で実装の誤りを 3 回出したら、同じ worktree・同じ依頼パックで astra に切り替える** (ユーザー指示 2026-10-06。数えるのはレビュー P1/P2・列挙した検査・取り込みの全体検査・ゲスト受入で見つかった実装の誤りで、環境や依頼パックの誤りは数えない — そのときは依頼パックを直す。切り替えるときは 3 回の経緯を依頼文の先頭に書く)。起動の形は §2 |
| **独立レビュアー** | **差分のレビューは `gpt-6-astra`** (§2 の Codex read-only の形、所見は §5 の書式) — sol の実装はすべて astra が見る。**Claude のサブエージェント** (`.claude/agents/reviewer.md`。**Opus 5.5** (`claude-opus-5-5`)) が設計票・判断用文書のレビューを担当する。差分を見るのは、astra が書いた実装・修正 (同じモデルに自分の仕事を見させない) と、PM が大物と判断した sol の差分 (カーネル層・判定ロジックの作り直し・複数サブシステムにまたがるもの) に astra と並べて見せるときだけ。どちらも読み取りだけ、書き手と別のモデル、実装者の報告は渡さない、冒頭でモデル ID を名乗らせる。**ドライバ設計は Codex と Claude の両方の目を通す** (astra が書いた設計票を Opus が見れば満たす)。尽きたらスキル `os32-local-review`、それも無ければ止まって報告 |
| **カウンターの原則** | 設計票と判断の材料になる文書は **astra が書き、Opus 5.5 のサブエージェントがレビュー**。sol の実装 → astra がレビュー。astra の実装・修正 → Opus 5.5 がレビュー。同じモデルに自分の仕事をレビューさせない (PM も Opus 5.5 だが、レビューは別のサブエージェントに出し、PM が代行しない)。**事務的な文書 (台帳の照合・受入の記録・状態行・HANDOVER) は PM が書く** (2026-10-14)。3 往復で決着しない争点はユーザーへ |
| **設計票** | **`gpt-6-astra` が書き、Opus 5.5 のサブエージェント (`.claude/agents/reviewer.md`) がレビューする**。astra は `codex exec --skip-git-repo-check -m gpt-6-astra -s workspace-write -C ~/os32-tmp/run/<題> "<依頼>" < /dev/null` の形で (`~/os32-tmp` は git の外なので `--skip-git-repo-check` が要る)、リポジトリは読むだけ、書くのは `-C` の下の票の 1 ファイルだけ (依頼に置き場を書く)。Opus は読み取りだけで、所見は P1/P2/P3 と反例。往復の記録は `opus_r<N>.md` / `astra_r<N>_response.md`、票は `<名前>.r<N>.md` で版を残す。**初版から「観測で判定できる受入条件」と「既存の利用者 (アプリ・道具・試験) が退行しないか」を書く**。確定版は本文を持ち、前の版を参照でつながない (2026-10-14 反省会)。**3 往復で決着しない争点はユーザーが決める**。**依頼の前提**: OS32 に不要な防御を増やさないため、設計・レビューの依頼の冒頭に「OS32 は単一利用者・単一タスク・協調切替で攻撃者を想定しない。守るのはハードウェアの誤動作とバグに対する頑丈さ (固まらない・壊さない・戻せる)。権限分離の強化や悪意ある入力への防御は、求められない限り足さない」と書く。PM は、OS32 の前提で起こらない脅威に基づく所見を採らないか P3 に下げ、採否を記録する。**範囲とレビュー往復の管理**: (1) 依頼パックに触ってよいファイルの範囲を書き、範囲の外は報告で理由を述べさせる。(2) 設計票は PM が節の枠と行数の上限を先に決めて渡す。(3) 取り込みの前に PM が散らかり (作業ログ・未使用の定義・範囲の外の文書) と変更ファイル数を確かめる。(4) 同じ論点が 2 往復続いたら PM が扱いを決めて打ち切る。(5) astra の差分の Opus レビューでは、過剰な防御と範囲の外の変更も見させる。**後片付けは Claude 系に任せる**: astra の実装の後、同じ worktree で Opus 5.5 のサブエージェントが片付ける (作業ログ・一時ファイル・未使用の定義・重複・範囲の外の変更の差し戻し・体裁)。判定の論理には触らず、論理の直しが要れば報告だけして astra へ戻す。片付けの差分は PM が読んで受ける (小さい機械的な直しの枠)。そのあと別のインスタンスの Opus レビュアーが全体を見る |
| **実行の道具** (役ではない) | 配備・回帰・ゲスト操作は PM が**決定的な道具**で回す: スキル `run-os32` (`driver.py`)、`tools/guest_tests.py`、`tools/emu_agent/playbook.py`、`tools/np21w_ctl.py`。ローカル AI (`tools/emu_agent/agent.py`、スキル `os32-local-ai`) は任意。合否は PM が観測を読んで決める (§4) |
| **検査** | **実装者は軽く、変異の確認は PM が 1 回** (重複実行と待ちを減らすため)。**実装者の完了条件**は `make all` と**足した・触った試験** (直接の試験だけ) を `MUTATE=0` で rc=0、それに `python3 tools/check_select.py --lint` (数秒。対応表の登録漏れで PM の全体検査が落ちるのを防ぐ — ユーザー承認 2026-10-16)。変異・`--select` の候補の全部・静的 5 本は回さない。**Tx の流れ (複数の段に分けた実装、T4 から正式、ユーザー決定 2026-10-17 — T3ab の試行の結果)**: 段ごとの完了条件は `make all` の代わりに `make kernel` (ユーザーランドの像に触る段はその像も) + その段の直接の試験 `MUTATE=0` + `--lint`。最後の段の後、レビューに出す前に 1 回だけ、`make all` + `check_select.py --select --files <Tx 全体の差分>` の候補を `MUTATE=0` + 静的 5 本を実装者が回す (段の外の既存試験・静的検査の追従漏れをレビュー前に拾う — T3ab の手戻りの多くがここだった)。その後はレビュー → PM の取り込みの検査 (下の 3 段)。KAPI・配置の世代が変わる取り込みは、PM が `make clean` を先に挟む ([ABI3])。検査を途中で止めて最初から回し直さない。sandbox で動かない runner (native) は回さず報告に書く。**PM** はレビューが通ってから取り込みの検査を 1 回だけ回す (下の 3 段。(2) の候補は `MUTATE=1` で、各試験の正常の対照も回る)。落ちたら実装者に直させ (直した所の試験だけ `MUTATE=0`)、PM は落ちた検査だけ回し直す。**合格に数えるのは最後の変更より後のログだけ**。新しく足した・変えた試験は PM が `tools/test_changes.py` の要確認で確かめる。変更が依頼の範囲から広がったら実装者は触ったファイルを報告に列挙し、PM が `check_select.py` で候補を出し直す。**取り込みの検査は 3 段**: (1) **文書だけ** (差分が `docs/`・`*.md`・`.claude/` だけ) は `check-docs-status` `check-docs-links` `check-docs-orphans` `check-constraints`。(2) **小さい取り込み** (P3 の直し、PM が着地する機械的な小さい依頼、カーネル・ユーザーランドに触れない `tools/` だけの変更) は `make all` + `check_select.py --select --files <差分>` の候補 + 静的 5 本 + `--lint`。(3) **全体 (`make all` + `make -k check`) は節目に PM が統合した状態で 1 回** (`-k` を付ける — 付けないと最初の失敗で残りの検査を打ち切り、落ちた検査だけを回し直すと回らなかった検査がすり抜ける。2026-10-17 に check-h4-manifest-host がこれですり抜けた、ユーザー承認同日) — ゲスト受入・実機配備の前 (試す版は必ず全体を通ったもの)、カーネル層 (POLICY_DEV §1) を変えた段の取り込み、試験の仕組み (`check_select.py`・`build/checks.d`・変異の枠組み) を変えた取り込み、(2) で push したものがあって前回の全体から 1 日たったとき。どれにも当たらない取り込みは `make all` + `make check-fast`。全体を飛ばして push したら HANDOVER §1 の main 行に「最後の全体検査: <SHA>」を書き、次の節目で追いつかせる。GitHub Actions (push ごとに check-fast) を安全網として必ず見る。rc を読んでから push。**修正のやり直しの中で全体検査を回さない** |
| **並行** | **触るファイルが衝突しない段は、並列で出せるだけ出してよい**。衝突しうる段 (同じファイル・同じ生成物・同じ世代) は直列にする。共有の登録ファイル (検査の目録など) の衝突は PM が取り込みで解く。 **ただし試験・検査の実行は全体で同時に 2 本まで** (ユーザー指示 2026-10-09) — 実装者も PM も `make check-*`・`test_*.py` は `~/os32-tmp/bin/check_slot.sh <名札> <コマンド>` を通す (依頼文に書く)。全体検査は `~/os32-tmp/bin/check_slot.sh` の枠を通す。エミュレータの操作者は同時に 1 人 |
| **段の大きさ** | 1 段 = **独立して受入できる契約・挙動** (実装 + レビューの直し + 対象の受入で半日〜1 日が目安)。同じ受入条件への直しは**同じ worktree・同じレビュアー**で続ける (fix の段を新しく切らない)。**fix の依頼は所見に書かれた直しだけ** — 範囲の外の P3 (性能・整理) は台帳か次の段へ回し、P1/P2 の直しと混ぜない。**PM の文書の直し (台帳・票の追記) は段の worktree に混ぜず、取り込みの後に main へ別のコミットで入れる** (ユーザー承認 2026-10-08)。未結線の先行部品は、結線先が決まっているときだけ分ける。**受入条件 (事前レビューの反映後) が 10 項を超える段は、依頼パックを書く時点で分ける** — 同じ取り込みに入れるべきもの (契約の切替と世代の更新など) は分けず、受入台本・文書の固定値・記録を後ろの段へ。走らせた段は、timeout に当たるか、最後の検査を 3 回以上回し直したら止めて分ける (ユーザー承認 2026-10-08)。ゲストの台本は実ゲストで目的を達するまで閉じない。ゲスト受入は、退行の危険が大きい段 (カーネルの heap・exec・paging の挙動を変える段) を取り込んだところで、それまでのホストだけの段とまとめて行い、その上に次の段を積まない |
| **取り込みの順** | 上の「検査」の 3 段のうち当たるものを回す → rc=0 なら push → **GitHub Actions の結論 (build・check) を確かめ、HANDOVER §1 の main 行に書く** (X-3 の放置の反省、2026-10-14)。受入まで済んだ段の記録は archive へ移し、閉じた台帳の行を片付ける (票は 1 段 10 行に戻す)。生成文書は `make docs-gen` で `build/out/` に作る (コミットしない)。 |
| **記録** | 票に人が書くのは **1 段 10 行以内** — 決定・未確認・持越し・証拠の所在。**受入の結果は票・台帳・HANDOVER には「合否 1 語 + 証拠のパス」だけ**、中身は証拠の `RESULT.md` に (HANDOVER §2 を長文にしない)。受入の観測スクリプトは `tools/accept/` にだけ新しく作る (ユーザー承認 2026-10-10、実施 2026-10-14)。コマンド・runner・rc・時刻・RED/GREEN は道具のログに残し、票に貼らない。契約の変更は仕様の正典へ書く |
| **持越し** | 延ばした試験・SKIP・ホストだけの合格・未結線は [DEFERRED_TESTS.md](../DEFERRED_TESTS.md) の 1 か所に書く (何を・なぜ・どの関門で必ずやるか)。そこに無い SKIP は合格に数えない |
| **レビューの重さ** | P3 だけの直し、および**機械的な小さい依頼 (文言・表示・設定の追従など、試験を含めて 30 行程度まで、判定ロジックを変えない)** は PM が差分を読んで着地する (ユーザー決定 2026-10-14)。P1・P2 の直しの確認は**前回と同じレビュアーに差分だけ**。**3 往復で決着しない争点はユーザーへ** |
| **決裁** | PM の推奨は**基本的に承認** (その範囲で止まらずに進める)。**[D2] の操作と実機の物理操作は個別に承認**。互換の無い更新 (配置の世代や ABI が変わり、新旧のカーネルとユーザーランドが混ざると起動しない) を実機に入れるときは、手順をユーザーに示してから行う (2026-10-16)。NP21/W の ini を変えてよいのは PM だけ (原本を残す経路で、終わったら戻す — スキル `os32-emu-config`) |
| **場所** | 開発は os32-v3 (このリポジトリ)。os32 の v2.x は戻り先で新機能を入れない ([ROADMAP.md §0-1](../../ROADMAP.md))。**worktree は `~/wt/os32-v3/<名前>`** に作り (ホーム直下に作らない)、取り込んだら撤去する。一時ファイルは `~/os32-tmp/` の下 |

**見直し**: 次の REVIEW_<日付> で §4-1 の各項目を「道具で機械化した / まだ人が見る / 直近の段で出ていない」に分け、出ていない項目は落とす (ハーネスの部品はモデルの欠点の仮定 — 定期的に外して試す)。

## 1. 役の細則

| 役 | すること | してはいけないこと |

## 2. 起動

```bash
# 実装者 (Bash の run_in_background で直接起動し、完了通知で読む。pgrep / pkill -f で待たない・止めない)
timeout 7100 codex exec -m gpt-6.1-sol -c service_tier='"priority"' -s workspace-write -C <worktree> \
    --add-dir /home/hight/os32-v3/.git --add-dir /home/hight/os32-tmp \
    -c sandbox_workspace_write.network_access=true "<依頼文>" < /dev/null > <ログ> 2>&1
#   上位モデルは -m gpt-6-astra。出力の `model:` 行でモデルを確かめる。`< /dev/null` と timeout は必ず付ける。
#   sandbox は .git を読み取り専用にする — 実装者はコミットせず、PM が worktree の差分をコミットする
#   (末尾は `Co-Authored-By: Codex <モデル名> <noreply@openai.com>`)。

# 差分のレビュー (既定、sol の実装) — astra の read-only。対象の worktree を -C に、依頼は §5 の書式:
timeout 1500 codex exec -m gpt-6-astra -s read-only -C <worktree> "<依頼文>" < /dev/null > <ログ> 2>&1
# 差分のレビュー (astra の実装・大物の sol の差分) — Agent(subagent_type: "reviewer")、model は reviewer.md の opus。読むだけ・編集禁止。
# 設計票の書き手 — astra。書くのは指定した一時ディレクトリの票だけ、リポジトリは読むだけ:
timeout 7100 codex exec --skip-git-repo-check -m gpt-6-astra -s workspace-write -C ~/os32-tmp/run/<題> "<依頼文>" < /dev/null > <ログ> 2>&1
# 設計票のレビュー — 別インスタンスの Agent(subagent_type: "reviewer")、model は opus。
```

**worktree の環境** (ここを外すと検査が環境のせいで落ちる):
- 依頼の最初に `tools/preflight.sh --base <SHA> --fix-fonts` を実行し、NG を直してから始める。
- worktree には `.env` が無い — `CROSS_DIR=/home/hight/opt/cross` を明示する。`TMPDIR` はディスク上 (`~/os32-tmp/…`、`/tmp` は RAM)。
- Codex の sandbox では native の runner が SIGSYS で動かない — qemu で回させ、native は PM が列挙分だけ補う。
- 検査が読む成果物 (`make all` の出力) が worktree にあることを、依頼の前に確かめる。

**依頼パック** (PM が 1 本のファイルにまとめ、依頼文の冒頭で「最初に読む」と指定する。票の節番号を指すだけで済ませない):
期待する基点の SHA / **実装者のモデルと選んだ理由 1 行** (sol / astra、§0 の基準で) / 契約の正典 (節) / 触る関数と呼出し元 (file:line) / 決定済みの事項 / **期待が変わる既存試験** /
**回す検査の名前と runner** (`python3 tools/check_select.py --select --files <触る予定のファイル>` の候補から PM が選ぶ。**全体に効く静的検査 `check-p2v` `check-c-dialect` `check-constraints` `check-arch-asm` `check-privileged` は毎回含める**。これは PM が取り込みで回す一覧で、実装者に回させるのは `make all` と足した・触った試験だけ — §0「検査」) / 受入条件 (**配備・照合の経路を変える段は、実ゲストでの予行を受入条件の 1 番目に置く** — h1c の反省) / 既知の未確認 / 外部の実物の形 (NP21/W の API の返り値など) / 環境 (上の 3 点)。
依頼パックの事実は `tools/check_select.py --pack --files <触るファイル…>` の出力を貼る。着地前に `tools/test_changes.py --base <SHA> --pack <依頼パック.md>` で列挙外の試験変更と要確認行を読む。
実装者は最初に `git log --oneline -1` を実行して報告の先頭に書く。期待と違えば合わせる (`--hard` は使わない)。
PM は着地の前に worktree の `git log -1` を確かめる。参照先が「無い」と報告されたら、まず基点を疑う。

**依頼の書き方** (OpenAI の Codex 指針との照合、2026-10-07): 到達点・完了条件・制約 (罠・PM の決定・[C1]〜[D3]) を書き、工程の語りと毎回同文の禁止列挙は書かない (環境と規則は `AGENTS.md`)。検査は前面で回させ、途中のログを繰り返し読ませない。reasoning effort は実装 `high`・小さな直し `low` を試行中 (`-c model_reasoning_effort=`)。`service_tier` の `fast` は `priority` と同じ要求。**astra の設計級の段は、受入条件を先にレビュアーに読ませ「観測で判定できるか」と「既存の利用者 (アプリ・道具・試験) が退行しないか、今の挙動を固定する試験があるか」を 1 往復で確かめてから実装に出す**。**範囲の外は「何を断るか」ではなく「今の挙動のうち何を保つか」で書く** (例: 「64KiB 以上は f10」ではなく「既存 arena に収まる 64KiB 以上は今までどおり通し、伸長だけ f10」 — f9 の P1、ユーザー承認 2026-10-08)。

**待ちに入る前に**、出した実装者・レビュアー・検査の全部について、出力ファイルの末尾の `rc=` と
`check_slot.sh --status` で終わったかどうかを確かめ、`tools/jobs.sh status` で、終わっていて確認していないものが無いか確かめる。終わっていて次の手を出していないものは、すぐ出す。

## 3. 規約

1. **PM が止まってよいのは 4 つだけ** — [D1]/[D2]/[D3] の承認、仕様の分岐、スコープ拡大、
   **独立レビューが要る地点**。それ以外は承認済みスコープを最後まで進め、各段の終わりに「次に進んでよいか」を訊かない。
2. **ブロックできるのは到達可能な反例を伴う所見だけ**。現契約の違反はブロック、将来要件は別の関門に落とす。
   反例を示せない指摘で正しいコードを変えない。誤検出はレビュー記録側を訂正する。
3. **段ごとに rc と状態を確かめてから次へ** — 取り込み → 配備を `;` や `&&` で連結しない。共有ファイルの編集は PM が直列化する。

## 4. 合否の判定

- 合否は PM が観測 (道具の出力、ゲストの画面とカウンタ) を読んで決める。実行した側の「ok」は自己申告として扱う。
- 配備の反映は [08_build.md §8-4](../../08_build.md#配備3経路) の経路と、ゲスト側のサイズ照合・**新しい** `kernel.map` の番地で確かめる ([V1]/[V4])。
- ゲスト受入の回帰には `db_test` と `db_v50_test` を必ず入れる。拒否カウンタは起動時の kselftest の残り値のことがあるので、kill の前後で値が変わったかを見る。
- **SKIP・未実行・環境不足は合格ではない**。[DEFERRED_TESTS.md](../DEFERRED_TESTS.md) に行があるものだけを「延期」と数え、無いものは失敗として扱う。FAIL・crash・timeout を延期に書き換えない。
- ハード構成を変える試験 (8MB・音源・Cirrus・実機) は段ごとにやらず、台帳の関門でまとめて行う。

## 4-1. PM が差分で見る点 (実装者が繰り返す見落とし)

依頼パックを書くとき・差分を読むとき・マージの後に確かめる。列挙した検査では捕まらない種類。
- 実物のソースを差し替えの定義で組む試験が、新しい定数・関数・include に追従しているか (`grep -rln '<触ったファイル>' tools/tests/`)。
- 関数を改名したら、名前で引く表 (`tools/check_p2v_allow.txt` など) も直したか。
- `exec/exec.c` を変えたら、逆アセンブルに頼る `check-h3-park-resume-host` が列挙にあるか (インライン化で観測点が消える)。
- 新しい検査・中断点の置き場: 呼ばれる頻度 (毎周の経路に置かない)、共有の関数に置かない (内部からも呼ばれる)、割込みを止めた区間の走査量。
- 新しい検査の対応表 (`tools/check_map.d/*.yaml`) に `Makefile`・`build/*.mk` を直接書かない (`broad` に)。
- 試験の `--mutate` の分岐で正常の段を省かない。入力に毎回ちがう乱数を使わない (固定の種と失敗の入力)。
- ゲストの試験プログラムは `int main` で PASS 0 / FAIL 1 を返す。
- 同じ箇所を 2 本が別の形で直したときは、マージの後にその箇所を読む。

## 5. レビュー依頼の出し方

依頼文には次の 5 点を揃える。対象ファイルを列挙して範囲を絞り、判定は `## 判定` の見出しで返させる。

| 項目 | 内容 |
|---|---|
| 対象 | コミット SHA か `git diff` の範囲、主なファイル |
| 変更の要旨 | 何を、なぜ変えたか (3 行以内) |
| 見てほしい観点 | 正しさ / [C1]〜[C5] / ABI / 資源回収 など、絞って挙げる |
| 判定基準 | **到達可能な反例を伴う所見だけがブロック要因**。将来要件は別の関門 |
| 既知の未確認 | ゲスト未検証の範囲、呼出し元が無い API など |

**網羅性の要求を必ず入れる**: 「今回の往復で見つかる到達可能な欠陥を**すべて**挙げる (1 件見つけて止めない)。
対象の経路を列挙し、経路ごとに見た / 見ていないを明記する。次の往復で新しい領域の指摘を出すなら、今回なぜ見えなかったかを書く」。
往復を数える単位は「指摘の集合」。**3 往復で Approve に至らなければ、争点を整理してユーザーへ**。

所見が返ったら、**鵜呑みにせず PM が反例の到達可能性を確かめてから**着手する。票の記録にどのモデルが見たかを書く。
