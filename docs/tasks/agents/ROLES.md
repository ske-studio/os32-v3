## 0. 現行の体制

| 項目 | 現行 |
|---|---|
| **PM** | Claude Code の対話セッション、**Opus 5.5** (`claude-opus-5-5`)。分解・依頼パック・統合・受入判定・git 操作・[D1]〜[D3] の承認取得・エミュレータの操作 |
| **実装者** | Codex、worktree 隔離。**既定は terra (安いので、なるべく terra に出せる形に段を切る)**。terra に出すのは 400 行以下・1〜3 ファイル・確定設計か手本がある段 (直しや小さな追従の段は、元の実装がどちらでも terra)。sol に出すのは、400 行を超える段・1,000 行超のファイルや判定論理の変更・検証の重い段・ビルドしないまとめの段・宣言の段を挟まない並列の波。大きい段は最初を sol、同形の残りを terra。terra が同じ段で 2 回止まるか 1 回打ち切られたら sol に替える (走っている回は完走させる)。失敗や容量切れの切替は terra → sol → astra、sol が同じ仕事で実装の誤りを 3 回出したら astra、sol の混雑は astra に切替可。terra の依頼には「試験のリンクの一覧・固定のハッシュ・dep-dir の追従を自分で洗う」と書き、差分はレビューに出す。terra は 10 分ごとに進捗確認、微修正と後片付けは Opus のサブエージェントを基本とする。 |
| **独立レビュアー** | 差分は astra が読み、astra の実装・設計票は Opus のサブエージェントが読む。sol の差分には大物でも Opus を並べない (ユーザー承認)。読み取りだけ、書き手と別モデル、実装者の報告を渡さず、冒頭でモデル ID を名乗る。ドライバ設計は Codex と Claude の両方が見る。 |
| **カウンターの原則** | 設計票と判断の材料になる文書は **astra が書き、Opus 5.5 のサブエージェントがレビュー**。sol の実装 → astra がレビュー。astra の実装・修正 → Opus 5.5 がレビュー。同じモデルに自分の仕事をレビューさせない (PM も Opus 5.5 だが、レビューは別のサブエージェントに出し、PM が代行しない)。**事務的な文書 (台帳の照合・受入の記録・状態行・HANDOVER) は PM が書く** (2026-10-14)。3 往復で決着しない争点はユーザーへ |
| **移植 (手本あり)** | 手本 (nouveau など) がある移植は、コンパイル・検査を全部の実装の後にまとめる (ユーザー指示 2026-11-03、評価中)。流れ・設計の段の点検・依頼に必ず書くこと・踏んだことの表は [PORT_FLOW.md](PORT_FLOW.md)。手本の無い段は従来どおり段ごとにビルド・検査 |
| **調査** | コードや資料を読み比べる調べ (手本との比較・所在の洗い出し・原因の切り分けの下調べ) は **sol** に頼む (ユーザー指示 2026-11-02「調査は今後solに頼んでください」)。読み取りだけ、結果は file:line 付きで ~/os32-tmp/run/<題>/ に。PM は要所を確かめてから報告する。 |
| **設計票** | astra が起草し Opus のサブエージェントがレビュー。観測で判定できる受入条件と既存利用者の退行を初版に書く。確定版は本文を持つ。3 往復で決着しない争点はユーザーへ。範囲と往復の管理は `os32-design-rally` と `os32-delegate`。 |
| **実行の道具** | 配備・回帰・ゲスト操作は PM が `run-os32`、`tools/guest_tests.py`、`tools/emu_agent/playbook.py`、`tools/np21w_ctl.py` で回す。合否は PM が観測を読んで決める。 |
| **検査** | 取り込みの検査は **GitHub の CI** (check と build。**全部の検査を変異込みで回す** — build の `checks` 6 シャードと check の PowerPC の段、`docs/POLICY_CI.md` G1、2026-11-18)。夜だけ・手動だけの全体検査は無い (関門にならない検査を作らない)。メインストリームを含めて全部の枝を push → CI が通ったら main に早送り ([PARALLEL_BRANCHES §3](PARALLEL_BRANCHES.md)、ユーザー決定 2026-11-05「取り込みの検査は GitHub の CI に一本化する (メインストリームも含む)」)。実装者は触った像のビルド (`make kernel` か触った部品・ユーザーランド、`make all` も可)・足した・触った試験の `--mutate` (目印一意・実行時 RED)・`--lint` だけ (ユーザー承認 2026-10-31)。手元で関係する検査をまとめて見たい時は `make check-changed` を使ってよいが、関門ではない (30 分を超えるなら止めて push する、ユーザー決定 2026-11-06)。合否を決めるのは CI だけ。実機の試験・調べの版はビルドが通れば実機へ (CI の artifacts のジョブが成功した SHA、ユーザー決定)。NP21/W の受入も CI の成果物を `tools/ci_fetch.sh` で取って配る (検査した版と配った版が一致する)。最後の変更後のログだけを合格に数える。 |
| **並行** | **触るファイルが衝突しない段は、並列で出せるだけ出してよい**。機能ごとにブランチを分け、触るファイルを依頼に書いてから出す ([PARALLEL_BRANCHES.md](PARALLEL_BRANCHES.md)、ユーザー指示 2026-11-03)。衝突しうる段 (同じファイル・同じ生成物・同じ世代) は直列にする。共有の登録ファイル (検査の目録など) の衝突は PM が取り込みで解く。 手元で走る重い仕事 (実装者の make all・変異) は同時に数本まで (2026-11-01 にメモリ不足で裏の検査が止められた) — 取り込みの検査は GitHub の CI なので手元の枠は使わない。エミュレータの操作者は同時に 1 人 |
| **段の大きさ** | 1 段 = **独立して受入できる契約・挙動** (実装 + レビューの直し + 対象の受入で半日〜1 日が目安)。同じ受入条件への直しは**同じ worktree・同じレビュアー**で続ける (fix の段を新しく切らない)。**fix の依頼は所見に書かれた直しだけ** — 範囲の外の P3 (性能・整理) は台帳か次の段へ回し、P1/P2 の直しと混ぜない。**PM の文書の直し (台帳・票の追記) は段の worktree に混ぜず、取り込みの後に main へ別のコミットで入れる** (ユーザー承認 2026-10-08)。未結線の先行部品は、結線先が決まっているときだけ分ける。**受入条件 (事前レビューの反映後) が 10 項を超える段は、依頼パックを書く時点で分ける** — 同じ取り込みに入れるべきもの (契約の切替と世代の更新など) は分けず、受入台本・文書の固定値・記録を後ろの段へ。走らせた段は、timeout に当たるか、最後の検査を 3 回以上回し直したら止めて分ける (ユーザー承認 2026-10-08)。ゲストの台本は実ゲストで目的を達するまで閉じない。ゲスト受入は、退行の危険が大きい段 (カーネルの heap・exec・paging の挙動を変える段) を取り込んだところで、それまでのホストだけの段とまとめて行い、その上に次の段を積まない |
| **取り込みの順** | 枝を push → **GitHub Actions の結論 (build・check) を確かめる** → 成功なら main に早送り (または merge して push し、main の CI も確かめる)。受入待ちの段は統合の枝にまとめて CI と NP21/W を 1 回ずつ (§4-2)。HANDOVER §1 の main 行に書く (X-3 の放置の反省、2026-10-14)。受入まで済んだ段の記録は archive へ移し、閉じた台帳の行を片付ける (票は 1 段 10 行に戻す)。生成文書は `make docs-gen` で `build/out/` に作る (コミットしない)。 |
| **記録** | 票に人が書くのは **1 段 10 行以内** — 決定・未確認・持越し・証拠の所在。**受入の結果は票・台帳・HANDOVER には「合否 1 語 + 証拠のパス」だけ**、中身は証拠の `RESULT.md` に (HANDOVER §2 を長文にしない)。受入の観測スクリプトは `tools/accept/` にだけ新しく作る (ユーザー承認 2026-10-10、実施 2026-10-14)。コマンド・runner・rc・時刻・RED/GREEN は道具のログに残し、票に貼らない。契約の変更は仕様の正典へ書く |
| **持越し** | 延ばした試験・SKIP・ホストだけの合格・未結線は [DEFERRED_TESTS.md](../DEFERRED_TESTS.md) の 1 か所に書く (何を・なぜ・どの関門で必ずやるか)。そこに無い SKIP は合格に数えない |
| **レビューの重さ** | P3 だけの直し、および**機械的な小さい依頼 (文言・表示・設定の追従など、試験を含めて 30 行程度まで、判定ロジックを変えない)** は PM が差分を読んで着地する (ユーザー決定 2026-10-14)。P1・P2 の直しの確認は**前回と同じレビュアーに差分だけ**。**3 往復で決着しない争点はユーザーへ** |
| **決裁** | PM の推奨は**基本的に承認** (その範囲で止まらずに進める)。**[D2] の操作と実機の物理操作は個別に承認**。互換の無い更新 (配置の世代や ABI が変わり、新旧のカーネルとユーザーランドが混ざると起動しない) を実機に入れるときは、手順をユーザーに示してから行う (2026-10-16)。**実機への配備・再起動・シリアルの試験は、PM が ssh で直接流さず、ノートの Remote Control のセッションに依頼する** (スキル [os32-realhw-update §1](../../../.claude/skills/os32-realhw-update/SKILL.md#1-ノートへの依頼の形-この順で書く) の形、入れる版は CI の build が成功した SHA — 実機の調べ用の診断ビルドだけは例外。PM の ssh は**ファイルを置くこと** (CI を待たない版の成果物を scp で送り展開する) と状態の確認までで、置いた後の処理 (lanfs_host の起動・hsync・再起動・シリアルの試験) はノートに頼む、2026-10-30)。NP21/W の ini を変えてよいのは PM だけ (原本を残す経路で、終わったら戻す — スキル `os32-emu-config`) |
| **場所** | 開発は os32-v3 (このリポジトリ)。os32 の v2.x は戻り先で新機能を入れない ([VERSIONS.md §2](../../decisions/VERSIONS.md))。**worktree は `~/wt/os32-v3/<名前>`** に作り (ホーム直下に作らない)、取り込んだら撤去する。一時ファイルは `~/os32-tmp/` の下 |


## 1. 役の細則

| 役 | すること | してはいけないこと |
|---|---|---|
| **PM** | 分解、依頼パック (§2)、取り込みと統合の検査、受入、配備とゲスト操作、[D1]〜[D3] | 実装。レビューの代行 (「問題なし」を自分で結論しない) |
| **実装者** | 実装 + ホスト TDD (`tools/tests/`)、列挙された検査 | 配備・エミュレータ操作・`main` への取り込み・全体検査の繰り返し |
| **独立レビュアー** | 独立に読み、到達可能な反例つきで所見を挙げる (§5) | ファイルの変更・コミット |

## 2. 起動

役の呼び名とモデル ID (2026-11-18 に `codex debug models` と実際の起動で確かめた。名前が変わったらこの表を直す):

| 呼び名 | モデル ID | 一覧での位置づけ |
|---|---|---|
| terra | `gpt-6.1-terra` | 効率の良いモデル |
| sol | `gpt-6.2-sol` | 普段使いのコーディングのモデル (`gpt-6.1-sol` は前の世代) |
| astra | `gpt-6.2-astra` | 一番能力の高いモデル (`gpt-6-astra` は前の世代) |

略称 (`terra` だけ) は受け付けられない。`codex exec … resume <sid>` は `-m` を付けないと `~/.codex/config.toml` の既定のモデルで続くので、resume でも `-m <元のモデル>` を付ける。

```bash
# 実装者 (Bash の run_in_background で直接起動し、完了通知で読む。pgrep / pkill -f で待たない・止めない)
timeout 7100 codex exec -m gpt-6.2-sol -c service_tier='"priority"' -s workspace-write -C <worktree> \
    --add-dir /home/hight/os32-v3/.git --add-dir /home/hight/os32-tmp \
    -c sandbox_workspace_write.network_access=true "<依頼文>" < /dev/null > <ログ> 2>&1
#   上位モデルは -m gpt-6.2-astra、安い段は -m gpt-6.1-terra。出力の `model:` 行でモデルを確かめる。`< /dev/null` と timeout は必ず付ける。
#   sandbox は .git を読み取り専用にする — 実装者はコミットせず、PM が worktree の差分をコミットする
#   (末尾は `Co-Authored-By: Codex <モデル名> <noreply@openai.com>`)。

# 差分のレビュー (既定、sol の実装) — astra の read-only。対象の worktree を -C に、依頼は §5 の書式:
timeout 1500 codex exec -m gpt-6.2-astra -s read-only -C <worktree> "<依頼文>" < /dev/null > <ログ> 2>&1
# 差分のレビュー (astra の実装) — Agent(subagent_type: "reviewer")、model は reviewer.md の opus。読むだけ・編集禁止。
# 設計票の書き手 — astra。書くのは指定した一時ディレクトリの票だけ、リポジトリは読むだけ:
timeout 7100 codex exec --skip-git-repo-check -m gpt-6.2-astra -s workspace-write -C ~/os32-tmp/run/<題> "<依頼文>" < /dev/null > <ログ> 2>&1
# 設計票のレビュー — 別インスタンスの Agent(subagent_type: "reviewer")、model は opus。
```

**worktree の環境** (ここを外すと検査が環境のせいで落ちる):
- 依頼の最初に `tools/preflight.sh --base <SHA> --fix-fonts` を実行し、NG を直してから始める。
- worktree には `.env` が無い — `CROSS_DIR=/home/hight/opt/cross` を明示する。`TMPDIR` はディスク上 (`~/os32-tmp/…`、`/tmp` は RAM)。
- Codex の sandbox では native の runner が SIGSYS で動かない — qemu で回させ、native は PM が列挙分だけ補う。
- 検査が読む成果物 (`make all` の出力) が worktree にあることを、依頼の前に確かめる。

**依頼パック** (PM が 1 本のファイルにまとめ、依頼文の冒頭で「最初に読む」と指定する。票の節番号を指すだけで済ませない):
期待する基点の SHA / **実装者のモデルと選んだ理由 1 行** (sol / astra、§0 の基準で) / 契約の正典 (節) / 触る関数と呼出し元 (file:line) / 決定済みの事項 / **期待が変わる既存試験** /
**回す検査の名前と runner** (触ったファイルを直接組む試験だけ。`python3 tools/checks/run.py --select --files <触る予定のファイル>` の候補から選び、候補を全部は回させない — 全体は push した後の CI。実装者・PM の完了条件と検査の分担は §0「検査」、移植の例外は [PORT_FLOW](PORT_FLOW.md)) / 受入条件 (**配備・照合の経路を変える段は、実ゲストでの予行を受入条件の 1 番目に置く** — h1c の反省) / 既知の未確認 / 外部の実物の形 (NP21/W の API の返り値など) / 環境 (上の 3 点)。
実装者は最初に `git log --oneline -1` を実行して報告の先頭に書く。期待と違えば合わせる (`--hard` は使わない)。
PM は着地の前に worktree の `git log -1` を確かめる。参照先が「無い」と報告されたら、まず基点を疑う。

**依頼の書き方** (OpenAI の Codex 指針との照合、2026-10-07): 到達点・完了条件・制約 (罠・PM の決定・[C1]〜[D3]) を書き、工程の語りと毎回同文の禁止列挙は書かない (環境と規則は `AGENTS.md`)。検査は前面で回させ、途中のログを繰り返し読ませない。reasoning effort は実装 `high`・小さな直し `low` を試行中 (`-c model_reasoning_effort=`)。`service_tier` の `fast` は `priority` と同じ要求。**astra の設計級の段は、受入条件を先にレビュアーに読ませ「観測で判定できるか」と「既存の利用者 (アプリ・道具・試験) が退行しないか、今の挙動を固定する試験があるか」を 1 往復で確かめてから実装に出す**。**範囲の外は「何を断るか」ではなく「今の挙動のうち何を保つか」で書く** (例: 「64KiB 以上は f10」ではなく「既存 arena に収まる 64KiB 以上は今までどおり通し、伸長だけ f10」 — f9 の P1、ユーザー承認 2026-10-08)。

**待ちに入る前に**、出した実装者・レビュアー・検査の全部について、出力ファイルの末尾の `rc=` と
`gh run list` で CI が終わったかどうかを確かめ、`tools/jobs.sh status` で、終わっていて確認していないものが無いか確かめる。終わっていて次の手を出していないものは、すぐ出す。

## 3. 規約

1. **PM が止まってよいのは 4 つだけ** — [D1]/[D2]/[D3] の承認、仕様の分岐、スコープ拡大、
   **独立レビューが要る地点**。それ以外は承認済みスコープを最後まで進め、各段の終わりに「次に進んでよいか」を訊かない。
2. **ブロックできるのは到達可能な反例を伴う所見だけ**。現契約の違反はブロック、将来要件は別の関門に落とす。
   反例を示せない指摘で正しいコードを変えない。誤検出はレビュー記録側を訂正する。
3. **段ごとに rc と状態を確かめてから次へ** — 取り込み → 配備を `;` や `&&` で連結しない。共有ファイルの編集は PM が直列化する。

## 4. 合否の判定

- 合否は PM が観測 (道具の出力、ゲストの画面とカウンタ) を読んで決める。実行した側の「ok」は自己申告として扱う。
- 配備の反映は [08_build.md §8-4](../../08_build.md#配備3経路) の経路と、ゲスト側のサイズ照合・**新しい** `kernel.map` の番地で確かめる ([V1]/[V4])。
- ゲスト受入は [TASK_POLICY_LIGHT §C](../v3/TASK_POLICY_LIGHT.md) の段 3 で最小回帰と変更箇所だけ、段 4 で約束を一通り回す。
- **SKIP・未実行・環境不足は合格ではない**。[DEFERRED_TESTS.md](../DEFERRED_TESTS.md) に行があるものだけを「延期」と数え、無いものは失敗として扱う。FAIL・crash・timeout を延期に書き換えない。
- ハード構成を変える試験 (8MB・音源・Cirrus・実機) は段ごとにやらず、台帳の関門でまとめて行う。

## 4-1. PM が差分で見る点 (実装者が繰り返す見落とし)

依頼パックと差分で、検査・中断点の頻度と割込み停止中の走査量、検査の `CHECK` 宣言、変異時の正常対照、ゲスト試験の終了値を確認する。同じ箇所を別々に直した場合は取り込み後に読む。

## 4-2. 統合の枝と一括の受入 (本線)

ユーザー承認 2026-11-10 (「すべて承認」「ドキュメントにも」)。理由: 11-10 に段を 1 本ずつ受け入れて、統合が 6 回・受入 1 回が 26〜47 分になった。PowerPC の側の積み方と依頼の形は PPC_IMPL_RULES §4 (`docs/decisions/ppc/PPC_IMPL_RULES.md`)。

- **統合の枝**: 受入待ちの枝を全部 1 本の統合の枝 `wt/int-<日付><記号>` に merge → CI 1 回 → NP21/W の受入 1 回 (各段の台本の和)。失敗したら段ごとに二分で外して原因の段を見つける。本線の変更を待つ段だけ単独で受ける。
- **基点の使い回し**: NP21/W の受入の基点は前回の受入の像の結果を使う。カーネル・部品の CRC が同じなら SHA が違っても同じ基点と数える。
- **1 回の起動で回す**: 各段の追加の項目は、最小受入 (HDD 起動・ver/mem・CUI の固定の組・スタックの最大・GUI の 1 往復・STOP) と同じ起動の中で続けて回す。道具は 1 本のスクリプト (`~/os32-tmp/run/acc-min/acc_batch.py`、リポジトリ外)。大きな項目は一括で落ちたときだけ広げる。
- **R1 版**: メモリの配置・カーネルの入口 (paging・GDT/IDT/TSS・ring3 への遷移・exec の入口・memmap) を触った段のときだけ回す。各段の台本に R1 の要/不要と理由を書く。
- **NP21/W を省く段**: build_compare でカーネル・部品がバイト一致する段 (区分 I) は CI だけで受け入れる。
- **受入は main に入る節目で (既定)**: ユーザー指示 2026-11-11 (「NP21Wの受け入れの頻度を下げたほうが」「まとめて」「ドキュメントにもmainに入る段での受け入れを既定に」)。NP21/W の受入は、統合の枝を main に入れる直前の 1 回だけを既定にする。段ごと・宣言だけの段・直しの段では回さない。大きな票は結線の節目 (HAL v2 なら I1・I2・I3) ごとに 1 回。PowerPC の x86 が変わる段は次の節目の回に相乗りさせ、急ぐ理由があるときだけ単独で回す。試験・文書・packaging だけの直しは CI だけ。ゲスト試験の原因調べは受入と別に、要るときだけ短く回す。受入の間は、その統合の枝の作業木を触らない。

## 4-3. 変更の種類ごとに追従させる表 (ユーザー指示 2026-11-14「検査表の更新忘れが多い」)

段の依頼を書くときに、触る種類の行を**全部**完了条件に写す。PM は取り込みの前に、同じ行で差分を照らす。
一覧・指紋・生成値は手で書かない (生成器か試験が出す値を写し、変わった理由が意図した追加だけかを基点と比べて確かめる)。

| 変更の種類 | 追従させるもの | 確かめ方 |
|---|---|---|
| カーネル・部品に新しいソースを足す | `build/sources/order.mk` (リンクの順)、`build/sources/common.mk` か arch・platform の一覧 (選択)、`tools/tests/fixtures/build_profile_x86.json` の `C_KERNEL`。PowerPC の像に入るなら `build/targets/ppc-powermac.mk` の一覧 | `check-build-selection-host`、`make all` |
| KAPI を足す・変える (`sdk/kapi.json`) | 版の 2 か所 (kapi.json・`os32_kapi_shared.h`) と、版を書いた文書 (README・INDEX・KAPI_SPEC)。前の口は変えない (末尾追加だけ、`kapi-abi` が基点と比べる。壊す時はコミットの本文に `KAPI-Break: <理由>`)。レビュー済みの指紋: `tools/tests/hwdev_contract_fixture.py` の HWDEV の layout CRC と inventory、`tools/tests/test_ime_display_boundary.py` の FEP_MODULE_ABI_GEN | `check-kapi-abi`・`check-hwdev-image-host`・`check-ime-display-boundary-host`・KAPI の検査 (audit・ranges・version)、`make clean && make all` |
| 共通の場所 (kernel/・net/・fs/・include/・userland/shell・kernel/console) を触る | PowerPC の像のリンク (CI の job ppc-compile が merge-base からの差で判定して組む。手元で先に確かめるときも同じコマンド) | `PATH=/home/hight/opt/cross-ppc/bin:$PATH make ARCH=ppc PLATFORM=powermac KBOOT_SH=1` |
| 製品の関数の呼び出しを 1 つ足す | その関数の兄弟の stub を持つ試験の土台 (`#include` で取り込む土台と、python が切り出して組む試験の両方) | grep で呼び手と stub を全部見る |
| PowerPC の toolchain・QEMU・socket を使う試験を足す・変える | 無い環境では理由を表示して SKIP・rc=0、`OS32_REQUIRE_PPC=1` (job ppc-compile) では失敗にする ([PPC_NOTES](../../decisions/ppc/PPC_NOTES.md) §6) | `PPC_CROSS_DIR=/nonexistent make check-<名前>` が SKIP と rc=0 |
| 試験を足す・名前や式を書き換える | 検査の `CHECK` の covers、`basis` か `kind`、該当すれば `env_limit`・`pins`、変異の目印 (試験の中の元の式の文字列) | `tools/checks/run.py --lint`、`python3 ~/os32-tmp/bin/stale_anchor.py <基点>` |

## 5. レビュー依頼の出し方

依頼文には次の 5 点を揃える。対象ファイルを列挙して範囲を絞り、判定は `## 判定` の見出しで返させる。

| 項目 | 内容 |
|---|---|
| 対象 | コミット SHA か `git diff` の範囲、主なファイル |
| 変更の要旨 | 何を、なぜ変えたか (3 行以内) |
| 見てほしい観点 | 正しさ / [C1]〜[C5] / ABI / 資源回収 など、絞って挙げる |
| 判定基準 | **到達可能な反例を伴う所見だけがブロック要因**。将来要件は別の関門 |
| 既知の未確認 | ゲスト未検証の範囲、呼出し元が無い API など |

**網羅性の要求を必ず入れる**: 「今回の往復で見つかる到達可能な欠陥を**すべて**挙げる (1 件見つけて止めない)。
対象の経路を列挙し、経路ごとに見た / 見ていないを明記する。次の往復で新しい領域の指摘を出すなら、今回なぜ見えなかったかを書く」。
往復を数える単位は「指摘の集合」。**3 往復で Approve に至らなければ、争点を整理してユーザーへ**。

所見が返ったら、**鵜呑みにせず PM が反例の到達可能性を確かめてから**着手する。票の記録にどのモデルが見たかを書く。

## 6. 承認の要る操作・要らない操作と、運用の決まり (ユーザー決定の一覧)

§0 の「決裁」を、操作ごとに今有効な形で並べる。決定が変わったら行を書き換える (経緯は git)。PM の個人の memory には写さない。
設計の前提の一覧は POLICY_DEV §10 (`docs/POLICY_DEV.md`)。行の足し方と memory の畳み直しはスキル `.claude/skills/os32-decision-fold`。

| 操作 | 承認 | 条件・やり方 | 決定 |
|---|---|---|---|
| 推奨を付けた選択 | 要らない | 返事が無くても推奨で進め、報告に「推奨で進めた」と書く。資料が足りない時は FreeBSD・X.Org のソースを参照してよい | 2026-09-29 |
| 仕様の分岐・スコープの拡大・ライセンス・決定済みのユーザー決定を覆す事 | 要る | 設計の往復の途中でも、版を待たずにユーザーへ。往復は 3 回まで PM が回し、決着しない争点をユーザーに尋ねる | 2026-11-09 |
| NP21/W の上の試験 | 要らない | いつ実行してもよい。本 NHD を使う ini への配備・本 NHD の作り直しも確認なし ([D1] の停止 → 配備 → 起動の順は守る)。開発中は NHD のバックアップを取らなくてよい | 2026-10-09、2026-10-14、2026-10-18 |

運用の決まり:

- **並行を保つ** (2026-11-06): ある領域で不具合が続いても、その 1 本に付きっきりにならない。直列にするのは実機 (1 台) とノートのセッションの順番だけ。
- **main に入れた後に止まらない** (2026-11-17): 区切りで走る段が 0 本になるなら、同じ返事の中で次の段を出してから報告する。止まってよいのは [D1]〜[D4]・仕様の分岐・ユーザーの決定待ちだけ。
- **CI の結果を読んでから取り込む** (2026-11-08): 待ちの終了と merge・push を 1 本のコマンドに繋げない。待つのは push した最後の SHA。push の直後に、要る workflow が起動した事を確かめる。
- **直しても良くならない時** (2026-11-13): 当て推量を重ねず、上位のモデル (Fable) のサブエージェントに、測った数値・試した直し・制約を渡して解決策を求める。答えは案として受け取り、PM が段に切る。
- **整理・分割の段で直してよい物** (2026-10-31): 見つけたバグと冗長は直してよい。セキュリティの懸念を理由にした変更 (防御を足す・権限を絞る) と新機能は入れない。直しは移動のコミットに混ぜず、別のコミットか別の段にする (移動は中身の一致で、直しは試験とレビューで確かめる)。依頼文に「見つけたバグ・冗長は場所を挙げて報告、直すのは別の段」と書く。
- **codex の本数の上限と待ち行列** (ユーザー決定 2026-11-19、本線 PM と PowerPC PM の案を採用): 詰まり所はセッションの数ではなく、機械 (PowerPC 4 コア、本線 WSL 16 コアで同じ機械に NP21/W)・NP21/W と G4 が 1 本ずつ・PM の注意。(1) 上限は各 PM で、ビルド・QEMU を伴う実装は本線 4・PowerPC 3、読むだけの調べ・設計の起草・レビューは 8。超えた段は待たせる。(2) 段の待ち行列は機械ごとに 1 枚 (`~/os32-tmp/run/QUEUE.tsv`: 段・依存・状態・種類・作業木、リポジトリに入れない) と、種類ごとの空きと依存を見て `codex_run.sh` を起こす薄い入口 (`~/os32-tmp/bin`、両 PM で同じ台本。PowerPC PM が起草し本線 PM がレビュー)。自動で起こすのは「依存が済み、依頼の PACK がある」段だけ。取り込み・設計の確定・止まった実装者の再起動は自動にしない。(3) 実装者は対象の検査と 1 回の make all まで。QEMU で完結する PowerPC の受入は CHECK にして CI の ppc-qemu で回し、手元では重ねない (手元の受入は G4 と NP21/W だけ、runner の重みはスキル os32-ci-inventory で見直す)。取り込みは統合の枝・積んだ枝で 1 回の CI にまとめる。
- **実装者の傾向** (2026-10-15、2026-11-02): astra は神経質で防御を足しがち、仕事を散らかしがち。依頼で範囲と前提を縛り、計画に無い機能を足させず、レビューの指摘は PM が濾す。行数は目標で強制しない。
