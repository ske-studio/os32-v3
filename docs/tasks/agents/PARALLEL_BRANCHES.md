# 機能ごとのブランチで並列に実装する

> 状態: **現行 (2026-11-03)**
> 上位: ROLES.md (§0 の「並行」の行)

ユーザー指示 (2026-11-03): 「検査のバッティングは防げないですが、機能はブランチで分けて実装することを（触るファイルが被らない）正典化したら並行で出せるものは？」「これはGeforceに限った話ではないです」。

GeForce・ラスタに限らず、機能の開発全般の決まり。手本がある移植の流れ (PORT_FLOW.md) も、この決まりの上で段を並列に出す。

## 1. 決まり

1. **1 機能 = 1 ブランチ = 1 作業木** — `wt/<名前>` を main から切り、`~/wt/os32-v3/<名前>` で実装する。終わったら main に merge する。
2. **触るファイルを先に決める** — 依頼に「触るファイルの一覧」を書く (設計票のファイルの割り当ての表、[POLICY_DEV §2](../../POLICY_DEV.md) の 1 機能 1 ファイル)。PM は出す前に、走っているほかのブランチの一覧と突き合わせ、重ならないものだけを並列に出す。
3. **一覧の外のファイルに触る必要が出たら、実装者は止めて報告する** — PM が重なりを確かめてから許す。
4. **重なるブランチは直列** — 同じファイル・同じ生成物・同じ世代 (KAPI の版・配置の世代) に触るものは、先のブランチが main に入ってから、その main から次を切る。

## 2. 重なりやすいものの扱い

| 種類 | 例 | 扱い |
|---|---|---|
| 共有の登録ファイル | `build/*.mk`・`*_imports.def`・`tools/module_schema.py`・試験の登録・`build/packages.yaml`・`docs/INDEX.md` | 持ち主のブランチを 1 本に決める。ほかのブランチは足したい行を報告に書き、PM が merge のときに足す |
| 生成物 | 契約・schema・レイアウトの台帳・KAPI のラッパー | ブランチでは生成しない (または生成物をコミットしない)。PM が merge の後に 1 回だけ作り直す |
| 共有の上限 | 像の大きさ・起動 FD の空き (64KB)・KAPI の版 | 出す前に PM がブランチごとに予算を割り当てる。足りないときは [部品の上限の規則](../../08_build.md#起動時に読む部品の大きさの上限と由来) に従い、物理の制約が無ければ広げてから並列に出す |
| 結線の段 | 複数の機能をつなぐ段 (起動の順・ops の受け渡し) | 部品のブランチが全部入ってから、直列に 1 本 |

## 3. 検査と実機

- **取り込みの検査は全部 GitHub の CI** (メインストリームを含む、ユーザー決定 2026-11-05「取り込みの検査は GitHub の CI に一本化する (メインストリームも含む)」)。枝を push し、check と build (`make check` = 全部の検査を変異込みで、6 シャード) が通ったら main に早送りする。**`[skip ci]` を付けたコミットは取り込めない** — 関門はその SHA の check・build の success を要る。文書だけの変更 (差分が全部 `docs/**`・`**.md`・`.claude/**`) は、push で起動する check (static-check だけが走り約 4 分、build は `paths-ignore` で起動しない) の success を読んでから main に早送りする。build は手で起こさない (ユーザー決定 2026-11-19)。main の push は、同一 SHA・同一 workflow の枝 (`wt/**`) の push の成功を API で確認できれば build の検査 (checks) を省略する (ユーザー決定 2026-11-19、前は統合枝 `wt/int-*` だけ)。check の static-check と配布物 (artifacts) は main で毎回回す。取得失敗・不明な結果・dispatch の成功・打ち切りは証拠にしない (`tools/ci/reuse_success.py`)。**枝の成功を読んでから早送りする** — 先に main を進めると、枝の PowerPC の範囲の判定 (`tools/ci/ppc_scope.py` は回った時点の origin/main との差を見る) が空になり、PowerPC が飛んだまま success になる ([08_build §8-6](../../08_build.md#8-6-github-actions-での本体ビルド))。
- **実装者**は触った像のビルドと、足した・触った試験 (`--mutate` を含む)・lint だけを回す。全体は CI が回す。関係する検査を手元でまとめて見たい時は `make check-changed` を使ってよい (関門ではない)。
- **build の検査**は ROLES §6 の決定 (2026-11-19) に従い、指定シャードだけ ci-server の使い捨て runner に振り分ける。配布物と回し直しは常に標準で実行する。振り分けの条件と戻し方は [08_build §8-6](../../08_build.md#8-6-github-actions-での本体ビルド)。
- **substream** (Ubuntu 24.04・gcc 13) は PowerPC (PowerMac G4) の移植の開発機 (ユーザー決定 2026-11-07、セッション os32powerpc)。GitHub Actions の runner は止めてあり、CI には使わない (GitHub より 2.5〜4 倍遅い、ユーザー決定 2026-11-05)。
- **受入待ちの枝は統合の枝 (`wt/int-<日付><記号>`) にまとめて受け入れる** — 形は ROLES §4-2。
- **merge は終わった順** — 後から入るブランチは、入る直前の main を取り込んで push し直し、CI を通し直す (衝突の解消を含む)。
  - **緑で待つ枝が先** (ユーザー決定 2026-11-19): main に push する前に `gh run list` で相手の PM の `wt/**` を見る。CI 中か、緑で早送りを待っている枝があれば、そちらを先に入れる。小さい段 (POLICY_CI R5 の 1 ジョブずつの段、文書だけのコミット) のほうが譲る。待てない時は相手に一言伝える。相手の緑の枝の上に自分の段を積んで push し、1 回の CI で両方を確かめる形 (手で作る merge train) も使ってよい。
  - **取り込み直しの差が文書だけなら CI を省いてよい** (ユーザー決定 2026-11-19): 判定は機械で、`git diff --name-only <枝の緑の SHA> <取り込み後の SHA>` の全部が build.yml の `paths-ignore` と同じ型 (`docs/**`・`**.md`・`.claude/**`) に当たる時だけ。基準の JSON など .md でない物が混ざれば CI を回し直す。省く時は、取り込み後の木で文書の検査 (スキル os32-land の「文書だけ」の行) と `python3 -B tools/checks/run.py --select --files <main 側で増えた文書>` が挙げる検査を変異込みで回し、早送りの後にその SHA の main の CI の結論を読む (赤なら次の取り込みより先に直すか戻す)。緑の SHA・差分のファイル名・回した検査を取り込みの連絡に書く。「ファイルが重ならない」は判定に使わない (重ならないファイルの間の依存で落ちる。2026-11-18 の S2a の covers の漏れ)。
  - **ゲストの受入は CI と並べて頼む** (ユーザー決定 2026-11-20「手元の qemu で回してから送っていませんか？ これをビルドと検査までの保証にして受け入れまで送っては？」→ PM の案「受入を CI と並べる」に「OK」): 手元のビルドと触った検査 (変異込み) が通って push したら、CI の配布物 (artifacts のジョブ、push から 1〜2 分) が出た時点でその SHA の受入 (pc98emu の NP21/W・QEMU) を頼む。CI の check・build の終わりを待たない。main への早送りの条件は今どおり「その SHA の CI の success と受入の PASS の両方」(どちらかが欠けたら入れない)。CI が赤なら、直した SHA で受入を頼み直す (前の受入の結果はその SHA の分だけ有効)。手元の QEMU の結果を CI の QEMU のジョブの代わりにはしない (手元は触った検査だけで、CI は全部を変異込み。build の x86 のシャードが一番長く、省いても待ちが縮まないため — 見直すのは x86 の側が縮んだ後)。本線と PowerPC の両方に当てる。
  - **枝の CI の残りを待たずに早送りしてよい場合** (ユーザー決定 2026-11-19「先に入れて問題ないのでは？ むしろ止めてから行ってもいいぐらい」、wt/int-1119g で初めて使った): 次の 4 つが全部そろう時だけ。(1) 同じ枝の前の回の CI の赤は全部直し、落ちた検査を手元で変異込みで通した (ログを取り込みの連絡に書く)。(2) 今の回で、直した検査が入るシャードと、static-check・ppc-compile が success。(3) 前の回から今の回までの差は、直しと、レビュー済みで手元の検査を通した段だけ (新しい未検査のコードを混ぜない)。(4) 枝が origin/main から早送りできる。入れる時は枝の run を取り消してから main を早送りする — main の push は同じ SHA の枝の成功が無いので build の検査を省かずに全部回し、PowerPC の範囲も前の main との差で判定される。早送りの後は main の CI の結論を読み、赤なら次の取り込みより先に直すか戻す。条件が 1 つでも欠けたら、枝の成功を読んでから早送りする (上の既定)。
  - **文書だけの枝は最新の main から作り、main を取り込んでから初めて push しない** (2026-11-19、wt/docs-emu-remote で build が 19 分走った原因、sol の調べ): 新しい枝の初回の push は、取り込んだ main のコードの差まで build.yml のパスの判定に入り、build が全部回る。枝を作った後に main が進んだら、初回の push の前は文書のコミットを最新の main に載せ直す (公開前なら rebase でよい)。
  - **作業中の push は `wip/**` へ** (ユーザー決定 2026-11-19): CI は `main` と `wt/**` の push でだけ起動する。作業中・直しの途中の push は `wip/<名>` に置き、取り込む SHA だけを `wt/<名>` に 1 回 push する (取り込む SHA は必ず check・build の全部を通るので関門は弱まらない)。同じ枝への push の繰り返しによる build の打ち切り (2026-11-18 の S1 で checks のジョブ 120 本中 37 本) と、赤の回し直しを減らす。同じ SHA の build を手で dispatch しない (dispatch の成功は main の再利用の証拠にならない)。
  - **記録の文書だけのコミットを別に main へ入れない** (2026-11-19): 段の記録 (設計書の実測・票の状態行) は次の段のコミットに含める。最後の段の記録は、待っている枝が無い時に入れる。同じ SHA を何度も回す確かめ (揺れの 10 回など) も、相手の枝が待っていない時間帯に回す。
- **実機とエミュレータは 1 つずつ** — 実機の受入・NP21/W の操作は直列。ブランチを並列にしても、実機の回は順番に並べる。

## 4. PM が出す前に確かめること

- 走っているブランチの触るファイルの一覧 (依頼パックの「触るファイル」) と重ならない。
- §2 の共有の登録ファイル・上限の持ち主と予算を依頼に書いた。
- 依存の票・ユーザー決定・実機の待ちが無い。
