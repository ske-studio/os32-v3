# 機能ごとのブランチで並列に実装する

> 状態: **現行 (2026-11-03)**
> 上位: ROLES.md (§0 の「並行」の行)

ユーザー指示 (2026-11-03): 「検査のバッティングは防げないですが、機能はブランチで分けて実装することを（触るファイルが被らない）正典化したら並行で出せるものは？」「これはGeforceに限った話ではないです」。

GeForce・ラスタに限らず、機能の開発全般の決まり。手本がある移植の流れ (PORT_FLOW.md) も、この決まりの上で段を並列に出す。

## 1. 決まり

1. **1 機能 = 1 ブランチ = 1 作業木** — `wt/<名前>` を main から切り、`~/wt/os32-v3/<名前>` で実装する。終わったら main に merge する。
2. **触るファイルを先に決める** — 依頼に「触るファイルの一覧」を書く (設計票のファイルの割り当ての表、[POLICY_DEV §2](../../POLICY_DEV.md) の 1 機能 1 ファイル)。PM は出す前に、走っているほかのブランチの一覧と突き合わせ、重ならないものだけを並列に出す。
3. **一覧の外のファイルに触る必要が出たら、実装者は止めて報告する** — PM が重なりを確かめてから許す。
4. **重なるブランチは直列** — 同じファイル・同じ生成物・同じ世代 (KAPI の版・配置の世代) に触るものは、先のブランチが main に入ってから、その main から次を切る。

## 2. 重なりやすいものの扱い

| 種類 | 例 | 扱い |
|---|---|---|
| 共有の登録ファイル | `build/*.mk`・`*_imports.def`・`tools/module_schema.py`・試験の登録・`build/packages.yaml`・`docs/INDEX.md` | 持ち主のブランチを 1 本に決める。ほかのブランチは足したい行を報告に書き、PM が merge のときに足す |
| 生成物 | 契約・schema・レイアウトの台帳・KAPI のラッパー | ブランチでは生成しない (または生成物をコミットしない)。PM が merge の後に 1 回だけ作り直す |
| 共有の上限 | 像の大きさ・起動 FD の空き (64KB)・KAPI の版 | 出す前に PM がブランチごとに予算を割り当てる。足りないときは [部品の上限の規則](../../08_build.md#起動時に読む部品の大きさの上限と由来) に従い、物理の制約が無ければ広げてから並列に出す |
| 結線の段 | 複数の機能をつなぐ段 (起動の順・ops の受け渡し) | 部品のブランチが全部入ってから、直列に 1 本 |

## 3. 検査と実機

- **ローカルの検査はメインストリーム 2 本だけ** (ユーザー決定 2026-11-04「コンピューターリソースの兼ね合いでメインストリーム2本はこのマシンでCIを回して、他のものはgitのciを回すようには出来ませんか？」「GeForceとラスタですね」): メインストリームは GeForce と ラスタスプラッシュ。この 2 本は今までどおり実装者の `check-changed` と PM の `check_wt.sh` の取り込みの検査をこのマシンで回す。
- **それ以外の機能のブランチ**: 実装者は触った像のビルドと、足した・触った試験 (`--mutate` を含む) だけをローカルで回し、`check-changed` は回さない。PM がブランチ `wt/<名前>` を push し、GitHub の CI (`.github/workflows/check.yml`・`build.yml`、`wt/**` の push で走る) の成功を取り込みの検査の代わりにする。main への取り込みは CI が緑の SHA を merge し、main の push の後の CI も確かめる。CI に無いもの (変異・NP21/W・実機) は従来どおりローカルと実機で。

- **検査の衝突は防げない** — 枠 (`check_slot.sh`、全体で同時 2 本、ROLES §0) で順番を待つ。並列のブランチ数は枠に合わせて増やさない。重い仕事は同時 2 本まで。
- **merge は終わった順** — 後から入るブランチは、入る直前の main を取り込み、`check-changed` を回し直す (衝突の解消を含む)。
- **実機とエミュレータは 1 つずつ** — 実機の受入・NP21/W の操作は直列。ブランチを並列にしても、実機の回は順番に並べる。

## 4. PM が出す前に確かめること

- 走っているブランチの触るファイルの一覧 (依頼パックの「触るファイル」) と重ならない。
- §2 の共有の登録ファイル・上限の持ち主と予算を依頼に書いた。
- 依存の票・ユーザー決定・実機の待ちが無い。
