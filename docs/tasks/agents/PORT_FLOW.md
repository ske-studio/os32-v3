# 手本がある移植の進め方 — コンパイルを全部の実装の後に

> 状態: **現行 (2026-11-05)** — 評価中の進め方。GeForce の層 1 の残り (C9・D) と層 2 で使った。層 3 以降と、手本がある移植に使う。
> 上位: ROLES.md (§0 の「移植 (手本あり)」の行)

ユーザー指示 (2026-11-03): 「コンパイルはすべての実装を終えてからにしてください」「層２はすべてコーディングを終えてから検査を回してください」「手本がある場合のスキームではこの流れ採用したいと思っていますので後で評価したいと思っています」「層２での問題点は最初に把握していればある程度防げたように見えます。完全でなくともそうであるべき」。

## 1. 使う場面

- 手本 (nouveau など、写せるライセンスの実装) があり、確定設計が書くレジスタ・順序を手本の file:line で決めている移植。
- 手本の無い段 (ラスタスプラッシュの再生器のように、実測で決める段) は使わない。段ごとにビルド・検査する (ROLES §0 の「検査」の行)。

## 2. 流れ

1. **設計の確定** — 確定設計の段の表 (1 ファイル = 1 段)。この段で §3 を点検する。
2. **宣言の段** — 型と関数の宣言 (例: `hwdev/gf/command.h`) を先に 1 段で凍結し、レビューを通して統合ブランチの起点にする。
3. **並列のコーディング** — 宣言の上で、部品の段を並列に出す。実装者は**ビルド・試験・生成をしない** (lint と `git diff --check` は可)。共通の依頼に §4 を入れる。
4. **設計の欠けの往復** — 実装者が止めた欠けは、設計者 (astra) が追記を書き、Opus がレビューし、PM が確定設計の末尾に写す。同じ実装者が続きを書く。
5. **レビュー** — 段ごとに読み取りだけのレビュー。コンパイルしないので、コンパイラが見つける誤り (宣言の食い違い・型・include・未定義) もレビューで挙げさせる。 観点に §4-1 の手本のガードの照合を必ず入れる。
6. **統合ブランチ** — レビューを通った段を `wt/<名前>-l<層>` に順に merge する。共有の登録ファイルの衝突は PM が解く (§3 の持ち主の決め方で減らす)。
7. **まとめビルド** — 生成 (契約・schema・import) と `make all` を 1 回。落ちた誤りは種類ごとに分け、機械的なものは PM が直し、それ以外は持ち主の段に返す。
8. **段の検査** — 枝を push して GitHub の CI (check・build の check-fast、変異なし)。落ちた試験は原因ごとに分け、追従は直し、製品の不具合は持ち主の段に返す。
9. **取り込み** — 段の検査が rc=0 で main に入れて push、CI を確かめ、段ごとの作業木を片付ける。

## 3. 設計の段で点検すること

確定設計を段に出す前に、設計者に 1 回点検させる (PM が依頼する)。 段の並列の出し方は [PARALLEL_BRANCHES.md](PARALLEL_BRANCHES.md) に従う。

| 点検 | 何を見るか | 見落としたときに起きたこと |
|---|---|---|
| 段の境目 | 誰が呼び、誰が持つか (状態の遷移・初期化の順・ops の受け渡し・時計) | 層 2 で設計の欠けが 8 件 (A0・B0・B7・C1/C2・T2・T2a1/T2a2/T2b) |
| 像と媒体の予算 | 部品の増分の見積りと、像 ([部品の上限表](../../08_build.md#起動時に読む部品の大きさの上限と由来)) と起動 FD の空き (64KB) | geforce.mod が 46→61KB で FD の空きが 56KB (ユーザー決定で FD から外した) |
| 共有の登録ファイルの持ち主 | 契約の生成器・レイアウトの台帳・試験の登録など、複数の段が追記するファイルを、1 段だけが持つか、ほかは報告に書いて PM が足すか | 層 2 で 3 本が衝突 (`gen_hwdev_contract.py`・`hwdev_layout.json`・`test_gf_command.py`) |
| ゲストかホストか | 移す部品が、ゲスト (newlib nano) で組むものか、ホストの試験 (libc なし) で組むものか | 層 2 の試験の一部が 32bit glibc を前提にした |
| 宣言の段に入れる範囲 | 型と関数だけでなく、(a) 部品の段の host 試験が使う試験の土台の API (stub の選び方・失敗注入・参照像)、(b) 段どうしで共有する表・検査の宣言、(c) 結線の段が部品の状態 (予約・窓・受付・slot) に触る口、(d) 範囲・所有の責任の境界、(e) 部品の段が使う番地の定数・台帳の識別子 (memmap.h・pgalloc.h、[C4])、共有の状態の欄 (IME_State の FepStore など) と部品の関数の表の欄、(f) 段どうしで受け渡すファイルの形式 (manifest の JSON など)、(g) 部品が新しく呼ぶ関数の import の宣言 (`tools/prototypes/<名>_imports.def`・`kernel/module/kdebug_imports.def`) と、それで変わる照合の固定値 (`tools/tests/fixtures/dep_dir_a/l01.json` など)、まで決めてから部品の段を出す | 層 3 で宣言の段の後に欠けが 3 回 (第 1 波 G1〜G3、B4 の alias、結線 C1/C2/C4 の 5 件)。試験の土台 A1 を部品の段と並べて出したので、部品の段の試験が書けなかった 2026-11-06: DICT_META の段 A の後に C・C2 が共有の状態の欄と関数の表の欄の無さで止まり、E・E2 は manifest の形が食い違った。Trident の段 3a は資源の段が要る番地の定数・識別子が無く、Opus が P1 で止めた。 |
| 既存のファイルと型 | 設計が「新」と書くファイル・CHECK の名前が既にないか、置き換える型の既存の利用者 (offsetof・位置指定の初期化・契約の STATIC_ASSERT) を grep で列挙 | 層 4 の点検で、既存の test_gf_display.py を「新」と書いていた・gfinit_mode の差し替えで 8 か所が壊れる |
| 型と算術 | 使う型が include/types.h にあるか (u64/i64 は無い)、64bit の除算・剰余が -nostdlib の host でリンクできるか (__udivdi3)。カーネル・部品・kdebug・ブートローダーも libgcc を使わず、自前の helper か乗算の比較にする ([L1](../../CONSTRAINTS.md#l1-gpl--lgpl-の物は-os-の外のユーザーランドに置く)) | 層 3 A1 の ref_scale、層 4・5 の PLL・vmap |
| 追記の後の宣言の段 | 確定設計への追記 (欠けの埋め・前提の点検) が共有の宣言 (下の層の口・ctx の欄・callback の実体の名前) を足すなら、部品の段を出す前に宣言の段を挟む | 層 4 で X1〜X4 の追記の後に宣言の段を挟まずに C2 の 6 段を出し、6 段とも宣言の欠けで止まった |
| 下の層が入った後の前提 | 下の層が main に入ったら、上の層の確定設計の前提 (型・所有・公開・期限) を実物と照らす点検を設計者にさせる (ユーザー指示 2026-11-04「GeForce層３が終わったら層４、５の前提が変わっていないかをチェック」) | 層 3 の後の点検で層 4・5 に食い違い 4 件 (X1〜X4) |
| 呼び出しの回数と手本の関数の対応 | OS32 の口 (HAL の init・enter・leave・shutdown、2 回目の init) ごとに、手本のどの関数 (ScreenInit・EnterVT・LeaveVT・CloseScreen) に当たり、何を 1 回だけ・何を毎回流すかの表 | Trident 段 3 の r1 が、全画面アプリに入るたびに PC-98 の初期化・保存・VRAM の書き込み確認を流す形だった (手本の EnterVT はモード設定と Enable だけ)。leave の後の shutdown でもう一度 Restore を流した (手本は `vtSema` で何もしない) |
| 起草中の決定の変化 | 起草の途中でユーザー決定が変わったら、走っている起草者の依頼に書き足さず、決定の原文を添えて r2 で直させる (レビュアーにも決定の原文を渡して最初に照合させる) | 2026-11-06、GeForce の層 5 の熱の追記で、依頼に追記した「しきい値ごとに分ける」を起草者が読まず、r1 が古い決定のまま書かれた (Opus の P1 が 3 件) |
| 起草の依頼の並び | 依頼の章立てに手順の並び (「Init → Save」など) を書かない。順序は手本と実機で動いた台本から取らせる | Trident 段 3 の r1 で、PM の依頼の章立ての並びを起草者が決定と読み、Save と Init、Disable と Restore を手本と逆にした |

## 4. 依頼に必ず書くこと

並列の実装者に渡す共通の依頼 (`~/os32-tmp/run/gf2-nocompile.md` が雛形) に、次を入れる。

- **素の環境で通す** — この PC と CI に無い道具・ライブラリ (32bit glibc など) を作業用の場所に展開したり PATH に足したりしない。host 試験は libc なし (`-nostdlib`・自前の `_start`) で、共有の土台のヘッダーに寄せる (ユーザー指示 2026-11-03「libcなしで」)。
- **型の名前** — `s32` は無い。`i32` を使う (`include/types.h`)。
- **import を足すとき** — `hwdev/hwdev_imports.def` だけでなく、`docs/design/hwdev/hwdev_imports.md` §3 の表と件数、`tools/gen_hwdev_contract.py` の件数を同時に (生成器が完全一致で照合する)。取得元は kdebug と同じヘッダー。
- **部品を足すときに追従が要る試験** — HWDEV の import の宣言とレイアウトの固定値 (`tools/tests/hwdev_contract_fixture.py`・`test_dep_dir_a_l02.py`)、shell をホストで組む試験のソースの一覧 (`sh_status_host.c`・`sh_shell_host.c`・`sh_truncation_host.c`)、`recover_virtual_fixture_host.inc` の写し、`hwdev_audit.py`。どの試験が当たるかを報告に書く。
- **固定値はマジックナンバーにしない** — 試験の中のハッシュ・CRC・件数は、元から求められるなら求める形に、求められない値は何の値かと作り直し方を名前と注記で残す (ユーザー指示 2026-11-03)。
- **止める欠けの範囲** — 止めて報告するのは、宣言・試験の土台への追加か、既存の状態の持ち主の変更が要る欠けだけ。ほかの細かな判断は設計の節と手本に沿って実装者が決め、報告の「実装者が決めたこと」に 1 行ずつ (レビューで確かめる)。カードの行数は目安で、超えても止めずに書き切る。
- **変異の項目の形** — `('<名前>', '<製品のファイル>', '<置き換える前 — 一意>', '<置き換えた後>', '<RED になる試験>')` を報告に。置き換えでコンパイルが失敗する変異 (唯一の呼出しを消すなど) は RED に届かないので避ける。
- **最適化で消える照合** — 自前の `assert` は、照合の呼出しが最適化で消えないようにする (コンパイラのバリア)。
- **新しい作業木にはフォントを写す** — codex のサンドボックスはネットに出られず、`make all` がフォントの取得で rc=2 になる。作業木を作るときに `~/os32-tmp/bin/seed_fonts.sh <作業木>` (スキル os32-delegate §1)。
- **本番の組み立てを通す試験を 1 本** — 偽物の土台 (fake) が時計・待ち・ops を自前で渡すと、本番の組み立て (例 `hwdev/gf/devinit.c` の prepare) の渡し忘れが host 試験で見えない。部品の試験とは別に、本番の組み立ての関数で作った構造体の口が全部埋まっていることを確かめる試験を、結線の段か統合の段に置く。
- **失敗の rc を捨てない** — 段を `||` でつないで 1 つの失敗にまとめない、黙って別の経路 (例 98 の描画) に替えない。失敗した段と rc を 1 行出す (層 4・5 の実機で、GeForce の表示の立ち上げが黙って pc98-planar に戻り、原因の段が分からなかった)。
- **devinit の後でしか意味のない値を、その前に読まない** — OS32 は GeForce の ROM の初期化の命令列 (devinit) を自前で流してカードを立ち上げる (BIOS 無しの初期化、段 4a から)。その devinit は最初の video_start で走るので、起動時の予約の段ではカードはまだ冷えていて、PFB などが 0 を返す。段を足すときは、その段が devinit の前か後かを確かめ、後でしか決まらない値 (VRAM の大きさ・push の位置など) は devinit の後で求める (層 4・5 の実機で、起動時の予約の段で PFB 0x10020c を読んで VRAM 0 と判断し、黙ってページ表の用意を飛ばした)。
- **準備されていない部品の口を公開しない** — 準備 (prepare) が失敗・未実行なら、診断や試験の ops を公開せず、呼び手も NULL の口を呼ばずに誤りを返す (同じ回で gf1 status が NULL を呼んで #PF)。
- **試験の土台を段ごとに書く** — 共通の依頼に「必ず fake を使う」と一律に書かない。段の表に、その段の試験の有無と使う土台 (UNIT) を書いてから出す (層 5 で 3 段が止まった)。
- **手本との照合は期待値をリポジトリに置く** — 試験は手本のソース (`~/os32-tmp/refs` など PM の手元) を読まない。手本から生成した期待値 (fixture、出典・ライセンス・作り直し方を冒頭に) を置き、CI は fixture と製品を照合する。手本との直接の照合は `--oracle` などで分け、PM のローカル検査として DEFERRED_TESTS に 1 行 (層 2 B4 の形)。
- **待ちの期限は手本と同じ単位で数える** — nouveau の待ちは操作ごとに開始から数える (`nvkm_msec`、`timer.h:52-67`)。長い段 (devinit など) の前に作った 1 本の期限を後の段まで使い回さない — 実機は devinit に秒単位かかり、後の段が待ちに入る前に期限切れになる (2026-11-05 objects_init -205、`now-dl≒2 秒`・GET=PUT)。
- **偽物は本番と同じ初期状態と上限で始める** — 初回の起動では NULL の欄 (`ch->f` は gf2_start まで NULL) を偽物が前もって埋めない。本番の口の契約を偽物も持つ。待ちの 1000µs (`GF_INIT_WAIT_CHUNK_US`) は現在は口の内側の確認間隔で、呼び元の要求長の上限ではない (GF_FEAT5_DESIGN の PM 決定 22)。どちらも host 試験で隠れて実機で落ちた (2026-11-05 の -401・mode_load -1)。
- **アクセス幅は手本のとおり** — 1 バイトのレジスタ (CR/SR の index/data、AR、パレット) を u32 で読み書きしない。手本の `rd08`/`wr08` と同じ幅で、偽物は幅ごとの回数と番地を記録して照合する (2026-11-05 の foundation の幅の捨て)。
- **手本の表は既定の行まで全部写す** — 判別の表 (Trident の VRAM 容量 SPR、`trident_driver-1.4.0.c:2919-2975`) を一部だけ写すと、実機の値が表に無く空振りする。既定 (`default`) の値も写す。
- **手本の初期化の関数と機種の分岐は全部たどる** — 手本が機種で分ける所 (`xf86IsPc98()` など) を grep で全部挙げ、どれを写したかを設計に表で書く。初期化の関数を「この機械の前提でない」と判断して省かない。実機で止まる危険も省く理由にしない (ユーザー 2026-11-05「止まることを理由にしないで」)。Trident の設計 v6 が `PC98TRIDENT96xxInit` を省いて、実機で BAR0 が書けなかった。
- **共有の構造体に欄を足すときは、全欄を回す既存のコードを探す** — 宣言の段で関数の表 (facade) に欄を足すと、全欄を照合・複写・比較する既存のコードが、後の段で埋まるまで 0 の欄で断ることがある。`grep` で構造体の全欄を回す所 (`for ... <名>_SLOTS`・`sizeof` で回す照合) を挙げ、0 の欄の扱いを決める。偽物の初期化子は本番 (例 `lan_body.c`) と同じ値にする (2026-11-05、lan.mod の照合が 0 の欄で断り、実機で LAN と sfs が使えなくなった。偽物は全欄を埋めていて試験で拾えなかった)。
- **任意の機能の失敗を本体に返さない** — 手本の周期の worker (温度・ファン・時計) は失敗を記録して自分だけ止まり、表示には返さない (nouveau `therm/fan.c:76-81`、`clk/base.c:308-342`)。OS32 の協調の poll に移すときも、その失敗を present などの本体の rc にしない (2026-11-05、ファンの無い GeForce で present が `rc=-502` で止まった)。
- **依頼にレビューの指摘や設計を写す前に、手本の該当の行を PM が確かめる** — 写した指摘が手本と違うと、実装者は依頼どおりに手本から外れる (2026-11-05、GeForce 直し 4 の R3: 「GPIO2/9 以外は toggle に回す」と写したが、手本は nv40.c:111-115 で -ENODEV → fannil)。実装者には「依頼と手本が食い違ったら手本を正として報告」と書く。
- **HAL が今渡している値の幅を、既存のバックエンドで確かめる** — 新しいバックエンドの宣言は、今の HAL の口が渡す値の幅 (例: パレットの成分は今の KAPI の口では 4 ビット、`include/pegc.h` の PEGC_PAL_KAPI_MASK) を既存のバックエンド (cirrus_pal6・geforce の ×17) と照らしてから決める。ただしその幅は HAL の下限であって決まりではない (色は最大 32 ビット、票 TASK_VIDEO_HAL)ので、バックエンドは成分の幅を定数で受けて換算し、決め打ちしない (2026-11-06、Trident 段 3a が 8 ビットと宣言し白がほぼ黒になる形だった。ユーザー「最低が4bitなだけで最大32bitはいるはず」)。
- **優先の順は 1 つに書く** — 共通の依頼に「台本の列が正」と「手本どおり全部」を並べて書くと、部品の段ごとに解釈が割れる。「順序・値・対象は台本と手本を照らし、食い違ったら手本を正として差を注記と報告に書く。台本は実機で動いた証拠」と 1 文で決める (2026-11-06、Trident 3b で保護の基点が pc98_init と route で割れた)。
- **手本の状態が途中で切り替わる所は、その状態を 1 つの欄で持つ** — 手本の値が関数の途中で変わるもの (vgaHW の IOBase は Save で保存値、VGA の Restore で color、TRIDENTRestore で保存値に戻る) を、PM が「この時点の値に揃える」と決め打ちしない。手本の切り替わる行を全部挙げ、同じ時点で切り替える欄を契約に置く (2026-11-06、Trident 3b の P2-1)。
- **入口の共有のファイルに呼び出しを足したら、同じ種類の落ちをまとめて直す** — `exec/exec_syscall.inc` のような入口は、関数を切り出して組む host 試験が 50 本を超える。CI で 1 本落ちたら、その 1 本だけ直して push し直さない。`python3 -B tools/checks/run.py --select --files <変えたファイル>` で当たる試験を挙げ、同じ切り出しの形の試験を grep でまとめて直してから push し、CI で全部を確かめる。手元で選ばれた検査を全部回すことはしない (時間がかかる。検査は CI に任せる、ROLES §0「検査」) (2026-11-06、gf-cui の `exec_cui_display_abort` で CI が 3 回続けて 1 本ずつ落ち、その後に手元で 71 本を回させた依頼が 1 時間を超えた)。
- **新しい部品の生成ヘッダーは clang の検査にも見せる** — 部品の `<名>_imports.h` は生成物なので、`tools/prototypes/<名>_imports.def` と各検査 (arch-asm・p2v・c-dialect) の covers・`tools/source_roots.py` を cirrus と同じ形で足す (2026-11-06、Trident の枝で 3 本の検査が `trident_imports.h` を見つけられず落ちた)。
- **並列の段がどちらも共有の構造体に欄を足したら、統合で生成物と固定値を作り直す** — `hwdev/generated/` の契約と `tools/tests/hwdev_contract_fixture.py` の固定値は手で衝突を解かない。片方を取って `make all` で作り直し、`--snapshot` の値を入れて、`test_dep_dir_a_l01/l02`・`test_ci_stab` を回す (2026-11-06、ガードの第 1 波の gw-stage と gw-irq)。
- **止める条件は項目ごとに書く** — 「〜と重なるなら止める」を依頼の 1 項目に書くと、実装者が依頼全体を止める。重なる部分を名指しで範囲の外に置き、残りは続けるよう書く (2026-11-06、gf-cui の直し 7 が 3 項目とも止まった)。
- **共有の試験の土台に定義を足したら、取り込む試験を grep で全部見る** — `gfx_kernel_fb_host.c` のような土台を `#include` する試験が自分の定義を持っていると二重定義になる。取り込む側が外せる形 (`#ifndef HOST_OWN_<名>`) にする (2026-11-06、`pc98_route_safe` で geforce-host・trident-emergency が順に落ちた)。
- **出す前に、設計のファイルの表と出した段を突き合わせる** — 並列の波に分けて出すと、表の 1 行を出し忘れる (2026-11-06、Trident 3b の 12 ファイルのうち vram.c を出し忘れ、統合のときに気づいた)。
- **宣言の段で、期限・世代などの引数が下の層の口まで渡るかを確かめる** — 上の層の関数に期限を足しても、送信・待ちの口 (`SfsIo.put` など) が受けなければ、下の層が自分の上限で待ち続ける。並列の 2 段が同じ欠けで止まる (2026-11-07、Host Services の C1・C3 が `lan_put` の 1000ms の待ちで揃って止まった)。
- **部品の関数の表 (ops) に入っている型を広げたら、同じ段で表の版・枠の数・生成物を上げる** — 表の大きさの STATIC_ASSERT、`tools/module_schema.py` の版、契約の試験の offset が揃って落ちる (2026-11-07、`SfsIo` に 1 枠足して `LanModuleApi` が 22→23 枠、OPS 版 2→3)。
- **試験の `needs` に、カーネルと対になる成果物 (`make:build/out/*.mod` など) を足さない** — CI は検査を並列に回すので、検査の最中の make がカーネルを作り直し、ほかの試験の照合 (memmap の generations-manifest) が落ちる。CI は検査の前に全部を組む。手元で古い成果物を読む試験は、先に `make kernel` してから回す (2026-11-07、DICT_META 段 L)。
- **検査・照合の位置を 1 か所に寄せる直しでは、その関数の呼び手の全部 (起動の経路を含む) の試験を回す** — 触ったファイルの試験だけでは、別の呼び手の既存の case を見落とす (2026-11-07、DICT_META の L2 で起動の open まで予約の照合で断るようになり、`settings-lower-reserve` が落ちた。Opus の承認も見落とした)。
- **1 つの経路に診断・段を足す枝を合わせるときは、共通の出口 (`pc98_route_to_98` など) の呼び手を grep で全部見る** — 衝突の無い所で、片方の経路だけに入る (2026-11-07、gf-cui の leave の診断が、熱・寿命の側の再起動の経路に入らず foreground-reboot が落ちた)。
- **製品の関数の呼び出しを 1 つ足したら、その関数の兄弟の stub を持つ試験の土台を全部洗う** — `vfs_fd_invalidate_mount` の stub を持つ土台は、新しい `vfs_fd_stale_mount` も要る。`#include` で取り込む土台だけでなく、python が切り出して組む試験 (`*_host_source.c`・`index('static ...')`) も含める。触ったファイルを組む試験を 1 本ずつ手元で回してから push する (2026-11-07、Host Services の D の統合で、kernel-shell・hostsvc-serialfs・kapi-ranges を CI で 1 本ずつ落とした)。
- **ゲストの SQL は、製品の SQLite の OMIT の設定 (lib/sqlite3/os32_sqlite_config.h) で通る形だけ使う** — CAST・CTE・window 関数などは prepare で必ず誤りになる。host の普通の SQLite では通るので気づけない。`tools/tests/test_sqlite_product_sql.py` に新しい SQL の置き場を足す。KAPI の `db_column_text` は INTEGER の列を文字にしないので、整数は `db_column_int` か SQL の `''||列` で読む (2026-11-07、hsync の CAST で実機の同期が全部止まり、fep_meta_test は CAST と INTEGER の読み方で 2 回落ちた)。
- **レビューの指摘を次の依頼に回す前に、PM が「動くアプリは 1 つだけ」で読み直す** — 依頼文に前提を書いても、指摘をそのまま流すと持ち主の区別・並行の再入の守りが入り込む (2026-11-07、GeForce の熱の停止。ユーザー「なんかシングルタスクOSって忘れてませんか？」)。

レビューで 1 つの段に見つかった誤りが、ほかの段にもありうる種類なら、PM は走っている全段の依頼に追記し、統合の前に grep で確かめる (層 2 では B6 の `s32` を B0・B1 に流さず、まとめビルドで再び出た)。

### 4-1. レビューで照合すること — 手本のガード

ドライバの実装 (段ごとの差分、統合、実機で不具合が出た後) のレビューでは、**手本が守っている前提を OS32 も守っているか**を照合する。手本はガードを明示の検査として書くとは限らない。作り方・呼ぶ順・状態の持ち方で暗に保証していることが多い。OS32 は呼び手が記述子や値を直接渡すので、手本では起きない入力が届く。

| 種類 | 手本の守り方の例 | OS32 で見ること |
|---|---|---|
| 整列 | 面を作るときに揃える (xf86-video-nouveau `nv_accel_common.c:58-60` の `pitch = ALIGN(width*cpp, 64)`、`nouveau_exa.c:434-435` の offset 256・pitch 64) ので、送る時点の検査が無い | 呼び手が渡す pitch・offset・矩形・転送の長さを、受け取る境目で断るか、作る側で揃えるか |
| 上限 | class ごとの座標・pitch の幅、push の長さ、表の範囲 | 型の幅だけでなく、手本の上限で断っているか |
| 組み合わせ | format と class、bpp と object | 手本が作らない組み合わせを受けたときの扱い |
| 送る順・状態 | object・context の bind の後に描く、idle・fence の後に触る、IRQ の ACK の順 | 順を飛ばす呼び方ができないか |
| 失敗の後 | 失敗の経路でも必ず戻す物 (表示・保護・session) | 失敗の後に leave・再入場ができるか |
| 時間切れ | 時間切れの後に手本がすること (reset・再初期化・記録) | 時間切れの後の状態が次の呼び出しを壊さないか |

- 指摘の形は、項目ごとに「重さ (A 実機で止まる・壊れる / B 誤った値を受けて黙って誤る / C 手本と違うが害は無い)」「手本の file:line と前提」「OS32 の file:line (無い・違う)」「直し方 (受け取る境目で断る / 作る側で揃える / 手本どおりの順にする)」。
- 試験も見る。試験が手本の範囲外の入力を作っていると、実機で試験そのものが GPU を止める。
- **逆向きの差も見る — 手本より厳しい条件を足さない**。手本が誤りにしない値 (源の無い時計の 0)、手本がしない照合 (設定の後の読み戻しと計算の一致) を設計で足すと、実機の正常な状態を誤りにする (2026-11-06、GeForce の層 5 の save 系が -509、`clock.c:104` の「0 なら ESTATE」は手本 `clk/nv40.c:82-115` に無い。熱の P0 の「readback と calc の厳密一致」は固定の第 2 段で成り立たず、手本 `clk/nv40.c:146-195` にも無い)。足すなら手本に無い理由を設計に書き、実機の値で確かめてから。
- **手本は他の OS で動いた実績のある正解として、そのまま移す** — 不具合が出たら、調べの版を重ねる前に「手本と 1 手順ずつ同じか」を見て、外れた所を手本どおりに直す。BSD/MIT は写してよい (著作権表示を残す)。調べの版は、手本の前提が PC-98 で成り立たない所 (経路の切り替え・書き込みの幅) を確かめるときだけ (2026-11-07、Trident の 2 回目の白い矩形は、手本に無い全域の VERIFY が後ろの 2MB を壊したためで、調べの版を 3 回作った後に手本どおりに揃えて直った。ユーザー「手本をなんと思っているのでしょうか？」)。
- **実機で 1 件見つかったら、その 1 件を直す前に、同じ型の穴をドライバ全体で洗い出す** (読み取りだけの調べの段)。同じ教訓が当たるほかのドライバも一緒に調べる (ユーザー指示 2026-11-06「先にこのようなガードが手本にあって実装にないところを探してください」)。
