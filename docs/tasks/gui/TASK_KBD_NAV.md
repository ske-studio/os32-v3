## 0. 事実 (2026-09-25 の調査、ファイル:行)

- キーは IRQ1 → raw リング → gshell `capture_keyboard` (`userland/gshell/src/input.rs`)。1 件 = `scan | down<<8 | mods<<9`。mods の並びは `drivers/kbd.h:131-135` (SHIFT 01 / CAPS 02 / **KANA 04** / GRPH 08 / CTRL 10)。修飾キー自身 (0x70-0x74) は Key として配らない (input.rs:349)。
- 振り分けの順: X4 の退避判定 (input.rs:317) → 修飾 → CTRL+STOP → SHIFT+SPACE (FEP) → modal (input.rs:377) → startmenu → (窓なし) standalone → FEP → 最前面の窓。
- マウスは `capture_mouse` がキーボードを読み切った**後に 1 回**、`mouse_poll` の現在値と `prev_buttons` の差分でエッジを作る (input.rs:454-)。X4 では WM の領分のエッジを保留して `prev_buttons` を進めない (input.rs:551)。全画面 GFX 中はマウスを誰にも配らない (input.rs:466)。
- **カナ**: `drivers/kbd.c:299` は **make でだけ状態を反転**し break を無視する (CAPS も同じ)。OS32 のどこもカナの状態を使っていない。修飾の現在値は KAPI `kbd_get_modifiers` で読める。
- FEP の確定文字は**確定した時点の**フォーカス窓へ配る (fep.rs:454)。WM のフォーカス変更 (`wm::set_focus`、wm.rs:1032) は FEP の未確定文字を確定も取消もしない — **マウスで窓を切り替えたときにも同じ穴がある** (既存)。
- `libos32ui` (microUI、`mui_pump_input_ch`) のアプリは WM のイベントではなく `mouse_poll` を直接読む (`userland/lib/ui/libos32ui_core.c:192`)。今の利用者は `apps/ui_demo` だけ。

## 1. 方針

### 1-1. キーの読み替え (PC-98 → Win98)

| Win98 | PC-98 | 備考 |
|---|---|---|
| Alt | **GRPH** | |
| Windows キー | 無し | Win98 でも CTRL+ESC で代わりになる。Win+E / Win+R などは割り当てない |
| F4 / F10 | f･4 / f･10 | |
| NumLock (MouseKeys の切り替え) | **カナ** | Win98 の既定は左 Alt+左 Shift+NumLock。PC-98 にはラッチの効くカナがある |
| テンキー / * - + . 0〜9 | 同じ | PC-98 のテンキーは全部ある (= と , は使わない) |
| IME の切り替え | SHIFT+SPACE (今のまま) | Win98 の Alt+半角/全角 は PC-98 に無い |

### 1-2. WM のショートカット (Win98 と同じ意味)

| 操作 | Win98 | OS32 | v1 |
|---|---|---|---|
| スタートメニューを開く / 閉じる | CTRL+ESC | CTRL+ESC | ○ |
| 窓を切り替える | Alt+TAB (Shift で逆) | GRPH+TAB (SHIFT で逆) | ○ 一覧の代わりにタスクバーのボタンで選択を示す (下) |
| 窓を最背面へ回して次へ | Alt+ESC | GRPH+ESC | ○ ただし最小化した窓は飛ばす (**Win98 との差**、下) |
| 最前面の窓を閉じる | Alt+F4 | GRPH+f･4 | ○ 窓が無ければ Shut Down の確認 (Win98 と同じ) |
| 窓メニュー (元のサイズ / 移動 / サイズ / 最小化 / 最大化 / 閉じる) | Alt+SPACE | GRPH+SPACE | ○ |
| 移動・サイズの実行中 | 矢印 / RETURN / ESC | ↑↓←→ 8 ドット、SHIFT+矢印 1 ドット、RETURN で決定、ESC で元へ | ○ XOR 枠 (既存) |
| 右クリックメニュー | Shift+F10 | SHIFT+f･10 | ○ **窓があれば窓へ配る** (選んでいる項目のメニューはアプリの領分、Win98 と同じ)。窓が無いときだけ WM がデスクトップのメニューを出す |
| タスクバーへ | CTRL+ESC → ESC → TAB | 同じ | v2 |
| アプリのメニューバー | Alt 単独 / F10 | GRPH 単独 / f･10 | **v1 は未対応**。f･10 は今までどおり窓へ配る。GRPH 単独は今も**どこへも配っていない** (修飾キーは input.rs:349 で捨てる) ので、Alt 単独の動作は v2 で libos32gui のメニューバーと一緒に決める |

**GRPH+TAB の意味 (Win98 の Alt+TAB と同じく、GRPH を離したときに切り替える)**:
GRPH を押している間を 1 回の「切り替え」とする。最初の TAB で、その時点の **MRU 順** (最後にフォーカスを持った順。
最小化すると末尾へ — Win98 も最小化した窓は Z 順の最後へ回る) を写して選択を 1 つ先 (SHIFT で 1 つ前) に置く。
以後の TAB で選択を進める。**途中では窓を動かさない** — 選択中の窓は**タスクバーのボタンを押し込み表示**して示す
(Win98 の一覧の代わり)。GRPH を離したら選択した窓へ切り替える (最小化なら元に戻す)。ESC で取り消し (何も変えない)。
フォーカスは離したときに 1 回だけ移るので、FEP の確定 (§1-6) も 1 回だけ起きる。
GRPH の break は修飾キーとして捨てる (input.rs:349) **前に**見る。

**GRPH+ESC**: 最前面の窓を MRU の末尾へ回し、次の窓にフォーカスを移す。Win98 は最小化した窓に来るとタスクバーの
ボタンを選ぶ (元に戻さない) が、v1 はタスクバーのフォーカスを持たないので**最小化した窓は飛ばす** (v2 でそろえる)。

**SHIFT+GRPH+SPACE は FEP の切り替え** (今の SHIFT+SPACE の規則が先)。窓メニューは SHIFT 無しの GRPH+SPACE だけ。

**Win98 との差 (v1)** — 割り当ては Win98 のまま、動作が違うところ:

| Win98 | OS32 v1 | 理由 |
|---|---|---|
| Alt+TAB で窓の一覧を出す | 一覧の代わりに**タスクバーのボタンの押し込み表示**で選択を示す | 一覧の窓は v2 |
| Alt+ESC は最小化した窓に来るとタスクバーのボタンを選ぶ | 最小化した窓は飛ばす | タスクバーのフォーカスが v2 |
| Alt 単独 / F10 でメニューバー | GRPH 単独は何もしない (f･10 はアプリへ) | libos32gui のメニューバーと一緒に v2 |
| Ctrl+Esc → Esc → Tab でタスクバー | 無し | v2 |
| Win キーの組み合わせ | 無し | PC-98 に Win キーが無い |
| MouseKeys は / - * でボタンを選んでから 5 / + / 0 | ボタンを選ぶ操作 (/ - *) を持たず、5 = 左・- = 右・+ = ダブル・0 = 左を押したまま | ユーザー決定 (2026-09-26): 手数を少なく |
| MouseKeys の速さは設定画面で決める | CTRL を押している間は半分の速さ | ユーザー指示 (2026-09-26) |

**状態ごとの扱い** — WM が拾ったキーは**どの状態でもアプリへ渡さない** (消費する):

| キー | 通常 | モーダル中 | スタートメニュー表示中 | 全画面 GFX 中 | 移動・サイズ中 |
|---|---|---|---|---|---|
| CTRL+ESC | 開く | 無視 | 閉じる | 無視 | 無視 |
| GRPH+TAB / GRPH+ESC | 切り替え (GRPH+TAB は GRPH を離したとき) | 無視 | 閉じてから切り替え | 無視 | 無視 |
| GRPH+f･4 | 閉じる要求 | **ダイアログへ ESC** (Win98 と同じくダイアログを閉じる = 取消) | 閉じる (メニューだけ) | 無視 | 無視 |
| GRPH+SPACE | 窓メニュー | 無視 | 無視 | 無視 | 無視 |
| SHIFT+f･10 | 窓があれば**窓へ配る** (WM は拾わない)。窓が無ければデスクトップのメニュー | ダイアログへ (今までどおり) | 無視 | アプリへ (今までどおり) | 無視 |

「無視」も消費する (アプリへ漏らさない)。全画面 GFX 中は画面がアプリのものなので WM は何もしない
(CTRL+STOP だけが今までどおり効く)。

### 1-3. マウスキー (カナ = マウスモード、配置は Win98 の MouseKeys)

**カナの状態がオンの間だけ**、テンキーをポインタの操作に使う。オフならテンキーは数字 (今までどおり)。

| テンキー | 動作 (移動は Win98 MouseKeys と同じ。ボタンは**直接割り当て** — ユーザー決定 2026-09-26、手数を少なく) |
|---|---|
| 8 / 2 / 4 / 6 | 上 / 下 / 左 / 右 |
| 7 / 9 / 1 / 3 | 斜め |
| CTRL + 上の 8 方向 | **半分の速度** (ユーザー指示 2026-09-26、下) |
| 5 | 左クリック (押下 → 離し) |
| - | 右クリック |
| + | 左ダブルクリック (同じ X3 周期の中で down・up・down・up) |
| 0 | 左ボタンを押したまま (ドラッグの開始) |
| . | 押したままのボタンを離す |
| / と * | 使わない。**マウスモード中は消費して何もしない** (数字として窓へ渡すと、ポインタを操作しているつもりの打鍵が文字として入る)。ボタンの選択の状態は持たない |

- **+ のダブルクリック**: 4 つのエッジを同じ取り込み周期で処理するので、アプリが見る tick の差は 0。gshell のファイル選択 (`modal.rs` の DBLCLICK_TICKS・同じ行) と filer (`userland/rust/filer` の 30 tick 以内・同じ行) の判定に必ず入る (K1 ④ で WM のファイル選択を開かせて確認)。
- **CTRL の半分速度**: 移動量は make 回数の加速 (1 / 4 / 8 ドット) に 1/2 を掛ける。1 ドットの半分は丸めると 0 になるので、**1/2 ドットの端数を軸ごとに持ち越す** (make ごとに半分を足し、整数になった分だけ動かす。マウスモードが切れたら端数は捨てる)。CTRL の有無は raw に焼き込まれた修飾ビットで見る (§1-5 と同じ理由で現在値は読まない)。CTRL+テンキーは既存の割り当て (カーネルの CTRL+STOP・CTRL+GRPH+DEL、WM の CTRL+ESC、`translate` の CTRL+英字) のどれともぶつからない。

- **移動量は make の回数で決める** (時刻ではない — ホスト試験で再現できる)。PC-98 のキーボードは押し続けると make を繰り返す。
  1 回目〜7 回目は 1 ドット、8 回目〜15 回目は 4 ドット、16 回目以降は 8 ドット。break で数え直し。定数は 1 か所。
- **合成したボタンは実際のマウスと別に持つ** (`st.synth_buttons`)。マウスキーは X3 でだけ実行する (§1-4) ので、キーを処理した
  **その場で**エッジを 1 つずつ順に処理する (ダブルクリックなら down → up → down → up)。列に溜めない — 溜めないので容量の問題が無い
  (Codex 2 回目 A3)。`prev_buttons` の差分には混ぜない (同じ周期の押下 → 離しが消えるため — 1 回目 P1-2)。
  ポインタの `buttons` として配る値は `実マウス | synth_buttons`。
- **エッジの処理は実マウスと同じ関数を通す**: `capture_mouse` の X3 側の分岐 (モーダル中はダイアログへ (input.rs:488)、それ以外は
  `wm_button_down/up`・`wm_right_down/up`) を `edge_x3(st, x, y, btn, down)` に切り出し、実マウスのエッジとマウスキーの両方がそれを呼ぶ。
  **モーダル中のテンキー 5 は背後の窓へ届かない** (Codex 2 回目 A4)。
- ポインタ位置: 合成の移動も**実マウスの移動と同じ分岐を通す** (モーダル中はカーソルだけ、WM のドラッグ中は `update_drag` (input.rs:522)、
  それ以外はカーソルと `forward_pointer`)。エッジと同じく `move_x3(st, x, y)` に切り出して両方が呼ぶ。実マウスの値が**変わったら**実マウスの値から続ける
  (最後に動いた方が勝つ)。範囲は画面に収める。
- 表示: マウスモード中はタスクバーに `[M]`。CUI では何もしない。全画面 GFX 中はマウスと同じく誰にも配らない (キーも消費しない — カナがオンでもテンキーはアプリへ)。
- **v1 の対象は WM のイベントで動くアプリ** (libos32gui)。`libos32ui` (microUI) のアプリは `mouse_poll` を直接読むので合成の
  ポインタは届かない (今は `apps/ui_demo` だけ)。これらを動かすには `mouse_poll` に合成値を載せる KAPI が要る → v2 の判断。

### 1-4. X4 (ポンプ) での扱い — Codex 指摘 P1-1

WM のショートカットとマウスキーは状態機械を動かすので **X3 でだけ実行**する。X4 で見つけたら、
今の FEP と同じく **その raw と以後の raw を全部 `pending_raw` へ退避**して次の X3 へ回す (順序を保つ)。

- 退避の条件 (input.rs:317 の `defer`) に「この raw は WM のキーである」を足す。WM のキー = §1-2 の make、GRPH+TAB 切り替え中の
  GRPH の break と ESC、**カナの make / break そのもの**、カナ中のテンキー、**マウスキーが消費したテンキーの break** (モードが切れた後でも)
  (Codex 2 回目 A1)。**判定は raw を取り出した後**になるので、X4 では `pending_raw` に空きが無いときは
  (退避しない種類のキーであっても) 読まずに止める。
- 退避が 1 件でもあれば、今までどおり後続もすべて退避される (`st.pending_raw_n > 0`)。

### 1-5. カナの状態と、モードが切れるとき — Codex 指摘 P2-5

- モードは **raw に焼き込まれた修飾の KANA ビット**で決める (`drivers/kbd.c:283` — 修飾キー自身の raw は更新後の値を載せる)。
  カナの raw を修飾として捨てる前に、その raw の KANA ビットでモードを決め直す。**現在値 (`kbd_get_modifiers()`) は使わない** —
  「カナ ON → 5 → カナ OFF」が溜まっていると最初から OFF を読んでしまう (Codex 2 回目 A2)。
  現在値を読むのは gshell の起動時の初期化だけ (カナをロックしたまま GUI に入った場合)。
- **オン → オフのとき**: 移動の数え (make 回数) を 0 に、押したままの合成ボタンがあれば**その場で離しのエッジを `edge_x3` に通す** (ドラッグは落とした位置で終わる)。
- マウスキーが消費したテンキーの make に対応する break は、モードが途中で切れても**マウスキー側で消費する** (scan ごとの「消費した」印)。
  逆にモードの外で押したテンキーの break はアプリへ。

### 1-6. FEP の未確定文字とフォーカス移動 — Codex 指摘 P2-4

**フォーカスが別の窓へ移る前に、未確定文字を元の窓へ確定する** (Win98 の IME も窓を切り替えると確定する)。
WM の共通経路 (`wm::set_focus` とその同類) に入れるので、**マウスで切り替えたときの既存の穴も同時に塞ぐ**。

- 確定のしかた: FEP の「今すぐ確定」を足す (カーネルの FEP に RETURN と同じ確定を流し、`flush_text` を**フォーカス移動の前に**呼ぶ)。
  候補の選択中なら今の候補で確定。未確定が無ければ何もしない。
- FEP のオン / オフは窓ごとに持たない (今と同じ、全体で 1 つ)。

## 2. カナの make / break の方式 (§3 の実機確認の結果で決める)

- 方式 A (2026-09-26 までのドライバ): make で反転、break を無視。
- 方式 B (機械式ロック = ロックで make、解除で break の場合): make でオン、break でオフ。
- **方式 B を採った (2026-09-26、wt/kbd-lockkeys、カナ・CAPS とも)**。根拠は §3-1 の NP21/W の観測 (カナ・CAPS とも
  1 回目 make・2 回目 break) と資料: BIOS ワークエリア 0000:053Ah (KB_SHFT_STS) の bit2 カナ / bit1 CAPS は SHIFT・CTRL と同じ
  「1= 押されている」で「INT 09h ハンドラがセット／リセットする」(`memsys.md`、Bible §2-5 の INT 18h AH=02h も「押下中」)
  = BIOS 自身が make で立てて break で落としている。シフト系キーはキーボード側でリピートしない (`memsys.md` 052A〜0539h)。
  NP21/W の `keystat.c` も「シフトメカニカル処理」として同じ送り方。実装は `drivers/kbd.c` の `kbd_lock_apply`:
  make の繰り返しでも ON のまま (冪等)、**V86 中も追う** (打鍵はゲストへ回すがロックの物理状態は OS32 側でも持つ)。
- **起動時の初期値**: IRQ1 を開く前の make は OS32 に届かないので、`kbd_init` が 053Ah のカナ・CAPS ビットを引き継ぐ
  (SHIFT / GRPH / CTRL は引き継がない)。起動行 `[kbd] ... lock=XX` (XX = 02 CAPS / 04 カナ)。電源投入時にロック済みの
  キーを BIOS が 053Ah に載せるかは資料に無い — §3 の表の 6 で確かめる。
- 新キーボード (0000:0481h bit 6/3) はロックをソフトから制御できる (0041h へ 9Dh で LED 設定・読み出し、`io_kb.md`)。
  OS32 はキーボードへコマンドを送っていない (0043h に BIOS の定常値 16h を書くだけ、POLICY_DEBUG §4-57) ので使わない。NP21/W では 9Dh の設定がロック状態を
  make / break 無しで書き換える — OS32 が送らない限り起きない。
- **実機は CHECKLIST_2026-09-26 の手順 10 で確かめる** (解除で break が来ること)。実機が方式 A の送り方 (押すたびに make だけ)
  だった場合は、方式 B では外せなくなる (make しか来ないので ON のまま) — そのときは戻す。
- gshell は **raw に焼き込まれた KANA ビット** (§1-5) だけを見るので、どちらでも gshell 側は変わらない。

## 3. 実機で確かめること (次の実機の回)

準備 (**実装済み 2026-09-26、wt/kbd-diaglog、KAPI v67、手元ビルドとホスト試験のみ — NP21/W・実機は未確認**。
使い方は [POLICY_DEBUG.md](../../POLICY_DEBUG.md) §4-57 の `kbdstat -w`、試験は `make check-kbd-dlog-host`
([記録](../../../tools/tests/kbd_dlog_tdd.md))): **受信のたびに記録する診断リング**をドライバに足す (`drivers/kbd.c` の IRQ1 で、受け取った 1 バイトごとに
`seq / code / make・break / 更新後の修飾` を 32 件の循環リングへ)。読むのは KAPI `kbd_diag_log` (追記、診断専用) と
`kbdstat -w` (リングを読んで新しい分を 1 行ずつ出す。ESC か 30 秒で終わる)。**seq が飛んだら「取りこぼし — この区間は判定不能」と出す**。
今の `kbdstat` では足りない: `last_code` は最後の 1 件だけ、`irq_count` は EMPTY / ERROR の判定より前に増えるので受信件数ではない、
`now` は 8251 のステータスであってカナの状態ではない (Codex 1 回目 P2-6、2 回目 A5)。
代わりに GUI 中なら raw リングを読む手もあるが、実機のシリアルからは CUI で見たいのでリングを足す。

### 3-1. NP21/W での観測 (2026-09-26、5992fd5、`kbdstat -w`)

`/api/key` で KANA・KANA・CAPS・a・ESC の順に送った:

```
seq=1 code=72 make  key=72 KANA mods=KANA
seq=2 code=F2 break key=72 KANA mods=KANA
seq=3 code=71 make  key=71 CAPS mods=CAPS|KANA
```

- **NP21/W のカナ・CAPS は機械式ロックの模擬**: 1 回目の押下で make (ロック)、2 回目で break (解除)。
- 今のドライバ (方式 A、make で反転・break を無視) では 2 回目の後も `mods=KANA` のまま = **ロックを外しても OS32 はカナ ON と思う**。
  NP21/W の上では**方式 B (make で ON、break で OFF) が要る**。実機が同じかは下の手順で確かめる (NP21/W の模擬が実機に倣っている可能性は高い)。
- `kbdstat -w` の出力は `/api/cmd` の EOT 待ちが先に切れて返らない (画面には出る)。NP21/W では本体の画面 (`/api/tvram`) で読む。

## 6. 実装の記録 (2026-09-26、wt/kbd-nav)

新しいモジュール `userland/gshell/src/kbdnav.rs` (ショートカット・切り替え・窓メニューの実行・キーボードの移動/サイズ・マウスキー)。
入口は `input.rs` の `capture_keyboard` の 2 か所 (`kbdnav::pre` = 修飾キーを捨てる前、`kbdnav::on_key` = SHIFT+SPACE の後・モーダルより前) と、X4 の退避判定 `kbdnav::is_wm_raw`。
マウスのエッジと移動は `input::edge_x3` / `input::move_x3` に切り出し、実マウスとマウスキーが同じ関数を通る。試験は `userland/gshell/host/kbdnav_tests.rs` (K1 ①〜⑧ + 窓メニュー等 + 代行レビューの探り、36 本)、変異は `host/integration.py` の `MUTATIONS` (32 本、`make check-gshell-host` が `--mutate` で毎回回す)。

§0 と今のコードの差: 行番号は 2026-09-25 時点でほぼ合っていた (input.rs のモーダル分岐は 377 がコメントの頭で本体は 383、全画面の判定は 470)。**最小化・最大化・元のサイズは WM に無かった** (票 §1-2 の窓メニューと GRPH+TAB の「最小化した窓」が前提にしていた) ので下のとおり足した。

票に書いていなかったことの決め (実装者判断。PM の確認待ち):

| 事柄 | 決め | 理由 |
|---|---|---|
| 最小化 | `Win.minimized` を足し、`visible` を落としてタスクバーにだけ残す (`GUI_WF_VISIBLE` = アプリの意図は触らない)。アプリの show / hide で解ける。タスクバーのボタンを押すと元に戻る | 新しい描画の仕組みを足さずに済む。露出と Paint は既存の `visible` の経路 |
| 最大化 / 元のサイズ | `Win.maximized` と `restore` (元の外形)。最大化 = 作業領域いっぱいへ `wm::set_outer` (旧 ∪ 新を損傷、全面再描画、Configure)。libos32gui は Configure で面を作り直して再レイアウトする | マウスのドラッグ確定と同じ手順 |
| 窓メニューの使える項目 | Restore = 最大化中、Move / Size / Maximize = `GUI_WF_MOVABLE` かつ最大化でない、Minimize = 常に、Close = `GUI_WF_HAS_CLOSE`。使えない項目は灰色 (`GUI_COLOR_SHADOW`) で描き、選んでも何もしない (メニューも閉じない)。**初期カーソルは最初の使える項目** (ふつうの窓では Move)。項目名は英語 (Start メニューと同じ) | Win98 と同じ灰色の扱い |
| Size の操作 | 左上を固定して矢印で右辺・下辺を動かす。下限は `resize_window` と同じ (min_w/min_h、60 × タイトル+8)、上限は作業領域 | Win98 は最初の矢印で動かす辺を選ぶが、v1 は 1 通りに絞った (**Win98 との差**) |
| 移動・サイズ中 | キーは make も break も全部 WM が取る (窓メニューの Move / Size を選んだ RETURN の離しも移動中に来るので漏れない。**Minimize / Close などほかの項目の RETURN の離しは Start メニューと同じく今までどおり前面の窓へ行く**)。マウスは枠を動かさず、エッジも無視 (前に配った押下の離しだけは相手へ返す)。窓が消えたら枠を消して終わる (`wm::drop_drag_frame`、マウスのドラッグも同じ) | 表の「移動・サイズ中」の列 |
| マウスで窓をドラッグ中 | WM のショートカットは「移動・サイズ中」と同じく無視 (消費) | 枠が残ったまま窓が入れ替わるのを避ける |
| GRPH+f･4 | 閉じるボタンの無い窓 (`GUI_WF_HAS_CLOSE` なし) には Close を送らない | 閉じるボタンと同じ規則 |
| SHIFT+f･10 (窓なし) | デスクトップのメニューはポインタの位置に出す (作業領域へ寄せる) | 右クリックと同じ |
| §1-6 の X1 の経路 | アプリの `set_focus` / `create_window` / `show_window` (X1) でフォーカスが移るときは、確定の宛先 (元の窓) だけ控え、**次の X3 の頭** (`capture_keyboard` の先頭と、アプリへ配る打鍵の直前) で確定して元の窓へ流す。**モーダル中は予約を残し**、閉じてから流す | 確定は辞書の学習 (SQLite) まで走るので X1 では呼べない (契約 T8)。WM 自身の経路 (マウス・タスクバー・キー) は X3 なのでその場で確定する |
| WM が消費したキーの break | scan ごとの印 (`consumed`) で、make を WM が取ったキーの break は WM が取る (マウスキーのテンキーに限らず、ショートカットの TAB・ESC・f･4・SPACE も)。新しい make で印は消える | §1-4 の「マウスキーが消費したテンキーの break」を一般化 |
| 押したまま (0) の左ボタンがある間の 5 / + | 押し直さない (何もしない) | 合成ボタンの状態を壊さない |
| 実マウスの位置 | `GuiState.real_x/real_y` に実マウスの前回値を持ち、実マウスが動いた周だけ `mouse_x/y` を実マウスの値にする | 止まっている実マウスの値で合成の位置を毎周巻き戻さない (§1-3「最後に動いた方が勝つ」) |
| 確定の回数 | RETURN を素通り (= 未確定が無い) になるまで流す (上限 16 回) | 候補の確定は最長一致で、残りのかなを未確定へ戻す (kernel/ime.c の commit_candidate) — 1 打では確定し切らない |
| 最小化した窓へのアプリの `set_focus` | 何もせず 0 を返す (Focus も出さない) | Win98 の SetFocus も復元しない。前へ出すと不可視の窓が Z の最前面に居るのに打鍵は可視の窓へ行き、Focus だけ食い違う |
| アプリの move / resize と最大化 | アプリが最大化中の窓を動かす・大きさを変えると `maximized` を落とす (Restore は使えなくなる) | 古い矩形へ戻さない |
| GRPH+TAB の途中でモーダルが開いた | GRPH↑ で切り替えず取り消す | ダイアログの裏で窓が入れ替わらない |
| X4 で配った make | WM の印 (`consumed`) を消す | break を取りこぼした後に印が残ると、X4 で配った make の break を X3 が握り潰す |
