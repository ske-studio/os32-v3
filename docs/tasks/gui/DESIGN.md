## 0. 前提の整理 (何が GUI の可否を決めるか)

**プロジェクトの意義と上限 (2026-09-04 ユーザ明言)**: このプロジェクトは過去の遺産である
PC-9801/9821 の実用性を証明するためのもの。目標は **Pentium 100MHz / 32MB で「超快適」に
動くこと**で、それ以上の性能を要する機能は PC-98 でやること自体がナンセンスと位置づける。
GUI の設計判断はすべてこの上限の内側で行い、下限は 386 で成立させる。

- 386 で GUI が成立するかは **CPU 世代ではなく、1 フレームに VRAM へ送る
  ダーティ面積 × 4 プレーン**で決まる。VRAM 書き込みはバスのウェイトで
  頭打ちになり、CPU が速くなっても縮まない。
- OS32 は主記憶のバックバッファに描いて `gfx_present_rect` で転送する方式なので、
  GRCG/EGC は転送量を減らせない (多色データはプレーンごとに別)。[HW1] の
  「CPU 直書き」はこの構造では唯一の選択肢であり、失っているのは VRAM 内
  スクロールと VRAM 直接の単色塗りだけ (どちらもバックバッファ側で済む)。
- **486 機能ティア (`cpu_features` / `-march=i486` / FPU 層) は見送り** (2026-09-04)。
  命令生成の差は数 % で、GUI の律速には効かない。
- `userland/lib/ui/` の microUI はテスト導入のみ。本採用ではない。

## 1. 再描画モデル (採用済み 4 点)

| # | 決定 | 理由 |
|---|------|------|
| R1 | **InvalidateRect 方式**。アプリは汚れた矩形を申告し、OS 側が矩形にクリップして再描画要求 (WM_PAINT 相当) を投げ、`gfx_present_rect` で送る。全画面 present はデスクトップ切替など例外にだけ許す | Win3.1 が GUI の骨格をこの形にしたのは 386 の VRAM 帯域のため |
| R2 | **ウィンドウ移動は XOR 枠だけ動かす**。ドロップ時に一度だけ再描画 | 実体を動かすと毎フレーム露出領域の再描画が発生し、386 で最も重い操作になる |
| R3 | **全画面 1 枚のバックバッファ + クリップ**。per-window バッファは持たない | シングルタスク前提なら不要。0x6A000 の 128KB をそのまま使う。文字は KCG からバックバッファへ、ターミナルは lconsole の差分セル方式 |
| R4 | **テキスト VRAM でクローム (メニューバー・ステータス行) を描くのは 9801 バックエンドの最適化に格下げ**。GUI 本体はクロームをグラフィックに描く前提 | ウィンドウアクセラレータは表示出力を 98 側から切り替えるのでテキスト面が出ない。PEGC 256 色でのテキスト面合成も未確認 (§5) |

## 2. バックエンド抽象 (採用済み 3 点)

| # | 決定 | 内容 |
|---|------|------|
| B1 | **バックエンド関数表 + 描画プリミティブ段階の HAL** (2026-09-04 改訂) | libos32gui は HAL の描画プリミティブ (塗り・矩形転送・文字・ビットマップ) と `present_rect` だけを呼ぶ。9801 / PEGC バックエンドはそれを主記憶のバックバッファ (9801 = 4 プレーン、PEGC = 8bpp) に描いて present し、Cirrus バックエンドは画面の実体をカードの VRAM に置いてエンジン (BitBLT / 塗り / 色展開) に流す。この違いは HAL の中に閉じ、GUI には見せない (Win3.1 の GDI とディスプレイドライバの分担と同じ)。present 時にチャンキー→プレーン変換する方式は 386 では重すぎるため不採用。改訂理由は §8 |
| B2 | **能力ビット** | テキスト面オーバーレイ可否 / HW 塗り / HW ブロック転送 / 画面サイズ (400・480・それ以上) / 色数を問い合わせ、GUI 側は決め打ちしない。HW 塗り・転送はアクセラレータ用の空きスロットとして先に定義しておく |
| B3 | **[HW1] の追記** | 「98 標準グラフィックでは CPU 直書き」は維持し、「アクセラレータ系バックエンドはチップの 2D エンジンを使ってよい」を `docs/CONSTRAINTS.md` に追記する。アクセラレータの VRAM は待ちの性質が違い、逆転現象の議論が当てはまらない |

色: GUI のシステム色は **16 色に固定**し、3 バックエンドで同じ見た目を保証する。
256 色はアイコン・画像にだけ使う。アイコン資産は必ず 16 色版を持つ。

## 3. 対象ハードウェア

| バックエンド | 画素形式 | VRAM | NP21/W で検証 |
|---|---|---|---|
| 9801 標準 (16 色, 640x400) | 4 プレーン | 0xA8000〜 (現行) | 可 (現行) |
| 9821 PEGC (256 色, 640x480) | 8bpp パックド。1 ラインは 640 バイトで 16 色プレーンの約 2 倍 | 512KB。0xF00000 リニア窓 (E0102h=1 で出現) または A8000h/B0000h の 32KB バンク窓 ×2 | 可 (`SUPPORT_PEGC`) |
| ウィンドウアクセラレータ (Cirrus GD54xx) | 8bpp 以上、チップの BitBLT | 独自 VRAM 1〜4MB。VRAM 窓 / MMIO 窓は 0xF00000〜0xF9FFFF に開く | **可** (§4)。他チップ (S3 / MGA / Trident) は不可 |

### 3.1 PEGC の資料上の仕様 (PC-9801 Bible §3-2、`C:\WATCOM\docs\PC9800Bible\3-2_グラフィック256色表示.md`)

- モード切替は 6Ah のモード F/F2: `07h` (拡張モード変更可) → `21h` (拡張グラフィックモード) /
  `20h` (標準へ戻す)。現在値は 09A0h に `0Ah` を書いてから読む (bit0 = 1 で拡張モード)。
- 同期周波数: 09A8h に `1` で 31KHz (640x480)、`0` で 24KHz。
- VRAM 形式: メモリマップト I/O E0100h に `00h` = パックドピクセル、`01h` = プレーン。
  E0004h / E0006h に 32KB 単位のバンク番号 (0〜0Fh) を書くと A8000h / B0000h の窓に現れる。
  E0102h に `0001h` で VRAM 全体 (512KB) が F00000h に出現する。
- アドレス計算: `ADR = y * 640 + x`。
- パレット: A8h に番号 (0〜255)、AAh / ACh / AEh に G / R / B を 0〜255 で書く
  (16 色時と同じポート、輝度が 8bit に拡張)。読み戻しも可。
- 拡張 BIOS INT 18h: AH=30h (画面モード設定: 640x480 + テキスト 30 行)、AH=31h (取得)、
  AH=4Dh (標準/拡張モード切替)。OS32 は BIOS を使わないので I/O 直接で行う。
- **16MB システム空間**: 16MB 以上積める機種では F00000h〜FFFFFFh をシステム用 (PEGC VRAM /
  アクセラレータ窓) か通常 RAM かを 043Bh bit2 で選ぶ (`0` = システム使用)。RAM にすると
  PEGC VRAM は F00000h では見えなくなるが FFF00000h〜FFF7FFFFh で使える (UNDOCUMENTED
  `io_mem.md`)。**OS32 の物理メモリ上限計算は F00000h〜FFFFFFh を RAM に含めない**。
- テキスト面: 拡張 BIOS が 640x480 拡張モードでテキスト 30 行を設定できることから、
  資料上は 256 色モードでもテキスト面は合成される (明文の記述は無い。§5)。

### 3.2 ウィンドウアクセラレータの資料上の仕様 (UNDOCUMENTED 9801/9821 Vol.2、`C:\WATCOM\docs\undocumented\io_wab.md`)

- 搭載チップは機種で異なる: S3 86C928 (Ap2/As2/An 内蔵、A-E01)、S3 Vision864 (Xs/Xp/Xn/Ap3/As3)、
  CL-GD5428 (Bp/Bs/Be/Bf/Ts/Np/Ns/Ne2/Nd/Es、PC-9801-96)、**CL-GD5430 (Xe/Cf/Cx/Cb/Cx2/Cb2/Xe10、
  PC-9801BX4)**、CL-GD5440 (Xa7e/Cx3/Cb3/V10/V7/Xb10)、MGA-II / MGA-2064W (X-B01/B03)、
  TGUI9680XGi (Xa16/Xa13/Xa12/Xa10/Xa9/Xa7/Xv13)、Cyber9320 (Ne3/Nd2/Na7/Nx/Lt2)。
- 制御は 2 段階 I/O: ボード型は **0FA2h (INDEX) / 0FA3h (DATA)**、内蔵型は **0FAAh / 0FABh**。
  レジスタ `00h` = ID 読み出し (内蔵: Xe=58h, Cb=59h, Cf=5Ah, **Xe10=5Bh**, Cb2=5Ch, Cx2=5Dh,
  Be 系=50h; ボード: PC-9801-96=60h など)、`01h`/`02h` = VRAM 窓 / MMIO 窓アドレス
  (80h=F20000h, A0h=F00000h, C0h=F40000h, E0h=F60000h; MMIO は F80000h〜F98000h)、
  **`03h` bit1 = 映像出力リレー (1 = アクセラレータ出力, 0 = 本体スルー)**、bit0 = MMIO 有効。
- PCI 機は **0FACh** bit1 (1 = 内蔵アクセラレータ, 0 = 98 グラフィック)、bit0 (RGB IN スルー)。
- 内蔵 GD5428/5430 の VGA レジスタは 0904h、0CA0h〜0CAFh、0DA4h/0DA5h/0DAAh、FF82h に
  写像される (PC-9801-96 は 0C50h〜0C5Fh、0D54h/0D55h/0D5Ah、0902h)。
- NP21/W の ID 定数 (`CIRRUS_98ID_*`) はこの資料の ID 値と一致する。
- **40E1h / 42E1h / 46E8h / 51E1h / 5BE1h は Xe10 のポートではない** (2026-09-04 に訂正)。
  これらはメルコ WAB-S / WSN-A2F / WSN と I-O DATA GA-98NB という **C バス製ボード**の
  ポートで、NP21/W は機種 ID が 0x100 以上 (サードパーティ) か AUTO のときだけ登録する。
  C バス流の 16bit I/O デコードで、下位バイト E0h/E1h (+ジャンパオフセット) がボード選択、
  上位バイトが VGA レジスタ番号 (40E0h+n·100h → 3C0h+n、58E0h/59E0h → 3B4h/3B5h、
  54E0h/55E0h → 3D4h/3D5h、5AE0h → 3DAh)。奇数側 (xxE1h) がボード制御
  (40E1h bit0 = リレー、51E1h = ドライバのチェック値、5BE1h = VRAM 容量フラグ) で、
  値は「この値でないと Win95 ドライバがボードを認識しない」と試行で決めたもの
  (`cirrus_vga.c` のコメント)。
  Xe10 モードでは NP21/W も資料どおり 0FAAh/0FABh と 0904h / 0CA0h〜 / 0DA4h 系を
  使うので、**OS32 のドライバは資料のポートだけ実装すればよい**。
- NP21/W の `GD5430TYPE` の AUTO 値 (FFF7h〜FFFFh) は「Xe10 として起動し、サードパーティ
  ボードのドライバが探査ポートに触れた瞬間にそのボードへ化ける」実用機能
  (`cirrusvga_setAutoWABID`)。OS32 の検証では AUTO ではなく **明示的に 5Bh (Xe10)** を
  指定し、化けないようにする。

## 4. NP21/W のウィンドウアクセラレータ再現範囲 (ソース確認 2026-09-04)

`~/np21w-src/src/wab/` に実装がある。ai-debug fork の x64 Release
(`np21vs2019.vcxproj`) は `SUPPORT_WAB` + `SUPPORT_CL_GD5430` + `SUPPORT_PEGC`
+ `SUPPORT_PCI` を定義してビルドしている。

- **Cirrus GD54xx** (`cirrus_vga.c`, QEMU 由来): 対応 ID は PC-9801-96 / Be / Xe /
  Cb / Cf / **Xe10 (既定)** / Cb2 / Cx2 のオンボード、PCI GD5446、メルコ WAB-S /
  WSN-A2F / WSN、I-O DATA GA-98NB I/C・II・IV。
- **Trident TGUI9680** (`tgui9680.c`) と **I-O DATA GA-1280A** (`ga1280a.cpp`)、
  仮想アダプタ **NPDISP** (`npdisp.cpp`) もソースにあるが、x64 Release の定義には
  **入っていない** (`SUPPORT_TRIDENT_TGUI` / `SUPPORT_WAB_GA1280A` /
  `SUPPORT_WAB_NPDISP` 未定義)。
- ini キー (`src/win9x/ini.cpp`): `USEGD5430` (有効化) / `GD5430TYPE` (機種 ID) /
  `WAB_ANSW` (リレー初期値) / `GD5430FCUR` / `GDMELOFS`。**現在のユーザ ini には
  どれも無い = 無効**。有効化は [D2] の承認事項。
- 98 側 I/O (Xe10 モード): 0xFA2 / 0xFA3 / 0xFAA / 0xFAB と、VGA レジスタの写像
  (0x0904, 0x0CA0〜0x0CAF, 0x0BA4/0x0BA5/0x0BAA, 0x0DA4/0x0DA5/0x0DAA, 0xFF82)。
  資料 (§3.2) と一致する。0x40E1 系は C バス製ボード専用 (§3.2)。
- **PCI 型の MMIO は 0xF00000 で PEGC のリニア窓と同じ場所** (`i286c/cpumem.c`):
  256 色モードのときは PEGC が優先される。OS32 の物理メモリ上限計算は
  0xF00000〜0xFFFFFF を RAM として扱ってはならない (16MB 以上積んだ 9821 の
  システム空間)。
- **ai-debug の `/api/screenshot` は 98 側 VRAM からしか描かない**
  (`src/vram/scrnsave.c` は WAB を参照しない)。アクセラレータ出力は
  `np2wabwnd.hBmpBuf` (GDI バッファ) にあるので、WAB 検証を始める前に
  screenshot API をそちらも拾えるよう拡張する必要がある。

## 6. HAL とドライバの層構造 (承認済み 2026-09-04)

**GUI (libos32gui) はデバイスを意識しない。** 触ってよいのは HAL (§2 のバックエンド表)
だけで、ポート・VRAM アドレス・機種名を GUI 側に書かない。画面サイズ・色数・画素形式は
起動時に HAL から受け取り、それ以外の前提を持たない。

HAL の下は 2 層に分ける:

```
libos32gui ──► HAL (バックエンド表 + 能力ビット)
                 ├─ 9801 プレーン      (CPU 直書き、現行 gfx_vram.c)
                 ├─ PEGC 8bpp          (CPU 直書き、E0000h MMIO + F00000h 窓)
                 └─ Cirrus GD54xx      = チップドライバ (3C0h 系の論理番号だけで書く)
                                        + ボードグルー (Xe10 内蔵 / PC-9801-96 / メルコ / ...)
```

- **チップドライバ**はレジスタ体系・BitBLT・リニア FB を扱い、PC-98 のポート番号を
  一切含まない。VGA レジスタは 3C0h 系の論理番号で `glue->out(reg, val)` に渡す。
- **ボードグルー**は「ポート翻訳表 + 制御レジスタ (ID / リレー / VRAM 窓 / MMIO 有効)」だけを
  持つ小さな 1 枚 (100 行前後)。NP21/W の `vga_convert_ioport()` と同じ役割。
- 当面のグルーは **Xe10 内蔵 (ID 5Bh) の 1 枚だけ**。他ボード・他チップ (S3 / MGA /
  Trident)・PCI 型は必要になった人が書く。今は不要と決定 (2026-09-04)。

## 7. ドライバの書き方の指針

新しいバックエンド / グルーを書く人が守ること。守れば GUI 側は無変更で動く。

1. **HAL の契約を満たす**: probe / init / shutdown、能力ビットの申告、描画プリミティブ
   (塗り・矩形転送・文字・ビットマップ)、`present_rect`、パレット設定、`enter` / `leave`
   (表示出力の切替。フルスクリーン GFX プログラムの前後で呼ばれる)、カウンタ (§8)。
   ソフトウェアバックエンドはプリミティブを共通の CPU 実装 (バックバッファ記述子 =
   先頭・ピッチ・画素形式を渡す) に委ね、present だけ自前で書けばよい。アクセラレータ系は
   プリミティブをエンジンで実装し、未対応のものは NULL にして CPU 版へフォールバックする。
2. **能力ビットは正直に**: 画面サイズ・色数・テキスト面の可否は実際に使える値だけを立てる。
   GUI はこれを信じて決め打ちを一切しない。
3. **層を越えない**: チップドライバにポート番号を書かない。グルーにチップの知識を書かない。
   GUI からドライバのヘッダを include しない。
4. **定数は [C4] の三層方式**: ポート・ID・窓アドレスはボードごとのヘッダに集め、
   資料 (`C:\WATCOM\docs\undocumented\io_wab.md` 等) の出典をコメントで示す。
5. **CPU 直書きの原則 ([HW1]) は 98 標準グラフィックにだけ適用**: アクセラレータ系は
   チップの 2D エンジンを使ってよい (B3)。
6. **検証は同じテストで**: HAL 越しに同じ描画列を流し、screenshot (NP21/W) または実機の
   目視で全バックエンドが同じ絵になることを確認する。NP21/W で検証するときは
   `GD5430TYPE` を AUTO ではなく機種 ID に固定する (§3.2)。ai-debug の screenshot は
   アクセラレータ出力を拾わないので、Cirrus 検証の前に拡張が要る (§4)。
7. **[V1]〜[V4] は通常どおり**: HostDrv 配備だけを検証と呼ばない、配備 yaml に載せる、
   失敗はそのまま報告する。

## 8. ボトルネックの所在 (採用 2026-09-04)

CPU との兼ね合いで、どこが律速になるかの整理。設計判断 (B1 改訂・§7-1 の
プリミティブ契約・カウンタ) の根拠。

共通の土台:

- **VRAM アクセス時間は CPU クロックに比例しない。** 表示コントローラが表示走査で VRAM を
  読み続けており、CPU アクセスは調停ウェイトを挟む。486DX2 でも 386 でも 1 アクセスの
  時間は大差ない。
- **データ幅は 16bit。** 32bit アクセスはバス側で 16bit ×2 に割られ、`rep movsd` にしても
  書き込み回数は減らない。9821 でも 98 標準グラフィックの VRAM 経路が 32bit 化された
  記述は資料に無く、16bit として扱う。
- **I/O ポートはさらに遅い。** OUT/IN 1 本が VRAM 書き込み数回分。レジスタを何本も叩く
  操作は小さい仕事ほど損 ([HW1] の根拠)。
- **VRAM の読み出しは書き込みより遅い** (値が返るまで CPU が止まる)。VRAM を読まない
  設計を維持する。

| 観点 | 9801 プレーン | PEGC 256 色 | Cirrus 内蔵 (Xe10 等) | Cirrus C バス製ボード |
|---|---|---|---|---|
| present 1 ピクセルあたりの VRAM 書き込み | 0.5 バイト | **1 バイト** | 1 バイト (CPU 転送時) | 1 バイト |
| CPU と VRAM の間のバス | 16bit + 調停ウェイト | 16bit + 調停ウェイト | ML バス 32bit (io_wab.md の ID レジスタ bit5,4 = 01b) | C バス 16bit、8〜10MHz 級 |
| ハードウェア描画 | なし | なし | BitBLT / 塗り / 色展開 | 同左。レジスタ設定が OUT 経由で遅い |
| 支配的なコスト | VRAM 書き込み回数 | 書き込み回数が 9801 の 2 倍 | 小さな操作のエンジン設定と同期待ち | CPU→VRAM 一括転送そのもの |

PEGC:

- 1 ピクセル 1 バイトなので、同じダーティ面積で VRAM 書き込みが 9801 の 2 倍
  (全画面 640x480 で 307KB)。R1〜R3 はそのまま通用するが、**ダーティ面積の予算は半分**。
- 32KB バンク窓 (A8000h) を使うと 51 ライン毎にバンク切替の MMIO 書き込みが要り、矩形が
  バンク境界で割れる。**F00000h のリニア窓を使う** (ページングで張る)。
- パレット 256 色の初期化は OUT 1024 本。起動時 1 回に限り、毎フレームは不可。
- CPU 側は楽になる: 8bpp はビット操作が無く、バックバッファ合成と文字描画はプレーンより軽い。

Cirrus:

- アクセラレータの価値は「CPU がピクセルを運ばない」こと。主記憶のバックバッファで合成して
  present する方式だとエンジンが遊び、C バス製ボードでは CPU→VRAM 転送が PEGC 並みかそれ
  以下になる。**画面の実体をカードの VRAM に置き、塗り・矩形移動・文字の色展開をエンジンで
  行う** (B1 改訂の理由)。
- **小さい操作は設定コストが本体を上回る**: BitBLT 1 回にレジスタ書き込み 10 本前後。十数
  ピクセル角以下は CPU 直書きの方が速い。GD5430 の BLT レジスタは MMIO 化できるので、
  OUT ではなくメモリ書き込みで設定する。**逸脱 (2026-09-06、H3 実装)**: Xe10 内蔵モードには
  MMIO 窓が無い (NP21/W `wab/cirrus_vga.c` の Xe10 経路は 0FAAh/0FABh + VGA レジスタ写像のみ)
  ため、現行の `drivers/wab_cirrus.c` は BLT レジスタを **I/O (GR 拡張レジスタ) 経由**で設定する。
  MMIO 化は MMIO 窓を持つボード (PCI 型 / C バス製) のグルーを足すときの課題。CPU 直書きの
  閾値は `backend_cirrus.c` の `CIRRUS_CPU_DIRECT_PIXELS` (256 画素)。
- **エンジンは非同期**: 次の描画や CPU の VRAM アクセスの前にビジービットを IN で待つ。
  細かい操作の連発は同期待ちが支配的になるので、操作を矩形単位にまとめて投げる。
- 表示リレーの切替はミリ秒単位 (メカニカルリレーまたはアナログスイッチ) + モニタ再同期。
  `enter` / `leave` のときだけ行う。

計測方針:

- **NP21/W はこれらのウェイトを再現しない**ので、性能はエミュレータで測れない。
- HAL に **カウンタ** (present したバイト数 / 発行したエンジン操作数 / I/O アクセス数) を
  持たせ、エミュレータでは回数を測り、実機で一度測ったコスト定数を掛けて見積もる。
  回数は機種に依らず正確に取れる。

## 9. GUI API の前提 (2026-09-04)

### 9.1 既にあるもの

- `userland/rust/libos32gui/` (Rust, no_std, staticlib、約 1.4K 行、コーダー2 タスク
  `docs/archive/kernel_v2/TASK_coder2_libos32gui.md`): ウィンドウ管理 (固定配列、Z 順、フォーカス)、
  枠描画、ボタン / ラベル / チェックボックス / テキストボックス / リストボックス、
  `gui_pump` / `gui_poll_event` によるイベント配送。描画は libos32gfx を FFI で呼ぶ。
  デモは `gui_demo`。**すべてがアプリ 1 本の中で動く構成**で、gshell とアプリの分離は無い。
- v2 M0 (get_tick スピン根絶) は 2026-09-01 に実施済み。`sys_halt` KAPI あり。
  入力は `kbd_trygetkey` / `kbd_get_modifiers` / `mouse_poll` のポーリング。
- 無いもの: タイマ (WM_TIMER 相当。`get_tick` だけ)、イベント待ち (`gui_pump` は
  ポーリングで、ループ側で `sys_halt` を挟む作法がまだ無い)、アプリと gshell の境界。

### 9.2 決定 (承認 2026-09-04)

- **ウィンドウマネージャ (Z 順・フォーカス・ウィンドウ一覧・入力の配送) は常駐の gshell に
  置く。** アプリ (0x400000, CPL=3) からは KAPI に 1 本だけ足す入口 `gui_call(op, args)`
  経由で呼び、要求と応答は SHM で渡す。既存 libos32gui のウィンドウ管理部はこの WM の核に
  転用する。
- メッセージに**ポインタを載せない** (PD 切替で別アドレス空間になるため)。文字列などは
  SHM 経由で値渡し。API を切る時点でこの制約を型に埋め込む。

### 9.3 共有ライブラリ (採用 2026-09-04)

- GDI 相当 + ウィジェット + クライアントスタブは描画が重く、`gui_call` 越しに
  1 プリミティブずつ呼ぶのは遅すぎる。アプリのリング 3 文脈で直接呼べる
  **固定アドレス常駐・先頭ジャンプ表・位置依存の共有ライブラリ帯域**を設ける
  (KAPI 表の user 版。再配置不要、ローダ変更は帯域のマップだけ)。バージョン番号を表の
  先頭に置き、スタブが初期化時に照合する (KAPI_VERSION と同じ作法)。
- ライブラリ自身の .data/.bss は「同じ仮想アドレスにアプリごとの物理ページ」で持たせる
  (アプリごとの PT を既に持つので現行機構で可能)。
- **配置はユーザ帯域 (0x400000〜0x7FFFFF, 4MB) の内側で完結させる** (ユーザ決定)。
  当初案 (ライブラリを 0x500000 に挟む) はアプリ本体を 1MB で頭打ちにするため取り下げ、
  **案 A: ライブラリを帯域先頭に置く** を採用 (2026-09-04。再ビルドのコストは現時点では
  無視できるとのユーザ判断):

  | 範囲 | 用途 |
  |---|---|
  | 0x400000〜0x4FFFFF | **共有ライブラリ帯域** (read-only + USER、全 PD 共有) + アプリごとの data ページ |
  | 0x500000〜 | アプリ本体 (code + bss) → newlib sbrk → ガード → KAPI exec_heap (上方向に成長、約 2.75MB) |
  | 0x7BF000〜0x7FFFFF | ガード + ユーザスタック 256KB (変更なし) |

  ロードアドレスの移動 (`sdk/link/app.ld` と `MEM_EXEC_LOAD_ADDR`) は共有ライブラリ帯域を
  実際に置く段階で行い、os32 / os32-apps / os32-game の全 OS32X バイナリを一斉に
  再ビルドして NHD を入れ替える (stale バイナリの罠に注意)。
- **本体の固定 1MB 上限は撤廃済み (2026-09-04, `exec/exec.c`)**: 子プロセス帯は
  [本体][sbrk (最低 256KB)][ガード][exec_heap]〜スタックガード直下、の順に動的に決める。
  exec_heap の大きさは OS32X ヘッダの heap_size 指定があればそれ、0 なら空きを折半。
  併せて、CPL=3 の sbrk 上限が RING3_HEAP_TOP になっていて sbrk が exec_heap に
  伸び得た重なりも解消 (上限 = ガード直下)。実機検証 (`userland/tests/heap_test`):
  guard_a=0x600000、malloc 1984KB + mem_alloc 1728KB、重なりなし、既存テスト
  (alloc_demo / klibc_test 49/49 / ring3_guard kill / パイプ) 回帰なし、kselftest 42/0。
- 既知の制約 (別件): CPL=3 のスタックは物理 0x7C0000〜0x7FFFFF に固定なので、
  **物理メモリは 9.6MB 構成以上が実質の下限** (7.6MB 構成では帯域上端が実装されず、
  8MB ちょうどでもホットデプロイ窓と重なる)。

### 9.4 API の様式 (採用 2026-09-04)

Win16 を再現するのではなく、その欠点 (協調型で机が止まる / ハンドルのリークとダングリング /
DC の状態機械 / 型なしメッセージとポインタ越境 / SendMessage の再入 / 入れ子ループ /
巨大 switch / 固定座標 / 描き過ぎ) を、386 で払える範囲の現代の様式で解消する:

| 採用 | 解く欠点 | 386 でのコスト |
|---|---|---|
| **Wayland 型の協定** (非同期・ID 参照・損傷 + commit・入力 serial・バージョン付き) | 再入、ポインタ越境、ちらつき | `gui_call` の往復 (6µs 級)。イベントは 1 回で一括取り出し |
| **保持型ウィジェット木 + 世代付きハンドル + 明示的無効化** (Qt/GTK 系) | ダングリング、描き過ぎ、巨大 switch | 固定配列で O(変更分) |
| **ステートレス描画** (呼び出しごとに Style を渡す) | SelectObject の順序問題 | なし |
| **モーダルは状態機械** (WM が入力宛先を限定、完了はイベント) | 入れ子ループと再入 | なし |
| **箱レイアウト** (行・列、固定/伸縮) | 固定座標 | 整数演算のみ |
| **型付きイベント** (enum + ペイロード、16B 固定) | WPARAM/LPARAM の解釈間違い | なし |
| **クライアントが共有バックバッファへ直接描く** | プリミティブごとの syscall | クリップは共有ライブラリの善意 (v1)。API は「サーフェス」抽象で切り、後でウィンドウごとの SHM サーフェス + WM 合成に差し替え可能にする |
| **syscall 境界で WM の入力ポンプ** + ISR の強制脱出キー | 1 アプリが机を止める | プリエンプション無しの範囲で最善。純粋な計算ループには効かない |

捨てるもの: 宣言的差分再構築 (React/SwiftUI 系) と即時モード (ImGui/microUI) の全面採用、
入れ子メッセージループ、同期の越境メッセージ。

凍結インターフェース: [API_CONTRACTS.md](API_CONTRACTS.md) (G 描画 → T 経路 → U 窓)。2026-09-04 凍結。
