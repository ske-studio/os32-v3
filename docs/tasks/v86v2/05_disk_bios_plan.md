## 1. どこまで出来ていて、何が足りないか

`INT n` を `#GP` で受けて `AH` / `CF` を書き換えてゲストに返す**器はできている**
（実機で `INT 1Bh` の往復を確認済み）。足りないのは中身だけ。

```c
/* kernel/v86_bios.c — 現状はここが空っぽ */
static void bios_int1b(u32 *frame)
{
    bios_set_ah(frame, 0x00);
    bios_set_cf(frame, 0);      /* 何もせず「成功」と嘘をついている */
}
```

やることは **PC-98 の INT 1Bh の引数を解釈して `loop_dev` を呼ぶ**、それだけ。

## 2. PC-98 の INT 1Bh レジスタ規約

**前回プロジェクトが取り違えて詰まった箇所**なので、ここは慎重に。
（`archive/feat-vdm` の `freedos98_boot_debug_report.md` に
「誤: `DH`=シリンダ, `CH`=ヘッド / 正: `CL`=シリンダ, `CH`=セクタ長, `DH`=ヘッド, `DL`=セクタ」
という記録が残っている）

| レジスタ | 内容 |
|---|---|
| `AH` | コマンド。bit7 が立っていると「リトライあり」等の修飾 |
| `AL` | DA/UA (装置番号)。`0x90` = 2HD FDD#1、`0x30` = 2DD、`0xA0` = SASI HDD |
| **`CL`** | **シリンダ** |
| **`CH`** | **セクタ長コード** (0=128, 1=256, 2=512, 3=1024 バイト) |
| **`DH`** | **ヘッド** |
| **`DL`** | **セクタ** (1 起算) |
| `BX` | 転送バイト数 |
| `ES:BP` | 転送バッファ |

戻り値: `CF=0` で成功、`CF=1` で失敗。`AH` にステータス。

### 実測で確認済みの呼ばれ方

Ys の IPL が実際に発行していたもの（[03_ys_profile.md](03_ys_profile.md) §3 の
シリアルトレースより）:

```
AH=D6 AL=90 CL=00 CH=03 DH=00 DL=06 BX=0400 ES=0000 BP=0600
AH=D6 AL=90 CL=00 CH=03 DH=01 DL=04 BX=1400 ES=1994 BP=0060
AH=D6 AL=90 CL=01 CH=03 DH=00 DL=01 BX=2000 ES=1994 BP=0000
```

`AH=0xD6` = READ DATA (0x06) + リトライ等の修飾ビット。
`CH=03` なので 1024 バイト/セクタ。**下位ニブルだけ見てコマンドを判定すること。**

### 最低限実装するコマンド

| AH & 0x0F | 機能 | 優先度 |
|---|---|---|
| `0x06` | READ DATA | **必須** (これが無いと何も始まらない) |
| `0x04` | SENSE (装置状態) | **必須** (DOS/ゲームが起動時に叩く) |
| `0x00` | SEEK | **必須** (物理トラック位置を決める。→ §3.5.2) |
| `0x03` | INITIALIZE | 中 |
| `0x05` | WRITE DATA | 中 (セーブに要る) |
| `0x07` | RECALIBRATE | 低 |

## 3. loop_dev への繋ぎ方

既存 API がそのまま使える。**新しいディスクコードを書く必要は無い。**

```c
int  loop_dev_attach(const char *vfs_path, int slot);
int  loop_dev_read_chs (int slot, u16 cyl, u8 head, u8 sect, void *buf);
int  loop_dev_write_chs(int slot, u16 cyl, u8 head, u8 sect, const void *buf);
int  loop_dev_get_geometry(int slot, u16 *cyls, u8 *heads, u8 *spt, ...);
u8   loop_dev_get_sec_n(int slot);      /* セクタ長コード */
int  loop_dev_get_media(int slot);      /* 2HD/2DD/2D */
void loop_dev_detach(int slot);
```

- `sect` は **1 起算** (FDC/ATA 準拠) で、INT 1Bh の `DL` と同じ。変換不要
- D88 のトラックテーブル走査は `loop_dev` が内部でやる
- **物理トラックと論理 ID がずれたディスクも読める** — `loop_dev_seek_d88()` は
  トラック選択とセクタ ID 照合を分けて受け取るように作られている。
  `Ys.D88` はまさにこれが要る (→ §3.5)。
  ただし **`loop_dev_read_chs()` のほうは使えない** (→ §3.5.4)

### 転送先

`ES:BP` はゲストのセグメント:オフセット。バッキング RAM にリマップ済みなので、
カーネルからは `(ES << 4) + BP` をそのまま触れる（`v86_ptr()` と同じ考え方）。

**1 回の呼び出しで `BX` バイト分＝複数セクタを転送する**点に注意。
セクタ長は `CH` から得て、`DL` を増やしながら回す。
トラック境界を跨いだら `DH` → `CL` の順に繰り上げる。

## 3.5 【解決済】物理位置と論理 ID の分離

段取り 5 は完了した。ここに至る過程で分かったことを残す。**推測で書いていた
「コピープロテクト」という理解自体が間違っていた。**

### 3.5.1 プロテクトではなく、ディスク全体の ID がずれている

`Ys.D88` のトラックテーブルとセクタヘッダを実際にダンプした結果:

| 物理トラック | 中身 | セクタ ID |
|---|---|---|
| trk0 (C0,H0) | 256B × 16 | C=0, H=0, R=1..16 |
| trk1 (C0,H1) | 1024B × 5 | C=0, H=0, R=1..5 |
| trk2 (C1,H0) | 1024B × 5 | C=0, H=1, R=1..5 |
| trk3 (C1,H1) | 1024B × 5 | C=0, H=1, R=1..5 |
| trk4 (C2,H0) | 1024B × 5 | C=1, H=0, R=1..5 |
| … | | |

**特定セクタだけを細工したコピープロテクトではない。ディスク 155 トラック
全部で ID が物理位置とずれている。** 論理 C は物理トラック番号のおよそ 1/4、
論理 H は物理トラック番号の bit1。同じ ID を持つ物理トラックが 2 本ずつあり、
中身は互いに異なる。

したがって「CL を物理シリンダとみなす」実装ではトラック 0 以外を一切読めない。
実測で 1647 回失敗していたのはコピープロテクトではなくこれだった。

### 3.5.2 物理位置は SEEK の CL と **DH の両方**で決まる

`INT 1Bh` の呼び出しをリングバッファに記録して並べたら一発で分かった。

| # | 呼び出し | 選ぶべき物理トラック |
|---|---|---|
| SEEK C=0 H=0 → READ ID(0,0,1) N=1 ×16 | | trk0 (16×256) |
| SEEK C=1 H=0 → READ ID(0,1,1) N=3 ×2 | | trk2 |
| **SEEK C=0 H=1** → READ ID(0,0,3) N=3 ×3 | | **trk1** |
| SEEK C=2 H=1 → READ ID(1,0,1) N=3 ×5 | | trk5 |

**READ の DH を物理ヘッドとして使うと 3 番目が trk0 になる。**
trk0 に N=3 のセクタは無いので必ず失敗し、`0x1700` へのロードが空振りして
ゲストが未初期化領域へ飛び `#UD` になる。実際にこれを踏んだ。

→ **SEEK は CL と DH の両方を記憶する。READ の C/H/R/N は ID 照合にだけ使う。**

### 3.5.3 セクタ長 (N) も必ず照合する

最初の実装は N を見ずに ID の C/H/R だけで探していた。その結果:

```
READ ID(0,0,3) N=3 count=3072    ← ゲストは 1024B × 3 を要求
  → trk0 の 256B セクタ 3 個 (768 バイト) を返して「成功」と回答
  → ロード先 3072 バイトのうち 2304 バイトが未初期化のまま
  → ゲストがそこへ飛んで #UD
```

**見つからないなら見つからないと答えるほうがゲストは正しく振る舞える。**
NP21/W も `searchsector_d88()` で `c/h/r` に加えて `n` を比較している
(`src/diskimage/fd/fdd_d88.c`)。

### 3.5.4 `loop_dev_read_chs()` は D88 では使えない

2 つの理由で使えない。

1. 物理 = 論理を仮定している (`seek_d88(cyl, head, cyl, head, sect)` を呼ぶ)
2. 読み出し長を **イメージ全体の `bps`** で頭打ちにする。`bps` はトラック 0 の
   セクタ長から決まるので `Ys.D88` では 256。**1024 バイトのセクタが
   256 バイトしか転送されない。**

`loop_dev_seek_d88()` + `loop_dev_get_fd()` + `vfs_seek`/`vfs_read_fd` で
自前に読む。`spt` もトラックごとに違うので、`loop_dev_get_geometry()` の値
(= トラック 0 の 16) ではなく `loop_dev_seek_d88()` が返す値を使う。

### 3.5.5 DH を 1 ビットにマスクしてはいけない

実測で `DH=3` の SEEK が飛んでくることがある。FDC の HD は 1 ビットなので
マスクしたくなるが、**やると別トラックが「それらしく」読めてしまう**
(同じ ID の物理トラックが 2 本あるため)。ID は合っているので成功として返り、
中身だけが違う — いちばん質の悪い壊れ方になる。

マスクしなければ範囲外トラックとして読みが失敗し、**ゲストは自分で `DH=0` に
直して読み直す**。その結果が正しい。実際に両方試して確認した。

### 3.5.7 【最終】物理ヘッドは `DH XOR (AL>>2)` — 正本は NP21/W の bios1b.c

§3.5.2 と §3.5.6 はどちらも外れていた。正解は NP21/W の
**BIOS エミュレーション**のソースにそのまま書いてある。

```c
/* src/bios/bios1b.c:335 */
hd = ((CPU_DH) ^ (CPU_AL >> 2)) & 1;
```

```c
/* src/bios/bios1b.c:68 — セクタ ID 照合に使う H は DH そのまま */
fdc.H = CPU_DH;
```

```c
/* src/bios/bios1b.c:375 — AH bit4 が立っていれば READ 自身がシークする */
if (CPU_AH & 0x10) { biosfd_seek(CPU_CL, ndensity); }
```

つまり **トラック選択のヘッドと、セクタ ID 照合の H は別物**。
前者は `DH` と DA/UA bit2 の XOR、後者は `DH` そのまま。

「AL bit2 だけ」でも 2 本のトラックは別々に読めてしまうので、
**失敗が出ず、同じシリンダの 2 本が逆順にロードされるだけ**になる。
これがいちばん質が悪く、ロードは全部成功しているのに
ゲストが `#UD` を起こす、という形で 1 段遅れて表面化した。

修正後の実測 (30 秒フルセッション):

| | AL bit2 のみ | `DH ^ (AL>>2)` |
|---|---|---|
| READ 成功 | ロードは通るが中身が入れ替わる | **18 回すべて成功** |
| 失敗 | 0 | **0** |
| 到達点 | `0160:01E6` で `#UD` | **30 秒走り切る** (トラック 61→68 を順次ストリーム) |

> **教訓**: `INT 1Bh` の仕様は FDC の仕様ではない。
> `fdd_d88.c` (FDC 層) だけ読んで `bios1b.c` (BIOS 層) を読まなかったのが
> 遠回りの原因。前回プロジェクトの `kernel/v86_disk.c` には
> 「NP21/W bios1b.c 準拠」と明記した実装が最初から入っていた。

### 3.5.6 【途中経過・誤り】物理ヘッドは READ の AL bit2 と考えた

§3.5.2 で「物理位置は SEEK の CL と DH の両方」と書いたが、**DH の部分は
誤りだった**。呼び出しログを最後まで並べたら決め手が出た。

```
SEEK C=1 → READ AL=94 ID(0,1,1) N=3 x2 → 0x15000
           READ AL=90 ID(0,1,1) N=3 x2 → 0x15800
```

**同じ ID を連続する 2 つのバッファへ読んでいる。** ローダが同じ 2KB を
二度読む道理は無い。イメージを確認すると物理 trk2 と trk3 は ID が同一で
中身が違う (先頭が `"CHSRD10"` と `"BEPMU1"`)。`AL` bit2 をヘッドとすれば
trk3 → `0x15000`、trk2 → `0x15800` となって辻褄が合う。

DH をヘッドとみなす実装では、SEEK に `DH=3` や `DH=34` が飛んでくる
(ゲストは SEEK で `CL` しか設定していない) ため成立しない。
**ヘッド 1 が要る場面はすべて `AL=0x94` で来ていた。**

同じ ID を持つ物理トラックが 2 本ずつあるこのディスクの書式は、
「`AL` でヘッドを選ぶ」前提で初めて意味を持つ。

直した結果:

| | DH をヘッドとした場合 | AL bit2 をヘッドとした場合 |
|---|---|---|
| INT 1Bh 呼び出し | 38,072 回 | **11 回** |
| 失敗 | 19,014 回 | **0 回** |
| リトライ | あり | **無し** |

### 4-1. 次のブロッカーはディスクではない

段取り 5 を入れたあとの実測:

```
BIOS コール : 15 回 (すべて成功、失敗 0)
#GP         : 50,001 → V86_GP_LIMIT に到達して打ち切り
最後の #GP  : CS=0160 IP=0DF7   E6 08 E4 08  = OUT 08,AL / IN AL,08
I/O トラップ: 49,981 回 (ほぼ全部これ)
```

**ゲストはスレーブ PIC (`0x08`) を叩き続けている。**
いまの PIC は「読み `0xFF` / 書き破棄」のスタブなので、ゲストが待っている
状態が永遠に来ない。ディスク経路は片付いたので、次は **PIC / PIT の実仮想化** →
[06_pic_plan.md](06_pic_plan.md)。

### 4-2. 記録の取り方 — INT 1Bh 呼び出しログ

`v86_disklog` に 32 エントリ × 8 ワードのリングを置いてある。
1 コールぶんが `AX / CX / DX / BX / ES:BP / 呼び出し時の物理シリンダ /
転送できたバイト数 / 結果`。

```bash
emu_read_mem addr=v86_disklog len=1024
```

**カウンタだけでは足りなかった。** 「何回失敗したか」は分かっても
「どういう順で何を要求されたか」が分からず推測が始まる。
§3.5.2 の物理位置モデルはこのログを並べた瞬間に確定した。

## 5. 先に潰しておくべき懸念

### 5-1. PIC の仮想化がまだスタブ → **当たった**

現在 PIC ポートは「読み `0xFF` / 書き破棄」。

当初「IPL 実行〜次段ロードの間の I/O トラップは 3 回だけなのでまだ問題に
なっていない」と書いていたが、ディスク経路が通ってロードが最後まで進んだ
とたんにここで止まった (§4-1)。**次に潰すのはこれ** →
[06_pic_plan.md](06_pic_plan.md)。

### 5-2. ゲストがどの装置番号で来るか

`AL` の DA/UA を見て `loop_dev` のスロットへ対応付ける必要がある。
最初は「`0x90`(2HD FDD#1) → slot 0 固定」で十分。

### 5-3. ウォッチドッグは #GP 回数で持つこと

タイマ由来のタイムアウトは**ゲストが STI していることが前提**で、IOPL=3 では
ゲストが CLI したまま回り続けると一切効かない。実際、最初のブート試行で
セッションが止まらなくなりエミュレータのリセットが必要になった。

`V86_GP_LIMIT` (現在 50,000) で #GP 総数に上限を設けてある。
1 回の #GP が拒否ポートの読みだけなら数マイクロ秒だが、`INT 1Bh` のように
実ディスク I/O を伴うと数ミリ秒かかるので、上限は「必ず数十秒で戻る」値に
しておくこと。100 万回にしたら何分も帰ってこなかった。

### 5-4. 1MB 境界

`ES:BP` が 0xFFFF:xxxx のようにラップする指定は理屈上あり得る。
バッキング RAM は 0x00000-0x8EFFF しか無いので、
**範囲外を指されたら CF=1 で返す**こと。黙って書くとカーネルを壊す。
