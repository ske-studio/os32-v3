# 09. メモリマップの整理 — カーネルスタックを低位から追い出す

> 作成: 2026-08-11 / 完了: 2026-08-11
> 前提: [08_dos5.md](08_dos5.md) (MS-DOS 5.00A が `A>` まで起動)
> 結果: **V86 ゲストに 640KB を渡せるようになった。**
> 直前の状態は tag `v1.0.3`。

---

## 1. なぜ動かすのか — 「物理」ではなく「リニア」の問題

まず誤解しやすい点を先に潰しておく。**V86 ゲストの RAM の実体はもう上位にある。**
セッション中のページテーブルを実測するとこうなっている:

```
  linear 0x01000 -> phys 0x501000  P|RW|US   ★リマップ
  linear 0x8E000 -> phys 0x58E000  P|RW|US   ★リマップ
  linear 0x8F000 -> NP                       ← スタックガード
  linear 0x90000 -> phys 0x90000   P|RW      ← カーネルスタック (USER 無し)
  linear 0xA0000 -> phys 0xA0000   P|RW|US   ← VRAM 直マップ
```

バッキング RAM は `pgalloc_alloc_n()` が返した **物理 0x501000 以降**、
つまりプログラム空間 (`PGALLOC_BASE = 0x400000`) の中にある。
OS32 のフォントキャッシュや GFX バックバッファは物理 `0x1000-0x8EFFF` に
無傷で残っていて、セッション中だけ見えなくなっているだけ。

問題は物理ではなく**リニアアドレス空間**のほう。V86 では CPU が

```
linear = (seg << 4) + off
```

を作るので、ゲストが触れるリニアは **`0x00000-0x10FFEF` に CPU 仕様として固定**
されている。この窓を別の場所へずらす手段は 386 に無い。
そしてカーネルスタックが **リニア 0x90000-0x9FFFF を占有**していたので、
ゲストに渡せるコンベンショナルメモリはそこで頭打ちだった。

**しかも中途半端に空けても意味がない。** PC-98 のメモリ量申告は
`0000:0501` の下位 3bit で「(n+1) × 128KB」しか表現できないので、
572KB 張っても切り捨てで **512KB としか申告できない**。
`0x00000-0x9FFFF` を丸ごと空けて初めて 640KB になる。

---

## 2. 実測 — 64KB のうち 3,068 バイトしか使っていなかった

`0x90000-0x9FFFF` を全部ダンプして、下から最初の非ゼロを探した
(NP21/W はブート時に `bios_memclear()` でゼロ化するので、これが最深到達点)。

```
lowest non-zero: 0x9F400  → 深さ 3,068 bytes (4.7%)
  0x90000-0x9EFFF  nonzero = 0/61440   ← 61KB は一度も触られていない
  0x9F000-0x9FFFF  nonzero = 1266/4096
```

`find /usr` / `du /usr` を流して再測定しても **0x9F400 のまま**だった。

### なぜ増えないのか — ブート後は誰も使っていない

| 経路 | どのスタックを使うか |
|---|---|
| 割り込み・例外 | **その時走っているスタック**。GDT はリング 0 の 4 エントリだけ (`gdt_init()`: NULL / 0x9A / 0x92 / TSS) なので特権遷移が起きず、スタック切り替えが発生しない |
| シェル / 外部プログラム | `exec_run()` が子ごとに ESP を張り替える (シェル `0x380000`、プログラム `0x400000+`) |
| V86 の `#GP` フレーム | `v86_entry.asm` が `TSS.ESP0 = 今の ESP` にするので、**セッションを起動した `v86` プログラムのスタック**に載る。実測でも `isr_stub_13` 突入時の `ESP = 0x00EFFAF4` |

つまり `0x90000` のスタックに残っているのは `kernel_main → exec_run(shell)` の
外枠だけで、3KB はブート時 (ローダーの LZ4 展開 + ext2 マウント +
フォント/Unicode ロード + `gfx_init`) の最深値。

> **[04 §4-1](04_implementation_status.md) の記述は現状と食い違っていた。**
> 「カーネルスタック (0x90000-0x9FFFF) は絶対にリマップしてはならない —
> V86 から `#GP` が入ると CPU はそのスタックにフレームを積む」と書いてあるが、
> 積まれるのは呼び出し元のスタック。不変条件としては
> **「実行中のスタックをリマップするな」**が正しい。

## 3. やったこと

### 3-1. ローダーのスタックは低位のまま残す

3 本のローダー (`loader_hdd.asm` / `loader_fat.asm` / `loader_fat_new.asm`) は
PM に入った直後に `mov esp, 0009FFFCh` する。**ここは動かせない。**
ローダーはディスク BIOS (`INT 1Bh`) を呼ぶためにリアルモードへ戻るので、
`SS:SP` で届く 1MB 未満にスタックが要る。

動かすのはカーネル側だけでよい。V86 セッションはブートの遥か後なので、
ローダーが使い終わった低位スタックとは競合しない。
定数としては `MEM_BOOT_STACK_TOP` に名前を付けて残した。

### 3-2. `kentry` で張り替える

```asm
        ;; BSS クリア (rep stosd。CALL を挟まないので切り替え地点として安全)
        ...
        mov     eax, [esp + 4]          ;; mem_kb
        mov     edx, [esp + 8]          ;; boot_drive
        mov     esp, 001FFFFCh          ;; = MEM_KSTACK_TOP
        push    edx
        push    eax
        push    dword 0                 ;; ダミーリターンアドレス
        xor     ebp, ebp
        jmp     kernel_main
```

**引数の載せ替えを忘れないこと。** `kernel_main(u32 mem_kb, u32 boot_drive)` は
`__cdecl` で、ローダーが far jmp の前にスタックへ積んでいる
(3 本とも `[esp+0]` ダミー / `[esp+4]` mem_kb / `[esp+8]` boot_drive)。

> **一度これで踏んだ。** ESP を張り替えるだけにしたら、
> **ブートは成功するのに `mem` の表示が `Physical : 3229946883 KB` になった。**
> `mem_kb` がゴミになると `paging_init()` の「未実装メモリを NP にする」
> 判定が全部素通りし、保護が静かに消える。
> **落ちない壊れ方をするので、ブートしたことは確認にならない。**

`EBP = 0` にしているのは、例外時のスタックトレースがここで止まれるようにするため。

### 3-3. 新しいマップ

| 範囲 | 前 | 後 |
|---|---|---|
| `0x08F000-0x08FFFF` | スタックガード (NP) | **フォント/Unicode/GFX 用の空き** |
| `0x090000-0x09FFFF` | カーネルスタック 64KB | **同上 (V86 ゲストに明け渡す)** |
| `0x1CB000-0x1FFFFF` | SHM 後方予約 (NP) 212KB | 予約 192KB に縮小 |
| `0x1FB000-0x1FBFFF` | — | **スタックガード (NP)** |
| `0x1FC000-0x1FFFFF` | — | **カーネルスタック 16KB** |

16KB は実測 3KB の 5 倍強。
`paging_init()` は**プローブされたメモリ量に関係なくスタック範囲を R/W で
強制マップする** — ここを NP にした瞬間、次の push で三重フォルトになる。

### 3-4. 芋づるで直したところ

| 場所 | 内容 |
|---|---|
| `kernel/v86_mem.h` | `V86_REMAP_END` → `MEM_CONV_END` (0xA0000)、バッキング 143→160 ページ |
| `kernel/v86_bios.h` | `V86_GUEST_MEM_CODE` 3→4 (**512KB → 640KB**) |
| `kernel/paging.c` | 保護マップ、`paging_reclaim_conventional()` の範囲 |
| `include/memmap.h` | `MEM_CONV_RECLAIM_END` → 0x9FFFF、`MEM_CONV_END` 新設 |
| `drivers/kcg.c` | フォント展開の一時バッファ上限 `0x8F000` → `MEM_CONV_END` (282KB → **344KB**) |
| `kernel/isr_handlers.c` | スタックトレースの下限 `0x90000` → `MEM_KSTACK_BASE` |
| `cmd_sys.c` / `dbgserial.c` / `tests/crash.c` / `vbzview.c` | マップ表示・NP ブラックリスト・ガードページのテスト先 |
| `boot/boot_defs.h` | `MAX_IMAGE_SIZE` は**据え置き**。ステージング先の上限を決めるのは低位に残るブート時スタックのほうなので広げられない |

## 4. 検証

| 確認 | 結果 |
|---|---|
| ブート | OK。`mem` の `Physical : 15360 KB` も正しい |
| 新スタックの使用量 | **3,076 bytes / 16KB (18.8%)**。ガードまで 13KB の余裕 |
| `v86 -t` | OK (5 回連続) |
| `v86 -d /host/Ys.D88` | OK (直読みとバイト一致) |
| `v86 -b /host/dos5.fdi` | **`A>` まで起動**。BDA `0x0501 = 0xA4` → 640KB |
| ゲストのページテーブル | `linear 0x00000-0x9FFFF` → `phys 0x501000-0x59FFFF` 連続 160 ページ = **640KB** |
| `v86 -b /host/Ys.D88` | タイトル → RETURN → 本編。従来どおり |
| `blit_test` | 全項目 PASS |
| `crash` (ガードページ) | `0x1FB000` で `WRITE Not-Present`。スタックトレースも正常、シェルは生存 |
| `cal` などの外部プログラム | OK |

### 検証中に見つけた別件 — `v86 -t` の `iotrap == 2` は不安定だった

`crash` の直後に一度だけ `v86 -t` が FAILED になった。`v86_iolog` を見ると:

```
#0 IN  0x0000 = 0x00  at 8A00:0013   ← テストの拒否ポート読み
#1 OUT 0x0000 = 0x55  at 8A00:0017   ← テストの拒否ポート書き
#2 OUT 0x0000 = 0x0B  at FD80:0169   ← BIOS ROM
#3 IN  0x0000 = 0x04  at FD80:016D   ← BIOS ROM
#4 OUT 0x0000 = 0x20  at FD80:0187   ← BIOS ROM (EOI)
```

セッション中は VSYNC (IRQ2) とキーボード (IRQ1) の実割り込みが走っていて、
ゲストの IVT は実機から引き継いだままなので、それらが BIOS ROM の
ハンドラへ落ちて PIC のポートを叩いていた。テスト側が
`v86_pic_set_imr(0, 0x00)` で**マスタ PIC を全開**にしていたのが原因。

タイマ (IRQ0) だけ通す `0xFE` に直した。
**このテストが見たいのは「拒否ポートだけがトラップされること」であって、
実 IRQ の反射先の副作用ではない。**

---

## 5. 得られたもの / 残り

- **V86 ゲストに 640KB** (572KB 実装・512KB 申告 → 640KB 実装・640KB 申告)
- 低位の空きが 20KB → 88KB、フォント展開バッファが 282KB → 344KB
- カーネルスタックは 64KB → 16KB (実測の 5 倍強)

**リング 3 のユーザプログラムを導入したら測り直すこと。**
今回の 3KB は「割り込みで特権遷移が起きない」ことに全面的に依存している。
リング 3 を入れた瞬間、全プログラムの ISR ネストと KAPI 呼び出しが
`TSS.ESP0` = このスタックに積まれるようになる。
