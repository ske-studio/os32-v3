## 1. いま何が起きているか (実測)

ディスク経路が片付いて Ys の本体ロードが最後まで通った結果、次はここで止まった。

```
BIOS コール : 15 回 すべて成功 (失敗 0)
#GP         : 50,001 → V86_GP_LIMIT に到達して打ち切り
最後の #GP  : CS=0160 IP=0DF7   E6 08 E4 08  = OUT 08,AL / IN AL,08
I/O トラップ: 49,981 回 — ほぼ全部これ
最後のポート: 0x08
```

`0x08` は PC-98 の**スレーブ PIC のコマンドポート**。
`OUT` してすぐ `IN` する形なので、**OCW3 で読み出すレジスタを選んでから
IRR か ISR を読む**という 8259A の定石そのもの。

現在の実装は [`kernel/v86_io.c`](../../../kernel/v86_io.c) の

```c
u32 v86_io_in(u16 port, int size)   { return (size == 1) ? 0xFF : 0xFFFF; }
void v86_io_out(u16 port, int size, u32 value) { /* 破棄 */ }
```

**読みが常に `0xFF`** なので、ゲストから見ると「全ビットが立ちっぱなし」。
待っている状態が永遠に来ないので抜けられない。

---

## 2. なぜ素通しにできないか

PIC はゲスト専用デバイスではない。**OS32 自身が同じチップを使っている。**

| | OS32 | ゲスト (PC-98 の慣習) |
|---|---|---|
| マスタ ICW2 (ベクタ) | `0x20` | `0x08` |
| スレーブ ICW2 | `0x28` | `0x10` |
| IMR | OS32 が必要な IRQ だけ開けている | ゲストが自由に触る |

ゲストに実チップを触らせたら、OS32 のタイマもキーボードもシリアル (rshell) も
その瞬間に死ぬ。**完全仮想化しかない** — 方針表 ([04 §6](04_implementation_status.md))
でも最初からそう分類してある。

## 3. 作るもの — 仮想 8259A × 2

`kernel/v86_pic.c/h` を新設し、`v86_io_in/out` からディスパッチする。

### 3.1 ポート

| ポート | 役割 |
|---|---|
| `0x00` | マスタ コマンド (ICW1 / OCW2 / OCW3) |
| `0x02` | マスタ データ (ICW2/3/4 / OCW1=IMR) |
| `0x08` | スレーブ コマンド |
| `0x0A` | スレーブ データ |

### 3.2 状態 (チップごと)

```c
struct v86_pic {
    u8 imr;         /* OCW1 — ゲストのマスク */
    u8 irr;         /* 要求中 */
    u8 isr;         /* サービス中 */
    u8 base;        /* ICW2 — ゲストが決めるベクタベース */
    u8 icw_step;    /* 0=通常, 1=ICW2待ち, 2=ICW3待ち, 3=ICW4待ち */
    u8 icw4_needed;
    u8 read_isr;    /* OCW3 の RR/RIS。0=IRR を読む, 1=ISR を読む */
};
```

### 3.3 書き込みの解釈

コマンドポートへの `OUT` は 8259A の規則どおりに分岐する。

| 条件 | 意味 |
|---|---|
| bit4 = 1 | **ICW1** — 初期化開始。`icw_step=1`, `isr=irr=0`, `read_isr=0` |
| bit4 = 0, bit3 = 1 | **OCW3** — bit1(RR) と bit0(RIS) で `read_isr` を更新 |
| bit4 = 0, bit3 = 0 | **OCW2** — EOI 系。`isr` の該当ビットを落とす |

データポートへの `OUT` は `icw_step` を見る。`0` なら OCW1 (= IMR)、
それ以外は ICW2 → ICW3 → (ICW4) の順に食わせて `icw_step` を進める。

### 3.4 読み出し

| ポート | 返す値 |
|---|---|
| コマンド | `read_isr ? isr : irr` |
| データ | `imr` |

**ここが今回の本体。** `0xFF` を返すのをやめるだけでゲストの
ポーリングループは抜けられるはず。

### 3.5 割り込み反射をこのモデルに通す

いまの `V86_REFLECT` は**固定ベクタ**を注入している
(IRQ0 → `INT 08h`、IRQ12 → `INT 14h`)。PC-98 の慣習値なので Ys では
たまたま合うが、正しくは**ゲストが ICW2 に書いた `base` から引く**。

反射の手順を仮想 PIC 経由に変える:

1. `irr |= (1 << (irq & 7))`
2. `imr` でマスクされていたら**注入しない**（`irr` は立てたまま）
3. 通ったら `isr |= bit`, `irr &= ~bit`
4. ベクタ = `base + (irq & 7)` で `v86_do_int()`

> **前回プロジェクトの事故**: 仮想 PIC の IMR/ISR を無視して注入し続けた
> 結果、ゲストの SP が減り続けて **IVT を割り込みフレームで上書き**した。
> 計画書 (ローカルの `.claude/plans/`、リポジトリ外) の Phase 3-4 に明記されている。
> 手順 2 と 3 は飾りではない。

| # | 内容 | 検証 |
|---|---|---|
| 1 | **I/O トラップログを足す** (`v86_iolog`) | ゲストが実際に書いた OCW の並びが読める |

| 3 | 反射を `imr`/`isr`/`base` 経由にする | IRQ 反射のスモークテスト (`v86 -t`) が通ったまま |
| 4 | PIT ch0 (`0x71`/`0x77`) も同様に仮想化 | ゲストが自前のタイマ周期を設定できる |

**1 を先にやる。** §3.3 の分岐は 8259A の一般則であって、
**Ys が実際に何を書いているかはまだ測っていない**。
ディスクのときも、カウンタでは足りず呼び出しログを並べて初めて
物理位置モデルが確定した ([05 §4-2](05_disk_bios_plan.md))。同じ手を使う。

### 4-1. I/O トラップログの形

`v86_disklog` と同じ作りにする。32 エントリ × 4 ワード:

```
[0] port
[1] dir<<16 | size          dir: 0=IN, 1=OUT
[2] value                   IN なら返した値、OUT なら書かれた値
[3] cs<<16 | ip             どの命令から来たか
```

ポーリングで同じ組み合わせが延々続くので、**直前と同じ (port,dir,value) は
積まずにカウンタだけ増やす**こと。そうしないとリングが 1 種類の
エントリで埋まって何も分からなくなる。

## 5. 先に潰しておく懸念

### 5-1. OS32 側の PIC を壊さないこと

仮想 PIC は**カーネル内の構造体を触るだけ**で、`outp()` を一切呼ばない。
`v86_io_out()` から実 I/O 命令へ落ちる経路が無いことをコードで保証する。

### 5-2. ベースベクタが未初期化のとき

ゲストが ICW2 を書く前に IRQ が来ることがある。
`base` の初期値は **PC-98 の実機値** (マスタ `0x08` / スレーブ `0x10`) に
しておく。ゲストは実機の IVT をそのまま引き継いでいる
([04 §3](04_implementation_status.md)) ので、これが最も辻褄が合う。

### 5-3. スレーブのカスケード

PC-98 はスレーブがマスタの IR7 にぶら下がる。厳密にやるなら
スレーブの割り込みでマスタの IR7 の ISR も立てる必要がある。
**まずは各チップ独立でよい** — ゲストが EOI をスレーブとマスタの両方に
出すのは既定の作法なので、独立に処理しても破綻しない。
破綻したら実測で分かる。

### 5-4. `v86 -t` のスモークテストを壊さない

現在の IRQ 反射テストは「反射数とゲスト側 ISR カウンタが一致する」で
判定している ([04 §5-1](04_implementation_status.md))。
仮想 PIC を挟むと**ゲストが IMR を開けていない限り反射されなくなる**ので、
`kernel/v86_test16.asm` 側で IMR を開ける必要が出るかもしれない。
テストが落ちたらそれは仕様どおり — asm を直すこと。

> 実際には IMR の既定値を `0x00` にしたので asm の変更は要らなかった (§8-3)。

## 8. 【実測】実装した結果

### 8-1. ポーリングは抜けた

I/O トラップログ (§4-1) で回っていたのはこの 3 命令だった。

```
0160:0DF3  OUT 08, 20     OCW2 非特定 EOI
0160:0DF7  OUT 08, 0B     OCW3  ISR を読む指定
0160:0DF9  IN  AL, 08     ISR 読み出し → スタブは 0xFF を返す
```

ISR が全ビット立って見えるので EOI を出しても状態が変わらず、
永久に抜けられなかった。仮想 8259A を入れて `IN 08` が `0x00` を返すように
なった瞬間、ここは 1 周で通過するようになった。

### 8-2. §3.3 の分岐規則は当たっていた

ゲストが実際に使ったのは OCW2 (EOI) と OCW3 (読み出し選択) だけ。
**ICW1 は一度も来ない** (`v86_pic_icw1_n = 0`)。Ys は PIC を初期化せず、
BIOS が設定した状態を前提に動いている。だから ICW2 のベクタベースも
使われず、既定値 (マスタ 0x08 / スレーブ 0x10) がそのまま効いている。

### 8-3. IMR の既定値は決め手が無い

`0x00` (全許可) と `0xFF` (全マスク) の両方で走らせたが、
**Ys が止まる地点は変わらなかった**。ゲストが OCW1 を書かない以上、
どちらが実機に忠実かはこの実験では決まらない。
FM (IRQ12) が要る先のことを考えて `0x00` にしてある。

### 8-4. 反射を PIC 経由にしても回帰しなかった

`V86_REFLECT` の引数を**ベクタ番号から IRQ 番号に変えた**うえで、
ベクタもマスク判定も `v86_pic_should_inject()` に任せる形にした。
`v86 -t` のスモークテスト (反射数とゲスト ISR カウンタの一致) は通ったまま。

## 9. 次の停止点 (PIC とは別物)

PIC を抜けた先で、**ディスクの読み方の誤り**がもう 1 つ見つかった。
物理ヘッドの決まり方で、詳細は [05 §3.5.6](05_disk_bios_plan.md)。
これを直したあとの状態:

```
INT 1Bh   : 11 回 すべて成功 (失敗 0 / リトライ 0)
I/O トラップ: 6 回 (すべて BIOS ROM の タイマ ISR。EOI と PIT 再設定)
停止       : #UD  ゲスト CS:IP = 0160:01E6  バイト列 FF FF FF C8
             SS:SP = 0060:0001
```

**IRQ を全マスクしても同じ地点で止まる**ので、割り込み注入が原因ではない
ことは切り分け済み。ロードは全部成功しているのに、ロードしたコードの
途中で不正命令に当たっている。次はここを追う。
