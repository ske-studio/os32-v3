## 1. 現在地

**実ディスクイメージの IPL を V86 で起動し、ゲストが `INT 1Bh` で本体を
読み込み、仮想 PIC 経由で割り込みを回しながら走り続けるところまで
動作している。**
Ys I は IPL 実行 → 全リード成功 → トラックを順次ストリームしながら
**30 秒のセッション上限まで走り切る**。
**Ys I がタイトルから本編まで到達し、テンキーで操作できる。**
表示は素の NP21/W とピクセル単位で一致し ([07](07_gfx_state.md))、
FM 音源も鳴り (§4-17)、キー入力も届く (§4-18)。
セッション上限は 5 分 (当初 30 秒)。脱出は **CTRL+STOP** (§4-18)。MS-DOS 上では
CTRL+STOP が効かないことがあり、互換の CTRL+GRPH+DEL を使う ([08 §5-4](08_dos5.md))。

## 2. ファイル構成

```
kernel/
  tss.c/h          TSS (104B) + I/O 許可ビットマップ (8KB)
  gdt.c            GDT 4 エントリ化と TSS ディスクリプタ
  v86.c/h          #GP 一次ハンドラ、IN/OUT デコーダ、割り込み反射、
                   セッション管理 (setjmp/longjmp)、スモークテスト
  v86_entry.asm    iretd による V86 遷移、脱出口
  v86_mem.c/h      バッキング RAM 確保とアドレス空間の張り替え
  v86_io.c/h       I/O ポリシー (許可リスト) とポートディスパッチ
  v86_bios.c/h     BIOS コールの HLE、実機 IVT/BDA の退避と引き継ぎ、
                   INT 1Bh (SENSE / SEEK / READ DATA) と loop_dev への橋渡し、
                   呼び出しログ (v86_disklog)
  v86_test16.asm      ゲスト側スモークテストの正本 (NASM)
  v86_test16_disk.asm ゲスト側ディスクテストの正本 (NASM)
  isr_stub.asm     #GP/#DE/#DB/#UD/#PF の V86 分岐、RESTORE_KSEG、
                   V86_REFLECT、irq_stub_12
  idt.c            #DB (vec 1) と IRQ12 (vec 0x2C) の登録
  paging.c/h       PTE_USER の PDE 伝播、paging_pde_clear_user()
```

**カーネルに置いたのは特権命令の発行・例外の一次受け・I/O の一次デコード・
ページテーブル操作・モード遷移だけ**。BIOS HLE やセッション管理の高位ロジックは
ユーザ空間に寄せる方針を維持している（前回は 12,300 行がカーネルに積み上がった）。

## 3. 動作の流れ

```
v86_run(ctx)
  ├ exec_setjmp        脱出地点を記録
  ├ irq_enable(12)     サウンドボード IRQ を開ける
  └ v86_enter(ctx)     ← v86_entry.asm
       ├ TSS.ESP0 = 現在の ESP
       └ iretd (EFLAGS.VM=1, IOPL=3)  → ゲスト実行開始

  ゲスト実行中:
    許可ポートの IN/OUT ......... トラップしない (IOPM で素通し)
    VRAM 書き込み ............... トラップしない (直マップ)
    拒否ポートの IN/OUT ......... #GP → isr_stub_13 → v86_gp_handler
                                   → デコード → v86_io_in/out → IP を進めて復帰
    INT n ....................... #GP (IDT ゲートの DPL チェック)
                                   → HLE 対象なら v86_bios_dispatch で
                                     レジスタと CF を書いて IP を進める
                                   → 対象外なら v86_inject_int でゲストの
                                     IVT (多くは BIOS ROM) へ流す
    HLT ......................... #GP → セッション終了
    実 IRQ ...................... irq_stub_N → OS32 の処理 → V86_REFLECT
                                   → v86_reflect_irq → ゲスト ISR へ

  セッション終了:
    v86_exit_to_kernel → v86_longjmp_out → exec_longjmp
      → v86_run の setjmp 地点へ復帰 → irq_disable(12) → ESP0 復元
```

### 3-1. ディスクイメージからのブート (`v86 -b <image>`)

```
v86_boot(path)
  ├ loop_dev_attach(path, slot 0)     D88/FDI/HDI/RAW は loop_dev が判別する
  ├ v86_mem_setup()                   バッキング RAM を張る
  ├ IPL を C=0 H=0 R=1 から読む
  │    → 0x1FC00 (V86_IPL_SEG:0000) へ配置           ← PC-98 の IPL 規約
  ├ CS:IP = 1FC0:0000 / SS:SP = 0000:0290
  └ セッション開始 (以降は §3 と同じ)

  ゲストは INT 1Bh で次段を読み、そこへ far jump する。
  Ys I では実測で CS=0x0060 へ遷移することを確認した。
```

失敗時の戻り値は `-1` 画像なし/attach 失敗、`-2` メモリ不足、
`-3` IPL (C0/H0/S1) が読めない。

## 4. 【重要】守るべき不変条件

実装中に実際に踏んで、原因特定に時間がかかったものを残す。
**どれも破ると「原因不明のトリプルフォルト」になる。**

### 4-1. 実行中のスタックは絶対にリマップしない

V86 から `#GP` が入ると CPU は `TSS.ESP0` が指すスタックにフレームを積む。
そこを実行中に張り替えたらその瞬間に全てが壊れる。

**「カーネルスタック (0x90000) を避ければよい」ではない。**
`v86_entry.asm` は `TSS.ESP0 = v86_enter を呼んだ時点の ESP` にしているので、
フレームが載るのは**セッションを起動した `v86` プログラムのスタック**
(`0x400000` 以降) であって、低位のカーネルスタックではない。
実測でも `isr_stub_13` 突入時の `ESP` は `0x00EFFAF4` だった。

カーネルスタック自体は 2026-08-11 に `0x1FC000-0x1FFFFF` (16KB) へ移設した。
低位のリニアを空けないと V86 ゲストに 640KB を渡せないため
(PC-98 のメモリ量申告は 128KB 単位なので中途半端に空けても 512KB のまま)。
リマップ範囲は `0x00000-0x9FFFF` = 640KB になっている。
→ [09_memmap.md](09_memmap.md)

### 4-2. カーネル帯に `PTE_USER` を付けない

前回プロジェクトはトリプルフォルトの回避策としてカーネル帯に `PTE_USER` を
付け、その結果 V86 がカーネルメモリを実行できるようになり、それを
「エミュレータが U/S を無視している」と誤診した。
そこから 0x110000 スライドと A20 のリバート 4 連発に繋がっている。
→ [02_np21w_paging_analysis.md](02_np21w_paging_analysis.md)

### 4-3. USER は PDE と PTE の両方に要る

i386 の実効権限は **PDE と PTE の論理積**。PTE だけ USER にしてもユーザ
アクセスは拒否される。`paging_set_page()` が `PTE_USER` を PDE に伝播させる
ようにしてある。戻すときは `paging_pde_clear_user()`。

### 4-4. 全ての例外・IRQ スタブでセグメントを復元する

V86 → Ring0 の遷移で CPU は DS/ES/FS/GS を null セレクタにクリアする。
C ハンドラは DS を前提に動くので、復元前に呼ぶと即 `#GP`。しかもその `#GP`
ハンドラも DS=0 のまま C を呼ぶため**例外が無限再帰**し、カーネルスタック
64KB を食い潰してガードページに当たり `#DF` → トリプルフォルトになる。

**一次原因が完全に隠れる**のが最悪で、実際 Phase 1 の初回検証で
「#PF が起きていた」という事実がトリプルフォルトの裏に埋もれた。
`isr_stub.asm` の `RESTORE_KSEG` マクロを必ず通すこと。

### 4-5. IRQ フレームは `#GP` フレームと 1 ワードずれる

ハードウェア割り込みはエラーコードを積まない。取り違えると EFLAGS の
つもりで CS を読むことになり、**症状が出るのは注入した後**なので追いにくい。
`V86F_*`（#GP 用）と `V86I_*`（IRQ 用）を別定義にしてある。

### 4-6. PC-98 の PIT と CRTC は奇数/偶数で交互

PIT が `0x71/0x73/0x75/0x77`（奇数）、CRTC が `0x70-0x7A`（偶数）。
I/O 許可ビットマップを範囲でまとめて開けると、OS32 の 100Hz タイマを
ゲストに壊される。許可リストは `step=2` で偶数だけ開けている。

### 4-7. `INT n` は IOPL に関係なく IDT を引く

**IOPL=3 にしても `INT n` は素通しにならない。**
V86 の `INT n` はプロテクトモードの IDT を引く仕様で、OS32 のゲートは
DPL=0 / ゲストは CPL=3 のため「softint かつ `gate.DPL < CPL`」の規則で
必ず `#GP` になる。

設計当初これを「IOPL=3 なら素通し」と誤解し、IVT を自前スタブに向けて
スタブ内のトラップ命令で `#GP` を誘発する方式を実装してしまった。
実機で動かして初めて誤りに気づき、トランポリンを全廃して
`#GP` ハンドラで `CD ib` を直接デコードする形に作り直している。

**結果的にはこちらの方が簡単**なので実害は無かったが、
「IOPL=3 が消してくれるのは `CLI`/`STI`/`PUSHF`/`POPF`/`IRET` であって
`INT n` ではない」は憶えておくこと。

> `INT` は配送前に落ちているので**ゲストスタックには何も積まれていない**。
> BIOS の戻り値 (CF) はスタックではなくフレームの EFLAGS に書く。

### 4-8. セッション終了時に EFLAGS を復元する

セッションから抜けるのは `#GP` ハンドラからの `longjmp` なので、戻ってきた
時点の EFLAGS は「例外に入った直後の状態」になっている。

- **IF は割り込みゲートが自動でクリアしている**
- **IOPL は V86 ゲストの値 (3) がそのまま残る**

`longjmp` は EFLAGS を復元しない。直さずに返すとカーネルが**割り込み禁止の
まま動き続ける**。実際にこれを踏み、`v86 -t` の出力は正常に出たのに
シェルがタイマ待ちループから二度と抜けなくなった。
`v86_run()` が前後で `pushfl`/`popfl` して戻している。

> 症状が「コマンドは成功したのにその後シェルが固まる」なので、V86 自体は
> 正しく動いているように見えてしまう。`emu_regs` の `eflags` で IF を見るのが早い。

### 4-9. セッションは `pgalloc_init()` より後

バッキング RAM を `pgalloc_alloc_n()` から取るため。
初回はこれを踏んで `v86_mem_setup()` が `-2` を返していた。

### 4-10. ウォッチドッグは時間ではなく `#GP` 回数で持つ

タイマ由来のタイムアウト (§1 の 30 秒) は**ゲストが `STI` していることが前提**。
IOPL=3 ではゲストの `CLI` が実 IF を落とすので、`CLI` したまま回り続ける
ゲストには一切効かない。実際、最初のブート試行でセッションが止まらなくなり
**エミュレータのリセットが必要になった**。

`V86_GP_LIMIT` (現在 **50,000**) で `#GP` の総数に上限を置いてある。
値の決め方に注意が要る — 1 回の `#GP` が拒否ポートの読みだけなら数マイクロ秒
だが、`INT 1Bh` のように実ディスク I/O を伴うと数ミリ秒かかる。
最初 1,000,000 にしたところ**何分経っても帰ってこなかった**。
「必ず数十秒で戻る」値にしておくこと。

### 4-11. 診断用の変数を `static` にしない

`#GP` 発生地点などの診断値はカーネル内グローバル (`v86_gp_cs` / `gp_ip` /
`gp_fl` / `gp_n` など) にして `kernel.map` に載せること。
`static` にすると `emu_read_mem addr=<symbol>` で引けず、
**セッションが走っている最中に外から覗く**ことができなくなる。
ブート中の停止位置を突き止められたのはこれがあったから。

### 4-12. セクタ長はゲストの `CH` に従う (イメージの既定値ではない)

D88 は**トラックごとにセクタ長が違ってよい**。`Ys.D88` は
track0 が 256B×16、以降が 1024B×5 という構成になっている。

当初「ゲストの `CH` が `loop_dev` の bps と一致しなければ拒否」という
実装にしていたため、IPL は読めるのにその先で全滅した。
**`CH` (=N コード) をそのまま信じ、カーネル側の固定バウンスバッファ
(`static u8 secbuf[1024]`) 経由で転送する**のが正しい。

ただし**セクタ側の実長との一致は必ず見ること** (§4-13 の 2)。

### 4-13. 物理トラック位置と論理セクタ ID は別物

µPD765A は「いまどの物理トラックに居るか」をドライブ側で持ち、
READ DATA の C/H/R/N は**そのトラック上で照合する ID**でしかない。
両者が一致している必要はどこにもない。

`Ys.D88` は 155 トラック全部でずれている (特定セクタだけのコピープロテクト
ではない)。詳細は [05 §3.5](05_disk_bios_plan.md)。守るべき点は 3 つ:

1. **トラック選択のヘッドとセクタ ID の `H` は別物。**
   トラック選択は `DH XOR (AL>>2)`、ID 照合は `DH` そのまま。
   正本は NP21/W の `src/bios/bios1b.c:335` と `:68`。
   物理シリンダはドライブのトラックレジスタ (SEEK の `CL`、または
   `AH` bit4 付き READ の `CL`)
2. **`N` も照合する。** ID だけ見て 256B セクタを N=3 の読みに返すと、
   ロード先の 3/4 が未初期化のまま「成功」が返り、ゲストがそこへ飛んで `#UD`。
   **見つからないなら失敗を返すほうがゲストは正しく振る舞える**
3. **式を実測から推測しない。** 同じ ID の物理トラックが 2 本あるので、
   ヘッドの式を間違えても**読みは成功し、中身だけが入れ替わる**。
   失敗が出ないので気づけず、あとから `#UD` という別の形で表面化する。
   ここは実測ではなくリファレンス実装 (`bios1b.c`) を読むのが正しい

`loop_dev_read_chs()` は D88 では使えない (物理=論理を仮定し、かつ読み出し長を
イメージ全体の `bps` — トラック 0 の値 — で頭打ちにする)。
`loop_dev_seek_d88()` を直接使うこと。

### 4-15. 割り込み反射は必ず仮想 PIC を通す

`V86_REFLECT` に渡すのは **IRQ 番号であってベクタ番号ではない**。
どのベクタへ落とすかはゲストが ICW2 に書いた base で決まり、
そもそも落としてよいかは IMR で決まる。両方 `v86_pic_should_inject()` が見る。

前回プロジェクトは IMR/ISR を見ずに注入し続け、ゲストの SP が減り続けて
**IVT を割り込みフレームで踏み潰した**。ここは飾りではない。

### 4-14. `#GP` 以外の V86 例外も分岐させる

`#GP` にだけ V86 分岐を持たせていた頃、ゲストが不正命令を実行すると
OS32 の汎用例外ハンドラが **「カーネルが EIP=0x120 で落ちた」** と表示して
シェルへ戻していた。`[OUT OF CODE!]` と出るのでカーネルのバグにしか見えない。

見分けるのは `EFLAGS.VM` ひとつ。例外ダンプのスタックに
`EFLAGS=0x00023202` が積まれているのに気づいて初めて V86 由来と分かった。

`#DE(0)` / `#DB(1)` / `#UD(6)` / `#PF(14)` に V86 分岐を入れ、
`v86_fault_handler()` でベクタ・CS:IP・そこのバイト列を残してから
セッションを畳むようにしてある。

### 4-16. ゲストが設定しないものは、こちらが実機の初期値を用意する

Ys がグラフィックに出した I/O はセッション全体で **4 回だけ**だった
(テキスト GDC 2 回 + 表示開始 2 回)。解像度もカラーモードもページも
パレットも触らず、**BIOS が残した状態を丸ごと前提にしている**。

だから `v86_io_apply_policy()` は I/O 許可ビットマップを組む前に
`gfx_state_for_guest()` で BIOS 相当の状態を作ってから渡す。
200 ライン / 8 色 / CCHAR LR=2 / PRAM 全 0 / デジタルパレット既定値
(`A8h=0x37 AAh=0x15 ACh=0x26 AEh=0x04`) / 表示・描画ページ 0。
終了時は `gfx_state_for_os32()` が OS32 の設定に戻す (VRAM は消さない)。

**`mode1` bit4 (200 ライン) と CCHAR の LR は必ずセットで変える。**
bit4 は「奇数ラスタを捨てる」なので、GDC 側の行あたりラスタ数と揃わないと
飛び越し表示になる。片方だけ直して 2 回外した。

**デジタルパレットのポートは 8 色モードにしてから書く。**
16 色モードのままだと `A8h` はアナログパレット番号に化ける。
逆に OS32 の `palette_init()` を 8 色モードで呼ぶとデジタルパレットが
`0F0F0F0F` に潰れて画面が白一色になる。

書き込み専用レジスタはゲストからは検証できない。エミュレータ側の
`emu_gdc` で外から見ること。→ [07 §3](07_gfx_state.md)

### 4-17. FM 音源はゲストに明け渡す — OS32 の音源エンジンを止める

OPN のポート (`0x188`-`0x18F`) は素通しなので、OS32 の音源エンジンが動いたまま
だとゲストの音楽ドライバと同じチップを取り合う。`snd_tick()` は IRQ0 から毎回
呼ばれ、BGM 再生中なら OPN に書く。しかも `bgm_persist` があるので
**プログラムを跨いで鳴り続ける**。

`snd_state_for_guest()` が `snd_set_master(0)` を呼ぶ。これは全チャンネルを
キーオフしてから停止するので、鳴りっぱなしの音を残さずに明け渡せる。
終了時は `snd_state_for_os32()` が `snd_set_master(1)` で戻す。

前回プロジェクトの「FM を検出するのに音が鳴らない」はここでは再現しない。
**ポートの回数ではなく出力レベルで確認すること** (`emu_sound` の `peak`)。

| 場面 | peak (約 2 秒窓) |
|---|---|
| 何も鳴っていない (OS32 のシェル) | **0** |
| 素の NP21/W で Ys | 4,018 - 7,590 |
| **OS32 の V86 上で Ys** | **3,637 - 16,595** |

FM ch0-2 が 4 オペレータともキーオンされ (`keyreg f0f1f2`)、出力レベルも
素の NP21/W と同じ桁。`0x188`/`0x18A` への書き込みは 15 秒で 21,060 回 =
素の NP21/W (22,678 回) の **92.8%**。差は V86 のオーバーヘッド分しかない。

> 「書けている」と「鳴っている」は別。I/O プロファイラでは前者しか分からず、
> 前回プロジェクトはそこで止まっていた。エミュレータ側でミックス後の
> バッファのピークを拾う口 (`peak`) を足したら 1 回で片が付いた。
> チップ側のカウンタ (`opngen.playing`) は本ビルドでは再計算されず**当てにならない**。
> ここでも「読めないものは読める場所から見る」が効いた (§4-16 と同じ)。

### 4-18. キーボードは「所有権」の問題 — 8251A は読んだら消える

キーボードは PIC と同じでゲスト専用デバイスではない。OS32 自身が IRQ1 で
シェルを動かしている。しかも 8251A のデータレジスタ (`0x41`) は
**読んだら消える**ので、素通しにすると先に読んだ側がスキャンコードを奪い、
もう一方には二度と届かない。**どちらか一方しか持てない。**

経路はこうしてある (`kernel/v86_kbd.c`):

```
実 IRQ1 → OS32 の kbd_irq_handler が 0x41 を読む
        → セッション中なら v86_kbd_push() で FIFO へ入れ、
          OS32 自身のリングバッファには入れない
        → irq_stub_1 が V86_REFLECT 1 でゲストの ISR を起動
        → ゲストが 0x41 を読むと #GP → v86_kbd_in() が FIFO から返す
```

ゲストから見ると実機と同じ「IRQ1 が来て `0x41` を読むと 1 バイト取れる」。
OS32 から見ると実チップは 1 回しか読まれない。
`0x43` はステータスを合成して返す (FIFO の有無を RxRDY に反映)。
ゲストからの書き込みは**実チップに転送しない** — OS32 の設定を壊すため。

**脱出ホットキーは必須。** キーが全部ゲストに流れる以上、人間が明示的に
抜ける口が無いとセッションから戻れない。**CTRL + STOP** を `v86_kbd_push()`
で拾い、ゲストには渡さずに畳む。PC-98 で「止める」といえばこれで、
2 キーなのでゲームを操作しながらでも咄嗟に押せる。
(3 キーの CTRL+GRPH+DEL も互換で残してあるが、押しにくいので主ではない。)
longjmp は asm スタブに寄せてある — 割り込みスタックの畳み方を
1 か所に集めるため。タイマ側と同じ作法。

実測: 本編プレイ中に CTRL+STOP → `exit : hotkey` でシェルに復帰し、
`ver` が応答する。

> ホストから送るときの注意: `curl -d "seq=CTRL+STOP"` は**動かない**。
> フォームエンコードでは `+` が空白の意味になるので、
> `--data-urlencode` を使うか `%2B` と書くこと。
> これで 30 分溶かした。

実測: キーを 3 つ送って `push 6 / read 6 / drop 0`。
メイクもブレイクも全部ゲストに届いて、ゲストが全部読んだ。
セッション終了後に送ったキーは OS32 のシェルに入る (所有権が戻っている)。

### 4-19. ウォッチドッグは「累計」ではなく「tick あたりの予算」

§4-10 で入れた `#GP` ウォッチドッグは**累計**で数えていた。
キーボードが繋がって遊べるようになった途端、**正常なプレイが 35 秒で
打ち切られた**。キーボードのステータスポーリングだけで 1,300 回/秒 の
`#GP` が出るので、累計の上限はそのままプレイ時間の上限になる。

カウンタは実タイマ IRQ が入るたびに 0 に戻すよう変えた。
**生きているタイマは「ゲストが暴走していない」ことの証明そのもの**で、
IOPL=3 のゲストが `CLI` で固まった瞬間にタイマが止まり、
そこで初めてカウンタが溜まり始める。判定したいのはこれだった。

ついでに終了理由も分けた。`#GP` 上限を `V86_EXIT_TIMEOUT` として
返していたので、画面には「timeout」としか出ず**時間切れと区別できなかった**。
`V86_EXIT_GP_LIMIT` を足して "runaway guest (#GP watchdog)" と表示する。

セッション上限も 30 秒 → 5 分にした。見て確認するだけなら 30 秒で足りたが、
遊べるようになった以上、時間で切るのは邪魔でしかない。

### 4-20. PIC の初期マスクも実機の実測値で渡す

グラフィック (§4-16) とまったく同じ形の問題が PIC にもあった。
Ys は ICW1 も OCW1 も一度も書かない (`v86_pic_icw1_n = 0`)。
BIOS が IPL 直前に設定した IMR を丸ごと前提にしている。

素の NP21/W で `Ys.D88` を起動して `emu_pic` を読むと:

| | 値 | 意味 |
|---|---|---|
| master IMR | `0x7D` | **IRQ0 (タイマ) マスク** / IRQ1 (キー) 許可 / IRQ7 (カスケード) 許可 |
| slave IMR | `0x61` | IRQ9-12 許可 / IRQ8,13,14 マスク |
| master ICW2 | `0x08` | ベクタベース (こちらの既定と一致) |
| slave ICW2 | `0x10` | 同上 |

**IRQ0 がマスクされているのが要点。** こちらの既定は `0x00` (全許可) で、
実機なら絶対に来ないタイマ割り込みを毎秒 100 回ゲストに注入していた。
ゲストは `INT 08h` を差し替えていないので BIOS ROM のタイマハンドラが走り、
**毎 tick で PIT を再設定していた** (`FD80:00AD` の `OUT 71h`)。

決め手は I/O プロファイルの比較だった。素の NP21/W の上位ポートに
`0x71` が**一度も現れない**のに、こちらの `v86_iolog` には
`OUT 0071` が 14,930 回並んでいた。「あるはずのものが無い」ではなく
**「無いはずのものがある」**方向の差で、カウンタを眺めていても気づけない。

副次的に、ゲストがスレーブ IMR を read-modify-write する箇所
(`0160:0BBD` の `IN 0Ah` → `OUT 0Ah`) が正しい値を読むようになった。
以前は `0x00` を読んで `0x00` を書き戻し、**全 IRQ を開けてしまっていた**。

> スモークテストは「反射したタイマ IRQ がゲスト ISR に届くこと」を
> 見るものなので、この既定値のままでは成立しない。
> `v86_pic_set_imr()` でハーネス側から IRQ0 を開けている。
> ゲストコード側で OCW1 を書くのが筋だが、あのバイト列は相対ジャンプと
> 絶対 IVT 値 (`mov es:[0x20], 0x005E`) が混在していて先頭に足せない。

### 4-21. ゲストの page 0 は実物理のまま渡す

**NP21/W はキーボード BIOS (INT 09h) をホスト側の C で実装している**
(`src/bios/bios09.c`)。ROM の `FD80:0088` にある `NOP` を CPU が踏むと
`ia32_bioscall()` → `biosfunc()` → `bios0x09()` が走る仕掛けで、
ROM 側にはその 2 バイト (`90 C3` = nop; ret) しか入っていない。

問題は `bios0x09()` が **`mem[]` = 物理メモリを直接叩く**こと。
ページングを通らないので、低位メモリをバッキング RAM に張り替えていると
書き込みがゲストに届かない。実測:

```
物理    0x528 (キーバッファ個数) = 0x01   ← BIOS が書いた
ゲスト  0x528                    = 0x00   ← 誰も書いていない
```

Ys はタイトルで `0000:052A` のキー入力状態テーブルを舐め続けるので、
**キーが届いているのに永久に待ち続ける**状態になっていた。

対策は page 0 (IVT + BDA) だけ実物理のまま渡すこと。
OS32 が page 0 で使っているのは IVT と BDA だけで、どちらも
`v86_bios_save_real()` / `v86_bios_restore_real()` で退避・復元する。
フォントキャッシュ以降 (`0x1000`-) はバッキングのままなので、
ゲストが OS32 のデータを壊す心配はない。

> 実機なら ROM のコードがゲストとして走るので、その書き込みは
> ページテーブルを通って正しい場所に落ちる。これはエミュレータ特有の
> 事情だが、**page 0 を実物理で渡すのは実機でも自然**なので害はない。

### 4-22. VSYNC (IRQ2) を反射しないとゲームは 1 フレームも進まない

タイトルを越えた直後、ゲストは `0160:0866` で固まっていた:

```
0160:0866  mov al, [0F24]
0160:0869  cmp al, 0
0160:086B  jne 0866          ; カウンタが 0 になるまで待つ
0160:086D  mov al, 4
0160:086F  mov [0F24], al    ; 次のフレームぶんを積む
```

典型的なフレーム同期待ちで、カウンタを減らすのは VSYNC ハンドラ。
素の NP21/W で **本編に入った状態**の PIC を読むと:

| | タイトル | 本編 |
|---|---|---|
| master IMR | `0x7D` | **`0x79`** |

bit2 が落ちている = **ゲームがフィールドに入ると自分で IRQ2 (VSYNC) を
開ける**。こちらは IRQ0/1/12 しか反射しておらず、IRQ2 は OS32 側でも
塞いだままだった。

`irq_stub_2` を追加し、セッション中だけ `irq_enable(2)` する。
OS32 自身は VSYNC 割り込みを使わないので、普段は塞いだままでよい。

> タイトルの PIC だけ見て「IRQ2 はマスクされている」と判断していたら
> 永久に見つからなかった。**ゲストの状態は場面で変わる**ので、
> 詰まっている場面そのもので測ること。

## 5. 検証方法

### 5-1. スモークテスト

シェルから `v86 -t` で実行する (KAPI v36 `v86_selftest`)。
結果はカーネル側のグローバルにも残るので、`kernel.map` 経由で
ホストから直接読める。

```bash
# ゲスト側から
v86 -t

# ホスト側から (MCP)
emu_read_mem addr=v86_smoke_result len=4
```

| 変数 | 期待値 | 意味 |
|---|---|---|
| `v86_smoke_result` | `0` | 総合判定 |
| `v86_smoke_magic` | `0x1234` | ゲストがメモリに書けた |
| `v86_smoke_magic2` | `0x5678` | `#GP` 後もゲストが継続できた |
| `v86_smoke_reason` | `1` (HLT) | 想定どおりの終了 |
| `v86_smoke_gp` | `4` | I/O 2 回 + `INT` 1 回 + HLT 1 回 |
| `v86_smoke_iotrap` | `2` | **拒否ポートだけがトラップ = パススルーが効いている** |
| `v86_smoke_irq` | `3` | カーネルが反射した IRQ 数 |
| `v86_smoke_gcnt` | `3` | **ゲスト自身の ISR が数えた回数** |
| `v86_smoke_bcnt` | `1` | カーネルが処理した BIOS コール数 |
| `v86_smoke_bios` | `0xB105` | **ゲストが `AH=0` かつ `CF=0` を確認した印** |

`iotrap == 2` / `irq == gcnt` / `bios == 0xB105` の 3 つが機構の健全性を端的に示す。

失敗したときのために、最後に `#GP` した地点も残してある。
これが無いと「どの命令で落ちたか」が分からず手が止まる
(実際 §4-7 の `INT n` の件はこれで特定した)。

| 変数 | 意味 |
|---|---|
| `v86_smoke_gpcs` / `gpip` | 最後に `#GP` したゲストの CS:IP |
| `v86_smoke_gpop` | 同 先頭 4 バイト (オペコード) |
| `v86_smoke_gpfl` | 同 ゲスト EFLAGS (IOPL / VM / IF の確認用) |

ゲスト側コードの正本は `kernel/v86_test16.asm`。変更したら
`nasm -f bin kernel/v86_test16.asm -o /tmp/t.bin` で再生成して
`kernel/v86.c` の配列に反映する。

### 5-1b. ディスクテスト (`v86 -d <image>`)

ゲストが `INT 1Bh` READ DATA で C0/H0/S1 を読み、その中身を
カーネルが `loop_dev` で直読みした結果と突き合わせる (KAPI v37)。
**BIOS HLE とディスク経路だけを切り出して検証する**ためのもので、
ブートが失敗したときに「読めていないのか、読めた上で止まっているのか」を
一発で分けられる。

| 変数 | 意味 |
|---|---|
| `v86_disk_marker` | ゲストが READ を成功と判定した印 |
| `v86_disk_cmp` | 直読みと一致したバイト数 |
| `v86_disk_reason` | セッション終了理由 |

ゲスト側コードの正本は `kernel/v86_test16_disk.asm`。

### 5-1c. ブート (`v86 -b <image>`)

セッション中の様子はカーネルグローバルに残るので、
**走らせたまま**ホストから読める (§4-11)。

| 変数 | 意味 |
|---|---|
| `v86_boot_gp` | `#GP` 総数 (ウォッチドッグの分母) |
| `v86_boot_bios` | BIOS コール数 |
| `v86_boot_iotrap` / `v86_boot_ioport` | I/O トラップ数 / 最後に触ったポート |
| `v86_boot_gpcs` / `gpip` / `gpop` | 最後の `#GP` の CS:IP とそこのバイト列 |

`gpcs`/`gpip`/`gpop` の 3 つで「いまゲストがどの命令で足踏みしているか」が
そのまま出る。PIC ポーリングは `CS=0160 IP=0DF7` の
`e608 e408` (= `OUT 08,AL` / `IN AL,08`) で特定した。

`#GP` 以外の例外は別枠 (§4-14):

| 変数 | 意味 |
|---|---|
| `v86_flt_vec` | 例外ベクタ (6 = `#UD` など) |
| `v86_flt_cs` / `ip` | ゲストの CS:IP |
| `v86_flt_op` | そこの先頭 4 バイト |
| `v86_flt_fl` | ゲスト EFLAGS |
| `v86_flt_n` | 発生回数 |

### 5-1d. INT 1Bh 呼び出しログ

```bash
emu_read_mem addr=v86_disklog len=1024
```

32 エントリ × 8 ワードのリング。1 コールぶんが
`AX / CX / DX / BX / ES:BP / 呼び出し時の物理シリンダ / 転送バイト数 / 結果`。

**カウンタだけでは足りなかった。** 「何回失敗したか」は分かっても
「どういう順で何を要求されたか」が分からず推測が始まる。§4-13 の物理位置
モデルは、このログを並べた瞬間に確定した。デコードは
[05 §4-2](05_disk_bios_plan.md) に置いてある。

### 5-2. 失敗したときの追い方

Phase 0-0 で入れたフォルト捕捉が効く。トリプルフォルトでも
**モーダルは出ず、フォルト地点で凍結**したままレジスタとメモリを読める。

```bash
emu_status        # fault_generation が 0 以外なら発生している
emu_fault         # 理由 + 全レジスタダンプ + CS:EIP (シンボル注釈付き)
emu_regs          # eip_sym / prev_eip_sym でどのスタブか分かる
emu_read_mem      # ESP からスタックを遡って再帰の有無を見る
emu_resume        # 再開 (= リセットして再起動)
```

Phase 1 の初回トリプルフォルトは、この 4 コールだけで
「`isr_stub_13+0x39` から `#DF` へ、`cr2` はスタックガード、
スタックに vector 13 のフレームが反復」まで見えて原因が確定した。

## 6. I/O ポリシー (実測ベース)

分類の根拠は [03_ys_profile.md](03_ys_profile.md)。**推測ではなく実測**。

| 分類 | ポート |
|---|---|
| **パススルー** | FM音源 `0x188-0x18F` / I/Oウェイト `0x5F` / テキストGDC・VSYNC `0x60-0x6E` / CRTC `0x70-0x7A`(偶数) / GRCG `0x7C,0x7E` / グラフィックGDC `0xA0-0xAE` / EGC `0x4A0-0x4AF` / ビープ `0x37` / カレンダ `0x20` |
| **仮想化** | マスタPIC `0x00,0x02` / スレーブPIC `0x08,0x0A` / PIT `0x71,0x77` / KBD `0x41,0x43` / FDC `0x90-0x94,0xBE` / リセット `0xF0` / A20 `0xF2` |
| **保護** | RS-232C `0x30-0x35` / HostDrv `0x7EC,0x7EE` |

VRAM (`0xA0000-0xBFFFF`, `0xE0000-0xE7FFF`) は実物理を直マップ。
描画は I/O ではなくメモリアクセスなので**トラップコストがゼロ**になる。
これが 386DX20 で成立する最大の理由。

ROM 帯 (`0xC0000-0xFFFFF`) は R/O + USER で**ゲストから実行可能**にしてある。
前回は ROM 実行を排除する「方法C」を実装した翌日に全撤回しているので、
同じ回り道はしない。

## 7. 残作業

### 7-1. いま止まっている場所

**無い。Ys I が本編まで到達し、操作できる。**

- タイトル → RETURN → 本編のフィールド画面
- テンキー (`NUM2`/`NUM6` 等) で主人公が歩き、マップがスクロールする
- FM 音源は本編中も鳴っている (出力ピーク 14,109)
- 画面は素の NP21/W とピクセル単位で一致

ここまでに解けたもの:

- スレーブ PIC の EOI/ISR ポーリングで 49,981 回トラップして打ち切られていた
  → 仮想 8259A ([06](06_pic_plan.md))
- 絵は合っているのに表示だけ崩れていた → グラフィック状態の引き渡し
  (§4-16 / [07](07_gfx_state.md))
- 実機なら来ないタイマ割り込みを注入していた → PIC 初期マスクの実測値化 (§4-20)
- キーが届くのに BIOS がキー入力状態テーブルを更新しなかった
  → ゲスト page 0 を実物理のまま渡す (§4-21)
- タイトルは越えたが 1 フレームも進まなかった → VSYNC (IRQ2) の反射 (§4-22)

<details>
<summary>解決済み: タイトル画面のキー待ち (§4-21 で解決)</summary>


**Ys がタイトルから先へ進まない。** 5 分走らせても画面は 1 ドットも変わらない。

ゲストが回っているのはここ (逆アセンブルで確定):

```
0160:02C6  call 0160:0374     ; キーが押されているか
0160:02C9  cmp  al, 0
0160:02CB  je   0160:02C6     ; AL==0 の間ずっと待つ

0160:0374  push es
0160:0375  mov  bp, 0 / mov es, bp
0160:037D  mov  bx, 052A      ; ← BIOS の「キー入力状態テーブル」
0160:0380  mov  al, es:[bx]   ; 13 バイト = 104 キー分のビットマップを
0160:0383  cmp  al, 0         ;    先頭から舐めて、最初の非ゼロで抜ける
...
0160:039E  cmp  cx, 0068
```

`0000:052A` は PC-9800 Bible 表 2-16 の**キー入力状態テーブル**。
キーバッファ (`0000:0502`) ではなく**押下状態のビットマップ**を見ている。

素の NP21/W で同じ地点を測ると:

| | 素の NP21/W | OS32 の V86 |
|---|---|---|
| タイトルでの待ち場所 | `0160:02C6` の同じループ | **同じ** |
| キー送信前の `0000:052A` | 全部 0 | **同じ** |
| キー送信後の `0000:052A` | `052D = 0x10` (= コード 0x1C, RETURN) | **全部 0 のまま** |
| ループ脱出 (`0160:02CD` にブレーク) | **ヒットする** | ヒットしない |

つまり**キーは届いているのに、BIOS がキー入力状態テーブルを更新しない**。
ゲストの ISR (`IVT[09] = FD80:022B`) は仮想 `0x41` から
スキャンコード `0x1C` を確かに読んでいる (`v86_iolog` と
`v86_kbd_n_read` の両方で確認済み)。IVT[09] も BDA の初期値も
素の NP21/W とバイト単位で一致している。

BIOS ハンドラ本体はこうなっていて、`call 0x88` が唯一の処理点:

```
FD80:0232  in   al, 43h        ; ステータス
FD80:0234  test al, 38h        ; PE|OE|FE
FD80:0236  jne  25Ah           ; エラー時のリトライ経路
FD80:0238  mov  al, 16h ; out 43h
FD80:023C  mov  byte [0529], 0 ; リトライ回数クリア
FD80:0241  in   al, 41h        ; ← ここまでは実測で通っている
FD80:0245  call 0088h          ; ROM 上は nop; ret (素の NP21/W でも同じ)
FD80:024C  out  00h, 20h       ; EOI
```

`FD80:0088` は素の NP21/W でもバイト単位で `90 C3` (nop/ret)。
**ここから先がまだ追えていない。** 次は素の NP21/W 側で
`FD80:0245` にブレークを置いてシングルステップし、
`0000:052A` を実際に書いているのが誰かを突き止める。

</details>

### 7-3. OS32 側の別バグ (V86 とは独立)

**外部プログラムを 1 つでも実行すると PTE[0] が `0x001` → `0x000` になる**
(`cal` だけで再現する)。`paging.c` は NULL ガードを意図的に R/O
(Not-Present ではない) で維持しているはずで、`paging_set_not_present(0,...)`
の呼び出し元も見つかっていない。
V86 側は `v86_bios_save_real()` で自衛しているため当面ブロッカーではないが、
**別途調査が必要**。

## 8. 前回プロジェクトとの差分

| | 前回 (`archive/feat-vdm`) | 今回 (`feat/vdm-v2`) |
|---|---|---|
| 方式の根拠 | 設計判断 | **386DX20 実測** |
| IOPL | 0 (全命令トラップ) | **3** (#GP レート 5〜6 倍減) |
| カーネル配置 | `0x110000` へスライド | **`0x100000` のまま** (スライドの根拠が消えた) |
| カーネル帯の `PTE_USER` | 付与 (回避策) | **付けない** |
| IRQ 注入 | IRQ0/1/2 のみ | **IRQ12 を含む** (FM の要) |
| 例外スタブのセグメント復元 | #GP の V86 経路のみ | **全スタブ** |
| フォルト時の観測 | モーダル + 再起動で証拠消失 | **フォルト地点で凍結して調査** |
| 暴走時 | 手動リセット | **`#GP` 回数ウォッチドッグで必ず戻る** |
| カーネル内の行数 | 12,300 行 | 約 1,100 行 (現時点) |
