## 1. 推奨方針

1. **既定の同一判定を「サイズ＋内容のバイト比較」にする**。同サイズ・同一更新日時でも内容が違えばコピーする。
2. **CRC-32をコピー時とコピー後の検証に使う**。既存実装を再利用し、ストリーム更新できる形へ整理する。
3. **更新日時は取得・保存を実装するが、同一内容の証明には使わない**。日時対応を待たずに同サイズ問題を解消する。
4. **一時ファイルへの書き込みと検証を経て置換する方式へ移行する**。現行ext2のrenameは置換途中に宛先を失うため、単にrenameを呼ぶだけでは安全にならない。
5. **配備世代、変更理由、未反映・失敗を見えるようにする**。内容の一致と「期待したビルドか」「メモリ上で稼働中か」を分ける。

CRC比較だけでも今回の更新漏れは通常検出できる。ただし両ファイルを読む必要があるなら、バイト比較は同じI/Oで衝突なく判定でき、最初の相違で打ち切れる。CRCは検証・記録・将来の配備マニフェストに使い分ける。CRCとmtimeの追加だけで原子的更新や配備世代の整合性まで保証することはできない。

## 2. 現行実装で確認した事実

| 項目 | 現状と改善への意味 |
|---|---|
| ゲスト側の比較 | [hsync.c](../../../userland/system/hsync.c) の `sync_directory()` は宛先の `st_size` と列挙時のサイズが等しければスキップ。内容と時刻は見ない |
| 強制同期 | **`-f / --force` は既に存在**。比較を飛ばしてコピーする。新設不要 |
| 同期範囲 | 既定ではルート直下の `/sys` を除外。`hsync sys` で明示対象にする。設定DBとその関連名・同一実体は強制同期でも保護 |
| ホスト側の配備 | [hostdrv_deploy.py](../../../tools/hostdrv_deploy.py) は `filecmp.cmp(..., shallow=False)` で内容比較し、`shutil.copy2()` でコピー。この問題の直接の箇所はゲスト側 |
| CRC | [lib/crc32.c](../../../lib/crc32.c) に `crc32_calc()` がある。[save_meta.c](../../../userland/lib/save/save_meta.c) にも互換の計算がある。ゼロから別方式を増やす必要はない |
| 時刻の受け皿 | `OS32_Stat` は `st_atime / st_mtime / st_ctime` を既に持つ。[ext2_vfs.c](../../../fs/ext2_vfs.c) はinodeから返す |
| HostDrvの時刻 | [hostdrvfs_proto.h](../../../fs/hostdrvfs_proto.h) の `Np2FileBasicInfo` に `LastWriteTime` 等があるが、[hdrv_stat()](../../../fs/hostdrvfs.c) は時刻を転記せず、ゼロ初期化値のまま返す |
| HostDrvのstat失敗 | `hdrv_stat()` はBasic/Standard情報取得に失敗しても最後に成功を返す経路がある。ゼロサイズを実在する空ファイルと誤認しないよう直す必要がある |
| 更新日時の保存 | [VfsOps](../../../fs/vfs.h) と [sdk/kapi.json](../../../sdk/kapi.json) に時刻設定APIはない。ext2の通常書き込みはゲストの現在時刻でmtimeを更新する |
| コピー失敗 | `copy_file()` は宛先を `O_TRUNC` で開く。readエラーと短いwriteは失敗として返すが、元の宛先は既に破壊され得る |
| 完了確認 | 最後の `vfs_sync()` の失敗は非ゼロ終了になる。現行 `sys_close` はvoidなので「close戻り値の確認」を現行APIだけで追加することはできない |
| 置換 | [ext2_rename()](../../../fs/ext2_dir.c) は既存宛先をunlinkしてから新エントリを追加する。追加失敗時の旧宛先維持・電源断原子性は保証できない |
| 大きなディレクトリ | 1ディレクトリ128件、名前63バイト、再帰深さ8の上限。超過は既にエラーにするが、全件同期はできない |
| 説明のずれ | [hsync.1](../../manpages/hsync.1) は全体同期の `/sys` 除外や設定DB保護の説明が不足。実装着地時に更新する |

今回のshlibではファイル長を変えずにヘッダのBSSサイズ等が変わり、サイズ一致だけでは更新を検出できなかった。
暫定対応は、ホスト側を最新に配備してから **`hsync -f sys`**。事前の手動削除は不要。
ただしこれはディスク上の同期であり、起動時にロード済みのshlibをメモリ上で再ロードする操作ではない。

## 3. 同一判定とCLI

### 3.1 既定の判定順

保護判定と同期範囲判定を、内容を開く処理やmkdirより先に通す。

| 条件 | 推奨動作 |
|---|---|
| 範囲外、設定DB等の保護対象 | 理由付き除外。強制モードでも変更しない |
| stat・列挙失敗 | 未同期のエラー。不存在はNOTFOUNDと確認できた場合だけ扱う |
| コピー元が通常ファイルでない、型が不明 | 明示エラー。特殊ファイルを通常ファイルとして読まない |
| 宛先がディレクトリ等、通常ファイルでない | 型衝突エラー。勝手に削除・切り詰めしない |
| 宛先不存在 | コピー |
| `--force` | 同一性判定を省略しコピー。保護・型検査・コピー後検証は省略しない |
| サイズ不一致 | コピー |
| サイズ一致・内容不一致 | コピー。mtimeの新旧・一致を問わない |
| サイズ一致・全内容一致 | `unchanged`。時刻保存導入後は必要に応じmtimeだけ更新して `metadata_updated` |
| 比較中のI/O失敗・予定サイズに達しないEOF | エラー。未読部分を「同一」と扱わない |

同じ秒の再ビルド、`touch`、過去コミットへのcheckout、時計のずれ、mtimeを保存するコピーがあるため、**「mtimeが新しいものだけコピー」「サイズとmtimeが等しいから同一」は既定にしない**。

内容比較は固定バッファ2本で行う。両側のshort readの分割が異なっても、比較するオフセットと有効長を揃える。片方がreadエラーなら打ち切り、不一致扱いで上書きへ進まない。
比較に使うサイズは列挙結果だけに依存せず、直前に取り直す。空ファイル同士も型・I/O結果を確認する。

### 3.2 オプション案

| CLI | 意味 | 段階 |
|---|---|---|
| `hsync [dir]` | 上記の内容比較。既存の同期方向・保護を維持 | H1 |
| `hsync -f [dir]` | 既存の強制コピーを維持 | 現行/H1 |
| `hsync -n [dir]` / `--dry-run` | 読み取りと比較だけ行い、予定変更・除外・エラーを表示 | H1 |
| `hsync -v [dir]` / `--verbose` | スキップ理由と各ファイルの比較結果も表示 | H1 |
| `hsync --expect-build <id> [dir]` | 期待する配備世代とホスト側マニフェストを照合 | H4 |
| `hsync --quick [dir]` | サイズ＋有効mtimeだけで省略する高速モード | **初期実装に含めない**。測定で必要になった場合だけ別途検討 |

`--dry-run` ではmkdir、mtime更新、一時ファイル、同期台帳、明示的なsyncを行わない。読み出しに伴うFS側atime更新まで抑える保証には、別途FS対応が必要。
引数の未知オプションや複数のdirはエラーにし、現在の「最後の引数で上書き」を解消する。
対象パスは正規化してから `/host` 配下と宛先を決める。`..` による同期元脱出、切り詰め、同一実体への自己コピーを拒否する。`sys` 除外は「全体同期のルート直下」にだけ適用し、`hsync usr` の `usr/sys` を誤除外しない。

## 4. CRC-32の実装・使い方

### 4.1 再利用する仕様

既存 `crc32_calc()` と同じCRC-32を使う。
反転多項式 `0xEDB88320`、内部初期値 `0xFFFFFFFF`、最後に `0xFFFFFFFF` をXOR。
テストベクトルは空列 `00000000`、ASCII `123456789` → `CBF43926`。

- 更新関数は「未確定の内部状態」を入出力し、最後のXORは全ファイルで1回だけ行う。
- 既存一括関数の戻り値・保存形式は変更しない。各チャンクの完成CRCを単純XORして全体CRCにしない。
- 共有可能な依存の薄いCコアをカーネル・ユーザーランド双方でビルドする。hsyncからカーネル内関数の番地を直接呼ばない。CRC計算だけのためにKAPIを増やさない。
- 移行対象外のsave側との値の一致は共通ベクトルで固定し、無関係なセーブ形式変更を同時に行わない。
- 16要素表64B／256要素表1KB／既存ビット版をPC-98想定で測定し選ぶ。大容量全件走査にビット版が適切とは未確定。

### 4.2 コピー検証

コピー元を読むときCRCと総バイト数を計算し、書き込み後の宛先（H2以降は一時ファイル）を再オープンして読み、**バイト数とCRCの両方**を照合する。I/O失敗、予定長不一致、CRC不一致を成功件数に入れない。

- `vfs_sync()`の成功と読戻し一致を記録する。ただしキャッシュを経由する読戻しは媒体からの物理再読保証ではない。最終受入では再起動後の内容も検証する。
- CRCは偶発的破損の検出用。衝突があるため、同一内容の厳密な証明・署名・配布元認証には使わない。コピー前の同一判定はバイト比較を維持する。
- H1は現行の直接上書きのままでも導入可能だが、検証失敗時に旧宛先を復元する保証はない。**この制限の解消はH2の完了条件**。

### 4.3 メモリと負荷

既存64KBバッファを比較用32KB×2に分割する案を初期値とする。追加でファイル全体を確保せず、大ファイルも一定メモリで処理する。コピー時は64KBを使用してもよい。
CRC状態・件数・バイト数のオーバーフローを検査し、現行VFSのint戻り値・32bitサイズを超えるファイルは検出して拒否する。特にHostDrvの64bit `EndOfFile` をu32へ黙って切り捨てない。
時間、比較読取量、コピー書込量、検証読取量、スキップ率を測る。CRCを使うだけではHostDrvの読取I/Oは減らない。

## 5. タイムスタンプ対応

### 5.1 取得

最初に `hdrv_stat()` が `LastWriteTime` を `st_mtime` へ返すようにする。
NT系FILETIMEは1601-01-01 UTC起点・100ns単位。Unix秒へ変換し、秒未満を切り捨てる。
変換は64bit中間値で行い、1970年より前、未提供値、変換不能、`os_time_t` の範囲外を検査して回り込みを防ぐ。
UTCへJSTの9時間を加算しない。表示側のローカル時刻化と分ける。
根拠: [Microsoft FILETIME仕様](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ns-minwinbase-filetime)。

現行ABIは時刻の有効性ビットを持たないため、当面hsyncはmtime=0を保守的に「同一判定の根拠に使えない」と扱う。Unix epochそのものと不明を区別したい場合は将来の拡張statで定義する。
Basic/Standard問い合わせ失敗を成功にしない。ホストオープン時のエラーを一律NOTFOUNDに畳まず、実際の不存在とI/O等を区別する。
取得したBasic情報は次の問い合わせで共有バッファが上書きされる前に値として退避する。

`atime` と `ctime` は同期の同一判定に使わない。`ctime` は作成時刻ではなくinodeの状態変更時刻であり、Windows `CreationTime` をそのまま入れない。各FSで取得できる値と意味を定義する。

### 5.2 保存

**内容確認だけならKAPI変更は不要**。mtimeをコピー先に保存する段階で、仮称 `sys_set_mtime(path, mtime)` とVFSの任意実装フックを追加する。

- 時刻欄が既にあるので、`OS32_Stat` を拡大することは初期案の必須ではない。
- KAPIは `sdk/kapi.json` 末尾に追加し、版は実装時に [KAPI_SPEC](../../KAPI_SPEC.md) と調停する。現段階で番号を予約しない。
- ext2のみ先行実装し、非対応FSはNOSYSを返す。読取専用・不正時刻・パス／ポインタ不正は明示エラー。
- データを書き終えてからコピー元mtimeを設定し、宛先ctimeはゲスト側の変更時刻にする。H2のrenameもctimeを変更し得るため、適用順を固定する。
- 内容が同じで時刻だけ違えばファイル本体は書き直さずmtimeだけ更新する。
- 元のmtimeが不明なら時刻保存を省略したことを表示し、内容同期は続行する。有効時刻の保存を試みて失敗した場合は `metadata_failed` と非ゼロ終了。内容コピー成功だけで全成功と表示しない。
- 全生成ファイルへのABI影響確認、clean rebuild、CPL=3からのポインタ検証を含む。[ABI1]〜[ABI3]を適用する。

## 6. コピー途中の失敗から元ファイルを守る

CRCやmtimeとは別に必要な優先改善。目標は**新内容の書き込み・検証が済むまで旧宛先を残す**こと。

1. 同一ディレクトリ内に、一意かつ保護対象でない一時ファイルを排他的に新規作成する。
2. short writeは残りを進め、0バイト進捗・負値は失敗にする。read/write長と総量を検査する。
3. 書込完了 → sync → 再オープン → 長さ・CRC検証。失敗したら旧宛先は触らず、その実行が所有する一時ファイルだけを片づける。
4. 元ファイルが読み取り中に変化していないかを確認する。
5. 宛先の型・保護対象・比較時からの変化を再確認し、検証済みファイルを置換する。
6. mtime・管理記録を確定しsync。最後まで確認できたものだけを完了に数える。

**実装前提と保証の限界**

- 現行openに排他的作成の契約がないため、`O_EXCL` 相当または専用の安全な一時作成口が必要。statしてから固定名をO_TRUNCで開く方式は不可。
- 現行ext2 renameは宛先unlink後に追加する。renameの失敗で旧宛先を失わないよう、置換処理とエラー伝播を先に整備する。既存の `ext2_sync()` 戻り値の扱いも確認する。
- 通常I/O失敗時の旧ファイル維持と、電源断時の整合性は別の受入項目。後者はジャーナル／復旧記録／書込順序と永続化の契約が必要で、renameの名前だけで「原子的」と表現しない。
- 当面は同時hsync・同期中のビルド／make deploy・対象への別書込みを禁止する運用契約。HostDrvはreadチャンクごとにパスを再オープンし、VFSはopen時サイズを保持するため、FDを持つだけではスナップショットにならない。
- 前後のサイズ・mtime検査は通常の変更検出には有効だが、同サイズ・同時刻へ戻る変更を保証して捕捉できない。厳密な一貫性にはH4の不変な配備元を使う。
- hardlink先を置換すると他のリンクは旧内容に残る。初期H2では宛先 `st_nlink > 1` は競合として拒否し、別名まで更新する仕様を暗黙導入しない。
- 異なるFSをまたぐ置換、実行中の本体を含む複数ファイルの一括原子更新は別課題。一時ファイル方式には最大更新ファイル分の追加空き容量が要る。

## 7. その他の改善

### 7.1 配備マニフェストと世代の確認

古い `/host` からNHDへ戻してしまう問題は、CRCでもmtimeでも単独では解決しない。内容の違いは判定できても、どちらが意図した版かは分からない。

H4でホストの最終配備物から、形式版、build ID、dirtyの有無、対象パス、サイズ、CRC-32、mtimeを持つマニフェストを生成する。CRCを文字列保存するなら8桁固定など符号化を定義する。必要に応じSHA-256を追加する。
build IDはGit SHAだけでなく、未コミット差分・ビルド設定・生成物を識別する。日時やSHAの大小で新旧を決めない。

- ファイルの配備が全成功した後だけマニフェストを公開する。ホスト側ツールが失敗を握り潰して成功マニフェストを書く経路を禁止する。
- 同期中に中身が動かない世代別ディレクトリを用意するのが本命。マニフェストだけ最後に更新しても、同じディレクトリへ並行上書きすれば一貫性は得られない。
- `--expect-build` 不一致は変更前に拒否。既定では検出した世代を表示する。意図したロールバックは明示した旧IDへの同期として扱う。
- マニフェストは全件を先に検査し、重複パス、絶対パス／`..`、サイズ超過、不明形式、不完全な世代を拒否。既存のDB保護と範囲規則より優先しない。
- コピー元の期待CRCがあればゲストのコピー元CRC走査を削減できる。ただし宛先が同じだという証明には宛先の内容確認が必要。
- CRCキャッシュをサイズ＋mtimeだけで再利用すると同じ欠陥が戻る。初期実装では永続CRCキャッシュを作らない。
- 同期途中に失敗した世代は「全体適用済み」にしない。ファイル単位の成功一覧と失敗一覧を残す。kernel・shlib・apps一式を原子的に切り替える保証は別設計。

### 7.2 結果と適用状態

集計を `copied / unchanged / excluded / protected / metadata_updated / errors` に分け、失敗時は非ゼロ終了。
詳細理由は `size_changed / content_changed / forced / verify_failed / source_changed / type_conflict` 等を固定し、テスターが文字列の雰囲気で判定しないようにする。
例: `UPDATE /sys/lib/libos32gui.shlib reason=content_changed size=113752`。

`/sys` の既定除外は先頭で明示する。`hsync -f` でも除外は解除しない。
更新した対象に応じて「ディスク同期済み、再起動／シェル再起動が必要」を表示する。shlibは起動時ロード、カーネルはブート時ロードであり、hsync成功を稼働版の切替完了と扱わない。
再起動は自動実行せず、[08_build.md の配備経路](../../08_build.md#配備3経路)に従う。

### 7.3 管理対象・削除・列挙

- 将来のmanifest同期は配備管理対象に絞り、利用者がゲスト内で変更したファイルは前回適用時の内容と照合して競合表示する。初期版は既存の一方向更新を維持。
- `--delete` は初期実装に含めない。廃止バイナリの削除は既存deploy定義・pruneとの責務を整理し、管理下のパスだけを対象に別設計する。
- 128件・名前長・深さの制限は継続して明示エラー。将来は列挙カーソル等で分割処理し、スタック上の配列を単純拡大しない。
- `sys_ls` のコールバック内ではFSを呼ばず、列挙結果を私有バッファへ取ってから比較する。新しいCRC計算のために再入させない。
- 無関係な一時ファイル、設定DBの復旧用ファイルを再開処理で削除しない。

## 10. 実装前に確定する点

推奨は既定バイト比較・コピーCRC検証・mtime保存の順で、日時だけの高速スキップは初期版に入れない。
残る設計判断は、(1) H2の電源断復旧をどこまで保証するか、(2) 時刻有効性を将来のstat拡張へいつ載せるか、(3) manifestと世代ディレクトリの形式・保存先、(4) CRCコアの共通ビルド配置と測定後の表サイズ。
これらが未確定でもH1の同サイズ比較の実装範囲は切り出せる。
