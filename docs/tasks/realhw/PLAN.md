## 2. ディスク — 8GB は未知の領域

**確かめた事実**: `drivers/ide.c` は **CHS 専用**。`IDENTIFY` で `cylinders` /
`heads` / `sectors` を受け取り (`ide.c:197-199`)、LBA は `dev_blk_read_lba` が
CHS へ変換する。**CHS の上限がそのまま容量の上限になる。**

**現在の作業イメージは 200MB** (`build/nhd/os32.nhd`)。8GB は **40 倍**で、
**試したことがない。**

**確かめていないこと**:

- ATA の `IDENTIFY` が返す幾何の上限 (シリンダ 65,535 / ヘッド 16 / セクタ 63) は
  計算上 32GB 相当まで表現できるが、**実際に効くのは PC-98 の BIOS 側の制限**で、
  機種と設定で変わる。**測らないと分からない。**
- **起動パーティションの位置**。PC-98 の IDE BIOS は起動領域が特定の容量内にあることを
  要求することがある。**先頭に小さく切れば回避できる可能性が高い** (未検証)。

**2026-09-23 着手**: 票 [`TASK_HDD_INSTALL.md`](../../archive/realhw_v21/TASK_HDD_INSTALL.md) (幾何の食い違い F4 を含む)。

**やること (この順)**:

1. ディスクの健全性を確かめる (ユーザー)。
2. **先頭に小さい区画を切って**起動できるかを見る。8GB 全体を使うのは後。
3. `IDENTIFY` が実機で何を返すかを記録する。**まずそこから。**

## 3. 媒体 — フロッピーから起動して CD から入れる

**確かめた事実**:

| 媒体 | 実装 |
|---|---|
| FD **1.2MB** (2HD、77cyl × 2head × 8sect × 1024B) | **対応済み**。既定はこちら |
| FD **1.44MB** (80cyl × 2head × 18sect × 512B) | **エミュレータで対応済み** (2026-09-18)。`make fd144` → `images/os32_boot144.img`。実機は未検証 → [`TASK_FD144.md`](TASK_FD144.md) |
| FD 起動 **実機** | **2026-09-22 に合格** (1.2MB)。原因は 3 つ (シーク時間のタイムアウト / `0439h` bit2 の DMA 1MB 制限 / FRY) → [`TASK_FDC_REALHW.md`](../../archive/realhw_v21/TASK_FDC_REALHW.md) |
| CD | **対応済み**。`userland/system/cdinst.c`、`make iso`、`fs/iso9660.c` |
| IDE | 対応済み (§2 の上限つき) |

### 1.44MB — **「足さない」を覆した** (ユーザー指示、2026-09-18)

この節は以前「**1.44MB は足さない。** 1.2MB が使えるなら要らない」と書いていた。
**覆った理由は実機へ運ぶ手段**で、1.2MB (1024B/セクタ) は**現代の PC で書けない**。

やったこと・踏んだ罠・残件は [`TASK_FD144.md`](TASK_FD144.md)。要点だけ:

- 既定は **2HD のまま**。`-g 144` / `-DFD144` / `make fd144` で明示的に選ぶ
- 形式は **生イメージ**。D88 の 1.44MB は `fd_type=0x21` + 全セクタ `rpm_flg=1` が要り、
  `tools/mkd88.py` がまだ書けない (**実機へ D88 で渡すなら残件**)
- **エミュレータでは起動してファイルが md5 一致**。`04BEh` の 3 モード切り替えも実装済み
- **実機で 1.44MB 起動に対応する機種は資料で特定できなかった**

**段取り**: フロッピーから起動し、本体は CD から入れる。
フロッピーはブートローダだけなら容量が足り、**どちらも既に実装がある。**

## 4. 通信 — ここに一番大きい穴がある

> **2026-09-23**: 実機でのファイル更新は票 [`TASK_SERIAL_HOSTFS.md`](../../archive/realhw_v21/TASK_SERIAL_HOSTFS.md) (SerialFS の復活 + カーネルの 2 ファイル化・高圧縮)。

**ゲスト側は問題ない。** リモートシェル (`userland/shell/rshell.c`) は
**シリアル前提で既に動いている** (uPD8251A、IRQ4)。

### 速度 — **38400bps は実機では出ていなかった** (2026-09-18 に発覚・修正)

速度は 8253 TCU カウンタ#2 の**整数分周**で決まるので、割り切れない値は必ずずれる。
`serial_init` は 1.9968MHz 決め打ちで切り捨てていたため、**`SYS_SERIAL_BAUD` が
38400 のとき実際は 41600bps (+8.3%)** — UART の許容を超える。
**NP21/W は通信速度を模擬していないので通っていただけ。**

直したこと:

- **クロックを `0000:0501h` bit 7 から判定** (1 = 8MHz系 → 1.9968MHz / 0 = 5/10MHz系 → 2.4576MHz)
- 分周比が割り切れなければ **`[ser] WARN ... 実効 Nbps` を出す** ([V4])
- **既定を 9600 に戻した** — 1.9968MHz と 2.4576MHz の**どちらでもちょうど出る唯一の標準速度**
- `serial` コマンドで速度を指定できる (`serial 38400`)
- `I/O 0434h` の 4 分周 (19200bps 対応機の 4 倍速) は **API だけ用意して自動では触らない** —
  **極性が機種依存で資料に異論が併記**されており、bit0 が「ポート切り離し」で危ないため

**実機の実測 (2026-09-22)**: Ra266 は 2.4576MHz 系 (`count 16` で 9600)。`serial 38400` (count 4) で `ver` が返る。

### 115200bps への道 — ウェブ情報と UNDOCUMENTED の突き合わせ (2026-09-22)

ウェブの記述「Ra266 の標準 RS-232C は最大 115,200bps。16550 互換 UART で 9600/19200 の上限は無い」を
`docs/hw/undocumented/io_rs.md` と NP21/W のソースで検証した。

| 主張 | 資料 | 判定 |
|---|---|---|
| 最大 115200bps | **V･FAST モード** (`013Ah` bit7=1、bit3-0 = 分周: 0001b=115200 / 0010b=57600 / 0011b=38400 / 0110b=19200 / 1100b=9600)。8253 カウンタ#2 と無関係に速度が決まる。対象は「2nd CCU (16550) を持つ機種」と「**95 年 5 月以降発表の機種** (統合 I/O チップに 16550 相当を内蔵)」 | **正しい**。Ra266 (1996) は後者 |
| 16550 互換 UART | 図「RS-232C クロック」では **1st CCU は 8251 のまま**で、16550 は 2nd CCU (赤外線等) 側。プライマリは **FIFO モード** (`0138h` bit0=1、データ `0130h`、ラインステータス `0132h` (TxRDY bit1 / RxRDY bit2)、モデムステータス `0134h`、割り込み参照 `0136h`、16 バイト) という **16550 風の別のアクセス方法**を持つ (An 一部ロット・Np 以降) | **半分正しい**。機構は「8251 + FIFO 前段 + V･FAST クロック」であって 16550 そのものではない。従来互換モードでは 8251 のまま |
| 9600/19200 の上限が無い | 8253 経路では 2.4576MHz で 9600/19200/38400 が整数。それ以上は V･FAST が要る | **正しい** (V･FAST 前提) |

NP21/W は `io/serial.c` で `013Ah` (V-FAST の速度表 `{0,115200,57600,38400,28800,0,19200,0,14400,0,0,0,9600,...}` = 資料と一致) と
`0130h/0132h/0134h/0136h/0138h` を実装している。ただし通信速度そのものは模擬しない (§4-49) ので、**レジスタの手順はエミュレータで、速度は実機で**確かめる。

**実装の段取り** → 票 [`TASK_SERIAL_VFAST.md`](../../archive/realhw_v21/TASK_SERIAL_VFAST.md) (2026-09-22 着手、ユーザー決裁「ここの改善が開発のきも」):
1. `0136h` bit6 が読むたびに反転するかで FIFO 搭載を判定 (資料の判定法)。
2. `0138h` bit0=1 で FIFO モード、データは `0130h`、TxRDY/RxRDY は `0132h`。
3. `013Ah` = 0x80 | 分周 (115200 なら 0x81)。互換モードに戻すときは bit7=0 で 8253 経路へ。
4. **先に `serial_putchar` の送信ループを直す** — いまは TxRDY を 100 回見て `hlt` で 10ms tick を待つので、
   9600 で 490 B/s、38400 で 233 B/s と回線より遅い (TASK_FDC_REALHW §9-1)。115200 でも同じ壁に当たる。

**実機で速くしたいときの手順**: まず 9600 で通す → `serial_get_ext_ctrl()` で 0434h を読む
→ `serial_set_div4()` の向きを実測で決める。表と根拠は `drivers/serial.h`、
経緯は [`../../POLICY_DEBUG.md`](../../POLICY_DEBUG.md) §4-49 / §4-50。

**穴はホスト側。** 今の道具は**すべて NP21/W の HTTP デバッグ API を叩いている**。
**実際のシリアルポートを話す実装が無い。** → **2026-09-22 に `tools/rshell_serial.py` を追加** (Windows 側 Python + pyserial、`--port COM3 cmd <line>` / `repl`。rshell の 1 行 + `\n` → EOT 0x04 の約束を NP21/W の `/api/cmd` と同じに話す)。実機 Ra266 で `ver` / `ls` が返ることを確認。ランナーへの組み込みは未着手。

影響するもの:

- `.claude/skills/run-os32/driver.py` (実行スキル)
- `tools/guest_tests.py` (試験ランナー)
- `tools/np21w_mcp/` (レジスタ・メモリ・逆アセンブル)
- `tools/emu_agent/` (ローカル AI のテスター)

**ただし直すのは難しくない。** ランナーは**「ゲストを叩く部分」と「生成・集計する部分」を
意図的に分けてある** ([`../../archive/test/TASK_TEST_RUNNER.md`](../../archive/test/TASK_TEST_RUNNER.md) §2-2、受入 R7)。
叩く側を差し替えられる形なので、**シリアル版を 1 つ書けば集計側はそのまま使える。**

`tools/np21w_mcp/` の**メモリ・レジスタ系は実機では使えない** (エミュレータの
デバッグ機能に依存)。実機では `kselftest` のカウンタも読めないので、
**自己診断の結果を画面かシリアルに出す口が別途要る。**

## 5. LAN — **オンボードの Intel 82557 を狙う** (ユーザー決裁 2026-09-17)

> **2026-09-22 着手**: 票 [`TASK_LAN_82557.md`](TASK_LAN_82557.md) (段取り L-A〜L-E、決裁待ち §3)。Intel の SDM は `docs/hw/intel/`。

当初は「C バスに LGY-98 を挿すのが最短」としていたが、**取り下げる**。

### 決め直した理由

| | LGY-98 | **Intel 82557 (オンボード)** |
|---|---|---|
| 入手 | **高い。品薄** (2026-09 時点、ユーザー) | **機体に載っている。ゼロ円** |
| 技術資料 | `docs/hw/` に記述**なし**。NP21/W の解析記事に依存 ([`../network/PLAN.md`](../network/PLAN.md) の「ローカル資料の所在」) | **Intel の公開開発者マニュアルがある** |
| 参照実装 | PC-98 界隈のみ | **Linux `e100` (旧 `eepro100`)、FreeBSD / OpenBSD `fxp`** |
| エミュレータ | **再現される** | **再現されない** (下記) |

**資料と参照実装の差が決定的。** LGY-98 は一次資料が無く、エミュレータの解析ページを
頼りにしている。82557 は**一次資料と複数の実装が読める**。移植性調査の材料としても質が違う。

### 検証はエミュレータで取れない (確認済み、2026-09-17)

**NP21/W は PCI を一切再現しない。** 設定空間の窓 (`0x0CF8`) を扱う実装が無い。
再現している NIC は **LGY-98 だけ** (`src/network/lgy98.h`)。
→ **82557 のドライバは実機でしか動かせない。**

**それでも作る。** v3 の実機段階では**どのみち検証がエミュレータから離れる** —
ディスクの上限も、起動パーティションの位置も、シリアルの実装も、全部実機でしか
確かめられない。**LAN だけをエミュレータで確かめる意味が薄い。**

### §7 の Trident とどう違うか

Trident は「**PEGC が使えるので無くても困らない**」もの。
LAN は「**無いと開発が遅くなる**」もの。実機でしか検証できなくても作る価値がある。
**必要性が違うので、同じ「エミュレータで検証できない」でも結論が変わる。**

### LGY-98 のドライバは**消さない**

エミュレータで回帰が取れる唯一の LAN 経路なので、**そのまま残して回帰に使い続ける。**
[`../network/PLAN.md`](../network/PLAN.md) のリンク層 (`net/link.c`) は
**NIC の上に載っている**ので、82557 を足しても共通部分は動く。

| 層 | LGY-98 | 82557 |
|---|---|---|
| リンク層以上 (`net/link.c`、Host Services) | **共通** | **共通** |
| NIC ドライバ | 既存 (エミュレータで回帰) | 新規 (実機で検証) |

**M4 の宿題は 82557 側へ移る。** `../network/PLAN.md` の M4 に
「NP21/W は受信バッファ溢れを立てず黙って捨てるため、溢れからの復帰経路は
実カードでしか試験できない」とあるが、**実カード = 82557 になる。**
82557 は受信の作りが NE2000 と別 (ディスクリプタ連結) なので、
**同じ宿題を 82557 の言葉で立て直す必要がある。**

## 6. PCI — v3 で土台を作る (ユーザー決裁 2026-09-17)

**確かめた事実**: OS32 に **PCI の列挙は無い**。設定空間を読む仕組みごと未実装。
**NP21/W も再現しない** ので、PCI の土台そのものも**実機でしか確かめられない。**

**82557 は土台の最初の利用者として理想的。** よく文書化され、複数の参照実装があり、
動けば開発が加速する。**土台を作って最初に載せるものとして、これ以上ない題材。**

一度作れば、オンボード LAN も、拡張カードも、内蔵 Trident も**同じ入口から見える**。
個別のカードのためではなく**土台として**位置づける。

ユーザーが `1394US2G-PCI` (I-O DATA、ギガビット LAN + IEEE 1394 + USB 2.0 のコンボ)
を検討中。**3 機能の重さはまったく違う**ので、土台ができても一度には載らない。

| 機能 | 必要なもの | 目安 |
|---|---|---|
| ギガビット LAN | そのチップ専用のドライバ | 大 |
| IEEE 1394 | OHCI 1394 + 上位の転送層 | かなり大 |
| USB 2.0 | EHCI + 下位互換の OHCI/UHCI + 列挙 + クラスドライバ | **最大。単独で 1 つの計画になる規模** |

**まず 82557 を通す。** コンボカードはその後で改めて判断する。

## 7. Trident — 保留 (2026-09-17) → **ユーザー決定で着手 (2026-09-29)**

> **2026-09-29 のユーザー決定**: 「Cirrus はエミュレータ互換のためだけ。実機 (Ra266) は Trident。Trident のドライバが必要なら作成する」。
> 下の「保留」はこれで上書き。調査・設計は [TASK_TRIDENT_DRIVER.md](TASK_TRIDENT_DRIVER.md)。

ユーザーから「実機に合わせて Trident を優先してもよい」という話があったが、**保留**。

**理由**: エミュレータで検証できない。NP21/W のソースに `src/wab/tgui9680.c`
(1,803 行) はあるが、**本体のどこからも呼ばれておらず**、ヘッダ 2 つ
(`tgui9680.h` / `tgui9680_extern.h`) は**中身が 0 バイト**。**書きかけで結線されていない。**
Cirrus は対照的に `cirrus_vga.c` が 247KB あり ini のキーで切り替わり実際に動く。

**書いても動かして確かめられない**ので、「実証はエミュレータで十分」という方針と衝突する。
**PEGC が使えるなら OS32 は実機で動く。** 動かない機種のために先回りしない。

やるなら選択肢は 2 つ。(a) NP21/W 側の `tgui9680.c` を結線する (**OS32 の作業ではない**)、
(b) 実機で検証する前提に切り替える。**どちらも今の方針から外れる。**

**PEGC 自体も実機では 640x480 で桁がずれる** (2026-09-25、GUI を `gfxmode pegc` で起動したとき。pc98 は正しい)。
v3 の票 [TASK_PEGC480_REALHW.md](TASK_PEGC480_REALHW.md) — 480 ラインの SYNC 値がエミュレータ由来なのが最有力、実機の ROM が流す値を V86 で記録して合わせる。

ATAPI の待ち上限はループ回数 (約 1 秒) で、実機のスピンアップや SRST 後の BSY に足りない → [TASK_ATAPI_TIMEOUT.md](../../archive/realhw_v21/TASK_ATAPI_TIMEOUT.md) (秒単位に、SRST は 31 秒)。

## 8. 段取り (案)

| 段 | やること | 前提 | 検証 |
|---|---|---|---|
| 1 | `IDENTIFY` の実測とディスクの健全性確認 | 実機に触れること | 実機 |

延々と確かめることになる。**順序を入れ替えない。**
