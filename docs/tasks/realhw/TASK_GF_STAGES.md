# TASK_GF_STAGES — GeForce の実機の試験を「段ごとの小さなバイナリ + 共通部分」に分ける

> 上位: [実機の票の索引](PLAN.md)

> 状態: **計画 (2026-10-29)** — 反省会 (2026-10-29、GeForce 4c の映像を目視した日) のユーザーの提案を、設計の往復の前に書き留めた。次は設計票 (astra 起草・Opus レビュー)。迷う所はユーザーが決める。

## 0. ユーザーの提案と決定 (2026-10-29 の反省会)

- 提案 (原文): 「テストコマンドがテストの粒度ごとに分離していないので巨大なテストソースが出来上がっていません？ テスト用の実実行と読み取り部分のシンプルなソースとテストの段だけのソースに分離したほうが良かったのではないでしょうか？ テストコードの肥大化を感じます。テスト段ごとにバイナリをわけて、共通部分をインクルードする形のほうがスマートな実装なのではないでしょうか？」
- 反省会の案 3 (C だけを再開できる入口) を選んだ — この分け方なら自然に満たせる。
- 「一度この案をドキュメント化してから次の一手へ順に。astra は過剰に強固に作りたがるので考慮する。迷った場合はユーザーが判断する」。
- 位置づけ: 2026-10-28 の決定 3 (「最初の映像までは今の枠組み、その後は nouveau の load_state に近い簡素な作り」) の後半。2026-10-29 に映像が出たので、その切り替えの時。

## 1. 今の形と、困ったこと (2026-10-29 の数字)

- 製品: GeForce と戻す処理のまわりで手書き約 7,700 行 (`kdebug/recover.c` 2,423 行ほか) + 生成された表約 1,500 行。`kdebug.bin` 128KB・`hwdev.mod` 118KB に A1・A2・main 0〜4・C・VPLL の調べ・戻す処理が全部入る。
- 試験: ホスト試験の C と Python で 8,526 行 — 製品より多い。
- 段は汎用の「計画の実行器」(計画のノード・予算・CRC・hash・monitor との約束、確定設計 REALHW_RECOVER) に渡すデータ。1 つの段を直すと計画の全体 (hash・行数・予算) が変わり、試験は全体を固定しているので毎回波及した — 2026-10-29 は照合の直し 3 回のたびに試験の固定値を直し、取り込みでは GeForce と無関係の依存方向の試験 6 本 (HWDEV の契約の CRC の固定) と変異の目印 2 本まで落ちた。
- C だけを再開できない: 段が 1 つの計画とセッションに束ねられ、C の失敗で A2 と main 0〜4 (約 15 分) からやり直し。1 回の試行は版の入れ直しを含めて約 30 分、実機の前の時間の大半が待ちになった。

## 2. 目指す形 (案 — 設計の往復で決める)

- **共通部分** (各段が include する小さなソース、数百行の見込み): GeForce のレジスタの読み書き (BAR の上の MMIO・VGA の index)、記録の行の出力 (REC)、98 の画面へ戻す処理 (S0: 0FACh を 98 へ・PBUS/PMC を止める)。
- **段ごとの小さなバイナリ**: A1 (BAR の大きさ)、初期化 (今の A2 + main 0〜4)、C (画面モード)、戻し、調べ (VPLL などの読取り)。各段は「何をどの順で書くか」の列と、その段の必須の確かめだけを持つ。1 本 500 行程度まで (terra に出せる大きさ、POLICY_DEV §2)。
- **段の間の受け渡し**: 保存した値とどこまで済んだかの小さな状態を 1 つ (置き場は設計で決める — kdebug の中の構造体が素直)。C は「初期化が済んでいる」ことを確かめてから走り、失敗しても初期化からやり直さずに C だけを直して流し直せる。
- **試験も段ごと**: 共通部分の試験と各段の試験を分け、ある段を直してもほかの段の試験・無関係の試験が動かないようにする。全体の hash・行数を 1 か所で固定する試験は作らない。
- **照合の 2 段** (§3 の 1): 実機の初回は記録だけ、必須の確かめは設計で列挙したものだけ。外すものは実行時に渡す (2026-10-29 に `gfinit prepare --mode-c --verify required` / `--no-verify-file` として入れた形を引き継ぐ)。
- **今の実行器の扱い**: すぐには消さない。新しい形で実機の C が通るまで凍結し、そのあと縮める (消す範囲は別の段)。
- **本番の画面ドライバ** (nouveau の load_state に近い簡素な作り) も同じ共通部分の上に載せる。

## 3. 反省会の決定 (2026-10-29、ほかの実機の試験にも当てる)

1. **実機の初回は記録だけで流す** — 食い違いを 1 回で洗い出してから照合を締める。設計の段階でこの 2 段を決める (手本が書くだけのレジスタは読み返せるとは限らない、POLICY_DEBUG §4-63)。
2. **外す・変えるものは実行時に渡す** (引数かファイル) — ビルドの入れ直しを避ける。
3. **やり直しの単位を小さく** — C だけを再開できる (§2)。
4. **道具の判定の誤りが戻す操作を止めない** — 2026-10-29 は monitor の誤判定が状態のファイルに残って abort まで断り、`gfinit abort` を rshell_serial で直接送った。戻す命令は判定とは別の道で必ず送れること。
5. **台本の判定は道具の側に** — シェルの grep で PAUSED などを判定しない (末尾の空行で誤判定した)。
6. **試験は段ごとに分け、共通部分を include する** (§0 のユーザーの提案)。全体の値の固定を避ける。
7. 検査の結果は出力の OK/NG の行をそのまま貼って報告する (PM の報告の誤りの再発防止)。

## 4. 設計の往復への注意 (ユーザー 2026-10-29)

- astra は過剰に強固に作りたがる。依頼に **行数の上限** (共通部分と各段) と **足さないもの** (新しい防御・権限の分離・汎用の計画の実行器の作り直し・全体の hash の固定・複数の段の同時実行) を先に書く。OS32 は単一利用者・単一タスク・協調切替で、守るのはハードの誤動作とバグに対する頑丈さ (固まらない・壊さない・98 に戻せる) だけ。
- 迷う所 (状態の置き場、今の実行器をどこまで残すか、段の切り方) はユーザーが決める — 3 往復を待たずに、分岐が見えた時点で出す。
- 手本は nouveau (MIT) の modeset と load_state ([HW3])。
