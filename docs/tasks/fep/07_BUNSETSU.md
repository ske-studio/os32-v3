# [P7] 連文節変換 (将来構想・保留)

> 索引: [`00_INDEX.md`](00_INDEX.md)
> 優先度: **低 (当面着手しない)**

[`FEP_FUTURE.md`](FEP_FUTURE.md) 記載の通り、現状は単文節最長一致。連文節は実装コスト/メモリの兼ね合いで保留。
本書では**インターフェースだけ将来拡張可能に**しておく設計指針を示す。

---

## 1. 拡張余地の確保

- [`00_INDEX.md` §1.2](00_INDEX.md#12-状態機械の明確化) の状態列挙 (`IME_ST_*`) に将来 `IME_ST_BUNSETSU` を足せる構造にしておく。
- 文節境界を持つため `IME_State` に将来 `int bunsetsu[8]; int bunsetsu_n;` を追加できる
  余白を意識 (今は追加しない)。
- ← → キー (`KEY_LEFT`/`KEY_RIGHT`) は P1 で候補ページ送りに使うが
  ([`01_UI_CANDIDATE.md` §3](01_UI_CANDIDATE.md))、連文節導入時は「文節境界調整」に転用する想定
  → キーバインドは将来再設計。

---

## 2. アルゴリズム概要 (実装時)

- Viterbi / bi-gram 最適分割。2-gram 連接コストテーブルが必要 (辞書サイズ大幅増)。
- メモリ制約 (MEMSYS5 100KB) との両立が前提条件。連接コストは別 DB ファイルに分離し、
  オンデマンドで bi-gram を引く方式を検討。

---

## 3. 判断

> 実装コストが非常に高く、メモリ制約との兼ね合いもあるため、**当面着手しない。**
> 単文節変換 + 学習辞書 ([`04_DICT_QUALITY.md`](04_DICT_QUALITY.md)) で十分な品質を目指す方針を維持する。
