# P3 — ソースの移動とビルドを通す (現状が正。U10)

> 上位: [TASK_RESTRUCTURE.md](TASK_RESTRUCTURE.md)・[RULES.md](RULES.md) (入口と、どの段も先に読む決まり)

合格は 3 つ: **ビルドが通る** (x86 の `make all`、PowerPC の 6 像)、**生成物が基点と一致** (P2-1。一致しない所は理由を 1 件ずつ)、**起動する** (NP21/W と PowerPC の QEMU)。古い検査は回さない。中のパスは `tools/move_files.py` の置換で変わる分はそのまま入れ、手では直さない。古い workflow (check・build・sep・selfhost-probe) は移動の変更で止め、代わりに P6-0 の最小の workflow (ビルド) と仮の取り込みの判定を入れる。**触ってよい物**: 対応表の行、`.mk`、`.github/workflows/`、一致の道具（`tools/build_compare.py`・`tools/ci/sep_identity.py`）とその専用の試験、`tools/ci/land_gate.py`・`tools/ci_fetch.sh`、`docs/POLICY_CI.md` の例外の行 (下の 9)、[DEFERRED_TESTS](../DEFERRED_TESTS.md) の 1 行。

手順 (枝 `wt/rs-move`。ほかの枝は止める — RULES の 5):

1. 基点が P2-0 のタグである事、動いている枝が無い事を確かめる (`wip/snd-irq10-hwb` は止めたまま残す枝で、数えない)。
2. `data/move_map.json` を `tools/move_files.py` で移す (生成物の作り直しは回さない — `.mk` を直した 3 の後に別に回す。P2-3 で分けた形)。**1 回で全部を試み**、通らない時は置き場ごとに割る (割り方は詰まった所で決める。先に波の表は作らない)。
3. `.mk` を直す: 置き場の変数 (`KERNEL_SRC_DIRS` ほか) と所有者集合。**リンクの順 (`build/sources/order.mk`) と `-I` の順は変えない。**
4. ビルドを通す。直すのはパスと `.mk` だけ — ソースの中身を変えないと通らない所は止めて報告 (RULES の 1・7)。
5. P3 の枝で一致の道具を直す時は別のコミットにし、読み手が差ごとに確認する。修正後は全件を比べ直すことを取り込みの条件とする。PM の機械で P2-1 を使って基点と比べ、候補 SHA・基点 SHA・比較ログ・終了値 0・`SHA256SUMS` と `PRESENCE` それぞれの SHA-256 を取り込み判定に添える。一致しない物は原因を読み、パスの文字列だけなら `Sep-Changes:` に書く。それ以外は直す。
6. 起動: PowerPC は QEMU で 6 像のうち起動する像、PC-98 は NP21/W で ROLES §4-2 の最小受入 ([D1]・[D2] の範囲、pc98emu に頼んでよい)。**P6-0 の CI が作った配布物・媒体そのもの**を入れ、その sha256 と SHA を記録する (手元で組んだ物で代えない)。基点と同じ所まで進む事を画面とログで見る。
7. 文書・スキル・`CLAUDE.md`・`AGENTS.md` の中のパスは `move_files.py` の置換で直る分だけ。残りは P4 の 3 で文書の検査を載せた時に直す。
8. 読み手は、対応表のとおりに動いたか (`git diff -M --stat` の改名の率が 100% でない行)、`.mk` の差、置換の手直しの所、一致しなかった物の理由を読む。
9. `docs/POLICY_CI.md` に、この票の間の例外を書く: G1 (main に入れる SHA に全件) は移動から P6-2 まで外す、R2・R3 (別の workflow で先に動かし並べて比べる) はこの票では使わない (U10)、戻す条件は RULES の 6。CLAUDE.md・ROLES・スキルは G1 を指しているのでこの行で足りる。
10. **main に入れる前に** P0-8 の相手へ知らせる: 相手ごとに変わるパス (ノートの `/opt/os32/tools/…` の複製、pc98emu が呼ぶ道具)、CI の成果物の名前 (`tools/ci_fetch.sh` が読む workflow とジョブと成果物の名前 — 変えるなら同じ変更で `ci_fetch.sh` を直し、相手が取れる事を確かめる)、os32powerpc には止める期間と再開の条件。
11. **A3** (ユーザー: ビルド・一致・起動の結果) → 仮の取り込みの判定 (P6-0) が通った SHA を main へ。

気を付ける所 (P0 で分かっている物):

| 所 | 中身 |
|---|---|
| `include/` → `sys/include/` | **バイト一致にならない** — kdebug.elf と kselftest.o に文字列 `sys/include/memmap.h` が入る (P0-5 の A)。差がこの文字列だけである事を P2-1 で確かめる。公開のヘッダ (`sdk/include`) と混ぜない |
| `arch/`・`platform/` | 固定名 `arch_*.h`・`<platform_*.h>` の `-I`、asm の include、PowerPC の `.mk` (`build/arch/`)、起動の番地のヘッダ、`boot/` からの参照 |
| `drivers/`・`hwdev/` → `sys/dev/` | 部品 (`.mod`) ごとの `.mk` と出力先。GeForce の寄せは D-2 のとおり |
| `kernel/`・`mm/`・`exec/`・`init/` → `sys/kern/` | リンクの順、`sys/kern/init/kernel_start.c` の入口 |
| `kapi/` | 生成物 (`kapi_generated.c`) の置き場。[ABI] は変えない (`sdk/kapi.json` は動かさない) |
| `kdebug/` | D-3 のとおり。生成物 (`kdebug/generated`) |
| HAL の寄せ (`sys/hal/`)・`lib/` の分け | `hal_map.tsv` の「移すだけ」の行だけ。include の向きが変わる物は P8 |
| 置換しきれない形 | P0-5 の `unresolved.tsv` 7,517 行のうち、ビルドが読む物 (`.mk`・生成の道具・配備の道具) だけ手で直す。古い検査の中の行は手で直さない |
| 3 つの合格で見えない壊れ方 | 生成物が変わらない include の向きの違反 (共通 → 装置)、ビルドに登録されていないソース、起動の後でしか出ない回帰 (IRQ10・PCM)。前の 2 つは `P4.md` の 3 で、最後は 4・5 で拾う。それまで main に入れるのはこの票の変更だけ (RULES の 6) |

移動前は `p1_verify.py` で台帳を確認する。移動後は `p3_verify.py` で旧パスの消失・新パスの存在と改名集合を確認する。Git が削除・追加とした行は移動時の差分とパスだけを置換した内容で照合する。

P3 の終わり: 完了の基準 (2)・(6)、A3、main。実機には、その後に CI の成果物を 1 回入れて最小受入 (ROLES §4-2。[D2] と実機は個別の承認)。

**止めた枝への引き継ぎ (U4)**: 移動が main に入ったら、PM が別の作業木で枝 `wip/snd-irq10-hwb` を新しい main に載せ直す (`data/move_map.json` を `tools/move_files.py` で掛け、枝だけが持つ差分が残っている事とビルドが通る事を確かめる)。結果を [DEFERRED_TESTS](../DEFERRED_TESTS.md) の `SND-IRQ10-RA266` の行に書く (入れるのは実装の再開の時)。対応表は P7 で消す前にこの確かめを済ませ、載せ直した枝の名前を台帳に残す。
