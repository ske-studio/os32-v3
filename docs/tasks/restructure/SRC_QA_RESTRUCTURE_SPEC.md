## 1. 目的

OS32のソース管理構造、ビルド管理、依存関係管理および品質保証体制を一体的に再設計する。

BSD系のソース管理思想を参考とするが、BSDへの設計変更を目的とするものではない。OS32独自のカーネル、HAL、KAPIおよびアプリケーション実行モデルは維持する。

本改修の目的は以下とする。

- ソースコードの責任範囲の明確化
- CPU依存・機種依存・デバイス依存実装の分離
- HALの配置および管理体系の統一
- ソース管理とビルド管理の一元化
- ソースの責任範囲と検査の責任範囲の一致
- 検査の重複および不要な検査の削減
- CIの簡素化と合否判定の信頼性向上
- 将来的なアーキテクチャ追加への対応

## 2. 基本原則

### 2.1 ソース管理

ディレクトリは開発の経緯ではなく、実装の責任範囲によって分類する。

カーネル空間で動作するOS本体のソースは原則として `sys/` 以下に集約する。

CPU、機種、デバイスに依存しない実装は共通実装として管理する。

### 2.2 品質保証

検査は開発工程ではなく、保証する仕様および機能によって分類する。

検査の数を維持することを目的とせず、保証する仕様の範囲と強度を維持することを目的とする。

### 2.3 改修範囲

初期段階では機能追加、ABI変更、アルゴリズム変更、性能最適化を行わない。

配置変更と論理的な実装変更は分離する。

ソース配置変更に伴う検査パスの修正は許可するが、検査の期待値、判定条件、保証範囲の変更は別工程とする。

## 3. ディレクトリ構造

### 3.1 ルート構造

- `sys/` — OS本体
- `boot/` — ブートローダー
- `sdk/` — アプリケーション開発環境
- `lib/` — 共通ライブラリ
- `userland/` — 標準ユーザーランド
- `apps/` — アプリケーション
- `tools/` — ビルド・開発・運用支援
- `tests/` — 品質保証用検査
- `docs/` — 仕様・設計・開発文書
- `build/` — ビルド定義・生成物管理
- `assets/` — データ・リソース
- `.github/` — GitHub Actions実行定義

### 3.2 sysディレクトリ

| ディレクトリ | 責任範囲 |
|---|---|
| `sys/kern/` | カーネル共通処理 |
| `sys/hal/` | HAL契約・共通処理 |
| `sys/arch/` | CPUアーキテクチャ固有処理 |
| `sys/platform/` | 機種固有処理 |
| `sys/dev/` | デバイスドライバ |
| `sys/gfx/` | 描画サブシステム |
| `sys/sound/` | 音声サブシステム |
| `sys/input/` | 入力サブシステム |
| `sys/fs/` | ファイルシステム |
| `sys/net/` | ネットワーク |
| `sys/kapi/` | カーネルAPI実装 |
| `sys/include/` | OS内部共通ヘッダ |
| `sys/conf/` | OS構成定義 |

個別ファイルの配置は現行ソースの責任範囲を調査した上で確定する。

## 4. HAL管理方針

HALに属する契約、型定義、共通処理およびディスパッチ処理は `sys/hal/` に配置する。

具体的なハードウェア操作は実装の性質に応じて以下に配置する。

| 種別 | 配置 |
|---|---|
| HAL契約・共通処理 | `sys/hal/` |
| CPU固有バックエンド | `sys/arch/` |
| 機種固有バックエンド | `sys/platform/` |
| デバイス固有バックエンド | `sys/dev/` |

HALを一箇所に集約することと、ハードウェア固有の実装を一箇所に集約することは区別する。

共通サブシステムはHALの公開契約を使用し、原則として具体的な機種固有実装を直接参照しない。

GeForce等のデバイス固有コードについても、現行の分散配置を整理し、責任範囲を明確化する。

## 5. ソース所有権と依存関係

全ソースに以下の所属情報を定義する。

- 共通実装
- CPU固有実装
- 機種固有実装
- デバイス固有実装
- 公開インターフェース
- 開発・検査用実装

ソースの所属情報はビルドとCIで共有する。

CI側に独立したソースパス一覧を持たせない。

依存関係の判定には、ディレクトリ所属、include関係、コンパイル対象、リンク関係および生成物への依存を使用する。

未知の依存関係は検査対象外とせず、保守的に検査範囲を拡大する。

## 6. 検査ディレクトリ構造

検査は原則として `tests/` に集約する。

| 検査ディレクトリ | 対応するソース |
|---|---|
| `tests/kern/` | `sys/kern/` |
| `tests/hal/` | `sys/hal/` |
| `tests/arch/` | `sys/arch/` |
| `tests/platform/` | `sys/platform/` |
| `tests/dev/` | `sys/dev/` |
| `tests/gfx/` | `sys/gfx/` |
| `tests/sound/` | `sys/sound/` |
| `tests/input/` | `sys/input/` |
| `tests/fs/` | `sys/fs/` |
| `tests/net/` | `sys/net/` |
| `tests/kapi/` | `sys/kapi/` |
| `tests/boot/` | `boot/` |
| `tests/lib/` | `lib/` |
| `tests/sdk/` | `sdk/` |
| `tests/userland/` | `userland/` |
| `tests/tools/` | `tools/` |
| `tests/integration/` | 複数サブシステムの結合 |
| `tests/system/` | OS全体・ゲスト・実機 |
| `tests/infra/` | 検査実行基盤 |
| `tests/support/` | 共通ハーネス・fixture |

検査用の共通実装と、製品の動作を保証する検査本体は分離する。

現行の `tools/checks/`、`tools/tests/`、`tools/accept/` に存在する検査については、責任範囲を調査して移行する。

製品の運用に使用するツールは `tools/` に残す。

## 7. 検査分類

検査対象の分類と検査方式の分類を独立させる。

| ID | 分類 | 保証対象 |
|---|---|---|
| L0 | 静的検査 | 配置、依存方向、規約、禁止命令 |
| L1 | ビルド検査 | コンパイル、リンク、ABI、成果物 |
| L2 | 単体検査 | 実際の関数・モジュール |
| L3 | 結合検査 | モジュール間の契約 |
| L4 | システム検査 | OS起動、アプリケーション動作 |
| L5 | 実機検査 | 物理デバイス、性能、タイミング |
| M | 検査品質検査 | ミューテーション、検査基盤 |

L0〜L5は検査の実行優先順位を意味しない。

ミューテーションテストは製品検査とは独立した検査品質検査として扱う。

## 8. 検査登録

全検査を単一の登録体系で管理する。

現行のCHECK宣言は活用するが、必要に応じて項目を再設計する。

登録情報は以下を含む。

- 一意の検査ID
- 保証する仕様ID
- 所属サブシステム
- 検査分類
- 対象ソース
- 必要な実行環境
- 対応アーキテクチャ
- 前提となる生成物
- 合否判定条件
- 検査の限界
- 必須となる関門
- 実行時間の計測記録
- ミューテーション検査との対応

GitHub ActionsのYAMLに検査名を個別列挙しない。

検査の選択、実行計画、実行結果の集計は統一された入口から行う。

## 9. 検査の棚卸し

既存検査について、以下の分類を行う。

| 分類 | 意味 |
|---|---|
| 維持 | 現行の保証が必要 |
| 移動 | 配置のみ変更 |
| 統合 | 他の検査と保証内容が重複 |
| 分割 | 異なる責任範囲を同時に検査 |
| 再実装 | 検査方式または判定条件に問題 |
| 診断化 | 品質関門ではなく調査用途 |
| 廃止候補 | 保証対象の消滅または完全な重複 |
| 新設候補 | 現行仕様に対する保証が不足 |

検査名ではなく、個々の判定条件を比較して重複を判断する。

開発工程名を持つ検査については、製品機能単位への再分類を行う。

模型のみを検査する試験は、実装との一致を保証できるか確認する。

コンパイル成功のみを確認する検査は、動作検査として数えない。

検査の削除、軽量化、実行頻度変更については、失われる保証を明記した上で承認を得る。

## 10. アーキテクチャ共通検査

共通仕様に対する検査は、原則として共通の判定条件を使用する。

CPUおよび機種によって異なる処理は、実行バックエンドによって吸収する。

PC-98とPowerPCの双方で提供するKAPI、ファイルシステム、HAL等は、共通契約に対する検査を優先する。

CPU固有ABI、割り込み、MMU、物理デバイス等は固有検査として扱う。

エミュレータで保証できない項目は実機検査として明示する。

PC-98の自動起動・システム検査の不足については別途対応方法を検討する。

## 11. CI実行体制

GitHub Actionsは品質保証処理の実行環境として扱い、品質保証の判定ロジックを持たせない。

CIは以下の独立した処理を実行する。

- 静的検査
- ビルド・生成物検査
- 単体・結合検査
- アーキテクチャ別システム検査
- 検査品質検査
- 結果集計・取り込み判定

配布物の生成は検査の完了を待たずに実行できるものとする。ただし未検査の生成物は合格済み生成物と区別する。

ローカル環境とCIは同じ検査実行入口を使用する。

検査実行環境の構築、依存ツールの導入、キャッシュ管理は共通化する。

## 12. 検査選択方針

変更されたソースの所属および依存関係から必要な検査を選択する。

変更影響の判定には、変更前後のパス、追加、削除、移動、ヘッダ依存および生成物依存を含める。

以下の場合は関連する検査範囲を拡大する。

- 共通カーネルの変更
- HAL契約の変更
- KAPI・ABIの変更
- ビルド構成の変更
- 検査基盤の変更
- 影響範囲を確定できない変更

全検査を毎回実行する現行方式については再検討対象とする。

ただし新しい選択方式の妥当性が確認されるまでは現行の必須検査を維持する。

## 13. ミューテーションテスト

ミューテーションテストは検査の異常検出能力を保証するために使用する。

通常の製品検査とは実行管理を分離する。

以下を再設計の対象とする。

- 変異の重複
- 変異の有効性
- 変異実行時間
- 同一契約に対する変異の過剰追加
- 検査変更時の再評価条件
- 対象実装変更時の再評価条件
- 全体的な検査品質の確認条件

変異を実行しない通常検査と、変異済みの検査品質保証を区別する。

具体的な実行頻度および必須関門は棚卸し結果に基づき決定する。

## 14. 合否判定

| 状態 | 意味 |
|---|---|
| PASS | 実行して合格 |
| FAIL | 実行して不合格 |
| ERROR | 実行環境または検査基盤の異常 |
| NOT_RUN | 必要な検査が未実行 |
| NOT_APPLICABLE | 対象外 |
| DEFERRED | 承認済みの延期 |
| REUSED | 条件を満たす既存合格結果の再利用 |

ERROR、NOT_RUNをPASSとして扱わない。

SKIPという曖昧な成功状態は廃止する。

対象外と延期を明確に区別する。

再利用は対象コミット、検査条件、実行環境、必要な生成物および検査結果の一致を確認する。

必須検査の未実行、失敗、環境異常が存在する場合は取り込みを許可しない。承認済み延期については個別に定めた取り込み条件に従う。

## 15. ソース構造の保証

以下の検査を構造管理の基本関門とする。

- ソース所属の検査
- 不正なディレクトリ配置の検査
- include依存方向の検査
- リンク依存関係の検査
- 機種独立性の検査
- HAL契約の検査
- ソース登録漏れの検査
- 検査登録漏れの検査
- 生成物の再現性検査
- 配置変更時の生成物同一性検査

重複実装については機械的な候補抽出を行うが、自動判定だけで削除・共通化しない。

## 16. 成果物管理

成果物の状態を以下のように区別する。

| 状態 | 意味 |
|---|---|
| BUILT | ビルド成功・品質保証未完了 |
| VERIFIED | 必須CI検査の合格 |
| ACCEPTED | 必要なゲスト・実機受入の完了 |

実機調査用にBUILT状態の生成物を使用することは許可する。

正式な取り込み・配布の条件は対象成果物と検査結果を対応付けて管理する。

## 17. 移行工程

### Phase 0 — 現状調査

全ソース、ビルド定義、検査、仕様および依存関係を棚卸しする。

現行CIの実行時間、検査総数、変異数、SKIP、失敗履歴を記録する。

### Phase 1 — 統合構造設計

新しいディレクトリ構造とソース所有権を確定する。

検査の配置と分類を決定し、旧配置から新配置への対応表を作成する。

### Phase 2 — 移行用検査基盤

生成物比較、ソース所属検査、依存関係検査を整備する。

現行CIは維持する。

### Phase 3 — ソースの機械的移行

ファイル移動、includeパス、Makefile、ビルド登録、CI参照パスを修正する。

CPU階層、HAL、デバイス固有実装の配置を統一する。

製品の論理的な動作は変更しない。

### Phase 4 — 検査の機械的移行

既存検査を新しいディレクトリ構造に配置する。

検査ID、期待値、判定条件は原則として維持する。

### Phase 5 — 検査内容の再編

重複検査、工程別検査、模型検査、変異検査を棚卸しする。

保証範囲を比較した上で統合、分割、再実装、廃止を行う。

### Phase 6 — CI再構築

検査の実行入口、選択方式、実行環境、並列実行、合否判定を統一する。

旧CIと新CIを並行運用して結果を比較する。

### Phase 7 — 切り替え

保証範囲、実行結果および移行完了条件を確認する。

承認後、旧CI、旧登録体系および不要になった移行用コードを撤去する。

### Phase 8 — 論理的な責務分離

機械的移行によって解決できなかったHAL、カーネル、機種固有実装の責務分離を実施する。

この段階は配置変更とは別の設計・実装案件として扱う。

## 18. 完了条件

- 全ソースの所属が確定している。
- HALの契約および実装の配置が統一されている。
- CPU・機種・デバイス固有処理の責任範囲が明確である。
- ビルドとCIがソース所属情報を共有している。
- 全必須検査の保証対象が明確である。
- 未実行の必須検査が成功として扱われない。
- 共通契約と機種固有契約の検査が区別されている。
- 検査の実行入口が統一されている。
- 新旧検査の保証範囲の差が説明可能である。
- 配置変更による意図しない動作変更がない。
- 旧構造および旧CIの不要な実装が撤去されている。
- CIの実行時間と検査コストの改修前後比較が記録されている。

## 19. 未決事項

- 個別ソースの最終配置
- 個別検査の統廃合
- ミューテーションテストの必須実行条件
- CIの変更影響別実行条件
- PC-98システム検査の自動化方式
- セルフホストRunnerの利用範囲
- CIの目標実行時間
- GitHub上の取り込み制御方式

以上については棚卸し結果を根拠として決定する。
