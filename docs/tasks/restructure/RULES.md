# 全体の決まりと依頼の型 (どの段の依頼にも写す)

> 索引: 全部の段が上位として指す決まり (段のファイルは `> 上位:` でここを指す)
> 上位: [TASK_RESTRUCTURE.md](TASK_RESTRUCTURE.md)

## 決まり

1. **1 段で変えるのは 1 種類。** 置き場の移動と中身の変更を同じコミットに入れない (仕様 §2.3)。移動の段で中身を直したくなったら止めて、P8 の候補の表 ([P8.md](P8.md)) に 1 行足す。
2. **移動の合格はビルド・生成物の一致・起動 (U10)。** カーネル・部品・ユーザーランドのバイトが基点 (タグ `v3-pre-restructure`) と同じ (P2-1 の道具)。一致しない理由が正しい時だけ `Sep-Changes:` をコミットの本文に書き ([sep_identity.md](../../design/tools/ci/sep_identity.md))、読み手が差を 1 件ずつ読む。古い検査は回さないので、起動は NP21/W と PowerPC の QEMU で見る。
3. **古い検査は移さない・直さない、新しい検査は設計から書く (U9・U10)。** 古い検査 (今の登録の全部) は移動から回さず、中のパスも直さず、P7 で消す ([P5.md](P5.md))。新しい検査は `tests/` に、要る所から足す ([P4.md](P4.md) の「満たす事」と「足す順」)。
4. **一覧は手で書かない。** 棚卸しの表・対応表の初版・数は道具が出す。人 (エージェント) が書くのは判断の列と理由だけ。移行時の採取方法は SHA `64aff86c9` に記録する。
5. **ほかの枝は A7 まで止める (U6、決定済み)。** 移動の枝は `wt/rs-move` の 1 本。移動の後も、機能の実装の再開 (A7) までは本線・os32powerpc の枝を動かさない (この票の枝だけ)。再開の時に新しい置き場へ載せ直す。
6. **関門 (U10)。** 移動の前までは今の CI の全部の success (`tools/ci/land_gate.py`)。移動の枝と、その後 P6-2 までは「ビルドが通る・生成物の一致・起動」(POLICY_CI G1 の「main に入れる SHA に全件」を一時的に外す。この間 main に入れるのはこの票の変更だけ)。この間の取り込みは P6-0 の仮の判定 (ビルドと一致の success + 起動の記録) を通った SHA だけ。P6-2・P6-3 からは新しい CI の全部の success。
7. **止まる所。** 対応表に無いファイルを動かす必要が出た・生成物が一致しない原因が 30 分で分からない・ソースの中身を変えないと組めない・[C1]〜[D4] に当たる・この票と正典が食い違う。止まったら、やった所までの差分と理由を報告する。
8. **報告の形** は [os32-delegate](../../../.claude/skills/os32-delegate/SKILL.md) の型: 先頭に `git log --oneline -1`、「通った」はログの絶対パスと最後の結果の行、回していない物は「未実行」。
9. **文書とスキルの中のパス。** 移動では `tools/move_files.py` の置換で直る分だけ。残りは、文書の検査を新しい CI に載せる時 (P4 の 3) に直す。`docs/archive/` は書き換えない。

承認の節目 (ユーザー): **A0** 着手 (済み、2026-11-25) → **A1** P0 の結果と P1 の配置 (D-1〜D-11。D-3・D-8 の「製品の入力か検査か」と `tests/` の置き場の予約を含む) と CI の前提 (runner の範囲・PC-98 の起動の確かめ方・目標の時間・取り込みの制御。見せる範囲は P1.md の「終わり」) → **A3** 移動の結果 (ビルド・生成物の一致・起動) を見て main に入れる。D-12 もこの時 (`P4.md` の 3 の前) → **A6** (全件の所要が目標を越えた時だけ) 途中の push で回す検査の選び方と変異の回し直しの条件 → **A7** P4 の 1〜3 が新しい CI に載った所で、機能の実装の再開と古い物の撤去。A4・A5 は無くした (U10)。A の間は止まらずに進める。

## 依頼の型 (PM が 1 段を出す時)

依頼パックは [os32-delegate](../../../.claude/skills/os32-delegate/SKILL.md) の型に、次を足す:

- 最初に読む物: この [RULES.md](RULES.md) と自分の段のファイル (`P<n>.md`) の該当の行、仕様の該当の § (段の表の「仕様 §n」)、段が指す正典。
- 基点の SHA、段の名前、書き手のモデルと理由 1 行 (今は書き手 astra・読み手 sol — DECISIONS の U8)、触ってよい置き場 (P0 は棚卸しの道具と `docs/tasks/restructure/` だけ、P3 は対応表の行と [P3.md](P3.md) の手順に挙げた物だけ、P4 は `tests/` と登録と設計書だけ)。
- 終わりの確かめを、表の列のまま写す (数で言う)。回す物の名前 (移動の前は `run.py --select --files <触るファイル>` の候補、移動の後は P6-0 の workflow と、新しい入口が出来たらその選びの候補)。
- 止まる所 (上の 7) と、止まった時に持ち帰る物。
- 読み手への依頼には書き手の報告を渡さず、差分・対応表・ログの場所だけを渡す (ROLES §0)。

**段の終わりのレビュー** (DECISIONS の U16): 段が終わったら、PM が Fable のレビュアーのセッション (`fable reviewer`) に段の全体のレビューを頼む。所見を直してから次の段へ。

段の記録は段のファイルの末尾に 1 段 10 行以内 (決定・未確認・持越し・証拠の所在)。数字と表は P0 の採取記録 (aad611885)・gate.md・証拠の `RESULT.md` に置く。
