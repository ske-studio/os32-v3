# タスク01: SQLite 全体アーキテクチャ設計

## 1. 概要

NEC PC-9801 向け 32bit OS (OS32) に SQLite 3.53.0 を組み込む。
アプリケーションごとに静的リンクするのではなく、**カーネル側に SQLite エンジンを統合**し、
外部プログラムからは KernelAPI (システムコール) + 共有メモリ経由で操作するアーキテクチャ。

### スペック

| 項目 | 値 |
|------|-----|
| SQLite バージョン | 3.53.0 (sqlite-src-3530000) |
| ビルド形式 | amalgamation (sqlite3.c 単一ファイル) |
| OS 統合方式 | カーネルリンク + KAPI 公開 |
| VFS | カスタム (SQLITE_OS_OTHER=1) |
| スレッド安全性 | 無効 (SQLITE_THREADSAFE=0) |
| メモリ管理 | MEMSYS5 固定プール (カーネル予約域) |
| ジャーナルモード | DELETE (デフォルト) |
| DB 接続上限 | 8 (`DB_MAX_CONNECTIONS`) |
| ターゲット FS | ext2 (メイン) + HostDrvFS |

## 3. メモリレイアウト

### 3-1. SQLite 専用メモリプール (MEMSYS5)

カーネルデータ域の未使用領域にSQLite専用の固定メモリプールを配置する。
**kmalloc ヒープとは完全に分離**され、SQLite のメモリ確保がカーネルの他の機能を圧迫しない。

```
カーネルデータ域 (0x100000 - 0x1FFFFF):
  0x100000-0x148FFF  フォントキャッシュ (~292KB)
  0x149000-0x168FFF  Unicode-JIS変換テーブル (128KB)
  0x169000-0x188FFF  GFXバックバッファ (128KB)
  0x189000-0x189FFF  KernelAPIテーブル (4KB)
  0x18A000-0x1FFFFF  ★ カーネル拡張域 (472KB)
                     ├─ SQLite .text (~360KB, -Os)
                     ├─ SQLite .data (~4KB)
                     ├─ SQLite .bss (~1KB)
                     └─ MEMSYS5 プール (~100KB)
                         ★ .text+MEMSYS5 合計 ~465KB ≦ 472KB: 収まる
```

| 項目 | 値 |
|------|-----|
| 拡張域開始 | 0x18A000 |
| 拡張域終了 | 0x1FFFFF |
| 利用可能サイズ | **472KB** |
| SQLite .text (`-Os`) | ~360KB |
| MEMSYS5 プール | ~100KB (必要に応じて調整) |
| 余裕 | ~7KB (タイトだが `--gc-sections` で縮小余地あり) |

> **注意**: `paging.c` で `0x18A000-0x1FFFFF` のページテーブル設定確認が必要。
> R/W + Present でアイデンティティマッピングされていること。

### 3-2. 共有メモリ (IPC 用)

既存の共有メモリ基盤 (16KB×16 ブロック = 256KB) をそのまま使用。
DB クエリ結果のやり取りに 1 ブロック (16KB) を使用する。

### 3-3. メモリ使用量見積もり

| コンポーネント | 推定サイズ |
|---------------|-----------|
| SQLite .text (`-Os`) | **360KB** (実測: OMIT付きamalgamation + `-Os`) |
| SQLite .text (`-O2`) | 527KB (参考: `-O2` 時) |
| .data | 3.7KB |
| .bss | 789B |
| MEMSYS5 プール (実行時) | 200KB (確保済み上限) |
| DB 接続 1 つあたり | ~50KB |
| ページキャッシュ (10 ページ) | ~10KB |
| IPC 共有メモリブロック | 16KB |

> **カーネル統合方式**: `-Os` 構成の .text 360KB は、カーネル拡張域
> `0x18A000-0x1FFFFF` (472KB) に収まる。コンベンショナルメモリではなく
> 拡張メモリ域を活用することで、カーネル直接統合が実現可能。

## 4. DB 接続管理

### 4-1. 接続スロット

```c
#define DB_MAX_CONNECTIONS  8

typedef struct {
    int in_use;
    sqlite3 *db;               /* SQLite 接続ハンドル */
    sqlite3_stmt *active_stmt;  /* 実行中のステートメント (イテレータ用) */
    int owner;                  /* 0=システム, 1=アプリケーション */
} DbSlot;

static DbSlot db_slots[DB_MAX_CONNECTIONS];
```

### 4-2. 接続のライフサイクル

```
db_open("path/to/db.sqlite")
  → カーネル: sqlite3_open_v2() → スロット確保 → ハンドルID返却

db_exec("CREATE TABLE ...")
  → カーネル: sqlite3_exec() → 結果を共有メモリに書き込み

db_exec("SELECT * FROM ...")
  → カーネル: sqlite3_prepare_v2() + sqlite3_step()
  → 1行目を共有メモリに書き込み → status=1 (まだ行がある)

db_step()
  → カーネル: sqlite3_step() → 次の行を共有メモリに書き込み
  → 最終行: status=0 (完了), sqlite3_finalize() 自動実行

db_close()
  → カーネル: 未finalize のステートメント強制クリーンアップ
  → sqlite3_close_v2() → スロット解放
```

## 5. カーネル統合方式

### 方針: カーネル拡張域への直接統合

`-Os` 構成の `.text` 360KB がカーネル拡張域 `0x18A000-0x1FFFFF` (472KB) に
収まることが実測で確認できたため、外部プログラム PoC を経由せず
**直接カーネルに統合する**。

| 項目 | 内容 |
|------|------|
| SQLite .text 配置 | `0x18A000`～ (カーネル拡張域) |
| MEMSYS5 プール | 同拡張域内 (.textの後方) |
| 最適化 | `-Os` (サイズ最適化) 必須 |
| リンカ | `--gc-sections` で未使用コード削除 |

### リンカスクリプトの調整が必要

SQLite の .text をコンベンショナルメモリのカーネル .text とは
別セクションで 0x18A000 に配置する必要がある。
Makefile での対応方法は Phase 1 で設計する。

## 6. HostDrvFS 対応

OS32 の VFS レイヤーがマウントポイントの解決を透過的に行うため、
SQLite カスタム VFS 内で `vfs_route()` を呼ぶだけで ext2 / HostDrvFS を
自動的に振り分けることができる。**追加実装コストはゼロ**。

```
/db/system.sqlite   → ext2 (ルートマウント)
/host/data/app.db   → HostDrvFS (HostDrv マウント時)
```

HostDrvFS 経由ではホスト側 Windows FS キャッシュが効くため、
読み込みが多いワークロードでパフォーマンス優位になる。
