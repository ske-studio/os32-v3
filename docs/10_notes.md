
## 第10部 既知の制約と注意事項

### §10-1 DMA 64KB境界

- FDD読み書きバッファが64KB境界をまたいではならない (§2-2参照)
- loader.asmでは0x10000以降をES:BP=seg:0000方式で回避
- disk.cのDMAバッファはBSS配置で自動的に安全な配置になる

### §10-2 IPL (boot_hdd.asm / boot_fat.asm) の制約

- **訂正 (2026-09-23、票 TASK_HDD_INSTALL 段 0)**: 以前ここには「NP21/W では IPL 内の
  INT 1Bh は 4 回まで、5 回以上だとブートメッセージすら出ない」「HDD は LBA 2 から
  16 セクタを 1 回の INT 1Bh で読む」と書いていたが、**どちらも現行のソースと合わない**。
  - `boot/boot_hdd.asm` は **1 セクタずつ 16 回** INT 1Bh を呼ぶ (`load_loop`、CX=16)。
    2026-04-29 (3fc5bee) に 4 回 → 16 回へ増やしており、その後も NHD 起動は動いている。
  - `boot/boot_fat.asm` もルートDir (2HD 6 / 1.44MB 12 セクタ)・FAT (2 / 9)・LOADER.BIN の
    クラスタ数だけ 1 セクタずつ呼ぶので、FD 起動でも 5 回を大きく超える。
  - 「5 回以上で表示されない」は初期 (`boot.asm` 時代) の観察で、原因は**未確認**。
    回数の上限ではなく別の要因 (当時の 0x400 以降の BDA 破壊 §10-5 など) だった可能性があるが
    確かめていない。**現行の IPL に回数の制約は無いものとして扱う**。
- 今も守っている制約は **IPL が 512B** であること。追加の読み込みと BIOS への問い合わせ
  (INT 1Bh AH=84h による HDD の幾何、ブート情報域 0x7E00) は第 2 段階ローダー
  (`loader_hdd.asm` / `loader_fat_new.asm`) で行う二段階ブート方式。

### §10-3 PM⇔RM遷移トランポリン (ブート時のみ)

- 32ビットPMからBIOS (16ビットRM) を呼ぶにはPM→RM→PM遷移が必要
- 現在この遷移は **第2ステージローダー内のディスク読み込み時のみ** 使用される
  (`boot/loader_hdd.asm` の `pm16_trampoline` / `rm_trampoline` /
  `pm32_return_trampoline`)
- カーネル本体は起動後 BIOS を呼び出さない
  (ディスクI/OはPM PIO — `drivers/disk.c` 冒頭に「BIOSトランポリンは使用しない」と明記)

### §10-4 EGC farポインタ問題 (歴史的注記)

※過去にOpen Watcomの16-bitスモールモデルを使用していた際の問題であり、現在のGCC (32-bit プロテクトモードフラットモデル) 環境では発生しません。
かつては、EGCアクティブ中に2つの別々のfarポインタでVRAMにアクセスすると、コンパイラのセグメントレジスタ再ロードコードがEGCパイプラインに干渉していました。

### §10-5 INT 1Bh 呼び出し時の BIOS ワークエリア (BDA) 破壊

- PC-98では `0000:0400h` 以降は **BIOS データ領域 (BDA)** として予約されている
- INT 1Bh は内部的にこの領域をワークメモリとして使用する
- **対策**: ローダー開発時、ループカウンタや一時変数をスタックや `0x400` より前の安全なアドレスに避難させる必要がある (`0x400` に変数を置くと壊れる)

### §10-6 ext2 シングルトン構造によるサブマウント破壊 (解決済み)

- ~~現在の ext2 ドライバはシングルトン（グローバル変数1セットのみ）で実装されていた~~
- ~~`vfs_mount()` を別デバイスに対して呼び出すと、既存のルートマウント済み ext2 が強制的にアンマウントされる問題があった~~
- **対策完了**: VFSマルチインスタンスリファクタリング (v0.2) により、全FSドライバ (ext2/FAT12/ISO9660) がコンテキスト渡し方式 (Ext2Ctx等をkmalloc/kfree) に移行。複数デバイスの同時ext2マウントが可能になった。

### §10-7 kentry における BSS ゼロクリアの必要性

- 通常の OS や CRT0 が行う BSS のゼロクリアは、ベアメタルの場合自作する必要がある
- `exec_nest_level` などのグローバル変数が不定値（ゴミデータ）で初期化され、起動直後に動作不良を起こす一因となった
- **対策**: リセット直後の `kentry.asm` 内で `rep stosd` を用いて BSS セクション全体を自前でゼロクリアする実装が必須

### §10-8 カーネル成長による ext2 パーティションの重複

- カーネルバイナリを LBA 6 から直接配置する場合、パーティションの開始 LBA が近すぎるとカーネル後部が ext2 スーパーブロックに上書きされてしまう問題があった
- **対策**: ext2 の開始位置を後方へ移した。現行の通常ブートは ext2 内 `/boot/vmkernel.lz4` を読む (`boot/boot_main.c:79`)。直接配置領域の範囲と上限は [03_disk.md §3-4](03_disk.md) を参照。

### §10-9 プログラム終了時のリソース自動クリーンアップ

- 外部プログラムの資源はアプリ ID を所有者として管理し、終了時にその ID の分だけ回収する。現行の回収対象・例外は [09_exec.md「資源の所有者」](09_exec.md) を参照。
- 以前はリダイレクト・パイプバッファ・FD を無条件に回収していたため、シェルのパイプライン `cmd1 | cmd2` で
  1 段目の終了がシェルのパイプバッファを解放し、2 段目が stdin をキーボードから読んでハングしていた。
- **親ヒープの復元**: 子プロセスから戻るとき、親の exec_heap は
  `exec_heap_restore_state()` で管理変数だけ戻す。`exec_heap_init_at()` で
  再初期化すると親ヒープ先頭の空きブロックヘッダを書き直し、親が子の起動前に
  確保していたブロック (パイプ用 seg_buf 等) の free が
  `[exec_heap] bad magic feeefeee (double free?)` になる
- **例外**: `vfs_fd_set_protect(fd, 1)` で保護されたカーネル常駐FDは回収しない。
  FEP辞書のSQLite接続 (`ime_dict_open`) がこれを使用する。保護を欠くと、
  外部プログラム (例: `ime on` を実行した ime.bin) の終了時に常駐fdが回収され、
  以後の辞書検索が全て `SQLITE_IOERR_READ` になる (2026-08-07 のFEP候補ゼロ
  問題の根本原因)。カーネル常駐のfdを新設する場合は必ず保護すること

### §10-10 未解決の技術負債 (小)

- `lib/path.c` が `dev_find` (ドライバ層) に依存している。関数ポインタの登録制にして疎結合にする
- `ide.c` などの `IDE_TIMEOUT_LOOP` 系ビジーループを、CPU クロック非依存の `kdelay_us` / `kdelay_ms` 待ちへ置き換える
- GUI v1.1 (2026-09-06、詳細は [tasks/gui/TASKS.md §7](tasks/gui/TASKS.md) 末尾の申し送り):
  - 9801 バックエンドは単一バックバッファを WM とアプリで共有するので、commit 前の描画が WM の present に
    巻き込まれて表示面に出うる (PEGC / Cirrus は面が分かれており出ない)。
  - (2026-09-06 当時) K3 の副作用で子プロセスの空間が 1MB 減った (shlib 帯 0x400000〜)。8MB 機では本体上限 ≈1.2MB だったが、T2c の高位私有 VA 化で解消済み。
  - (2026-09-11 の K6-RAM 以前の記録) `sys_mem_kb` は 16MB で頭打ちだった。現行は実 RAM の人為的な上限が無い (02_memory.md §2-1)。
  - Cirrus の setup 失敗 → 9801 フォールバックは実走未検証 (NP21/W では失敗を起こせない。写像は `ring3_guard bb`)。
  - NP21/W の `/api/mouse` の絶対座標上書きはプロセス寿命の状態で、検証後に `abs=off` を送らないと
    人間のマウスが効かない。

### §10-11 wasm のドット始まりラベル (歴史的注記)

Open Watcom の wasm では `.386p` + `USE16` でドット始まりのローカルラベル (`.wait:`) を
書くとオブジェクト生成を黙って飛ばした。NASM 移行で解消済みで、新規コードは `.loop:`
などのローカルラベルを使ってよい (POLICY_DEV.md §2)。
