# OS32 アプリケーション優先設計 — 草案

> 状態: **設計思想の草案**  
> 本文書は OS32 のリリース計画・ロードマップではない。  
> 個別機能の実装順序を定めるものでもない。  
> OS32 が将来の API、メモリ管理、デバイス抽象化、アプリケーション実行モデルを設計する際の判断基準を整理する。

## 1. 目的

OS32 は、現代的な汎用 OS と同じ方向を目指さない。

多数のアプリケーションを同時に実行し、それぞれへ公平に CPU・メモリ・描画資源・音声資源を配分することを主目的とはしない。

代わりに、

**現在利用している 1 本のアプリケーションへ、PC-98 が持つ資源を可能な限り集中して提供する**

ことを基本思想とする。

これは単なる「マルチタスク機能が未実装」という意味ではない。

マルチタスクを中心に据えないことによって得られる資源と設計上の自由を、前景アプリケーションの性能・表現力・互換性へ積極的に振り向ける。

---

## 2. 基本原則

OS32 の実行モデルでは、前景アプリケーションを主役とする。

カーネル、GUI シェル、Host Services、デバイスドライバなどは、前景アプリケーションを支えるための基盤であり、それ自身が恒常的に CPU 時間を消費することを目的としない。

したがって将来の設計では、次を優先する。

- 前景アプリケーションが CPU 時間を最大限利用できること
- 搭載 RAM を固定した小さなアプリ領域へ押し込めず、必要なアプリへ大きく払い出せること
- GPU、PCM、NIC 等のハードウェアを前景アプリが低いオーバーヘッドで利用できること
- 不必要なコピー、コンテキストスイッチ、バックグラウンド処理を増やさないこと
- ハードウェアアクセラレーションが存在する場合は積極的に利用できること
- アプリケーション固有の高速化を OS が妨げないこと

「すべてのアプリに公平」よりも、

**「今動かしているアプリに十分な能力を与える」**

ことを優先する。

---

## 3. マルチタスクを主目的としない

OS32 は、一般的なデスクトップ OS のようなプリエンプティブ・マルチタスク環境を最終目標としない。

GUI 上で補助的なプログラムやシステムサービスが存在することと、複数の重量級アプリケーションを並列実行することは分けて考える。

想定する主な利用形態は、

1. シェルまたは GUI からアプリケーションを選択する
2. 前景アプリケーションへ実行資源を集中する
3. アプリケーション終了後に OS 環境へ戻る

というモデルである。

ZSNES のようなエミュレータ、ゲーム、動画・音声処理、描画アプリケーションなど、CPU・メモリ・デバイス性能を継続的に要求する用途では、このモデルを特に重視する。

---

## 4. メモリ設計への影響

この思想から、アプリケーション用メモリを小さな固定領域へ制限することは望ましくない。

物理 RAM に余裕がある機種では、前景アプリケーションが必要とするメモリを大きく確保できる設計を目指す。

例えばエミュレータであれば、

- ROM イメージ
- エミュレート対象 RAM / VRAM
- フレームバッファ
- 音声バッファ
- キャッシュ
- セーブステート用作業領域

などを一つのアプリケーションがまとめて必要とする。

OS32 が多数のプロセスへ RAM を予約するために、これを不必要に制限するべきではない。

したがって将来のメモリ管理では、

**「何本のアプリを同時に載せられるか」より「1 本のアプリへどこまで安全に渡せるか」**

を重要な評価軸とする。

---

## 5. グラフィックスの世代境界

高機能グラフィックス環境については、機種名ではなく能力で境界を定める。

OS32 の高機能アプリケーション向け表示環境の基準を、

**640×480 / 16bit color をネイティブに提供できること**

とする。

ここでいうネイティブとは、OS32 のドライバがハードウェアを直接制御し、アプリケーションへ実用的な framebuffer 環境を提供できることを指す。

PEGC など、それ未満の表示機能を否定するものではない。

それらは OS32 の基本表示・CUI・軽量 GUI の対象として残し得るが、SDL、ZSNES などの高機能アプリケーションに対して同じ保証を求めない。

---

## 6. PCI 世代と追加グラフィックカード

PC-9821 では、PCI 導入初期に「PCI は搭載しているが、標準グラフィックスが 640×480×16bit という基準に十分届かない」移行期の機種が存在する。

これらについて、機種ごとの特殊対応を積み重ねることはしない。

PCI を持つ機種であれば、

**必要な能力を持つ対応 PCI グラフィックカードを追加する**

ことで高機能グラフィックス環境へ参加できる設計とする。

したがって、

- 本体標準 GPU が条件を満たす機種
- Matrox Millennium 等の対応 PCI GPU を追加した機種
- Cirrus 等で同等の表示能力を提供できる機種

を、上位アプリケーションから見て同じ Video HAL の下へ置く。

---

## 7. Video HAL と VESA2 的インターフェース

特定 GPU の機能をアプリケーションへ直接露出させることを基本形とはしない。

OS32 は、

- 640×480×16bit mode
- framebuffer
- pitch
- buffer 更新
- VSync
- page flip / double buffer
- optional な BitBLT / fill

などを共通化した Video HAL を提供する。

Cirrus、Matrox 等はその backend とする。

その上に必要であれば、

**VESA 2.0 を利用する既存ソフトウェアが要求する部分だけを提供する互換層**

を構築する。

完全な VBE BIOS を再現することを目的とはしない。

狙いは、ZSNES のような既存ソフトウェアが持つ描画エンジンを大きく書き換えず、OS32 上へ持ち込めることである。

---

## 8. 既存ソフトウェア資産の活用

OS32 は独自 API のみで閉じた環境を目指さない。

PC-98 の高速な 32bit 機、とくに Pentium 世代以降では、既存の DOS/Linux 由来ソフトウェア資産を利用できることに大きな価値がある。

そのため、

- VESA2 的 video interface
- PCM audio
- filesystem
- high-resolution timer
- keyboard / mouse / game input

などの薄い互換レイヤを整備し、既存ソフトの本体部分をなるべく変更せず移植できる構造を目指す。

特に SDL 1.2 のような薄い 2D マルチメディア層は、この方針と相性が良い。

理想形は、

```text
Application
    |
 SDL / VESA-like compatibility
    |
 OS32 common API
    |
 HAL
    |
 PC-9821 hardware / PCI devices
```

である。

アプリケーションごとに PC-98 固有コードを書く構造にはしない。

---

## 9. ハードウェアアクセラレーションの扱い

ハードウェアアクセラレーションは必須条件とはしない。

基本契約は framebuffer を中心とし、その上で GPU が持つ能力を optional capability として公開する。

例えば、

- hardware fill
- BitBLT
- VRAM-to-VRAM copy
- page flip
- VSync
- color key

などである。

アプリケーションはこれらの有無を問い合わせることができるが、特定 GPU のレジスタ仕様には依存しない。

この方式なら、

Cirrus → Matrox → その他の PCI GPU

と backend を追加しても、SDL や ZSNES を変更する必要がない。

---

## 10. ZSNES を設計上の試験台とする意味

ZSNES 移植そのものを OS32 本流の必須機能とはしない。

しかし ZSNES は、

- 32bit x86
- MMX
- 高い CPU 使用率
- 16bit framebuffer
- 60Hz 描画
- PCM 音声
- 高精度タイミング
- ROM を含む比較的大きなアプリメモリ

を同時に要求する。

したがって、

**「1 アプリへ全力で資源を渡す OS32」という設計思想を検証する非常に良い負荷試験**

になる。

ZSNES を無理なく動かせる基盤は、そのまま SDL ベースのゲーム、エミュレータ、マルチメディアアプリケーションにも利用できる。

---

## 11. OS32 が目指さないもの

この思想に基づき、少なくとも現段階では次を目的としない。

- 多数の重量級 GUI アプリを同時実行するデスクトップ
- アプリ間の CPU 時間の公平な配分
- すべての PC-9801/9821 で同一の高機能 GUI を提供すること
- 古いグラフィックハードウェアへ最新機と同じ能力を無理に提供すること
- あらゆる VESA/VBE 機能の完全エミュレーション
- GPU 固有 API をアプリケーションへ直接固定すること

古い機種を切り捨てること自体が目的ではない。

**能力の違うハードウェアへ同じ性能保証を課さない**

ことが目的である。

---

## 12. 判断基準

今後、新しい機能や抽象層を OS32 へ追加するときは、次を確認する。

1. 前景アプリケーションが使える CPU 時間を不必要に減らさないか
2. 前景アプリケーションへ渡せるメモリを不必要に制限しないか
3. データコピーやコンテキスト切り替えを余計に増やしていないか
4. ハードウェア本来の能力を抽象化のために失っていないか
5. 同じ抽象化を複数のアプリケーションで再利用できるか
6. 古いハードウェアとの互換性維持が、新しいハードウェアの性能を拘束していないか
7. 「汎用 OS らしさ」のためだけに OS32 の目的から外れる複雑性を追加していないか

迷った場合は、

**「この変更によって、1 本のアプリケーションが PC-98 をより有効に使えるか」**

を判断の中心に置く。

---

## 13. 要約

OS32 はマルチタスク性能を競う OS ではない。

代わりに、32bit 化された PC-98 の CPU、メモリ、PCI、グラフィックス、PCM などを一つのアプリケーションへ強く集中させることで、当時の標準 OS とは異なる使い方を可能にする。

グラフィックスについては 640×480×16bit を高機能環境の境界とし、PCI 搭載機では必要に応じて対応グラフィックカードを追加する。

その上に Video HAL、VESA2 的互換層、SDL 等を載せ、既存の 32bit ソフトウェア資産を大きく壊さず利用できる環境を目指す。

**「多くを同時に動かす」のではなく、「いま動かしているものを全力で動かす」。**

これを OS32 の性能設計における基本思想とする。
