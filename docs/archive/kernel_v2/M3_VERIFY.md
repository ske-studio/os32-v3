# M3 — リング3 の検証 (設計)

> 発行: PM (2026-09-01) / 状態: **完了記録 (2026-09-03)**
> 策定: 2026-09-01 / 親: [PLAN.md](PLAN.md) / 前提: M1・M2 完了
> 位置づけ: リング3 が「実際に守っている」ことを機械的に確かめる。
> M1/M2 の各段でも検証はするが、M3 はそれを恒久的な回帰テストにする。

---

## 0. M3 のゴール

リング3 の主目的は制約 [ABI4] の解消 —「プログラムのバグが即カーネル破壊」を
「プログラムのバグはそのプログラムだけを殺す」に変えること。M3 は次の 3 つを
恒久化する。

1. **フォールト注入テスト** — わざと不正をやり、カーネルが生き残ることを確認
2. **静的検査** — ユーザランドが特権命令やカーネル帯域に触れていないこと
3. **性能の再計測** — ゲート往復のコストが M0 後も無視できる水準であること

---

## 1. フォールト注入テスト (実機・自動)

現在の `kselftest` (`kernel/kselftest.c`) はカーネル内プリミティブの境界を
毎ブート検証し、結果を `kselftest_pass` / `kselftest_fail` に積む
(`emu_read_mem` で読める)。だが**「わざとフォールトさせて回復する」種類の
テストは無い**。リング3 ではこれが要る。

問題: フォールト注入はプログラムを 1 つ実行して #PF を起こす必要があり、
kselftest (ブート時・カーネル内) の枠組みでは動かない。**別の仕組みが要る。**

### 設計: フォールト注入プログラム + ホスト判定

```
userland/tests/faultprobe/  (CPL=3 で走る小さなテスト)
  ケース 1: カーネル帯域 (0x100000) に書く      → #PF で kill されるべき
  ケース 2: 未マップ番地 (0x7000000) を読む      → #PF で kill されるべき
  ケース 3: 他アプリの想定 PD 外を触る           → #PF で kill されるべき
  ケース 4: KAPI に NULL/範囲外ポインタを渡す    → M2 ディスパッチャが弾く
  各ケース後、シェルに戻れたら「回復成功」を SHM か既定番地に記録
```

- ホスト (np21w_mcp / os32-cycle) が各ケースを走らせ、
  **カーネルが生きていてシェルが応答する**ことを `ver` で確認する
- カーネルには「直近のフォールトで kill したプログラム」を数えるカウンタを
  置き (`fault_kill_count` 等)、`emu_read_mem` で読む。期待値と照合
- **合格条件**: 4 ケースすべてで「アプリは死ぬ、カーネルは生存、シェル復帰」

### os32-cycle への組み込み

```
os32-cycle fault-test   →  faultprobe を配備・実行し、各ケース後に ver で
                           カーネル生存を確認、fault_kill_count を照合。
                           RESULT: OK / FAIL を 1 行返す
```

M0 で作った計測基盤と同じく、判定はホスト側の 1 コマンドに畳む。

## 2. 静的検査 (make check に追加)

ユーザランドのコードが、リング3 で禁じられることを**ビルド時に**していないか。

| 検査 | 対象 | 検出方法 |
|------|------|----------|
| S1 特権命令 | userland/**/*.o | `objdump -d` で `cli`/`sti`/`hlt`/`in`/`out`/`lgdt`/`lidt`/`mov crN` を探す。CPL=3 では #GP になる |
| S2 カーネル帯域直書き | userland ソース | `0x100000`〜`0x3FFFFF` の即値アドレスへの書き込みを grep で警告 |
| S3 KAPI テーブル直呼び | userland | `KAPI_ADDR` 直参照 (M2 後は USER テーブル経由が正) |

- S1 が本命。`hlt` は M0 で `sys_halt` KAPI 経由にしたので、ユーザ .o に直の
  `hlt`/`cli`/`sti` が残っていればリング3 で即死する。ビルド時に落とす
- `tools/check_privileged.py` を新設し `make check` に載せる。
  `i386-elf-objdump -d userland/**/*.o | grep -E '\b(cli|sti|hlt|in|out|lgdt|lidt)\b'`
- 誤検出 (文字列 "hlt" 等) を避けるため、逆アセンブルのニーモニック列だけを見る

## 3. 性能の再計測

M0 で「アイドル 187%→0.3%、demo1 の get_tick 除き 233/s」を実測した。M2 で
KAPI が INT ゲート経由になった後、この前提が保たれているかを再測する。

- `-DKAPI_PROFILE` の計測カーネルで、CPL=3 の実プログラムを走らせて
  KAPI レートを取る (M0 と同じ手法)
- **合格条件**: get_tick を除く KAPI レートが数百/s 台に留まり、6μs 換算で
  1% 未満であること
- 悪化していたら、新規に KAPI をホットループで叩くコードが混入した合図。
  M0 の get_tick と同じパターンを疑う

---

## 4. V86 との共存 (M1 V5 の恒久化)

リング3 プログラムと V86 (DOS) はどちらも TSS.ESP0 を使う。M1 V5 で 1 度
確認するが、M3 で回帰テストにする。

- リング3 アプリを実行 → 終了 → V86 で DOS 起動、が壊れないこと
- 逆順 (DOS 起動 → 終了 → リング3 アプリ) も
- vdm-v2 は TSS.ESP0 稼働実績があるが、CPL=3 アプリとの往復は新規経路

---

## 5. 段階

```
M3a  faultprobe (CPL=3 フォールト注入プログラム) と fault_kill_count カウンタ
M3b  os32-cycle fault-test (ホスト側判定)
M3c  tools/check_privileged.py (S1 特権命令検査) を make check に追加
M3d  計測カーネルで KAPI レート再測 (M2 後)
M3e  V86 共存の回帰確認
```

---

## 6. 完了の定義 (v2 リング3 トラック全体)

M1-M3 が通り、次がすべて成立したらリング3 導入は完了とする。

- CPL=3 のプログラムが KAPI 経由で通常動作する (既存アプリ無変更)
- 不正メモリ/不正ポインタでアプリだけが死に、カーネルは生存する (V4/T4)
- ユーザ .o に特権命令が無い (S1)
- KAPI レートが M0 水準を保つ (性能非退行)
- V86/DOS 起動が壊れていない (V5)
- **`docs/CONSTRAINTS.md` から [ABI4] を削除できる** — これが最終的な成果物
