> 発行: PM (2026-09-01) / 状態: **完了記録 (2026-09-03)**

> 位置づけ: v2 で扱う**カーネルの構造変更**の計画。GUI の設計は含まない
> (後述 §7 のとおり別トラック)。判断の根拠は

## 1. スコープ

このトラックが扱うのは OS32 の identity を保ったままの**保護機構の導入**である。

**扱う (in scope)**

- リング 3 導入 (CPL=3 のユーザプログラム + CPL=0 のカーネル)
- KAPI をゲート経由の呼び出しに変える (トランポリン方式)
- `get_tick` ビジーポーリングの根絶 (リング 3 の前提条件)
- 複数プログラムの同時ロード方式 → PD 切替に確定 (§6)
- Rust の適用範囲の確定 (新規ユーザランド層のみ)

**扱わない (out of scope)**

- GUI シェル・`libos32gui`・ウィンドウマネージャの設計 → v1.x トラック (`docs/ROADMAP.md`)
- マルチタスク (スケジューラ・プリエンプション) → identity から外れる。§7 参照
- カーネル本体 23K 行の Rust 書き換え → 回収できない。§5 参照

## 2. 確定した決定 (2026-09-01)

| # | 決定 | 根拠 |
|---|------|------|
| D1 | **リング 3 を導入する** | [ABI4] (KAPI ポインタ非検証) を消せる唯一の道。土台 (TSS・CPL=3 遷移・PTE_USER) は V86 用に既にある |
| D2 | **identity は「DOS の 32bit ネイティブ版・シングルタスク」** | DOS エクステンダ (DOS/4GW 等) と同じ位置。`fork`/`pipe`/busybox は方向が逆 |
| D3 | **Rust は新規ユーザランド層に限定** | カーネルに来る新規コードが少なく、23K 行の書き換えは回収できない。GUI 層 (新規・大量・状態管理) が Rust の効く場所 |
| D4 | **apps / game はモノレポから分離済み** | `ske-studio/os32-apps` (20 commit) / `os32-game` (12 commit)。本体はカーネル + SDK に純化 (`4740bea`) |
| D5 | **V86 第1実装 (vdm-v1) は破棄** | vdm-v2 が MS-DOS 5.00A 起動を実機確認済み。第1実装は不要と判断し削除 |
| D6 | **複数アプリは PD 切替方式** | OS32X/ビルド無改変で既存アプリが動き、アプリ間もハードウェア分離。DOS エクステンダの正統手法。§6 参照 |

## 3. 実測: KAPI 呼び出し頻度

リング 3 では KAPI 呼び出しが INT ゲート遷移 (386 で ~6μs) になる。実プログラムの
呼び出し頻度が成立条件になるため、計測カーネル (`-DKAPI_PROFILE`) で実測した。

| 状態 | KAPI 呼び出し | うち `get_tick` | `get_tick` 除く | 6μs 換算 CPU |
|------|--------------|----------------|----------------|-------------|
| アイドル (rshell 待ち) | 311,703 /s | 100 % | 100 /s | **187 %** |
| demo1 実行中 | 5,726 /s | 95.9 % | 233 /s | 3.4 % (全体) / **0.1 %** (除く) |

計測手法: `kapi/kapi_profile.h` の `KAPI_HIT(slot)` が計測ビルドでのみ slot 別
カウンタを増やす。`kapi_hits[]` を `/api/mem` で読み、`tick_count` の差分で
calls/sec を出す (`tools/` 相当のスクリプトはセッション外)。

### 3.1 結論

- **`get_tick` を除けば KAPI レートは無視できる** (0.1 % CPU)。v22 で描画
  プリミティブを KAPI から外し、フレームバッファ直接操作に移した効果。
  **ホットパスは既に KAPI 境界を越えていない。**
- **`get_tick` のビジーポーリングが唯一かつ致命的な障害。** 残したまま
  リング 3 に進むとアイドルだけで CPU が振り切れる (187 %)。
- したがって **M0 (get_tick 根絶) がリング 3 の絶対的な前提条件**になる。

## 4. マイルストーン

順序に依存関係がある。M0 を飛ばして M1 以降に進むと即破綻する。

### M0 — `get_tick` スピンの根絶 (最優先)

「時間待ちのスピン」を `sys_halt()` ベースに置き換える。PIT は 100Hz なので
`hlt` は最大 10ms で必ず起きる。時刻取得としての `get_tick` (ベンチの差分計測等)
はそのまま残す。

棚卸し (v1.1.0 時点):

| 箇所 | 内容 | 対応 |
|------|------|------|
| `userland/shell/rshell.c` (3 箇所) | `w=get_tick()+1; while(get_tick()<w);` — **アイドル 311k/s の主因** | `sys_halt()` に置換 |
| `userland/cmds/sleep.c` | sleep コマンドの待ち | 同上 |
| `userland/system/sndtest.c` | 音長の待ち | 同上 |
| `tests/blit_test2` `rotate_test` `gfx_demo200` | fps 計測の frame 待ち | デモ。優先度低 |
| `tests/bench*` `mgx_test` `blit_test` | 経過時間の**計測** (待ちではない) | 触らない |

検証: 計測カーネルで「アイドルが 311k/s → 数十/s」に落ちることを確認する。
M0 は v1 にも効く (今アイドルでホスト CPU を無駄に食っている)。

**実施済み (2026-09-01, `56be33d`)**: rshell.c の 3 箇所を `sys_halt()` 化。
実測でアイドルが **311,703/s → 500/s (623 分の 1)**、6μs 換算 CPU が
**187% → 0.3%** に低下。内訳は get_tick 300/s + sys_halt 100/s +
kbd_trygetchar 100/s = 1 tick ごとに 1 周する設計どおりの形。生スピンは
rshell の 3 箇所だけで、sleep.c / sndtest.c / デモの fps 待ちは元から
halt 入りループ、通常シェルの kbd_getkey も元から hlt ブロックだった。
**リング3 の最大の障害が消え、M1 に進める状態になった。**

### M1 — リング 3 の土台

> 設計: [M1_RING3.md](M1_RING3.md)

- GDT に DPL=3 の code/data を 2 本追加 (`0xFA` / `0xF2`)。`GDT_ENTRIES` 4 → 6
- `exec` がロードするプログラムページに `PTE_USER` を立てる
  (`paging_set_page` は対応済み)
- ユーザスタックを CPL=3 用に用意。カーネルスタックは TSS.ESP0 で復帰

**完了 (2026-09-03) — 全ゲート実機通過。** commit `d662f77` (M1a+M1b) /
`1910a9a` (M1c+M1d) / `84ac4fb` (M1e)。

- **V1** PD 複製: 新 PD に CR3 を載せてもカーネル帯域が同一物理で共有・生存。
  ブート時 `kselftest` に常設 (fail=0 / pass=42)。
- **V2** CPL=3 到達 + USER マップした VRAM への描画 (`ring3_hello`: 0xA8000="RNG3")。
- **V3** 割り込みを跨いだ CPL=3 継続。`isr_stub` がユーザセグメントを復元せず
  #GP していたのを `IRETD_USER` マクロ (VM/RPL で分岐、CPL=3 復帰時のみ USER_DS
  再ロード) で修正。0xA8004="DONE" 書込で実証。
- **V4** CPL=3 由来の #PF/#GP でアプリのみ kill・カーネル生存 (`ring3_fault`:
  0x100000 書込 → kill、`fault_kill_count`=1、0x100000 無傷、シェル復帰)。
  = **[ABI4](CPL=3 からカーネル破壊)の構造的解消を実証。** 削除は M2+M3 後。

PD 切替単一アプリ (M1) で成立。複数アプリ同時ロード (§6) は後続。

### M2 — KAPI トランポリン

> 設計: [M2_KAPI_TRAMPOLINE.md](M2_KAPI_TRAMPOLINE.md)

KAPI 表の形 (172 エントリの関数ポインタ) を保ったまま、各エントリを
**ユーザ空間のスタブ**に向ける。スタブが `int 0x80` でカーネルに入る。

- プログラム側のソースは無変更 (`api->kprintf(...)` のまま)
- 制約 [ABI2] 「末尾追加のみ」も維持
- 関数番号を EAX に載せる全面 syscall 化より ABI の断絶が小さい

**完了 (2026-09-03) — 全ゲート実機通過。** commit `68fe74f` (M2a-M2d) /
`8c50d99` (M2e)。

- **M2a** `gen_kapi` が `kapi_argsize[168]` / `kapi_argptr[168]` / `KAPI_FUNC_COUNT`
  を生成 (append-only, KAPI_VERSION 据置)。
- **M2b-c** 全 PD 共有の USER トランポリンページ (magic/version/fn 表 + 168 スタブ
  `B8<slot>CD80C3`)。`STUB_BASE=align4(sizeof(KernelAPI))` (C3 式はデータフィールド
  2 本を見落としていたため実装で補正)。exec が CPL=3 アプリに api としてこのページを渡す。
- **M2d** int 0x80 ディスパッチャ: slot 範囲チェック → 引数コピー → 本物 wrap 呼出
  (CR3=アプリ PD)→ 戻り値。int80_stub は IRETD_USER で CPL=3 復帰。
  crt0 スタック規約ずれ (iret は call を通らず retaddr 無し) をダミー retaddr で補正。
- **M2e** [ABI4] の KAPI 版封鎖: (核) `ring3_in_syscall` ガード — wrap 内 (CPL=0) の
  #PF/#GP も syscall 中ならアプリ由来と判定し kill (可変長 %s も捕捉)。(補助)
  `kapi_argptr` による宣言ポインタ引数の早期範囲検証。
- **T ゲート**: 既存 `hello` を `--ring3` (ソース無変更) で CPL=3 起動 → CPL=0 版と
  同一出力・正常終了。`faultprobe` を `--ring3` で case 1-4 → 全 kill・カーネル生存・
  `fault_kill_count`=4・シェル復帰。誤爆なし・kselftest fail=0。

**残: ring3 は現状 `OS32X_FLAG_RING3` オプトイン。[ABI4] の完全削除には
ring3 をデフォルト化 (全外部プログラムを CPL=3) する判断と回帰掃きが要る (M3)。**

### M3 — 検証

> 設計: [M3_VERIFY.md](M3_VERIFY.md)

- 不正ポインタを KAPI に渡し、**カーネルが死なずページフォールトで止まる**
  ことを `kselftest` に追加 (現在この種のテストが無い)
- 6μs ゲートの実測 CPU が M0 後に無視できる水準であることを再計測

**完了 (2026-09-03) — ring3 デフォルト化 + 回帰ゼロ + [ABI4] 削除。**
commit `b96f27d` (M3 デフォルト化) ほか。

- ring3 を全外部プログラムのデフォルトに反転 (`want_ring3 = !is_shell &&
  !FORCE_CPL0`)。共有低位メモリ (フォント/Unicode 表/GFX バックバッファ) を
  USER マップ。プログラム帯 USER マップを code+heap 全域 [0x400000,0x7C0000) へ
  拡張し sbrk 上限を調整。ユーザスタック 256KB。
- **実機回帰掃き**: userland 15 プログラム中 14 が無変更で CPL=3 動作
  (漢字表示/GFX/GUI(coder2 gui_demo)/SQLite/CLI)。唯一の回帰 alloc_demo
  (ヒープ 1MB 超) も上記拡張で解消 → **回帰ゼロ** (fault_kill_count=0)。
- フォールト注入 (M1e ring3_fault / M2e faultprobe_r3 case 1-4) で
  「アプリ死・カーネル生存・シェル復帰」を実証済み。静的検査は
  `make check` の check_privileged。
- **[ABI4] を CONSTRAINTS.md / CLAUDE.md / SOUL.md の規則から削除** (規則
  17→16 件)。外部プログラムのバグはもうカーネルを破壊しない。例外は shell と
  FORCE_CPL0 (CPL=0 信頼扱い) のみ。**= v2 の中核目標を達成。**

残: ヒープ/スタック境界 (0x7C0000) のガードページ挿入は将来のハードニング候補
(旧 CPL=0 モデルと同等リスクのため今回スコープ外)。KAPI トランポリンの性能は
hello_r3 が体感遅延なく完走 (get_tick 根絶済みで KAPI 頻度 ~233/s)。

## 5. Rust の適用範囲

規模 (v1.1.0 実測): 自作カーネル C 23,131 行 / アセンブラ 3,308 行 /
vendored C (SQLite+FatFs+zlib) 278,281 行。**書き換え可能なのは 23K 行だけで、
リンクされる C は 278K 行残る。**

| 層 | 判断 | 理由 |
|----|------|------|
| `libos32gui` (新規 GUI 層) | **Rust で新規開発** | 量が多く状態管理のバグが出やすい。`no_std` + 固定配列でカーネル非依存。`os32_lz4` (text 541B) と同じ staticlib 形式 |
| V86/VDM のゲスト境界 | Rust 化を検討 | DOS プログラムを走らせるならゲスト値は全て信頼できない入力 |
| カーネル本体 | **C のまま** | 新規コードが少なく回収できない。リング 3 が入れば保護はハードウェアが担う |
| ドライバ・ISR 周辺 | **C のまま** | ポート I/O と `irq_save` が主。`unsafe` だらけになる |
| SQLite/FatFs/zlib | C のまま | 選択の余地なし |

**リング 3 と Rust は補完関係。** リング 3 が守るのは「プログラム→カーネル」、
Rust が守るのは「カーネル内部のバグ」。ただしカーネル新規コードが少ないため、
Rust の主戦場はカーネルではなく新規ユーザランド層になる。

## 6. 複数プログラムの同時ロード方式 — PD 切替に仮決め (2026-09-01)

現在 OS32X は `0x400000` 固定リンクの平坦バイナリで、`exec` はプロセスを置換する。
GUI で複数ウィンドウ (= 複数アプリ) を同時に持つには、この前提を変える必要がある。
2 案を比較し、**PD 切替**を採る。

| 観点 | 案 A 再配置可能バイナリ | 案 B PD 切替 (採用) |
|------|------------------------|---------------------|
| OS32X / ビルド | 全面改修 (再配置テーブル, mkos32x, app.ld, crt0) | **無改変** |
| 既存アプリ (os32-apps/os32-game) | 全再ビルド + 旧バイナリ非互換 | **そのまま動く** |
| アプリ間分離 | 無い (同一空間で相互破壊可) | **ハードウェアで完全分離** |
| リング3 との相性 | 中 (カーネルのみ保護) | **高 (相互保護)** |
| ポインタ受け渡し | そのまま効く | 共有メモリ経由が必要 |
| 切替コスト | 軽い (TLB 保持) | CR3 切替で TLB 全フラッシュ |
| ページング改修 | 最小 (単一 PD 維持) | PD 複製 + バッキング管理 |

### 採用理由

1. **ABI を壊さない。** 案 A は OS32X フォーマット改変で分離したばかりの
   2 リポジトリに全再ビルドと非互換を強いる。案 B は既存アプリが無変更で動く。
2. **リング3 の目的と一致。** v2 の主眼は保護。案 B はアプリ間も分離するため、
   プログラム→カーネルだけでなくプログラム→他プログラムも守れる。
3. **identity と一致。** DOS エクステンダ (CWSDPMI 等) が採った正統な手法。

案 A が勝る「ポインタ受け渡し」は共有メモリ (`MEM_SHM_BASE` を全 PD 共有に
する) で代替でき、「切替の軽さ」は切替頻度が低いので実害が小さい。

### 設計上の要点 (M1 のメモリマップに反映)

現状は単一 `page_directory[1024]` + 全 PT 静的確保 (`kernel/paging.c`)。
PD 切替では次の構造にする。

- **カーネル帯域 (0x100000-0x3FFFFF) と共有メモリは全 PD で共有。**
  同じ PT を各 PD から指す。カーネル・SQLite・シェル常駐帯域はどのアプリから
  見ても同一物理。
- **`0x400000` 帯 (プログラム空間) だけを PD ごとに差し替える。** ここの PDE
  だけがアプリ固有の PT を指す。
- **`MEM_SHM_BASE` を全 PD 共有に固定する。** アプリ間 / gshell-アプリ間の
  データ受け渡しはここを経由する (Win16 のメッセージにポインタを載せる方式は
  使えない)。
- **pgalloc に PD 複製とバッキングページ管理を足す** のが実装の山場。
  V86 が既にゲスト用の別マッピングを張っている (`v86_mem.c`) ので、
  PDE 単位の張り替えと巻き戻しの手法を流用できる。
- リング3 のユーザスタックも `0x400000` 帯側に置き、PD ごとに独立させる。

協調型マルチタスクを `gshell` (ユーザランド) の責務にする場合でも、どの PD を
CR3 に載せるかの決定は gshell が行い、切替自体 (CR3 書き込み) はカーネルの
KAPI として提供する。

## 7. GUI トラックとの関係

**GUI の設計はこのトラックに含まれない。** Win3.1 風デスクトップ、`gshell`、
`libos32gui`、ウィジェットは `docs/ROADMAP.md` の v1.x トラックにあり、
その 9 割以上はユーザランドである。カーネル側の GUI 作業は
`/etc/system.cfg` 解析・テキスト GDC 制御・CUI 出力の GUI リダイレクトの 3 つだけ。

両トラックは独立だが、3 点で交差する。

1. **KAPI 呼び出し方式** — リング 3 化は GUI アプリの KAPI 呼び出しにも及ぶ。
   M2 のトランポリンが GUI アプリにもそのまま効く (ソース無変更)。
2. **複数アプリの同時ロード (§6)** — GUI マルチウィンドウの要求そのもの。
   GUI 側の要件がこの未決事項の決め手になる。
3. **`get_tick` 根絶 (M0)** — GUI のイベントループも同じスピンに陥りやすい。
   M0 で確立するアイドル作法 (`sys_halt` ベース) を GUI ループの基準にする。

GUI の識別: v1.x の GUI は「シングルタスク GUI デスクトップ」であり、
Windows 3.1 が「シングルタスクの DOS 上で GUI シェルが協調マルチタスクを
実装する」構造だったのと同じ。協調マルチタスクを入れる場合も `gshell` の責務とし、
カーネルは DOS のまま保つ (D2)。

## 8. リスクと後戻り

| リスク | 影響 | 緩和 |
|--------|------|------|
| `get_tick` を残したままリング 3 | アイドル 187 % で常時振り切れ | M0 を絶対的前提とする (§4) |
| KAPI 呼び出しに毎秒数万回のプログラム | トランポリンが成立しない | 実測で 233/s (get_tick 除く) と確認済み。新規プログラムも同水準に保つ |
| V86 とリング 3 の TSS.ESP0 競合 | DOS 起動経路が壊れる | M3 で共存を検証。vdm-v2 は動作実績あり |
| PD 複製のカーネル帯域共有ミス | 一部アプリからカーネルが見えず即クラッシュ | 全 PD で 0x100000-0x3FFFFF の PT を共有。M1 で最優先に検証 |
