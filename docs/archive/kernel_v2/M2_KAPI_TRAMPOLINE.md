# M2 — KAPI トランポリン (設計)

> 発行: PM (2026-09-01) / 状態: **完了記録 (2026-09-03)**
> 策定: 2026-09-01 / 親: [PLAN.md](PLAN.md) / 前提: M1 (リング3 土台) 完了
> 位置づけ: CPL=3 のプログラムから KAPI を呼べるようにする。プログラムの
> ソースと OS32X フォーマットは無変更 ([ABI2] 維持) を最優先条件とする。

---

## 0. 何が問題か

M1 で CPL=3 のプログラムが走るようになると、現在の KAPI 呼び出しが二重に壊れる。

1. **テーブルが読めない。** KAPI テーブルは `KAPI_ADDR = KHEAP_BASE + KHEAP_SIZE`
   (カーネル帯域 0x100000-0x1FFFFF 内) にある。M1 の PD レイアウトではここは
   `USER` ビットなしで共有される → CPL=3 から読めず、`api->kprintf` の
   ポインタ取得自体が #PF になる。
2. **関数が呼べない。** テーブルの各エントリは `wrap_*` (カーネル帯域の CPL=0
   コード) を指す。仮に読めても CPL=3 から直接 `call` すると #GP。

M2 はこの 2 つを、**プログラムのソースを 1 行も変えずに**解決する。

---

## 1. 方式: ユーザ可視トランポリンテーブル (vDSO 相当)

カーネルが CPL=3 から読める USER ページを 1 枚用意し、そこに

- **ユーザ可視 KAPI テーブル** — `KernelAPI` 構造体と**同一レイアウト**。ただし
  各エントリは `wrap_*` ではなく、同じページ内の**スタブ**を指す
- **スタブ列** — 各スロットにつき小さなコード片。`int 0x80` でカーネルへ入る

を置く。`exec` はプログラムに、本物の KAPI テーブルではなく**この USER テーブルの
アドレス**を渡す。プログラムは `api->kprintf(...)` を今までどおり呼び、テーブルの
kprintf オフセットにあるスタブが走り、`int 0x80` でカーネルに落ちる。

```
CPL=3                              CPL=0
─────────────────────────────────────────────────────────
app: api->kprintf(attr,fmt,...)
  │  __cdecl: 引数はユーザスタックに積まれる
  ▼
USER テーブル[kprintf offset] → スタブ
  スタブ: mov eax, <slot>; int 0x80
                    │
                    ▼ (CPU が TSS.ESP0 でカーネルスタックへ)
              int 0x80 ハンドラ (DPL=3 ゲート)
                eax = slot
                ユーザスタックから引数を N バイトコピー
                本物の wrap_<slot> を call
                戻り値を eax に、iret
                    │
  スタブ: ret  ◀───┘ (cdecl: 呼び出し側が引数を掃除)
```

### なぜ成立するか

- `KernelAPI` は先頭 `magic`/`version` の後が**純粋な関数ポインタ表**
  (`os32_kapi_generated.h` で確認)。同一レイアウトの複製が作れる
- 引数は `__cdecl` でユーザスタック渡し。スタブは引数に触れず `int 0x80` するだけ。
  カーネル側がユーザスタックから引数を読む
- `int 0x80` は空きベクタ (現在 default stub のみ)
- プログラムが受け取る api ポインタは実行時にスタック渡し (`crt0` → `_start_c`)。
  `exec` が渡す先を差し替えるだけで、**crt0 もプログラムも再ビルド不要**

## 2. USER ページの中身

1 枚の USER ページ (全 PD 共有、`RW+USER` だが実行のため `RX` 相当) に 3 つ置く。
168 スロットで概算 table 672B + スタブ 168×8=1344B ≈ 2KB、1 ページに収まる
(引数サイズ表はカーネル帯域側で可)。

```
offset            内容
──────────────────────────────────────────────
0x000             magic, version (本物と同じ値)
0x008-            ユーザ可視テーブル: entry[i] = STUB_BASE + i*8
STUB_BASE         スタブ列: 各 8 バイト
                    B8 <slot:imm32>   mov eax, slot
                    CD 80             int 0x80
                    C3                ret
                    (計 8 バイト、末尾 1 バイトパディング)
```

- スタブはテンプレート `B8 ?? ?? ?? ?? CD 80 C3` で、slot だけ差し替え。
  **per-slot のコード生成は不要** — カーネルがブート時に 168 個を書き込む
- テーブルとスタブは同一ページなので、プログラムは USER テーブルの
  アドレス 1 つを知れば全部に届く

---

## 3. `int 0x80` ディスパッチャ (カーネル)

```
int 0x80 ハンドラ (IDT ゲート DPL=3):
  1. eax = slot。範囲チェック (0 <= slot < KAPI_FUNC_COUNT)。外れたら #GP 相当で kill
  2. 引数バイト数 = kapi_argsize[slot]  (生成テーブル、§4)
  3. iret フレームからユーザ ESP を取得し、そこから引数を N バイト
     カーネルスタックへコピー (ユーザポインタなので範囲検証: M1 の PD で
     0x400000 帯 or SHM のみ許可)
  4. wrap_<slot> を call (本物の KAPI 実装)
  5. 戻り値 eax を iret フレームの eax に格納
  6. iret → スタブの ret に戻る
```

- 可変長引数 (`kprintf(u8, const char*, ...)`) はユーザスタックをそのまま
  読むので N の下限だけ決めれば動く。上限は printf の実装がフォーマット文字列で
  止まる
- **ポインタ引数の検証がここで一元化される。** M1 [ABI4] 解消の実装点。
  ユーザが渡すポインタが 0x400000 帯 / SHM の範囲内かをディスパッチャで見る

## 4. 生成器 (gen_kapi.py) の追加出力

既存の生成物 (struct / wrap / init / rust) に加えて 2 つ出す。

| 生成物 | 内容 | 用途 |
|--------|------|------|
| `kapi_argsize[168]` | 各スロットの引数バイト数 (args から算出) | ディスパッチャの引数コピー量 |
| `KAPI_FUNC_COUNT` | 関数スロット数 (=168) | 範囲チェック / スタブ生成ループ |

- 引数バイト数は `args` の各型を 4 バイト (i386, ポインタ・int とも 4) として
  数える。可変長 (`...`) は「固定分のみ」を記録し、ディスパッチャが下限に使う
- append-only ([ABI2]) は自然に維持される。新スロットは配列末尾に増えるだけ

---

## 5. exec が渡すもの

```
現状 (CPL=0):  exec が KAPI_ADDR (本物のテーブル) を argv/kapi として渡す
M2   (CPL=3):  exec が USER トランポリンテーブルのアドレスを渡す
```

- USER テーブルは全 PD 共有なので、どのアプリからも同じ番地に見える
- crt0 (`_start_c`) は受け取ったポインタを `kapi` に入れるだけ。無変更
- カーネル内部 (シェルも CPL=0 で動くうちは) は本物のテーブルを直接使い続ける。
  シェルを CPL=3 に落とすかは別途 (M1 のゴールは単一アプリ)

---

## 6. 段階と検証

```
M2a  USER ページを確保し、magic/version + テーブル + スタブをブート時に構築。
     全 PD で同一番地に共有マップ (RX+USER)
M2b  int 0x80 ディスパッチャ (DPL=3 ゲート)。引数コピーと wrap 呼び出し、
     戻り値の受け渡し
M2c  exec が USER テーブルを渡すよう変更
M2d  CPL=3 の最小アプリから api->kprintf / api->get_tick を呼んで往復
M2e  ポインタ引数の範囲検証。不正ポインタを渡したアプリだけが死に、
     カーネルは生存
```

| 検証 | 確認 |
|------|------|
| T1 | CPL=3 から api->get_tick() が正しい値を返す |
| T2 | api->kprintf(可変長) が画面に出る |
| T3 | 戻り値 (int/u32/ポインタ) が正しく伝わる |
| T4 | 不正ポインタ引数でアプリのみ kill、カーネル生存 (M1 V4 の KAPI 版) |
| T5 | ゲート往復のコストが M0 後の実測レート (get_tick 除き 233/s) で無視できる |

---

## 7. 既存資産への影響

- **プログラム再ビルド不要。** api ポインタは実行時渡し、テーブルレイアウトは
  同一。os32-apps / os32-game は無変更で CPL=3 化の恩恵を受ける
- **[ABI2] 維持。** スロットは append-only のまま。argsize 表も末尾に増える
- **KAPI_SPEC.md の機械照合 (`check_kapi_version.py`) はそのまま使える。**
  argsize 表が kapi.json と一致するかの検査を 1 つ足す余地あり

---

## 8. リスク

| リスク | 緩和 |
|--------|------|
| 引数バイト数の誤り | gen_kapi が kapi.json から機械算出。手書きしない。check で照合 |
| 可変長引数のスタック読み過ぎ | kprintf 系はフォーマット文字列で止まる。N は固定分の下限のみ |
| USER ページが書き換え可能だと任意コード実行 | スタブページは RX (書き込み不可) で全 PD 共有。テーブルも読み取り専用 |
| int 0x80 の DPL=3 ゲートから他の悪用 | slot 範囲チェックを最初に。範囲外は即 kill |
