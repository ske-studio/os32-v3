# M1 — リング 3 の土台 (設計)

> 発行: PM (2026-09-01) / 状態: **完了記録 (2026-09-03)**
> 策定: 2026-09-01 / 親: [PLAN.md](PLAN.md) / 前提: M0 完了 (`56be33d`)
> 位置づけ: 実装前に固める設計。PLAN の D1 (リング3 導入) と D6 (PD 切替) を
> メモリマップ・GDT・スタック・CR3 切替 API・V86 共存の具体に落とす。

---

## 0. M1 のゴール

**1 つのユーザプログラムを CPL=3 で起動し、KAPI を 1 つ呼んで、正常終了で
CPL=0 のシェルに戻る。** 複数 PD の同時保持 (D6) は M1 の構造で可能にするが、
複数アプリの同時実行そのものは後続 (GUI トラック)。M1 は「1 プログラムが
リング3 で走り、不正メモリアクセスがカーネルを巻き込まずページフォールトで
止まる」ところまで。

KAPI 呼び出しの実際の配線 (トランポリン) は M2。M1 では暫定的に、KAPI を
呼ばない最小プログラム (画面に 1 文字書いて `sys_exit`) で CPL=3 往復を通す。

---

## 1. 現状 (v1.1.0) の確認

| 要素 | 現状 | M1 で変える |
|------|------|-------------|
| GDT | 4 エントリ: null / code DPL=0 (`0x08`) / data DPL=0 (`0x10`) / TSS (`0x18`) | DPL=3 を 2 本足して 6 エントリ |
| セレクタ | `KERNEL_CS=0x08` (`idt.h`)、`KERNEL_DS=0x10` (`tss.c`) | `USER_CS`/`USER_DS` を追加 |
| TSS | `ss0`/`esp0` 設定済み。V86 復帰で稼働中 | 変更なし (そのまま CPL=3→0 に使える) |
| ページング | 単一 `page_directory[1024]` + 全 PT 静的確保。全体アイデンティティ | PD を複製可能にし、`0x400000` 帯だけ差し替え |
| PTE_USER | `v86_mem.c` が VRAM/ROM に使用済み | プログラムページに立てる |
| exec | `0x400000` に平坦ロード、CPL=0 で `call` して実行 | CPL=3 への `iret` 遷移に変える |

## 2. GDT レイアウト (4 → 6 エントリ)

```
idx  selector  access  DPL  用途                  変更
 0   0x00      -       -    null                  既存
 1   0x08      0x9A    0    kernel code           既存 (KERNEL_CS)
 2   0x10      0x92    0    kernel data           既存 (KERNEL_DS)
 3   0x18      0x89    0    TSS                    既存 (GDT_TSS_IDX=3)
 4   0x20|3    0xFA    3    user code             ★M1 追加 → USER_CS=0x23
 5   0x28|3    0xF2    3    user data             ★M1 追加 → USER_DS=0x2B
```

- `GDT_ENTRIES` を 4 → 6 に。TSS のインデックスは 3 のまま (末尾に足すと
  TSS 番地が動くので、user code/data は TSS の後ろ idx 4/5 に置く)
- セレクタの下位 2 bit は RPL。CPL=3 で使うので `USER_CS=0x20|3=0x23`、
  `USER_DS=0x28|3=0x2B`
- access `0xFA` = P=1,DPL=3,S=1,type=code(exec/read)。`0xF2` = 同 data(read/write)
- リミット・粒度は既存の code/data と同じ `0xFFFFFFFF` / `0xCF` (4KB 粒度,
  4GB フラット)。保護はページ単位 (PTE_USER) で行い、セグメントはフラットのまま

## 3. メモリマップと PD レイアウト (D6: PD 切替)

### 3.1 共有と非共有の境界

```
物理/リニア        全 PD 共有か   PTE       CPL=3 から
─────────────────────────────────────────────────────────────
0x000000-0x0FFFFF  共有          RW(一部)  一部 (VRAM 0xA8000 等のみ USER)
0x100000-0x1FFFFF  共有          RW        不可 (カーネル帯域, USER なし)
0x200000-0x2FFFFF  共有          RW        不可 (SQLite 帯域)
0x300000-0x3FFFFF  共有          RW        不可 (シェル常駐帯域)
  └ MEM_SHM_BASE   共有          RW+USER   可 (アプリ間データ受け渡し)
0x400000-0x4FFFFF  PD ごと       RW+USER   可 (プログラム code/data/heap)
  └ ユーザスタック PD ごと       RW+USER   可 (0x400000 帯の上端)
(物理末尾 256KB)   共有          RW        不可 (ホットデプロイ窓)
```

**要点**: `0x100000-0x3FFFFF` (カーネル/SQLite/シェル) は全 PD が同じ PT を指す。
`0x400000` 帯の PDE だけがアプリ固有の PT を指す。CR3 を差し替えても
カーネルは同じ番地に見え続ける。

### 3.2 PD 複製の構造

```
共有 PT (静的, 1 セット)              アプリ PD (アプリごと)
  PT[0x100000..0x3FFFFF]  ←──┐        PDE[0..3]     → 共有 PT (0-0x3FFFFF)
  PT[SHM]                  ←─┼─────    PDE[4]        → アプリ固有 PT (0x400000-)
  PT[VRAM/低位]            ←─┘        PDE[SHM]      → 共有 SHM PT
                                        PDE[その他]   → 共有 (カーネルと同一)
```

- カーネルの PD (現 `page_directory`) を「共有 PDE の原本」とする
- アプリ起動時: 新しい PD を 1 枚確保し、**カーネル領域の PDE を全部コピー**、
  `0x400000` 帯の PDE だけアプリ専用 PT に差し替える
- `pgalloc` に「PD を 1 枚作る」「アプリ PT のバッキングページを確保/解放する」
  を足す。これが M1 実装の山場
- **カーネル領域を共有し忘れると、そのアプリから見てカーネルが消え、KAPI
  呼び出しや割り込みハンドラが即クラッシュする** (§8 の最優先検証項目)

### 3.3 流用元: v86_mem.c

V86 はゲスト用に低位 RAM のマッピングを張り替え、失敗時に巻き戻している
(`v86_mem.c`)。PDE 単位の張り替えと巻き戻しの手法、`paging_set_page` の
使い方はここを参照する。ただし V86 は単一 PD 内でのマッピング変更、M1 は
PD 自体の複製、という違いがある。

## 4. CPL=3 への遷移と復帰

### 4.1 遷移 (カーネル → ユーザ, exec)

CPL=0 から CPL=3 へは `call`/`jmp` では行けない。**`iret` で降りる**。
スタックに CPL=3 のコンテキストを積んで `iret` する。

```
exec_run (CPL=0):
  1. アプリ PD を作り CR3 に載せる
  2. ユーザスタックにダミーフレームを用意
  3. カーネルスタックに以下を push して iret:
        SS   = USER_DS (0x2B)
        ESP  = ユーザスタック top
        EFLAGS = IF=1 (割り込み許可)
        CS   = USER_CS (0x23)
        EIP  = エントリポイント (0x400000 + entry_off)
  4. iret  → CPU が CPL=0→3 に切り替わりアプリが走り出す
```

**流用元**: `v86_entry.asm` が既に iretd フレーム (GS/FS/DS/ES/SS/ESP/EFLAGS/
CS/EIP) を高位→低位で push して V86 へ遷移している。CPL=3 への iret も
同じ積み方 (SS/ESP/EFLAGS/CS/EIP の 5 つ) で、フレーム構築のコードを流用できる。

### 4.2 復帰 (ユーザ → カーネル)

3 経路ある。いずれも CPU が TSS.ESP0 からカーネルスタックを復元する。

- **正常終了**: アプリが `sys_exit` を呼ぶ → M2 では `int 0x80`。M1 では暫定的に
  専用の `int` ベクタか、`sys_exit` だけ先行実装する
- **割り込み (PIT/KBD)**: CPL=3 実行中に IRQ → IDT ゲート経由でカーネルへ。
  TSS.ESP0 が効く。既存の ISR がそのまま動くはず (要検証)
- **フォールト**: 不正メモリアクセス → #PF。カーネルがアプリを kill してシェルに
  戻す。**これが M1 の主目的の 1 つ** (カーネルを巻き込まない)

### 4.3 IDT ゲートの DPL

CPL=3 から `int 0x80` を呼べるようにするには、そのゲートの DPL=3 が要る
(M2 で使う)。それ以外の例外/IRQ ゲートは DPL=0 のまま (ユーザが直接呼べない)。
M1 では #PF ハンドラが CPL=3 から入っても正しく動くことだけ確認する。

## 5. ユーザスタック

- `0x400000` 帯の上端に置き、PD ごとに独立させる (D6)
- CPL=3 で使うので PTE は `RW+USER`
- カーネルスタック (`0x1FC000`, 16KB) は CPL=0 用。TSS.ESP0 がこれを指し、
  割り込み/フォールト時に CPU が自動で切り替える
- **多重フォールトに注意**: ユーザスタックが尽きた状態で #PF が起きると、
  CPU は TSS.ESP0 のカーネルスタックに切り替えるので二重フォールトには
  ならないはず。だがカーネルスタック 16KB の余裕は M3 で確認する

---

## 6. KAPI の扱い (M1 では最小限)

M1 では KAPI トランポリン (M2) を作らない。理由: PD 切替と CPL=3 往復を先に
単独で通したいため。M1 の検証プログラムは KAPI をほぼ使わず、以下だけで済ます。

- 画面出力: VRAM (`0xA8000`) を `RW+USER` でマップし、アプリが直接書く
  (v22 で描画は既に KAPI 非経由なのでこれは自然)
- 終了: `sys_exit` 相当を 1 本だけ、CPL=3 から呼べる `int` として先行実装

M1 が通れば、M2 で 172 エントリ全部をトランポリン化する。

## 7. 実装順 (M1 内)

```
M1a  GDT に USER_CS/USER_DS を追加。CPL=0 のまま起動に影響しないことを確認
M1b  PD 複製: カーネル PDE を共有しつつ新 PD を作る pgalloc API。
     CR3 を新 PD に載せてもカーネルが動き続けることを確認 (CPL=0 のまま)
M1c  0x400000 帯を RW+USER でマップし、テストプログラムを配置
M1d  iret で CPL=3 に降り、VRAM に 1 文字書いて sys_exit で戻る往復
M1e  不正ポインタアクセスで #PF → カーネルが生存しシェルに戻る
```

各段は前段が通ってから進む。M1b (PD 複製) が最大の難所で、ここでカーネル
共有を誤ると M1d 以降が全滅する。

## 8. 検証項目 (kselftest / 実機)

| # | 確認 | 失敗時の症状 |
|---|------|-------------|
| V1 | 全 PD でカーネル帯域 (0x100000-0x3FFFFF) が同一物理を指す | アプリ起動でカーネルが消え即クラッシュ |
| V2 | CPL=3 から VRAM (USER) に書ける / カーネル帯域には書けない | 保護が効かない or 正常書き込みが #PF |
| V3 | CPL=3 実行中の PIT/KBD 割り込みがカーネルに正しく入る | ハングor二重フォールト |
| V4 | 不正ポインタで #PF → カーネル生存 → シェル復帰 | カーネルごと死ぬ ([ABI4] が消えない) |
| V5 | V86 と CPL=3 の TSS.ESP0 共存 | DOS 起動経路が壊れる |
| V6 | アプリ終了後に PD とバッキングページが解放される | メモリリーク |

**V4 が M1 の存在意義。** これが通れば制約 [ABI4] (KAPI ポインタ非検証で
プログラムのバグが即カーネル破壊) が構造的に消える。

## 9. リスク

| リスク | 緩和 |
|--------|------|
| PD 複製でカーネル共有を誤る | M1b を単独で検証 (CPL=0 のまま CR3 切替)。V1 を最優先 |
| V86 の TSS.ESP0 と競合 | vdm-v2 は TSS.ESP0 稼働実績あり。V5 で共存を実機確認 |
| ユーザスタック枯渇時の二重フォールト | TSS.ESP0 でカーネルスタックに退避。M3 で余裕を測る |
| exec のネスト (現 MAX_EXEC_NEST) と PD 切替の相互作用 | M1 は単一アプリに限定。ネスト対応は後続 |
