## 1. 結論

**方式 A（V86 モニタ + 積極パススルー）を採用する。IOPL=3 で運用する。**

| 方式 | 判定 | 理由（すべて実測に基づく） |
|---|---|---|
| **A. V86 モニタ + パススルー** | ✅ **採用** | オーバーヘッド 6〜13%。要件を満たす唯一の実用解 |
| B. リアルモード復帰型モニタ | ⏸ 将来オプション | 速度は最速だが OS32 が制御と保護を失う。暴走時に復帰不能 |
| C. ソフトウェア 8086 エミュレータ | ❌ **棄却** | 必要 3.96 MIPS に対し供給 0.1 MIPS 程度。**約 40〜50 倍不足** |
| D. 静的移植 | ➖ 対象外 | ソースが無い市販ゲームには適用できない。自作 DOS プログラム向けには併存 |

## 2. 判断材料（実測サマリ）

Ys I を素の NP21/W で 19.968MHz（386DX20 相当）で動作させて計測。

| 指標 | タイトル+BGM | 本編プレイ中 |
|---|---:|---:|
| ゲスト命令実行レート | — | **3,964,474 instr/s (3.96 MIPS)** |
| `INT n` | **0/s** | **0/s** |
| V86 でトラップする命令 (IOPL<3) | 896/s | 359〜378/s |
| I/O アクセス | 7,331/s | 2,345〜2,367/s |
| うち FM 音源 (0x188/0x18A) | 5,901/s (80%) | 1,667/s (70%) |
| GDC / GRCG / EGC コマンド | **0**（上位に出現せず） | **0**（同左） |

**構造的に効いている 3 点**

1. **`INT n` がゼロ** — BIOS を INT 経由で一度も呼ばない。IOPL の選択がそのまま効く
2. **描画は I/O を使わない** — GVRAM へ CPU で直接書き込む。ページテーブルで直マップすれば
   **描画のトラップコストはゼロ**
3. **I/O の 7〜8 割が FM 音源のステータスポーリング** — I/O permission bitmap で
   素通しにすればここもゼロになる

## 3. 方式別の評価

### 3.1 A. V86 モニタ + 積極パススルー 〔採用〕

i386 の仮想 8086 モードでゲストを走らせ、OS32 と競合するデバイスだけを #GP で仮想化し、
それ以外は TSS の I/O permission bitmap で素通しにする。VRAM はページテーブルで直マップ。

**実測コスト**

| 構成 | タイトル | 本編 | 100µs/回換算 |
|---|---:|---:|---|
| IOPL=0・I/O 全仮想化（前回の実装） | 8,227/s | 2,745/s | 最悪 **82%** |
| IOPL=0・FM/VSYNC パススルー | 2,230/s | 938/s | 22% / 9% |
| **IOPL=3・同上** | **1,334/s** | **560/s** | **13% / 6%** |

ハンドラを 600 サイクル(30µs)まで詰めれば 4% / 1.7%。

**IOPL=3 が効く理由**: 386 には VME が無いため IOPL<3 では
`CLI`/`STI`/`PUSHF`/`POPF`/`IRET` が全て #GP に落ちる。
IOPL=3 にすればこれらは素通りする。実測でトラップしていた 896/s は
全てこの 5 種で占められていたので、丸ごと消える。

> **訂正 (Phase 3-3 の実装で判明)**: 当初「IOPL=3 なら `INT n` も素通しになる」
> と書いていたが**これは誤り**。V86 の `INT n` は IOPL に関係なく
> **プロテクトモードの IDT** を引く仕様で、OS32 のゲートは DPL=0 /
> ゲストは CPL=3 のため「softint かつ gate.DPL < CPL」の規則で必ず #GP になる。
>
> ただし**性能の結論は変わらない**。Ys の `INT n` は実測 0/s であり、
> IOPL=3 が消すのは上記 5 種の 896/s だからである。
> むしろ `INT n` が必ずトラップされるおかげで、BIOS コールを横取りするのに
> トランポリンを仕込む必要がなくなり、実装は簡単になった。

**長所**
- OS32 が制御を保持し続ける。ホットキーで脱出でき、暴走してもカーネルは生存する
- ページング保護が効くので、ゲストの暴走がカーネルメモリを壊さない
- 実機ハードウェアを最大限そのまま使える（FM・GVRAM・GDC・CRTC）

**短所 / リスク**
- IOPL=3 ではゲストの `CLI` が実 IF を落とす（→ §5.1）
- PIC の仮想化は外せず、残コストのほぼ全部がここ

### 3.2 B. リアルモード復帰型モニタ 〔将来オプション〕

ページングと PM を停止し、ゲストを素のリアルモードで実行する。トラップはゼロ。

**採用しない理由**

- **暴走から復帰できない**。本調査中に `Ys_FM.D88` がデータ領域を実行して暴走する事例に
  実際に遭遇した（IRET 1,317,447/s）。方式 A ならホットキーで抜けられるが、
  B では機械ごと固まる
- **復帰経路がゲスト依存**。Ys は IRQ0/1/2 を BIOS ROM のまま残しているので
  キーボード IRQ にフックを置けば戻れるが、自前の IRQ1 ハンドラを入れるゲームでは破綻する
- 低位 640KB の退避・復元は方式 A と同じだけ必要で、手間は減らない
- 保護が一切効かない

方式 A で性能が足りないタイトルが出てきた場合の**全画面専用モード**として残す。

### 3.3 C. ソフトウェア 8086 エミュレータ 〔棄却〕

**定量的な棄却根拠**

- ゲストの必要実行レート: **3,964,474 instr/s**（実測）
- 386DX 20MHz のネイティブ実行能力: 約 4 MIPS（本計測時のホスト相当）
- ソフトウェアインタプリタは 1 命令あたり fetch/decode/dispatch/execute/フラグ更新で
  **30〜100 ホスト命令**を要する
- したがって供給できるのは **約 40,000〜130,000 instr/s**

**不足は約 30〜100 倍**。極端に最適化して 20 ホスト命令/命令まで詰めても 20 倍足りない。
**ゲーム実行という目的では成立しない。**

（DOS の小さなツールを動かす程度なら成立する余地はあるが、本プロジェクトの
第一目標はゲームなので対象外）

### 3.4 D. 静的移植 〔対象外〕

`docs/ROADMAP.md:199-213` の公式方針（逆アセンブル → INT 21h を KernelAPI にマップ →
32bit 再コンパイル）。**ソースが無い市販ゲームには適用できない。**
自作 DOS プログラムの移植手段としては引き続き有効で、方式 A と併存する。

## 4. 採用方式の設計方針（Phase 1 への申し送り）

### 4.1 I/O ポリシー — 実測で確定した分類

| 分類 | ポート | 根拠 |
|---|---|---|
| **パススルー**（IOPM 許可・トラップ無し） | **0x0188/0x018A** (FM OPN)、**0x005F** (I/Oウェイト)、**0x0064** (VSYNCトリガ)、GDC/CRTC/GRCG/EGC 系 | 実測で I/O の 7〜8 割。ここを止めたら成立しない |
| **完全仮想化** | 0x0000/0x0002 (マスタPIC)、0x0008/0x000A (スレーブPIC)、0x0041/0x0043 (KBD 8251A)、PIT ch0、FDC、0xF0 (リセット)、0xF2 (A20) | OS32 が使用中。渡すと OS32 が壊れる |
| **保護（無視）** | RS-232C (0x30/0x32/0x33/0x35)、HostDrv (0x7EC/0x7EE) | rshell とファイル I/O 経路の保護 |

前回の分類表 (`archive/feat-vdm:docs/tasks/v86/03_io_port_map.md`) は**実測で上書きする**。
実際に叩かれないポートを仮想化しても無駄なコストにしかならない。

### 4.2 メモリ

- **VRAM (0xA0000-0xEFFFF) は実物理を直マップ**。描画がタダになる根拠そのもの
- 低位 1MB は `pgalloc_alloc_n(256)` でバッキング RAM を確保してリマップ
- **カーネル帯に `PTE_USER` を付けない**（[02_np21w_paging_analysis.md](02_np21w_paging_analysis.md) の結論）
- **`KERNEL_LOAD_ADDR` は `0x100000` のまま**。前回の `0x110000` スライドは根拠を失った

### 4.3 IRQ 注入 — IRQ12 が必須

[03_ys_profile.md §4](03_ys_profile.md) で確定したとおり、Ys が差し替える割り込みは
**IRQ12 (INT 14h) の 1 本だけ**で、演奏はこれだけに依存している。
前回の実装は IRQ0/1/2 のみを注入しており、**ゲストが使う唯一の IRQ を注入していなかった**。

- IRQ12 のマスクを解除し、受信時にゲストへ **INT 14h を注入する**
- 仮想 PIC の IMR / ISR を必ず尊重する（前回、無視して注入し続けた結果
  ゲスト SP が減り続けて IVT を割り込みフレームで上書きする事故があった）

### 4.4 #GP ハンドラの実装方針

残コストのほぼ全部が PIC なので、**PIC 経路だけをアセンブラで短絡させる**価値がある。
前回のような 1,000 行級の C 関数を全経路で通す設計にはしない。

## 5. 残るリスクと対処

### 5.1 IOPL=3 でゲストの `CLI` がホストの割り込みを止める

Ys は `CLI` を 286/s（本編 96/s）発行し、対の `STI` も同数なので通常は即座に復帰する。
問題は**ゲストが `CLI` したまま暴走した場合**で、これは机上の懸念ではない
（`Ys_FM.D88` の暴走を実際に観測）。

**対処**: NMI かウォッチドッグによる脱出手段を、Phase 1 で V86 遷移機構と同時に設計する。
IOPL=0 へのフォールバックも切替可能にしておき、実測で比較できるようにする。

### 5.2 1 タイトルのみの計測

本書の数値は **Ys I 1 本**の実測に基づく。GDC/GRCG/EGC を積極的に使うゲームや、
`INT n` で BIOS を呼ぶゲームでは分布が変わる。

**対処**: Phase 1 完了後、他タイトルで追試する。ただし
「描画は VRAM 直書き」「FM はポーリング」という性質は PC-98 ゲームに広く共通なので、
結論が覆る可能性は低いと見ている。

### 5.3 テストイメージ

`Ys_FM.D88` は素の NP21/W でも本編に入れない（イメージ側の問題）。
**本編到達の検証には `Ys.D88` を使う。**
