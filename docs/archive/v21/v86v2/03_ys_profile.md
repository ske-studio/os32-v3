## 1. 計測環境

OS32 は一切関与しない。**既存の `np21x64w.ini` は変更していない** — NP21/W は
コマンドライン引数で設定ファイルとディスクを差し替えられる (`np2arg.cpp:Parse()`)。

```bash
# HDD/SCSI/FDD を空にしたプロファイル専用 INI を用意 (aidebug=true は維持)
#   $NP21W_DIR\ysprof.ini
np21x64w.exe $NP21W_DIR\ysprof.ini C:\os32\Ys_FM.D88
```

- 拡張子 `.ini` の引数は設定ファイルとして解釈される (`-i<path>` も可)
- 拡張子がディスク系の引数は FDD 0-3 に順に挿入される (`diskdrv_readyfdd`)
- 設定の読み書き先も指定した INI に切り替わる (`ini.cpp:initgetfile()`) ので、
  終了時の書き戻しも本番の INI を汚さない

**起動確認**: タイトル画面 "Ancient Ys Vanished Omen" を表示。
`/api/status` は `protected_mode=0`（リアルモード）、`CS=0x0160`、
**`grph_disp=1`**（OS32 では 0）。

> 補足: 当初 `np21x64w.ini` の `FDD1FILE` に Ys を設定して再起動したが、
> HDD (`os32.nhd`) が先に起動してしまい Ys は立ち上がらなかった。
> Ys の D88 側は正常 — IPL は PC-98 標準の `MOV AX,0060` → `INT 1Bh`、
> media byte 0x20 = 2HD で IPL の DA/UA=0x90 (1MB FDD) と整合する。
> トラック 0/0 は 256B×16 セクタ、以降は **1024B×5 セクタ**という非標準
> フォーマットで、資料にある Ys のコピープロテクトと符合する。

## 1.1 【重要】クロックは目標機に合わせること

当初 `clk_base=1996800 × clk_mult=80` ≒ **160MHz** で計測していた。
目標機は **386DX 20MHz** なので、`clk_mult=10` (1996800 × 10 = **19.968MHz**) に変更した。

**BUSY ポーリング回数は CPU クロックに比例して増減する**ため、
速いクロックのままでは I/O 回数を過大評価する。以降の数値はすべて 19.968MHz 実測。

一方 `IRET` / `CLI` / `STI` のレートは 160MHz と 20MHz でほぼ同じだった
(319/287/287 → 318/286/286)。これは §4 で確定するとおり、
これらが **OPN のハードウェアタイマ**で駆動されており CPU クロックに依存しないため。
**この一致自体が診断の裏付けになっている。**

## 1.2 使用イメージ — `Ys_FM.D88` は壊れている

| イメージ | タイトル表示 | キー入力後 |
|---|---|---|
| `Ys_FM.D88` | ✅ | ❌ **暴走** (CS=1f30 でデータ領域を実行、IRET 1,317,447/s) |
| **`Ys.D88`** | ✅ | ✅ **ゲーム本編に到達** |

`Ys_FM.D88` は 160MHz でも 20MHz でも、ディスク 1 枚でも 2 枚でも、
**OS32 が一切関与しない素の NP21/W で**同じ地点で暴走する。イメージ側の問題。

> これは前回プロジェクトの「Ys I: タイトル画面表示。本編未検証」という記録の
> 説明にもなる。V86 の限界ではなく、使っていたイメージで本編に入れなかった可能性が高い。

以降、本編の計測は `Ys.D88` を使用。

## 3. 読み取れること

### 3.1 `INT n` がゼロ — ソフトウェア割り込みを一切使っていない

タイトル中も本編プレイ中も、Ys は BIOS を **INT 経由で一度も呼んでいない**。
ハードウェアを直接叩いている。DOS を通らない独自 IPL ブートゲームなので当然ではあるが、
**INT 命令のトラップコストはゼロ**ということ。

`INT n` はタイトル・本編とも **一貫して 0**。

### 3.2 支配項は FM 音源 — しかもその 2/3 がステータスポーリング

| 場面 | FM (0x188+0x18A) | I/O 全体 | FM の占める割合 |
|---|---:|---:|---:|
| タイトル | 5,901/s | 7,331/s | **80%** |
| 本編移動 | 1,667/s | 2,367/s | **70%** |

0x0188 の読みは書きのちょうど **2.00 倍**（両場面とも）。
OPN のレジスタ書き込み前に BUSY フラグが下りるのを待つポーリングで、
§4.1 で逆アセンブルしたヘルパーの構造とバイト単位で一致する。

**ここを #GP でトラップしたら 386DX20 では成立しない。**
逆に I/O permission bitmap で素通しにすればコストはゼロになる。

### 3.3 【重要】グラフィックスは I/O をほとんど使わない

本編のフィールド描画中にもかかわらず、**GDC コマンド (0x62/0x66/0x68/0x6A)、
グラフィック GDC (0xA0-0xAE)、GRCG (0x7C/0x7E)、EGC (0x4A0-0x4AE) が
上位ポートに 1 つも現れない。**

つまり Ys は **GVRAM (0xA8000-0xBFFFF) へ CPU で直接書き込んで描画している**。
VRAM 書き込みは I/O ではなく**メモリアクセス**なので、
V86 でページテーブルに VRAM を直マップしておけば **トラップコストはゼロ**。

→ **描画は実質タダ**。これは V86 方式にとって決定的に有利な性質である。
（OS32 自身も `docs/POLICY_DEV.md` §3 で EGC/GRCG/GDC 描画コマンドを禁止し
CPU 直接書き込みに統一しているので、方針も一致している）

画面同期は **VSYNC トリガ 0x0064 の 52/s** のみ。約 52fps で 1 フレーム 1 回叩いている。

### 3.4 音楽はスレーブ PIC 側の IRQ で駆動されている

- `IRET` 318/s ≒ スレーブ PIC 読み 3,202 (=318/s)
- スレーブ PIC への書き 6,404 = 割り込み 1 回あたり 2 回 (EOI 等)
- マスタ PIC への書き 3,523 のうち約 3,202 はカスケード EOI

つまり **約 320Hz の割り込みが スレーブ PIC (IRQ8-15) から入り続けている**。
PC-98 のサウンドボード (PC-9801-26K/86) の割り込みは既定で **IRQ12 = スレーブ側**。

`CLI` 286/s ≒ `STI` 286/s ≒ 割り込み頻度と同じオーダーで、
割り込みハンドラ内のクリティカルセクションと整合する。

**このレートは 160MHz でも 20MHz でも変わらなかった** — CPU クロックではなく
OPN のハードウェアタイマで駆動されている証拠。

## 4. 【重要】Phase 3-1「Ys で FM が鳴らない」問題への示唆

前回、Ys は **FM 音源の「検出」には成功したが音が出なかった**。一方で単体の
FM テストプログラムでは鳴っていた。

§2.3 の「スレーブ PIC が約 320Hz で叩かれている」という所見から
「FM ドライバはサウンドボードの IRQ で演奏を駆動しており、前回の V86 実装は
それを注入していなかったのではないか」という仮説を立て、
**IVT の直接読み出しとブレークポイントで確定させた**。以下その結果。

### 4.1 【確定】ゲストが差し替えている割り込みは IRQ12 ただ1本

ゲストの IVT (物理 0x20〜0x5F = INT 08h〜17h) を直接読んだ結果:

```
INT 08h (IRQ0  タイマ)   FD80:01FC   BIOS ROM
INT 09h (IRQ1  キーボード) FD80:022B   BIOS ROM
INT 0Ah (IRQ2  VSYNC)    FD80:0161   BIOS ROM
INT 0Bh 〜 INT 13h                    すべて BIOS ROM
INT 14h (IRQ12 サウンド)  0160:0540   ★ RAM — ゲスト自身のハンドラ
INT 15h 〜 INT 17h        FD80:0161   BIOS ROM
```

セグメント `0x0160` は実行中の CS と一致する。
**マスタ側 (IRQ0-7) は 1 本も差し替えられていない。**

`0160:0540` にブレークポイントを置くと即ヒットし、実際に実行されていることを確認した。
ハンドラの中身:

```asm
0160:0540  fa           cli
           1e 06 50 53 51 52 56 57 55    push ds,es,ax,bx,cx,dx,si,di,bp
           8c c8 / 8e d8 / 8e c0         mov ds,cs / mov es,cs
           b6 27        mov dh, 0x27     ; ★ OPN タイマ制御レジスタ
           b2 78        mov dl, 0x78     ; タイマフラグ リセット
           e8 01 08     call 2358        ; OPN 書き込みヘルパー
           b2 7a        mov dl, 0x7a     ; タイマ再ロード
           e8 fc 07     call 2358
           a0 04 10     mov al, [0x1004] ; テンポ分周カウンタ
           3c 03        cmp al, 3
           ...
```

`DH=0x27` は **YM2203 (OPN) のタイマ制御レジスタ**で、`0x78` → `0x7A` は
タイマフラグのリセットとタイマ B の再ロード。
**OPN 自身のタイマ割り込みを確認して再起動する、FM ドライバの定番シーケンス**である。

OPN 書き込みヘルパー (`0x2358`) も確認した:

```asm
2358:  call 23ce          ; BUSY 待ち (0x188 を読む)
       mov  al, dh
       mov  dx, 0x188
       out  (dx), al      ; レジスタ番号
       call 23ce          ; BUSY 待ち (再び)
       mov  al, dl
       mov  dx, 0x18a      ; データ
```

書き込み 1 組あたり BUSY 待ちが 2 回 — 実測の
0x188 読み 20,920 / 書き 10,460 = **ちょうど 2.00** と完全に一致する。

### 4.2 確定した診断

1. Ys が差し替える割り込みは **IRQ12 (INT 14h) の 1 本だけ**
2. そのハンドラは **OPN 自身のタイマ**を確認・再起動し、曲を 1 ステップ進める
3. 演奏は**この割り込みが来ることだけ**に依存している (実測 約 320Hz)
4. 前回の V86 実装が注入していたのは **IRQ0 / IRQ1 / IRQ2** — ゲストが
   使っていない 3 本であり、**唯一使っている IRQ12 は注入されていなかった**

→ **「FM 音源は検出できるのに曲が鳴らない」の原因はこれで説明がつく。**
OPN への書き込み自体はポートが通れば届くので初期化も音色設定も成功するが、
音符を進める割り込みが一度も来ないため無音のままになる。

### 4.3 設計への含意

FM ポートをパススルーする構成では、ゲストが OPN のタイマを直接設定し、
**実際のサウンドボードが実 IRQ12 を上げる**。したがって OS32 側は

- IRQ12 のマスクを解除し、
- IRQ12 受信時に V86 ゲストへ **INT 14h を注入する**

必要がある。IRQ0/1/2 だけを注入する設計では足りない。

## 5. V86 コスト見積もり (386DX 20MHz 実測ベース)

`INT n` = 0 なので IOPL の選択がそのまま効き、描画は I/O を使わないので
パススルー対象は FM (0x188/0x18A)・I/O ウェイト (0x5F)・VSYNC (0x64) の 3 系統で足りる。
残るトラップ源は PIC (0x0000/0x0008) とキーボード (0x41/0x43) — どちらも
OS32 が共有しているため仮想化を外せない。

### 5.1 タイトル + BGM (最も重い場面)

| 構成 | トラップ源 | #GP レート |
|---|---|---:|
| **(a) IOPL=0・I/O 全仮想化**（前回の実装） | 命令 896 + I/O 7,331 | **8,227/s** |
| **(b) IOPL=0・FM/0x5F パススルー** | 命令 896 + I/O 1,334 | **2,230/s** |
| **(c) IOPL=3・FM/0x5F パススルー** | I/O 1,334 のみ | **1,334/s** |

### 5.2 ゲーム本編 (フィールド移動中)

| 構成 | トラップ源 | #GP レート |
|---|---|---:|
| (a) IOPL=0・I/O 全仮想化 | 命令 378 + I/O 2,367 | **2,745/s** |
| (b) IOPL=0・FM/0x5F/0x64 パススルー | 命令 378 + I/O 560 | **938/s** |
| **(c) IOPL=3・同上** | I/O 560 のみ | **560/s** |

**(a) → (c) で 5〜6 倍の削減。**

### 5.3 オーバーヘッド換算

386DX 20MHz で #GP 1 回のコストを、前回のような 1,000 行級の C ハンドラで
2,000 サイクル (=100µs) と見積もると:

| 構成 | タイトル | 本編 |
|---|---:|---:|
| (a) | **82%** | 27% |
| (b) | 22% | 9% |
| **(c)** | **13%** | **6%** |

ハンドラを 600 サイクル (=30µs) まで詰めれば (c) はそれぞれ 4% / 1.7%。

**結論**: 「386DX20 で 286 相当」という要件に対し、
**(c) IOPL=3 + FM/VSYNC/I-Oウェイト パススルー + VRAM 直マップ**なら十分に射程内。
**(a) は要件を満たせない** — 前回の実装が重かった理由がここにある。

### 5.4 残るコスト源と最適化余地

(c) の内訳はほぼ PIC (タイトル 1,334/s のうち 1,334、本編 560/s のうち 519)。
OS32 が PIC を共有している以上、完全仮想化は外せない。
ここが唯一かつ最大の最適化余地で、#GP ハンドラのうち PIC 経路だけを
アセンブラで短絡させる価値がある。

### 5.5 IOPL=3 の代償

ゲストの `CLI` が実 IF を落とし、ホストの割り込みまで止まる。
Ys は `CLI` を 286/s (本編 96/s) 発行し、対の `STI` も同数なので通常は即座に復帰するが、
**ゲストが `CLI` したまま暴走した場合の脱出手段**（NMI かウォッチドッグ）が必須。
実際に本調査中、`Ys_FM.D88` がデータ領域を実行して暴走する事例に遭遇しており
(§1.2)、これは机上の懸念ではない。Phase 1 で遷移機構と一緒に設計する。
