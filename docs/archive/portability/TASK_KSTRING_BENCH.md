## 0. 目的

`lib/kstring_c.c` (移植準備 順序 4-b) を **x86 でも使うか**を、思い込みではなく実測で決める。
今は `build/kernel.mk:17` の `ifeq ($(ARCH),x86)` でアセンブリ版 `lib/kstring_asm.asm` を積んでいる。
C 版に一本化できれば、アセンブリの保守が 1 本減り、他アーキの移植で分岐が消える。

**この票は計測までを範囲とする。切り替えるかどうかは計測値を見てユーザーが決める。**

## 1. 前提 (確認済み)

- 両版は同じ契約を満たすことが `tools/tests/test_kstring_c.py` で保証されている
  (同じ実行ファイルに両方リンクし、戻り値とバッファ全体を突き合わせる)。
- 対象は 13 本: `kmemcpy` `memcpy` `kmemset` `memset` `kstrlen` `strlen` `kstrcmp` `strcmp`
  `kstrncmp` `strncmp` `kstrcpy` `kstrncpy` `memcmp` (`lib/kstring_asm.asm` の `global`)。
- `kstrcmp` の符号は `-fsigned-char` と C 版の `u8` 化で固定済み。日本語ファイル名の並び順は変わらない。
- 計時は `kapi->get_tick()` (100Hz)。前例は `userland/tests/blit_test.c:168`。

## 2. 進め方

1. **計測プログラム** `userland/tests/kstr_bench.c` (CPL=3 の普通の外部プログラム)。
   - 対象 13 本を、代表的な長さで回す: 4 / 16 / 64 / 256 / 1K / 16K / 256K バイト。
     アラインは「両方 4 境界」「片方 1 ずれ」の 2 通り。
   - 1 ケースにつき、合計 1MB 以上を処理するまで繰り返し、`get_tick()` の差で測る。
     1 ケースの所要が 30 ティック (0.3 秒) 未満なら繰り返し回数を倍にする (分解能の確保)。
   - 出力は 1 行 1 ケースの固定書式 `KSTR <関数> <長さ> <ずれ> <ティック> <回数>`。
     テスターが目で読む必要がないようにする。
   - `deploy.yaml` に登録 ([V2])。
   - **アプリからカーネルの kstring は呼べない**ので、計測対象のソース (`lib/kstring_c.c` と
     `lib/kstring_asm.asm`) をプログラム側にもリンクする。方法は
     `tools/tests/test_kstring_c.py` が両版を同居させている形をそのまま使う
     (関数名が衝突するので、片方を別名で参照する薄いラッパを `userland/tests/` に置く)。
     **出荷するソースそのものを測る** — 写しを作らない。
2. **測る条件**: NP21/W で 2 つ。
   - 既定の CPU 設定 (今の `np21x64w.ini` のまま)。
   - 高速側の設定 (P100 相当)。**ini の変更は [D2]**、手順はスキル `os32-emu-config`。
     変更したら**必ず元に戻す**。
   - エミュレータの絶対時間は実機の根拠にしない。**同じ条件での asm 版と C 版の比**だけを見る。
3. **判断の材料**: 関数ごとの比 (C 版 / asm 版) の表。
   - 目安: 全体で **1.5 倍以内**なら C 版に一本化する価値がある。2 倍を超える関数があれば、その関数だけ
     asm を残す形も選択肢 (分岐が残るので推奨はしない)。
   - どちらに決めても `ARM_GAUGE.md` §9 に数字を**追記**する。

## 3. 切り替える場合にやること (決まってから)

- `build/kernel.mk` の `ifeq ($(ARCH),x86)` 分岐を外し、全 ARCH で `lib/kstring_c.c` を積む。
  `lib/kstring_asm.asm` は**消さない** (比較の基準として残す。`tools/tests/test_kstring_c.py` が使う)。
- `make clean` → `make all`。カーネルの `.text` サイズの増減を記録する。
- ゲストで `kselftest_pass` / `kselftest_fail` を**新しい `kernel.map` の番地**で読む
  ([`POLICY_DEBUG.md`](../../POLICY_DEBUG.md) §2)。kstring のケースが落ちていないこと。
- 回帰 (`tools/emu_agent/tasks/regress.txt`) を通す。

## 6. 計測結果 (2026-09-17、基点 `63754b4`)

条件: NP21/W 既定設定 (`clk_base=1996800` / `clk_mult=8` = 約 16MHz)、ExMemory 既定、
ゲストの `/usr/bin/kstr_bench.bin` (`text=7240 bss=787264 api>=55`)。
同じ条件で **3 回**測り、升ごとに中央値を取った。1 回あたり約 13 分。

生データは `docs/tasks/portability/data/kstr_bench_2026-09-17_run{1,2,3}.txt`
(ゲストの出力そのまま。`python3 tools/kstr_bench_report.py <3 ファイル>` で下の表が出る)。

3 回とも **365 行 / `KSTR DONE` 到達 / `MISMATCH` 0 件 / ティック 0 の升 0 件**。
つまり 13 本すべてで両版の結果が一致し (受入 K1 のゲスト側)、
182 升すべてで比が作れた (受入 K3 の既定条件側)。

### C 版 / asm 版 の比 (1.00 = 同じ速さ、大きいほど C 版が遅い)

ずれ=0 (両方 4 境界):

| 関数 | 4 | 16 | 64 | 256 | 1K | 16K | 256K |
|---|---|---|---|---|---|---|---|
| kmemcpy / memcpy | 1.41 | 1.96 | 3.65 | 6.73 | 9.74 | 10.94 | 11.27 |
| kmemset / memset | 1.01 | 1.22 | 1.97 | 3.75 | 5.93 | 7.41 | 7.60 |
| memcmp | 1.07 | 2.02 | 4.65 | 9.02 | 11.68 | 13.33 | 13.58 |
| kstrlen / strlen | 1.07 | 1.41 | 1.89 | 2.12 | 2.25 | 2.26 | 2.28 |
| kstrncpy | 1.11 | 1.52 | 2.03 | 2.29 | 2.37 | 2.41 | 2.41 |
| kstrcpy | 0.96 | 1.16 | 1.40 | 1.53 | 1.55 | 1.59 | 1.59 |
| kstrcmp / strcmp | 0.99 | 1.03 | 1.06 | 1.08 | 1.08 | 1.08 | 1.08 |
| kstrncmp / strncmp | 0.99 | 1.03 | 1.06 | 1.07 | 1.07 | 1.07 | 1.07 |

ずれ=1 (片方 1 ずれ) も同じ傾向で、差は最大 0.4 ポイント。
**境界のずれはどちらの版にもほとんど効かない**。

全体: 中央値 **1.55**、最悪 **13.58** (`memcmp` 256K)、最良 **0.96** (`kstrcpy` 4)。

### ばらつき (受入 K2)

3 回の同じ升で `(最大 - 最小) / 最小` を取り、**10% を超えた升は 364 中 0 件**。
最悪は `memcmp asm 1024 ずれ=0` の 3.3%。回数を増やす必要は無い。

### 読み方 — 倍率はエミュレータで膨らんでいる

倍率は **asm 側が使う命令の幅**でほぼ決まり、3 段に分かれる:

| asm 側の実装 | 該当 | 比 |
|---|---|---|
| **語幅**の `rep` (`movsd` / `stosd` / `cmpsd`) | `kmemcpy` `memcpy` `kmemset` `memset` `memcmp` の 5 本 | 6.7〜13.6 |
| **バイト幅**の `rep` (`scasb` / `movsb`) | `kstrlen` `strlen` `kstrcpy` `kstrncpy` の 4 本 | 1.5〜2.3 |
| `rep` を使わない素のバイトループ | `kstrcmp` `strcmp` `kstrncmp` `strncmp` の 4 本 | 1.07〜1.08 |

エミュレータでは `rep` の 1 命令がホスト側の転送 1 回で終わるのに対し、C 版は
同じ仕事を数千命令として解釈される。`rep` を使わない 4 本が 1.08 に留まるのがその対照で、
**実機での倍率はこれより小さい**ことを意味する。向きは動かないが、
13 倍という数字を実機の値として引用しないこと ([V4])。

### 差の出どころは C の限界ではない

`lib/kstring_c.c` の `kmemcpy` は 1 バイトずつ 4 回読んで語に組み直している。
境界をまたぐ読み込みで例外を出す機種 (ARMv5 以前、MIPS、SPARC など) を避けるための
意図的な選択で、**C 言語の限界ではない**。送り元と送り先の境界が揃っているかを先に見て、
揃っていれば `u32` のまま動かす分岐を足せば、素の C のまま差の大半は縮む。
`kstrlen` の 2.3 倍も、語単位のゼロ検出 `(v - 0x01010101) & ~v & 0x80808080` で
1 に近づく。**今回測ったのは「今日の C 版は x86 で遅い」であって「C では速くできない」ではない。**

### 測っていないこと ([V4])

- **§2 の 2 つ目の条件 (高速側 = P100 相当) は測っていない。** 必要なのは
  `np21x64w.ini` の `clk_mult` の変更で、これは [D2] の承認対象であり、
  かつスキル `os32-emu-config` が扱うキー (`USEGD5430` / `GD5430TYPE` / `USEPEGCP` /
  `ExMemory` / `e_resume`) に**含まれていない**。推測でキーを足さない方針に従い見送った。
  よって**受入 K3 は既定条件だけ充足、K4 は該当なし** (ini を変更していないので戻す対象が無い)。
- 実機 (実 PC-9801/9821) では測っていない。

## 7. 決定 (2026-09-17、ユーザー判断)

票 §0 のとおり、切り替えの可否はユーザーが決める。結果は次のとおり。

1. **x86 (PC-9801 / 9821) は今のアセンブリ版を維持する。**
   `build/kernel.mk` の `ifeq ($(ARCH),x86)` 分岐はそのまま。§3「切り替える場合にやること」は**実施しない**。
2. **`lib/kstring_c.c` は他アーキテクチャ向けの本命として、今の設計方向で進める。**
3. **対象は 32 ビットアーキテクチャに限る。16 ビットと 64 ビットは範囲外。**
   64 ビット機に載せる場合は利用者が 64 ビットのプログラムを書く。
   この前提は [`ARM_GAUGE.md`](../../tasks/portability/ARM_GAUGE.md) §10 に置いた (移植性の正典)。

数字は [`ARM_GAUGE.md`](../../tasks/portability/ARM_GAUGE.md) §9 に追記した。
