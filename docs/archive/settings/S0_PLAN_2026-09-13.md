## 3. ユーザー判断が要る点

1. **KAPI v50 (7 本) を取るか**。DESIGN 初版の「KAPI 追加なし」は S0 の静的監査で不成立と判定済み (bind 無しでは SQL 引用 / hex 化になり、RO+no-create も保証できない)。ABI break は全体 clean rebuild で吸収 (F0 の方針、承認済み)。
2. **欠損時の生成をどうするか**。DESIGN は「初期値はインストール媒体だけが持ち、通常運用では自動生成しない」。開発中の NHD には settings.db が無く、リカバリ (S3、FDD ブート) は後回しにする案なので、**明示コマンド `cfg init`** (無いときだけ、配備した `/etc/settings.tsv` の初期値から生成。既存があれば拒否) を認めるか。自動生成ではないので DESIGN の趣旨 (誤操作で設定を失わない) は保つ。
3. **F2 の扱い**: 順序修正 (DB → FD) だけを S0-K に含め、FD lease の完全統合 (F2c/F2d の全体) は後回しでよいか。cfg は「開いて読んで閉じる」「書きは 1 トランザクション」なので、子の異常終了で残るのは最悪 hot journal 1 つで、次の RO open が検出して通知する (自動回復しない) 契約で受ける。
4. **S4 の最初の消費者**: gshell の何を設定にするか (案: デスクトップ色、taskbar の時計 12/24h、壁紙のパス (無ければ単色))。少なくて良い。`assets/filetypes` の DB 移行 (ファイラの関連付け) は次段。

決裁後に S0-K / S0-D / S0-T の 3 票を切り、Codex 設計レビューへ回す。
