## 0. なぜやるか

実機 PC-9821Ra266 との会話はシリアル (`tools/rshell_serial.py`) しかない。いまは 9600 で 490 B/s、
38400 に上げても 233 B/s — **回線ではなくゲストの送信ループが上限**。配備・試験を実機で回すには
ここが開発の要になる (ユーザー、2026-09-22)。

## 1. 資料が言っていること

| 事実 | 出典 |
|---|---|
| FIFO モード: `0138h` bit0=1。データ `0130h`、ラインステータス `0132h` (bit2 RxRDY / bit1 TxRDY / bit0 TxEMP、**互換モードの `0032h` とビット位置が違う**)、モデムステータス `0134h`、割り込み参照 `0136h` (bit3-0 要因、bit0=1 で要因なし)。16 バイト。An 一部ロット・Np 以降 | `io_rs.md` 227〜350 行 |
| FIFO 搭載判定: `0136h` bit6 が**読むたびに反転**、bit5 は常に 0 | 同 304〜323 行 |
| V･FAST: `013Ah` bit7=1 で 8253 と無関係に速度。bit3-0: 1100b=9600 / 1000b=14400 / 0110b=19200 / 0100b=28800 / 0011b=38400 / 0010b=57600 / **0001b=115200**。95 年 5 月以降の機種は統合 I/O に 16550 相当を内蔵し V･FAST 可 | 同 352〜380 行 |
| 1st CCU は 8251 のまま (FIFO は前段、16550 は 2nd CCU) | 同 図「RS-232C クロック」 |
| NP21/W は `013Ah` の速度表 (資料と一致) と `0130h/0132h/0134h/0136h/0138h` を実装。`0132h` への書き込みは `0032h` と同じハンドラ (コマンド)。通信速度は模擬しない | `np21w-src/src/io/serial.c` 820〜925 行 |
| 実機 Ra266: 2.4576MHz 系、9600 = count 16、38400 = count 4 で通る | TASK_FDC_REALHW §9-1 |

## 2. 決めたこと

| 決裁 | 内容 |
|---|---|
| 起動時の既定 | **9600 の互換モードのまま** (実機で通った経路を守る)。V･FAST は `serial N` で明示的に入る |
| V･FAST に入る条件 | FIFO 搭載判定が真 **かつ** N が資料の表にある速度。それ以外は従来の 8253 経路 (割り切れなければ WARN) |
| 送信ループ | tick (10ms) を待たない。TxRDY を **1 文字時間 × 2** の予算で `cpu_delay_us` を挟んで見る。予算を超えたら従来の `hlt` へ |
| 受信 | FIFO モードでは IRQ4 ハンドラが `0132h` の RxRDY (bit2) を見て `0130h` から最大 16 バイト取る。互換モードは従来 (`0032h` bit1、`0030h`) |
| 戻し | `serial 9600` で `013Ah` bit7=0、`0138h`=0 → 互換モードへ |
| ホスト道具 | `rshell_serial.py --fast N`: 9600 で `serial N` を送り、N で繋ぎ直して `sync` |

## 4. 結果

**基準値 (修正前、bee42cc 相当、実機 Ra266、2026-09-22)**: 9600bps で `hexdump /bin/sleep.bin` (出力 69,473 バイト) が 186.1 秒 = **373 B/s**
(回線の上限 960 B/s の 39%)。`ver` (296 バイト) は 490 B/s、38400 では 233 B/s。

**往復 1 (4600a9d)**: 実装は §2 の決裁どおり (コーダー報告)。NP21/W で S3 合格: `serial` → `mode=compat baud=9600 FIFO=yes`、
`serial 115200` → `mode=V-FAST`、`ver` が返る、`serial 9600` で戻る、`serial 38400` → `[ser] 38400bps (V-FAST div 3, FIFO)`。
`make clean` → `make all` → `make external` → `make check` (app.conf の kstr_bench を 56 に上げて) 合格。

**Codex 往復 1 (4600a9d)**: Request changes。3 件とも到達可能と判断して採用:

| # | 所見 | 対処 (往復 2) |
|---|---|---|
| B1 (P1) | 切替中 (`ser_head/tail=0` の直後) に IRQ4 が入るとリングが 1 バイトずれる。0035h の 0 書きは排他でない (NP21/W は 0035h を見ずに IRQ4 を上げる) | 切替全体を `irq_disable(4)` + IF 保存/復元で囲む |
| B2 (P1) | FIFO 無し機で `--fast 115200` → 互換経路が count=1 (153600) を**適用**し、ホストだけ 115200 へ → 戻れない。FIFO 搭載 ≠ V･FAST 動作確認 | (a) exact でない 8253 速度は**適用せず現状維持** (b) ゲストの番犬: 切替後 5 秒無通信なら直前の設定へ戻して EOT (c) ホストは切替後に `ver` で確認、失敗なら 9600 へ戻って確認 |
| B3 (P2) | `--fast` の受動 EOT 待ちで成功時も 15 秒止まる | (c) で実コマンドの往復に置換 |

非 blocker (記録のみ): FIFO 16 バイト上限 + 0136h 読みの再割り込みは資料で証明不能、0x38 の bit3 は資料で不明、0132h へのコマンド書きは NP21/W の根拠のみ — すべて実機で見る。KAPI の生成物・末尾追記・CPL=3 ポインタ引数は問題なし。

**往復 2 (07b256c)**: blocker 3 件を閉じた (排他、拒否、番犬 + `--fast` の `ver` 確認)。ホスト試験 10 ケース、変異 9 本 RED。

**実機 (往復 1 のビルド 17:07、Ra266、2026-09-22)**:

| 見たもの | 結果 |
|---|---|
| FIFO 判定 | `serial` → `mode=compat baud=9600 FIFO=yes` — **Ra266 で 0136h の判定が真** |
| V･FAST 38400 | `serial 38400` → 38400 で `ver` 296 バイト + EOT、`hexdump` 69KB 完走、`serial 9600` で戻って `ver` が返る — **実機で V･FAST が効く** |
| 実効速度 | 9600: **389 B/s** (基準 373)、38400: **437 B/s** — 速度を 4 倍にしても 1 割。1 バイト約 2ms の固定費 |
| 到着の形 | ホストで 16ms ごとに 4〜10 バイトの塊 (FTDI の遅延タイマ)。9600 なら 16ms に 15 バイト出せるはずで、**ゲストが回線より遅い** |

**固定費の原因 (PM が特定、往復 3)**: `kernel/cpu_calibrate.c` は 200,000 回の nop ループを 1 回だけ回して tick で割る。
266MHz では 1 tick 未満で終わり `elapsed=1` に丸められ、`s_loops_per_tick` が実際の 1/7〜1/13。`cpu_delay_us(5)` が
実際 0.5µs になり、送信の予算 (数え上げ) が約 200µs で尽きて `_halt()` → 次の割り込み (≒2ms) まで寝る。
旧コード (100 スピン → hlt) も同じ形。**校正が短すぎた影響は ne2000 のポーリング間隔と gfx の `RASTER_LINE_US` にも及ぶ**。
対処: 校正は 5 tick 以上回して合算、送信の予算は `tick_count` の実時間で判定。

**往復 3 (a7cde1e)**: 校正を 5 tick 以上回して合算 (`kernel/cpu_calibrate_math.c`、打ち切り 200 周、ticks=0 で 1 で割らない)、
送信の予算を `tick_count` の実時間で判定 (下限 3 tick = 20ms、FTDI の 16ms をまたぐ)、IF=0 では回数上限で諦める (`_irq_enabled()`)。
ホスト試験 `check-cpu-calibrate-host` (4 ケース、変異 5 本) / `check-serial-vfast-host` 11 ケース・変異 11 本。
NP21/W: kselftest 101/101、校正カウンタ ticks=5 / rounds=16 (**エミュレータでも旧式は 1 周 1 tick 未満で丸めていた**)、
`serial 115200` → V-FAST → `ver` → `serial 9600`。`make check` exit 0 (ホスト・ハーネス 2 本に `serial_watchdog.c` を取り込む修正を含む)。

**実機 (往復 3 のビルド 17:42、Ra266、2026-09-22)** — S5/S6:

| 見たもの | 結果 |
|---|---|
| 9600 `ver` (296 バイト) | **952 B/s** (修正前 490、回線の上限 960) — 送信ループの固定費は消えた |
| `serial 115200` → 115200 で `ver` | 返る (V･FAST div 1 が実機で効く) |
| 115200 `hexdump /bin/sleep.bin` (69,473 バイト) | **21.5 秒 = 3,224 B/s** (修正前 9600 で 186 秒 = 373 B/s、**8.6 倍**)。回線の上限 11.5 KB/s には届かない — 残る固定費は約 0.3ms/バイト (hexdump 側の出力経路: 1 文字ごとの KAPI 呼び出し・画面描画・行送り) |
| `serial 9600` で戻す | 戻って `ver` が返る |

**判定**: S5 の目標 (9600 で 900 B/s 以上、115200 で 8 KB/s 以上) のうち **9600 は達成、115200 は 3.2 KB/s で未達**。
残る壁はシリアルではなく出力側 (ユーザランドの 1 文字ずつの `sys_write` と console の描画)。次の票の候補:
console の行バッファ化 / `rshell` 中の画面描画を間引く / `sys_write` のまとめ書き。
状態行の `[ser]` は `[ser] 115200bps (V-FAST div 1, FIFO)`。

**Codex 往復 2 (07b256c + a7cde1e)**: Request changes。B1 閉鎖、B3 の受動待ちは解消。到達可能な反例 4 件を採用 → コーダー往復 4:

| # | 所見 | 対処 |

| B1 (P1) | 番犬が先読み経路 (`goto read_rest`) の受信を数えず、正常な `ver` の後に旧速度へ戻る | 受信の計数をリング取り出しの 1 か所に集約 |
| B2 (P1) | 「任意の 1 バイト受信」は双方向の成立ではない (EOT 欠落・化けたバイト・ローカルキーで解除) | 解除条件を「有効な 1 行 + その応答の EOT 送信完了」に |
| B3 (P2) | `probe()` が先行コマンドの EOT を成功と取り違え、以後の応答が 1 つずれる | 本文 (`Build:`) で識別、エコー行の検査 |

**往復 4 (47e9680)**: B1〜B4 と非 blocker 3 件を閉じた (コーダー報告)。NP21/W: `serial 115200` → V-FAST → `ver` → `serial 9600`、
スプラッシュは緑の背景に OS32 ロゴ (ラスタの縞は screenshot では捉えられない)。コーダーの判断で PM が受けたもの:
`serial_has_data` は KAPI に無いので `serial_trygetchar()` を先に見て由来を判定 / `_flush_dirty_line()` は IF=0 のまま (1 行で有界) /
overflow で断った行も EOT を返しているので「往復」と数える。実機での再計測 (§3 S5/S6) と Codex 往復 3 は結果待ち。

**Codex 往復 3 (47e9680、最終)**: Request changes (ROLES §5 の 3 往復に達したので争点をユーザーへ)。B4 は閉鎖、B1〜B3 は未閉鎖:

| # | 所見 | PM の判断 |
|---|---|---|
| ① (P1) | **切替コマンド `serial N` の行そのものが番犬の最初の 1 行に数えられ、新速度で一度も通信しないまま解除される** | 到達可能、本物。番犬の arm を「切替行の EOT を送り終えた後」に移す |
| ② (P1) | 改行無しの断片 (化けた 1 バイト + 読み取り空振り) や ESC 中断も「行」として数える | 到達可能。数えるのは「改行終端・シリアル由来・実行した行」だけに |
| ③ (P1) | `serial_putchar()` に戻り値が無く、EOT 送信失敗でも完了行に数える | 到達可能。`serial_putchar` に成否を返させ (TxRDY 予算切れ = 失敗)、失敗なら数えない |
| ④ (P2) | `rsh_getch()` が serial → kbd の 2 度読みで、間に届いたバイトはシリアル由来の印が付かない | 到達可能 (窓は小さい)。シリアルは 1 か所でだけ読む (kbd の fallback からシリアルを外す = ローカルキー専用の読み口) |
| ⑤ (P2) | 遅れた切替 EOT を新速度の `ver` の失敗と読んで、正常な接続を放棄 | ホスト側: 切替応答をエコー `> serial N` で識別して EOT まで待ってから移る |
| ⑥ (P2) | `exit` のエコー無しを desync と誤判定、`startswith` が行境界を見ない | ホスト側: `exit` を例外に、エコーは行全体で比較 |

非 blocker: 「1 周 0.31 tick なので旧コードでも elapsed ≥ 1」は生値と補正後の混同 (直す)、kselftest の整合性検査が複数周で常に通る、ラスタのコメントは VRAM 転送と VSYNC 待ちも IF=0 に含む実装に合わせる。

**争点の整理**: 実機で手動の `serial 38400` / `serial 9600` は往復 1〜3 のビルドで動いている。番犬と `--fast` は
「失敗しても 9600 で会話が生き残る」保険で、いまの形は**保険が効かない場面がある** (①〜③) が、通常運用を壊してはいない。

**往復 5 (3d6dffa)**: ①②③④⑥ を閉鎖 (Codex 往復 4 の確認)。⑤ 未閉鎖 + 新規 4 件:
B1 ホストの旧速度待ち (0.5 + 5 秒) が番犬の 5 秒を越え、正常な回線でも probe が失敗し得る / B2 本文が `SER_TX_DROPPED` で
EOT だけ通るとゲストは解除・ホストは失敗 / B3 ローカル CUI の `serial N` の pending が後の正常応答の末尾で arm / B4 arm 中に
ESC で rshell を抜けると poll されない。

**設計変更 (往復 6、PM)**: 暗黙の「有効な 1 行」で双方向を推定するのをやめ、**明示の確認コマンド `serial ack`** にする。
ゲストは切替直後に arm し、新速度で `serial ack` の行を受けたときだけ解除して `ACK <baud>` + EOT を返す。ホストは
切替後すぐ新速度へ移り `serial ack` を 0.5 秒ごとに最大 4 秒繰り返し、応答本文に `ACK` が見えたら同期 (他の応答は読み飛ばす)。
rshell を抜けるときに未確認なら即座に戻す。ローカル CUI の切替は arm しない (pending 廃止)。

**往復 6 (9625500)**: 明示の `serial ack` に置換 (§4 の設計変更のとおり)。NP21/W: `serial 115200` → `serial ack` → `ACK 115200 V-FAST` で
V-FAST が維持、ack を送らずに 5 秒放置 → `[ser] no ack after switch: reverted to 9600bps` で互換 9600 へ戻る。ホスト試験
serial_vfast 12 ケース・変異 19 本、rshell_serial 6 ケース・変異 9 本。コーダーの注記: ack 窓の最後の試行 (切替から 5.5 秒) は
番犬の 5 秒をはみ出すが、失敗時は 6 秒後に 9600 で拾い直すので取り残されない。**Codex の往復は 4 回で打ち止め** (ROLES §5)。
実機での `--fast 115200` は次の実機の回で (TASK_LAN_82557 §6 の R1〜R4 と同じ回)。

**実機 (2026-09-23、Ra266、Build Sep 23 10:20、Ubuntu 24.04 ノート + FTDI FT232、`sg dialout` 経由)**:

| 項目 | 結果 |
|---|---|
| `--fast 115200 cmd ver` | 1 回目で `[rshell_serial] linked at 115200`、`ver` が返る (rc=0)。実機の 013Ah 切替と `serial ack` の往復が**ホスト側の道具ごと**通った |
| `--fast 115200 --timeout 150 cmd "hexdump /bin/cfg.bin"` | **48.7 秒で完走** (rc=0)。出力 2,396 行・189,034 バイト = **3.9 KB/s** (往復 3 の 3.2 KB/s と同じ桁。回線 11.5 KB/s の 34% — 固定費は出力経路のまま)。既定の `--timeout 15` では足りない (15 秒で timeout、その後もダンプが流れ続けて次のコマンドと混線した) |
| 番犬 | 混線のなかで `[ser] no ack after switch: reverted to 115200bps` が画面に出た = **実機でも番犬が直前の設定へ戻す**。どの `serial` 行が引き金だったかは混線で特定できず |
| **道具の欠陥** | `--fast` で上げたゲストが**終了後も 115200 に残る**ので、次の通常 (9600) の呼び出しが 3 回とも化けて timeout。復旧は `--baud 115200 --fast 9600 cmd uptime` (`linked at 9600`)。→ 同日に直した: 終わる前に `serial <--baud>` を送って `--baud` で ack を待ち `restored to 9600` と報告、repl は `exit` の前に戻す、`--keep-fast` で残せる。ホスト試験に `restore` ケースと変異 2 本を追加 (11/11 RED) |

**残件**: 出力側の固定費 (3.9 KB/s)。`hexdump` のような長い出力は `--timeout 60` 以上で。
