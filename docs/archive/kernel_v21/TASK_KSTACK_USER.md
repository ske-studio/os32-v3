# TASK_KSTACK_USER — 共有メモリ帯がカーネルスタックに食い込んでいる

> 発行: PM (Claude Code `claude-opus-5`、2026-09-17) / 状態: **受入完了 (2026-09-17)** — 決裁は §7、ゲスト受入は §8 (G4 のみ未実施)

基点: `feat/gui` = `1dd3104`。
発見: テストランナー段 3 の下調べ中 (`crash` が落ちないことから辿った)。
**カーネル層なので [`POLICY_DEV.md`](../../POLICY_DEV.md) §1 により最優先。**

> **2026-09-17 の訂正**: 初版は「アプリがカーネルスタックの戻り番地を書き換えられる」
> と書いたが、**それは誤り**。実際に使われているスタック (`0x1FF000`〜`0x1FFFFF`) は
> US=0 で守られている。本当の問題は下の §2 — **スタックが設計の 16KB ではなく 4KB しかない**。

## 0. きっかけ

`userland/tests/crash.c` は `0x1FB000` (カーネルスタックガード) へ書いて
**落ちるはず**の試験だが、2026-09-17 の実測で**落ちずに素通りした**。

    Crash test: writing to guard page (0x1FB000)...
    ERROR: should not reach here!          ← ここに来てはいけない

`fault_kill_count` は前後とも 0。`crash.bin` の OS32X ヘッダの flags は 0 なので
`--cpl0` ではなく **CPL=3 で走っている**。書いた `0xDEAD` はそのまま残り、
PTE に Dirty も立っていた。

## 1. 実測 — ページ表 1024 本の全景 (CR3=`0x14A000`、PDE 0 = `0x00141027`)

PDE 0 は master PD とアプリ PD で**共有**されている
(`kernel/paging.c:837` の `paging_pd_clone_selftest` の注記)。

| linear | P | RW | US | 何か |
|---|---|---|---|---|
| `0x100000`〜`0x15FFFF` | 1 | 1 | 0 | カーネル .text/.data/.bss — 正しい |
| `0x161000`〜`0x1BCFFF` | 1 | 1 | 0 | カーネルヒープ + KAPI — 正しい |
| `0x1BD000` | **0** | — | — | SHM 前方ガード — 正しい |
| **`0x1BE000`〜`0x1FDFFF`** | 1 | 1 | **1** | **SHM 本体 256KB** |
| **`0x1FE000`** | **0** | — | — | **SHM 後方ガード** |
| `0x1FF000`〜`0x2DCFFF` | 1 | 1 | 0 | (実際に使われているカーネルスタック + SQLite) |

## 2. 何が起きているか

`include/memmap.h` の地図はこう書いている。

    0x1FB000-0x1FBFFF カーネルスタックガード (NOT PRESENT)
    0x1FC000-0x1FFFFF カーネルスタック (16KB)

**実際はこうなっている。**

    0x1BE000-0x1FDFFF SHM 本体 (present, RW, USER)   ← ガードとスタック下 8KB を飲み込む
    0x1FE000          SHM 後方ガード (NOT PRESENT)   ← スタックの**真ん中**
    0x1FF000-0x1FFFFF 実際に使えるスタック (4KB)

原因は **番地が浮いていること**。`KHEAP_BASE` は `__bss_end` から計算され
(`include/memmap.h:73`)、ヒープ → KAPI → SHM が芋づるで動く。カーネルが育った結果、
SHM の終端が固定番地のスタックに達した。地図のコメントは今も
「カーネルバイナリ ~220KB」と書いているが、実測では `__bss_end` ≈ `0x16C000` =
**約 432KB**。

その結果:

1. **カーネルスタックは 16KB ではなく 4KB しかない。** 深い呼び出しで
   `0x1FE000` (NOT PRESENT) に当たる。**これが今いちばん危ない。**
2. **設計上のガード `0x1FB000` は存在しない。** SHM 本体なので present + USER。
   偶然の代役を `0x1FE000` の SHM 後方ガードが務めている。
3. **`0x1FC000`〜`0x1FDFFF` (地図では「カーネルスタック」) が CPL=3 から書ける。**
   ただし `0x1FE000` が塞いでいるのでカーネルは**そこまで伸びられない**。
   だから戻り番地の書き換えは**できない** (初版の記述を訂正)。危ないのは
   「地図とアプリの見え方が食い違っている」こと自体。
4. **`MEM_SHM_RESV_START` > `MEM_SHM_RESV_END` で範囲が逆転している。**
   `0x1FF000` > `0x1FAFFF`。`kernel/paging.c:200` の
   `paging_set_not_present(MEM_SHM_RESV_START, MEM_SHM_RESV_END)` は**空振り**している。
5. **次にカーネルが 8KB 育つと SHM の終端が `0x200000` (SQLite 帯) を越える。**

## 3. なぜ気づけなかったか

- `kernel/paging.c:51-55` の `STATIC_ASSERT` は「ガードとスタックが隣接」
  「スタックが SQLite 帯より下」「ページ境界」しか見ていない。
  **SHM がスタックと重ならないことを誰も検査していない。**
- `paging_set_not_present(0x1FF000, 0x1FAFFF)` のような**逆転した範囲を誰も咎めない**。
- `crash` は `void main` で終了コードを出さないので、素通りしても緑に見えた
  (票 [`../test/TASK_TEST_RESULT.md`](../test/TASK_TEST_RESULT.md) の約束事を入れた
  副産物として露見した)。

## 4. 直し方 (設計、実装は別)

**番地を動かす前に、まず検査を足す。** 検査の無い修正は同じ穴を別の場所に作る。

1. **重なりの静的検査**。`kernel/paging.c` の `STATIC_ASSERT` に足す:
   - SHM 帯 (前方ガード〜後方ガード) が `MEM_STACK_GUARD` より下で終わること
   - `MEM_SHM_RESV_START <= MEM_SHM_RESV_END` (逆転を禁じる)
   - カーネルスタックの全 16KB が他のどの帯とも重ならないこと
   これは**コンパイルで落ちる**ので、次に誰かが育てたときに必ず止まる。
2. **逆転した範囲を実行時にも咎める**。`paging_set_not_present()` /
   `paging_map_range()` が `start > end` を渡されたら**黙って 0 ページ処理せず**、
   エラーを返すか自己診断で拾う。今は空振りが成功に見える。
3. **地図と実物の突き合わせをブート自己診断に入れる**。PDE 0 の 1024 本を
   `memmap.h` の期待値と比べ、食い違いを `kselftest_fail` に数える。番地は
   `memmap.h` から引く ([C4])。**これが本体** — 1 か所直して終わりにしない。
4. **そのうえで番地を直す**。選択肢は 2 つある。**どちらを採るかはユーザー判断**。
   - (a) SHM を縮める (256KB → 192KB など)。影響: GUI の 4 ブロック予約と
     `DB_SHM_BLOCK_SIZE`。
   - (b) カーネルスタックを別の固定番地へ移す。影響: `kentry.asm` の ESP、
     TSS の ESP0、地図。
   **浮いた番地と固定番地が同じ帯で隣り合う設計そのものを見直す**のが筋だが、
   本票では 1 と 2 と 3 を先に入れ、4 は数字を見てから決める。

## 4-bis. メモリマップの洗い出し (PM、2026-09-17) と**生成への置き換え**

生きているゲストのページ表 8 枚 (PDE 0〜7) を吸い出し、`memmap.h` の地図と
突き合わせた。`__bss_end` は `build/out/kernel.map` の実値 `0x16BF20`。

| 区間 | 地図の記述 | 実測 |
|---|---|---|
| カーネル本体 | 「~220KB」 | **約 432KB** (`0x100000`〜`0x16BF20`) |
| `0x1BD000` SHM 前方ガード | NP | NP — 正しい |
| `0x1BE000`〜`0x1FDFFF` SHM 本体 | — | present + USER |
| `0x1FB000` スタックガード | **NP** | **present + USER** — 食い違い |
| `0x1FC000`〜`0x1FDFFF` スタック下 8KB | **present, US=0** | **present + USER** — 食い違い |
| `0x1FE000` スタック中央 | **present, US=0** | **NP** (SHM 後方ガード) — 食い違い |
| `0x1FF000`〜`0x1FFFFF` | present, US=0 | present, US=0 — 正しい |
| `0x200000`〜 SQLite | US=0 | US=0 — 正しい |
| `0x300000`〜 シェル | US=0 | US=0 — 正しい |

**食い違いは 3 件**、すべて `0x1FB000`〜`0x1FEFFF` に集中している。
加えて `MEM_SHM_RESV` の範囲が逆転している (§2 の 4)。

`0x160000` の 1 ページ (RO + USER) は**誤検出ではなく意図的**。
`exec/exec.c:131` が KAPI の踏み台を「アプリから呼べるが書けない」形で
写している (`PAGE_RO | PTE_USER`)。突き合わせの期待値に入れること。

PDE 1〜7 も present。PDE 0/1 が US=1 (アプリ帯と低位 1MB の共有のため)、
PDE 2〜7 は US=0。

### 手書きの地図をやめて生成にする

`include/memmap.h:24` は今も「カーネルバイナリ ~220KB」と書いている。
**実際の半分以下** — 人が維持できていない証拠。以下を作る。

1. **`tools/gen_memmap.py`** — `include/memmap.h` の `#define` を解き、
   `build/out/kernel.map` の `__bss_end` を読んで**実値の表**を出す。
   `--check` で `make check` から呼ぶ。見るのは表そのものより
   **重なりと逆転**: 帯どうしが重ならないこと、`start <= end` であること。
   **今回の穴は両方ともこれで捕まる。**
   `--write` で `memmap.h` の先頭コメントを差し替える
   (`tools/gen_tests_inventory.py` が `docs/TESTS.md` にやっているのと同じ方式)。
2. **動的な突き合わせ** — ブート自己診断で PDE 0 の 1024 本を期待値と比べる (§5 の G3)。
   期待値は `memmap.h` から引く ([C4])。

静的 (1) と動的 (2) の両方が要る。(1) は「設計が矛盾していないか」、
(2) は「実装が設計どおりか」で、**別のことを見ている**。今回の穴は
(1) が無かったので設計の矛盾が入り、(2) が無かったので実装のずれが残った。

## 7. 決裁 (ユーザー、2026-09-17)

### 7-1. 根っこ — カーネル帯域 1MB が **17KB 足りない**

    本体 433.0KB + ヒープ 320KB + KAPI 4KB + ガード 2 枚 8KB
    + SHM 256KB + スタックガード 4KB + スタック 16KB = 1041.0KB  >  1024.0KB

**この超過は今回の作業で生まれたものではない** (着手前でも 15.8KB 超過)。

**そして余裕は 224 バイトしかなかった。** `__bss_end` = `0x16BF20` の次のページ境界まで
224 バイト。ここを越えると `KHEAP_BASE` が 1 ページ上がり、**SHM 後方ガードが
実際に ESP が乗っているページ `0x1FF000` を not-present にする** → 次の `push` で三重フォルト。
票 §2 の 5 (「8KB 育つと SQLite 帯を越える」) は正しいが、**その手前 224 バイトで死ぬ**。

### 7-2. 決裁 D1 — 配置は **SHM 224KB + カーネルスタック移設** (余裕 35KB)

| | 変更前 | 変更後 |
|---|---|---|
| 共有メモリ | 256KB (16 ブロック) | **224KB (14 ブロック)** |
| GUI 予約 | ブロック 12〜15 (`+0x30000` 決め打ち) | **常に末尾 4 ブロック** (定義を変える) |
| カーネルスタック | `0x1FC000`〜`0x1FFFFF` | **`0x2FC000`〜`0x2FFFFF`** (SQLite 帯の末尾) |
| スタックガード | `0x1FB000` | **`0x2FB000`** |
| 予算 / 余裕 | 416KB / **17KB 超過** | **468KB / 余裕 35KB** |

汎用ブロックは 12 個 → 10 個。**実測で汎用ブロックを使う利用者は 1 つも無い**
(DB はブロック 0 を直接、GUI は末尾 4 個)。

**ABI 変更**: `GUI_SHM_OFFSET` が `0x30000` → `0x28000`。
`sdk/include/os32/os32_gui_shared.h` と Rust の `os32api::gui::proto` の両方。
**`make external` が要る**。

スタック移設先 `0x2DD000`〜`0x2FFFFF` (140KB) は唯一の固定空き地。
末尾に置くので SQLite 側に 120KB 残る。

### 7-3. 決裁 D2 — `KHEAP_BASE` は**浮かせたまま**。門はリンカに置く

「固定にすると無駄や枯渇時に対処しにくい」というユーザーの指摘を受けた判断。

**浮動でも固定でも使われないバイト数は同じ** — 違うのは余りがどこに溜まるかだけ。
浮動は帯の**上端**に溜まってスタックを食い、固定はカーネルとヒープの**間**に溜まる。
総量は変わらず、**違うのは尽きたときの挙動**。よって番地は動かさず、門だけ作る。

    ASSERT(__bss_end <= KERNEL_LOAD_ADDR + MEM_KERNEL_IMAGE_MAX)   ← リンカスクリプト

これで無駄ゼロ・番地の組み直し不要・**溢れたら `make kernel` が止まる**。

**副作用が本命**: 予算の上限がリンクで保証されると、**最悪の場合の配置が定数式で書ける**。
今まで重なりの `STATIC_ASSERT` が書けなかったのは `KHEAP_BASE` が
`(u32)&__bss_end` 由来で定数式でないためだが、「予算いっぱいまで育った場合」なら
すべて定数。**重なり検査が書けるようになり、`kernel/shm.c:29`/`:33` の
死んでいる表明 2 本も生き返る** (今は毎ビルド `variably modified at file scope` の
警告になり、GUI 予約の整列も帯内収まりも**一度も検査されていなかった**)。

### 7-4. 先送り — **次期カーネル v3** で全体のメモリマップを再配置する / 規約を C11 へ

今回の穴の根は「1MB の帯に 1041KB を詰めていた」こと。個別に削って凌ぐのではなく、
**帯の切り方そのものを見直す**価値がある (ユーザー、2026-09-17)。
本票では D1 / D2 までとし、再配置は **v3** の計画に載せる。

> **呼び方**: 出荷済みのカーネルが既に **2.0** を名乗っているので、次期カーネルは
> **v3** と呼ぶ ([`../../ROADMAP.md`](../../ROADMAP.md) §0、ユーザー決裁 2026-09-15)。
> 2026-09-17 の決定を最初「v2」と書いたが、**過去の決裁と衝突するので v3 に直した**。
> 放置すると後で「v2 とはどちらか」で必ず事故る。

**v3 で規約を C11 に変える** (ユーザー、2026-09-17)。**変数は固定長を維持する**
(`u32` / `i32` などの明示幅を使い続ける。`int` の幅に寄りかからない)。

C11 になると今回の話に直接効くものが 2 つある。

| 今 (C89/GNU89) | C11 |
|---|---|
| `STATIC_ASSERT` は「負の配列長」の自作マクロ。`(u32)&__bss_end` を含むと**定数式でなくなり、警告に落ちて黙って無効化される** (`kernel/shm.c` の 2 本が実際にそうなっていた) | `_Static_assert` は**定数式でなければコンパイルエラー**。黙って無効にならない |
| 宣言はブロック先頭 | 使う場所で宣言できる |

**固定長を維持する決定は、移植の前提 (32 ビットのみ、[`../../tasks/portability/ARM_GAUGE.md`](../../tasks/portability/ARM_GAUGE.md) §10) と噛み合っている。**
`int` の幅に寄りかからない限り、語長の仮定は `u32` = ポインタ幅の 1 点に閉じる。

### 7-5. v3 に持ち越す懸念 (PM、2026-09-17)

1. **メモリマップ再配置と C11 移行を同時にやらない。** どちらも全ファイルに触れる。
   同時に動かすと、壊れたときに**どちらが原因か切り分けられない**。この領域は
   静かに壊れる (本票の 224 バイトがまさにそれ)。
2. **C11 を先に。** 今の `STATIC_ASSERT` は自作マクロで、定数式でないと**黙って
   無効化される** (`kernel/shm.c` の 2 本が毎ビルド警告を出しながら何も検査して
   いなかった)。C11 の `_Static_assert` は定数式でなければコンパイルエラーになる。
   **順序を逆にすると、再配置を検査なしでやることになる。**
3. **帯の中で削るのは延命でしかない。** D1 の後でも余裕は 34KB、`KHEAP_BASE` が
   動くまで **2.4KB**。カーネルは 433KB あり育ち続けている。再配置するなら
   **カーネル本体をどこまで大きくしてよいのか**を先に決める。決めないとまた同じ場所に戻る。
4. **ARM 実装との順序を決める。** KAPI 生成器の arch 対応が v3 まで保留なので、
   再配置してから ARM に手を付けると**配置の前提が 2 回動く**。
5. **`u32` を続けるか `<stdint.h>` に寄せるか決める。** 固定長の維持は
   32 ビット限定の前提 ([`../../tasks/portability/ARM_GAUGE.md`](../../tasks/portability/ARM_GAUGE.md) §10)
   と噛み合っている。どちらでもよいが、**混在が最悪**。
