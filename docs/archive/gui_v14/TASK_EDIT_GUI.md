### 決裁 A1 — **新しい種類を末尾に追記する** (ユーザー、2026-09-17)

[API_CONTRACTS.md](../../tasks/gui/API_CONTRACTS.md) は **「op 番号・イベント種別・構造体は末尾追記のみ。
以後の変更にはユーザ承認を要する」**と凍結している。

- **既存の `WK_TEXTBOX` は 1 行のまま。触らない。** 既存の利用者 (filer ほか) に影響が出ない。
- 複数行は **新しい種類を末尾に追記**する (`WK_TEXTAREA` 等)。**契約の「末尾追記のみ」に収まる。**
- 欠点は似た部品が 2 つ並び、描画と入力の処理が一部重複すること。**受け入れる** —
  凍結契約の変更を避けるほうが重い。

**重複は共通の下請けに寄せてよい**が、**`WK_TEXTBOX` の見え方と振る舞いを変えないこと。**
変わっていないことを試験で押さえる (受入 E10)。

残りの決めること:
- **どこまでを部品が持つか。** 折り返し / 縦横のスクロール / 選択範囲 / 桁と行の表示。
  **全部を部品に持たせない** — エディタ側が持つべきものを切り分ける。
- **1 画面に入らない大きさをどう扱うか。** 部品が本文を丸ごと持つのか、
  エディタが持って見える範囲だけ渡すのか。**後者でないと大きなファイルで破綻する。**

## 3. 本文の扱い — CUI 版を再利用しない (PM 判断)

CUI 版の中身 (行の管理・取り消し・検索) は **C で 3,248 行**ある。
Rust から呼ぶことは技術的には可能だが、**この票ではやらない。**

理由: **目的が API の穴を見つけることだから。** 言語をまたぐ呼び出しを挟むと、
不具合が出たときに「GUI の API が悪いのか、橋渡しが悪いのか」が分からなくなる。
**変数を増やさない。**

代わりに **GUI 版は意図して小さく作る**。行の配列と、挿入・削除・改行だけ。
取り消しも検索も**この票では要らない** (§6)。

**CUI 版はそのまま残る。** 2 つのエディタが併存するが、**役割が違う**ので問題ない。

### 7-1. 踏んだ罠 — **`hsync` は既定で `/sys` を外す**

**最初の起動で窓が出なかった。** 例外も中断も 0 件で、`launch_orphan_count` だけが増えた。

ゲストの `/sys/lib/libos32gui.shlib` は **113,752 バイト** (手元は 125,384 バイト) のまま。
`bind()` が本数の不一致で `sys_exit` していた。

`hsync` は既定で `/sys` を外す (稼働中のシェルと共有ライブラリのため)。
**`hsync sys` と明示し、さらに再起動が要る** (共有ライブラリは起動時に読まれる)。
`hsync sys` 自身がそう案内していた。

**GUI アプリを入れ替えたら `hsync sys` + リセット。** 静かに窓が出ないだけなので気づきにくい。

## 9. 穴 H13 の原因と修正 (PM、2026-09-18)

### 9-1. §8 の見立ては外れていた

§8 は「受け手 (`WK_TEXTAREA` のキー処理) がカーソルキーを扱っていない」と書いたが、**違った。**
`app.rs` の `GUI_EV_KEY` は、ウィジェット側の処理の結果に関わらず**アプリの `on_key` を必ず呼ぶ**。
キーはアプリに届いていた。

### 9-2. 本当の原因 — `widget::set_focus()` が通知を捨てていた

フォーカス移動の通知 (`WEV_FOCUS`) には**入口が 2 つ**あった。

| 入口 | 通知 |
|---|---|
| 入力から合成 (TAB / クリック) — `on_key` / `on_button_down` | `WidgetOut` でループへ返り、`on_widget_focus` として配られる |
| **アプリが自分で呼ぶ — `widget::set_focus()`** | **`WidgetOut` を作って捨てていた。どこにも返らない** |

`edit_gui` はフォーカスを `on_widget_focus` だけで追っていた
(`widget::focused()` は**窓スロットの添字**を取り、アプリが持つ WindowId から引けない — §8 の「報告 2」)。
そのため:

1. ボタンを押す → `WEV_FOCUS`(ボタン) が届く → `focus_area = false`
2. `on_click` の末尾が `set_focus(編集面)` で戻す → **通知が来ない**
3. `focus_area` は **false のまま固定**

文字は `GUI_EV_TEXT` → フォーカス中のウィジェット経由で入り `focus_area` を見ない。
だから**アプリ側の門を通る編集キーだけが落ちた**。

**「起動直後は効くのに、一度ボタンを押すと死ぬ」**性質だった (`focus_area` の初期値は `true`)。
§8 の調査が `Open` でファイルを選んでから試したので、最初から死んで見えた。

### 9-3. 修正 — 通知を溜めてループが配る

契約もジャンプ表 (118 本) も変えていない。

- `UiState.pending_focus` — アプリ発の通知の待ち行列 (1 件、最新が勝つ)
- `widget::set_focus()` — `WEV_FOCUS` をそこへ溜める / `take_pending_focus()` で取り出す
- `app.rs` の `drain_pending_focus()` — **窓を組む間のぶん**と、**ハンドラの中で移したぶん**
  (1 件配送するごと) の 2 か所で配る。往復には上限 `FOCUS_DRAIN_MAX`

**アプリは 1 行も変えていない。** ライブラリが約束を守るようになっただけで直った。

## 10. 穴 H16 — **開いて保存するだけでファイルが伸びる** (PM、2026-09-18)

E3 (日本語) を通す途中で出た。**票が狙っていた「人が使う経路を通したら露見する穴」そのもの。**

### 10-1. 何が起きたか

275 バイトの日本語ファイルを開き、全角 2 文字 (6 バイト) を消して保存したら
**`saved, bytes 270`**。269 のはずだった。編集せずに開き直して保存すると **271**。
**編集しなくても、開いて保存するたびに 1 バイトずつ増える。**

### 10-2. 原因

`Doc::load` が**末尾の改行を空行 1 本として数えていた** (`nlines = li + 1`)。
`save_file` は行ごとに改行を書くので、その空行にも改行が付く。

```text
"L1\nL2\n"  → 3 行 (L1, L2, "")  → 保存 → "L1\nL2\n\n"  (+1)
                                   → 次に開くと 4 行 → 保存 → +1 ...
```

**単調に増える。** 内容は壊れないが、**ユーザーが触っていない部分をアプリが書き換えている。**

### 10-3. なぜ試験が捕まえなかったか

- `load_file_round_trips` は**行の中身しか見ていなかった** (`d.line(0)` / `d.line(1)`)。
  `nlines` も、保存し直したバイト列も見ていない。
- `save_writes_every_line_with_a_newline` に至っては
  **`"ab\nあ\n"` → `"ab\nあ\n\n"` を期待値として書いており、不具合を固定していた。**

**往復を「行の中身」で見ると通り、「バイト列」で見ると落ちる。** 保存の試験は
**入れたものと出てきたものをバイトで突き合わせる**こと。

### 10-4. 直し方

`load` の末尾で、最後の区切りが空なら行として数えない。

```rust
self.nlines = if len == 0 && li > 0 { li } else { li + 1 };
```

**本物の末尾の空行は残る** (`"a\n\n"` は 2 行のまま。その行の終端の改行は 1 つ前で数え終えている)。
末尾に改行の無いファイルには 1 本足す (正規化。これは仕様)。

### 10-5. 試験

- `save_writes_every_line_with_a_newline` の期待値を正した
- `load_then_save_is_byte_identical` — 4 通りの入力で**バイト列が一致**すること
- `saving_over_and_over_does_not_grow_the_file` — 4 往復して長さが変わらないこと
- `a_real_blank_last_line_survives` — 修正が本物の空行を食っていないこと
- 変異 `trailing_newline_grows_the_file` (元に戻す) が **RED** になることを実測

### 12-1. なぜ既存 (77) の意味を変えないか

`os32gui_w_focused(win)` の引数は**窓スロットの添字**。これを WindowId に変えると、
**単一窓のアプリでは添字 0 が偶然 WindowId として通らず黙って壊れる** (逆も同じ)。
コンパイルは通り、実行時に静かに間違う — H13 と同じ種類の事故になる。
**77 は据え置き、118 を足す。**
