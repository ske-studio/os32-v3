# kcg_load_font クラッシュ — デバッグ仮説計画書

## 現象の整理

### 症状
- `kcg_load_font` を外部プログラム(font_load_test)からKAPI経由で呼ぶとトリプルフォールト
- カーネル起動時に直接呼んでも同様にトリプルフォールト

### クラッシュレジスタ (共通パターン)
| レジスタ | 値 | 意味 |
|---------|-----|------|
| EIP | 0x0011A61D〜0x0011A651 | カーネルコード内 (offset ~0x1A600) |
| CR2 | 0x00000000 | **NULLポインタ参照** |
| ESP | 0x00EFFB2C (外部) / 0x0009FF00 (カーネル) | スタック位置 |
| EDI | 0x0004C0B6 | 書き込み先? (Unicode領域内) |
| ESI | 0x00006646 | ソース? (フォントキャッシュ領域内) |

### クラッシュタイミング
- `[KCG] LZ4: 180779 bytes` の出力**直後**
- `vfs_read_fd` (または `kcg_read_chunked`) に入った直後〜途中

### 重大発見: EIPの関数特定

```
$ i386-elf-nm -n kernel.elf | grep "0011a"
0011a5bc T lz4_decode      ← EIP=0x0011A61D はここ (offset 0x61)
0011a73c T datetime_to_epoch
```

> [!CAUTION]
> **クラッシュは `vfs_read_fd` ではなく `lz4_decode` の実行中に発生している！**
> 読み込み自体は成功しており、LZ4展開処理が壊れたデータまたは不正アドレスを参照してNULLポインタ参照を引き起こしている。

### 試行結果

| # | 読み込み方式 | バッファ位置 | FS種別 | 結果 |
|---|-------------|-------------|--------|------|
| 1 | vfs_read 一括 (カーネル起動時) | kanji_cache (0x01000) | ext2 | トリプルフォールト |
| 2 | vfs_read_fd 一括 180KB | kmalloc (カーネルヒープ) | HostDrv | クラッシュ |
| 3 | vfs_read_fd 一括 180KB | 0x6A000 (GFX) | HostDrv | クラッシュ (スタックガード超え→設計ミス) |
| 4 | vfs_read_fd 一括 180KB | 0x4A000 (Unicode) | HostDrv | クラッシュ |
| 5 | vfs_read_fd 一括 180KB | 0x4A000 (Unicode) | **ext2** | クラッシュ |
| 6 | vfs_read_fd 1KBチャンク | 0x4A000 (Unicode) | ext2 | クラッシュ |

### 正常に動作しているもの
- `hsync` による大ファイル転送 (5.8MB fep.db 等) — HostDrvFS → ext2
- カーネル起動時の `kcg_init()` (ROMフォント読み込み)
- ext2上の通常ファイル read/write (シェルコマンド `cat`, `cp` 等)
- `vfs_read_fd(fd, hdr, 16)` — 16バイトのヘッダ読み込みは**成功**
- `[KCG] LZ4: 180779 bytes` まで出力される → **読み込みは成功している可能性大**

## 仮説リスト (EIP=lz4_decode 判明後の再構成)

### 仮説 F: lz4_decode のソースバッファオーバーラン

> [!WARNING]
> **有力度: ★★★★★ (最有力)**

`lz4_decode(LZ4_TEMP_BUF, compressed_size, kanji_cache, KCG_PAYLOAD_SIZE)` で展開中、入力データが破損しているか、LZ4フレームのパース中に不正なオフセットが生成されて、ソースバッファ (0x4A000+) の範囲外を読み込もうとしている。

特に: ソースポインタが `0x4A000 + 180779 = 0x76DFB` を超えて進んだ場合、0x8F000 (スタックガードページ, NP) に到達して PAGE FAULT → CR2 が記録される。

**しかし CR2=0x00000000** であり、スタックガードのアドレスではない。

**別のシナリオ**: lz4_decode の内部で出力ポインタを相対参照（バックリファレンス）する際、オフセット計算が `dst - offset` で **0x01000 より下 (= 0x0xxxx = NULLガード域)** にラップアラウンドしている可能性。kanji_cache は 0x01000 から始まるが、LZ4のバックリファレンスが 0x1000 以上のオフセットを持つと `dst - offset` が 0x00000 以下になる。

**CR2=0x00000000 と一致！**

**検証方法**:
1. `lz4_decode` の実装を確認し、バックリファレンスの境界チェックを調べる
2. ホスト側で `.kcgfont` ファイルを `lz4cat` で展開して整合性を検証
3. `lz4_decode` にバックリファレンスのアドレスチェックログを追加

### 仮説 G: LZ4圧縮データの生成時の問題

> [!IMPORTANT]
> **有力度: ★★★★☆**

フォントキャッシュの `.kcgfont` ファイルは、ホスト側のPythonスクリプトで生成されたLZ4圧縮データ。

**仮説**: 圧縮時に使用したLZ4フォーマット（フレーム形式 vs ブロック形式）と、OS32の `lz4_decode` が期待する形式が不一致。Python の `lz4.block.compress()` と `lz4.frame.compress()` では出力フォーマットが異なる。

**検証方法**:
1. `.kcgfont` 生成スクリプトのLZ4呼び出しを確認
2. OS32の `lz4_decode` が期待するフォーマット仕様を確認
3. 両者の整合性を検証

---

### 仮説 H: kanji_cache (0x01000) への書き込みでNULLガードに衝突

> [!IMPORTANT]
> **有力度: ★★★★☆**

`lz4_decode` の出力先は `kanji_cache = 0x01000`。展開中に出力ポインタが進み、ページ0 (0x00000-0x00FFF, NOT PRESENT) に**後方参照(バックリファレンス)で読み込む**と CR2=0x00000000 が発生する。

LZ4のバックリファレンスは `出力ポインタ - offset` でコピー元を計算するため、展開初期に大きなoffsetが出現すると 0x01000 - offset が 0x0xxxx (NULLガード域) にアクセスする。

**検証方法**:
1. `kanji_cache` のベースアドレスを 0x01000 から 0x02000 に変更してテスト（バックリファレンスが0ページに到達しにくくなる）
2. あるいは `lz4_decode` の出力先を拡張メモリ(0x100000+)に変更してテスト

---

### 仮説 E: C89 変数宣言違反 (優先度低)

> [!NOTE]
> **有力度: ★☆☆☆☆**

`kcg_read_chunked` 内で `while` ループの中に `int chunk` 宣言がある。C89では**ブロック先頭のみ**に変数宣言が許される。GCCのgnu89モードでは許容されるが念のため修正。

## 検証計画

### Phase 1: 情報収集 (最優先)

1. **`lz4_decode` の実装を確認** — バックリファレンス処理とバッファ境界チェック
2. **ホスト側で `.kcgfont` のLZ4展開を検証** — `python3 -c "import lz4.block; ..."` で整合性チェック
3. **`.kcgfont` 生成スクリプトの LZ4 圧縮方式を確認** — block vs frame

### Phase 2: 修正・デバッグログ追加

1. `lz4_decode` にバックリファレンスアドレスの安全チェック（`if (ref < dst_start) return ERR`）を追加
2. C89変数宣言違反を修正
3. `kcg_load_font` に read 完了ログと decode 開始ログを追加

### Phase 3: テスト

1. ビルド→フルデプロイ→NP21/W起動→テスト
2. スクリーンショットでログ確認

## 備考

- CR2=0x00000000 は「NULLポインタ参照」→ 関数ポインタ経由の呼び出しで NULL が入っている可能性
- EIPが一貫して 0x0011A6xx 付近 → `nm kernel.elf` でこのアドレスの関数名を特定すべき
