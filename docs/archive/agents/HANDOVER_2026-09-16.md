## 3. H2 — hsync の置換安全化

**目的**: 新内容の書き込みと検証が済むまで**旧宛先を残す**。今の hsync は宛先を直接
`O_TRUNC` で開いて上書きするので、書き込み途中の失敗で旧内容が消える
(POLICY_DEBUG §4-36 の末尾、`hsync.1` にも制限として明記済み)。

**正典**: [`HSYNC_IMPROVEMENT_PLAN.md`](../../tasks/shell/HSYNC_IMPROVEMENT_PLAN.md) §6 (手順 6 段と保証の限界)、
§9 の受入 A14 / A15 / A17、§10 の未確定 (1)。

### 3-1. 確認済みの事実 (2026-09-16、`a8a9a42`)

- `O_EXCL` 相当は無い。open フラグは `O_RDONLY / O_WRONLY / O_RDWR / O_CREAT / O_TRUNC` だけ
  (`sdk/include/os32/os32_kapi_shared.h:484-488`)。「stat してから固定名を `O_TRUNC` で開く」は
  計画 §6 が不可としている。排他的作成を VFS と ext2 / HostDrv に足すか、専用の一時作成口を作る。
- `ext2_rename` の**ファイル**の置き換えは「宛先を `ext2_unlink` してから新しい名前を載せる」順
  (`fs/ext2_dir.c:828` 以降。ディレクトリ側 `ext2_rename_dir` は B8 で旧名を先に消す順に決裁済み)。
  つまり rename の途中で失敗すると**宛先が無い状態**が残る。H2 の置換は rename に頼るなら
  この非原子性を先に直すか、置換手順の側で「宛先が消えている状態からの復旧」を契約に入れる。
  どちらにするかは §3-4 の決裁。
- hsync 本体は `userland/system/hsync.c` (1248 行) + `hsync_protect.inc` (269 行)、
  ホスト試験は `tools/tests/hsync_h1_host.c` (1758 行) と `hsync_h3_host.c` (859 行)。
  試験は VFS を偽物に差し替えて hsync のロジックだけを走らせる形なので、H2 の失敗注入も同じ枠で書ける。
- ext2 の失敗注入の枠 (`tools/tests/b8_open_host.c`、once / sticky の掃引、`media_check`、
  `b8_e2fsck.py` の本物 `e2fsck -fn`) が B8 で出来ている。**H2 の ext2 側の変更はこの掃引に必ず通す**。
- `hsync` は `/sys` を既定で除外し、`-f` でも解除しない。H2 でも変えない。
- 一時ファイルは最大ファイル 1 本分の空きが余分に要る。ext2 の `OS32_ERR_FULL` を H2 の
  失敗経路として扱う (満杯で旧宛先を壊さない)。

## 4. H4 — 配備マニフェストと世代

**目的**: 「古い `/host` から NHD へ戻してしまう」「途中で失敗した配備を完了扱いにする」を検出する。
CRC と mtime では**どちらが意図した版か**は分からない (計画 §7-1)。

**正典**: [`HSYNC_IMPROVEMENT_PLAN.md`](../../tasks/shell/HSYNC_IMPROVEMENT_PLAN.md) §7-1〜§7-3、§9 の A18。
配備の 3 経路は [`08_build.md`](../../08_build.md) §8-4、ホスト側は `tools/hostdrv_deploy.py`、
対象の正典は各層の `deploy.yaml` ([V2])、古い物の掃除は `tools/prune_stale.py`。

### 4-1. 確認済みの事実

- `make deploy` は `deploy.yaml` を読んで `C:\os32` (HostDrv) へコピーし、`prune_stale.py` で登録外を消す。
  マニフェストを書く場所はこの経路の**最後**、全コピー成功の後 (失敗を握り潰して成功マニフェストを
  書く経路を禁じる、計画 §7-1)。
- hsync 側の集計 `copied / unchanged / excluded / protected / metadata_updated / errors` と理由コードは
  H1 で固定済み。H4 はここに `generation` (検出した世代) と `expect_mismatch` を足す。
- CRC-32 のストリーム版 `lib/crc32_core.inc` はホスト試験からも同じソースで使える
  (H1 でホスト計算と同値を確認済み)。マニフェストの CRC はこれで出す。8 桁固定の 16 進で保存。

### 4-2. 進め方

票 `docs/archive/shell/TASK_H4.md` → 設計レビュー → ホスト側 (`tools/hostdrv_deploy.py`、Python、
`tools/tests/test_hostdrv_manifest.py`) とゲスト側 (`hsync` の読み取りと検査) を**別コミット**で →
実装レビュー → ゲスト受入 (A18: 不一致 / 欠落 / 重複パス / `..` / 途中失敗)。

### 4-3. 受入

A18 の 4 反例に加えて: マニフェスト無し (H4 以前の配備元) でも今の hsync と同じ挙動 (後方互換)、
`--expect-build` 不一致は**変更前に**拒否、途中失敗した世代は「ファイル単位の成功 / 失敗一覧」だけ残す。

### 4-4. 決裁が要る点

1. マニフェストの形式と置き場: 推奨は `C:\os32\.deploy\manifest.txt` (1 行 1 ファイル、
   `path size crc8 mtime`、先頭に `format=1 build=<git SHA>[+dirty] generated=<UTC>`)。JSON はゲスト側に
   パーサが無いので使わない。
2. 世代別ディレクトリ (同期中に配備元が動かない) を H4 に含めるか: 推奨は**含めない** (運用契約
   「同期中に `make deploy` しない」で代替し、後続票に回す)。

## 5. `gdt` / `tss` / `cr3` と CPL=3 降下 asm の `arch/x86/` 移設 (移植準備 順序 5)

**目的**: ARM 計測で落ちる (a) 分類 5 本 (`exec/exec.c` `gfx/gfx_vram.c` `kernel/gdt.c`
`kernel/paging.c` `kernel/tss.c`) のうち x86 の仕組みそのものを `arch/x86/` へ寄せる。
順序 3 で作った骨格 (`include/io.h` = 契約、`arch/x86/arch_io.h` = 実装、`-Iarch/$(ARCH)` で解決) に
載せるだけで、**動作は変えない**。

**正典**: [`ARM_GAUGE.md`](../../tasks/portability/ARM_GAUGE.md) §3 (a)、§7 「順序 3 で採るなら」、§9 の計測表。
骨格の説明は `arch/README.md` と `platform/README.md`。

**進め方**: 票 `docs/tasks/portability/TASK_ARCH_X86_MOVE.md` (小さい) → コーダー → 着地。
レビューは差分が機械的なら `.o` の md5 一致で代替できる (順序 2〜4 で使った証明方法:
移設前後で `make clean && make kernel` し、`kapi_sys.o` を除く全 `.o` の md5 が一致すること。
`kapi_sys.o` だけは `__DATE__` で毎回変わる)。**md5 が変わる変更は機械的ではない**ので、その時はレビューへ。
終わったら `make check-arm-compile` を回し、ARM_GAUGE §9 の表に**追記** (置き換えない)。
`tools/check_arch_asm.py` の `ARCH-ASM-OK` 許可コメントは、移した先で不要になったら外す。

**やらないこと**: `gfx/gfx_vram.c` の VRAM 直書きはデバイス層 (`platform/`) の話で、順序 5 には含めない。
`exec/exec.c` の降下 asm は**移すだけ**、リング遷移の順序や IF の扱い (POLICY_DEBUG §4-19) を変えない。

## 6. kstring を x86 でも C 版にするかの判断

**目的**: `lib/kstring_c.c` (順序 4-b、`ARCH != x86` で使う) を x86 でも使うかを**実測で**決める。
今は `build/kernel.mk:17` の `ifeq ($(ARCH),x86)` で asm 版 (`lib/kstring_asm.asm`) を選んでいる。

**確認済み**: 両版の等価は `tools/tests/test_kstring_c.py` (同じ実行ファイルに両方リンクして照合、
unsigned 比較、pad 無し) で保証済み。`kstrcmp` の 0x80 以上のバイト = 日本語ファイル名の並び順は
`-fsigned-char` で固定済み (ARM_GAUGE §6)。

**進め方**: ゲストで測る。`kselftest` に kstring の計時ケースを足すか、`userland/tests/` に
`kstr_bench` (memcpy / strlen / strcmp を 1MB 級で N 回、`kapi->get_tick()` で計る。
`userland/tests/blit_test.c:168` が同じ測り方をしている) を置く。
ASM 版と C 版のカーネルを NP21/W (i386 相当と、`np21x64w.ini` の CPU 設定を上げた P100 相当の 2 条件) で
比べる。**エミュレータの絶対時間は実機の根拠にしない** — 比を見る。
判断の目安: C 版が asm 版の 1.5 倍以内なら C 版に統一 (保守 1 本化)、それ以上遅いなら asm 版を残す。
どちらでも ARM_GAUGE §9 に数字を追記する。切り替えるなら `build/kernel.mk` の分岐を消し、
`kselftest` の kstring ケースが `kselftest_fail = 0` のまま通ることを新しい `kernel.map` の番地で読む
(POLICY_DEBUG §2)。

## 7. ゲスト側の一括試験ランナー

**目的**: 所定の試験 (kselftest、`userland/tests/` の各バイナリ、hsync / ext2 の実機項目) を
ゲストで一括実行し、**合否を機械が読める形でホストへ返す**。v3 の ABI 整理は「変更のたびに全試験を
ゲストで回せる」ことが前提なので、その前に作る (2026-09-15 のユーザーの思考、PM 評価: ランナーが先)。

### 7-1. 確認済みの事実 (ここが着手点)

- シェルに **`$?` が無い**。`env_expand()` (`userland/shell/cmd_env.c:97`) は環境変数の展開だけ。
- 外部プログラムの終了コードは**シェルが捨てている**: `userland/shell/sh_launch.inc:126` は
  `LAUNCH_ST_DONE` なら状態の下位バイトを見ずに `EXEC_SUCCESS` を返す。カーネル側は
  `exec_exit_status` (`exec/exec.c:169`、`kapi_sys_exit` が設定) を持ち、`exec_run` の CUI 経路は
  それを返している (`exec/exec.c:1552`) ので、**捨てているのは launch 表を経由する経路**。
- スクリプト実行 `script_source_file()` (`userland/shell/cmd_script.c:211`) は行を順に実行するだけで、
  失敗で止まる仕組み (`set -e` 相当) も無い。
- ホスト側の道具: `/api/cmd` は **POST の生ボディ**、画面は `/api/tvram` の `lines`、
  シェルの `time CMD` 組み込みが `real N.NNNs` を出す。テスターの回帰台本は
  `tools/emu_agent/tasks/regress.txt` (合否は `steps.jsonl` の `obs` を PM が読む)。
- 結果チャネルの候補は **HostDrv** (`/host` に結果ファイルを書けばホストの `C:\os32` に即座に見える)。
  画面スクレイプ (tvram) より確実で、[V4] の「文言で判断しない」にも合う。

### 7-2. 進め方 (3 段、各段を別票に)

1. **`$?` と終了コードの配線** (`docs/archive/shell/TASK_EXIT_STATUS.md`): launch 表の状態語は
   `exec/launch.c:266` で `LAUNCH_ST_DONE` を**そのまま**返し、終了コードを載せていない
   (`r->rc` は FAILED の側でだけ使う)。DONE の下位バイトに `exec_exit_status` を載せ、
   `sh_launch.inc:126` でそれを返す。`env_expand` に `$?` を足す。スクリプトに
   `set -e` 相当 (`script_abort_flag` は既にある) と `exit N`。ホスト TDD は `tools/tests/sh_launch_host.c` の枠。
   **注意**: 常駐シェルは `int` で受けると `-Wincompatible-pointer-types` (`sh_launch.inc:66` のコメント)。
2. **結果チャネル** (`TASK_TEST_RESULT.md`): 試験バイナリの約束事を決める —
   終了コードで合否、詳細は `/host/test/<name>.txt` に `PASS|FAIL <name> <理由>` を 1 行 1 件。
   `userland/tests/` の既存バイナリを順にこの約束に合わせる (全部ではなく、回帰台本に入っている物から)。
3. **ランナー** (`TASK_TEST_RUNNER.md`): ゲスト側 `runtests` (スクリプトで十分なら
   `/sys/etc/runtests.sh`) + ホスト側 `tools/guest_tests.py` (POST `/api/cmd`、`/host/test/` を集計、
   非ゼロ終了)。`make check-guest` として `make check` とは**別**にする ([D1] と NP21/W の稼働が要るため)。
   `tools/emu_agent/agent.py` の `MAKE_TARGETS` に足す。

### 7-3. 決裁が要る点

結果チャネルを HostDrv にするか (推奨)、tvram スクレイプで済ませるか。HostDrv だと NHD ブートでも
`/host` がマウントされている前提になる (今の運用では常にそう)。

## 11. 作業の型 (毎回同じ)

```
票を書く (docs/tasks/<領域>/TASK_<ID>.md、状態行「計画」)
  → 設計レビュー (Codex、3 往復まで、blocker は到達可能な反例つきのみ)
  → 状態「設計中」→「実装中」
  → コーダー (Opus 5、worktree、基点 SHA を依頼文に、最初に git log -1 を報告させる)
  → ホスト TDD RED→GREEN、tools/tests/<id>_tdd.md に記録、build/sdk.mk に check-* 登録
  → 実装レビュー (網羅指示つき)
  → 着地: worktree の差分を基点と比較 → feat/gui にコミット → make all → make check → push
  → ゲスト受入 ([D1]、os32-build-verify、[V4] で正直に) → 状態「受入完了 (日付)」
  → tools/gen_tests_inventory.py --write (試験を足したら) → main へ --no-ff merge → push
  → 票を tools/move_docs.py で docs/archive/<領域>/ へ (INDEX の行も動く)
```

## 12. 踏むと痛い所 (この 1 週間で実際に踏んだもの)

- **worktree の基点が古い** (`main` 側の古い merge から始まる) — 2 度踏んだ。依頼文に SHA を書き、
  報告の先頭で確かめる。「文書が無い」と言われたら基点を疑う (ROLES §2)。
- **Codex は stdin を閉じないとハングする** — `< /dev/null`。
- **push 忘れ** — Codex はリモートを見るので、着地したら即 push。
- **消費側を直さずに供給側だけ直して出荷した** — `hdrv_list_dir` の上限エラーを通した結果、
  `fs_is_dir` / `vfs_path_kind` / `vfs_open_internal` の 3 か所が壊れた (B5〜B7)。述語を変えたら
  **受け手を実物で通す**。
- **`/api/cmd` は POST の生ボディ**、`/api/tvram` は `lines`。完了検知は画面の変化ではなく
  ゲストの `time` 組み込みか結果ファイルで。
- **KAPI を足したら** `make clean` → `make all` → `make external` ([ABI3])。`kapi_db.c` の
  `db_slot_layout_ok` は下限比較 (等号で縛ると次の追加で落ちる)。
- **`.inc` を変えても `.bin` は再ビルドされない** — `build/programs.mk` に明示依存。
- **NHD 配備の後は先に `make deploy`** — `hsync` は HostDrv の内容で NHD を上書きする (§4-33)。
- **`kernel.bin` の md5 は毎回変わる** (`kapi_sys.o` の `__DATE__`)。等価の証明は `.o` 単位で。
- **文書を動かしたら** `make check-docs-links` / `check-docs-orphans` / `check-tests-inventory` が落ちる。
  `tools/move_docs.py` を使えば参照は書き換わる。新しい文書は `docs/INDEX.md` に行を足す
  (足さないと孤児検査で落ちる。`docs/.orphans-allow` は「意図した例外」専用)。
