> 実装済み・実機受入済み (`faa14df`、KAPI v52)。

- 正典: [`HSYNC_IMPROVEMENT_PLAN.md`](HSYNC_IMPROVEMENT_PLAN.md) §5 (取得・保存)、§8 の **H3** 行
- 前提: [`TASK_H1.md`](TASK_H1.md) の着地 (内容比較と CRC 検証)。H2 とは独立

## 1. なぜ H1 と分けて、しかし先送りにしないか

現状は **時刻を読めるのに設定できない**という非対称になっている。

| 経路 | 現状 |
|---|---|
| `OS32_Stat.st_mtime` | 定義済み (`sdk/include/os32/os32_kapi_shared.h:464`) |
| ext2 の読み | 実装済み (`fs/ext2_vfs.c:277`) |
| FAT の読み | 実装済み (`fs/fatfs_vfs.c:325`) |
| `sys_stat` の CPL=3 公開 | 実装済み (KAPI スロット 8) |
| **HostDrv の読み** | **`hdrv_stat()` が `st_mtime` を埋めていない** (`fs/hostdrvfs.c:635`) |
| **VfsOps の設定フック** | **無い** |
| **KAPI の設定口** | **無い** |

ext2 は inode に `mtime` を保持し、書き込みのたびに現在時刻で更新している (`fs/ext2_file.c:183`)。
値は持っているのに外から与えられないだけで、能力が欠けているわけではない。

KAPI は追記専用 ([ABI2]) なので、末尾へのスロット追加は既存の ABI を壊さない。
カーネルが持つ能力を CPL=3 へ渡すのに `__cdecl` ラッパを足すのは本プロジェクトの通常手順であり ([C3])、
**スロットを足さないことに価値は無い**。H1 と分ける理由は設計思想ではなく次の 2 つだけである。

1. [ABI3] により版を上げて `make clean` → `make all` と `make external` (`apps/` / `game/` の再ビルド) が要る。
   H1 の着地をこのゲートに縛らない。
2. FILETIME の変換境界 (1970 年より前・未提供・範囲外) と非対応 FS の扱いが、比較ロジックとは別種の検証を要する。

hsync のコピー元は HostDrv なので、**§3 の取得側を直さない限り時刻は一切伝播しない**。
H3 は取得と保存の両方で 1 つの機能になる。

## 2. 範囲

計画 §8 の H3 行: 「HostDrv 時刻変換、mtime 設定 API、時刻のみの同期」。
対象は `fs/hostdrvfs.c`、`VfsOps`、ext2、`sdk/kapi.json`、`hsync`。
`atime` / `ctime` は同一判定に使わない。`OS32_Stat` の拡大は本票に含めない (時刻欄は既にある)。

## 3. 取得 (計画 §5.1)

- `hdrv_stat()` が `LastWriteTime` を `st_mtime` へ返す。NT 系 FILETIME は **1601-01-01 UTC 起点・100ns 単位**。
  Unix 秒へ変換し秒未満を切り捨てる。変換は **64bit 中間値**で行い、1970 年より前・未提供値・変換不能・
  `os_time_t` の範囲外を検査して回り込みを防ぐ。**UTC に JST の 9 時間を加算しない** (ローカル時刻化は表示側)。
- Basic / Standard 問い合わせの失敗を成功にしない。ホスト open のエラーを一律 NOTFOUND に畳まず、
  実際の不存在と I/O 等を区別する (H1 の stat 是正と同じ箇所なので**着地順に注意**)。
- 取得した Basic 情報は、次の問い合わせで共有バッファが上書きされる前に値として退避する。
- 現行 ABI に時刻の有効性ビットが無いため、hsync は **`mtime = 0` を「同一判定の根拠に使えない」と保守的に扱う**。
  Unix epoch そのものと不明の区別は将来の拡張 stat で定義する (計画 §10 の未確定 (2))。

## 4. 保存 (計画 §5.2)

- 仮称 `sys_set_mtime(path, mtime)` を `sdk/kapi.json` の**末尾**に追加し、VfsOps に**任意実装のフック**を足す。
  **現段階でスロット番号を予約しない**。版は実装時に [`KAPI_SPEC.md`](../../KAPI_SPEC.md) と調停する (現行 51)。
- **ext2 のみ先行実装**し、非対応 FS は `NOSYS` を返す。読取専用・不正時刻・パス／ポインタ不正は明示エラー。
- **データを書き終えてから**コピー元 mtime を設定する。宛先 `ctime` はゲスト側の変更時刻とする。
  H2 の rename も `ctime` を変え得るので適用順を固定する。
- 内容が同じで時刻だけ違うなら**本体を書き直さず mtime だけ更新**する (`metadata_updated`)。
- 元の mtime が不明なら時刻保存を省略したことを表示し、内容同期は続行する。
  有効な時刻の保存を試みて失敗したら **`metadata_failed` + 非ゼロ終了**。
  内容コピーの成功だけで全成功と表示しない。
- H1 で導入した集計に `metadata_updated` を加える (計画 §7.2 の 6 区分が揃う)。

## 5. ABI 手順 ([ABI1]〜[ABI3])

`sdk/kapi.json` が唯一の真実。生成物を手で編集しない。版を上げ、`make clean` → `make all` →
`make external` で `apps/` と `game/` を再ビルドし、全生成ファイルへの影響を確認する。
CPL=3 からのポインタ検証を含める。

## 8. 日時を同一判定の前置フィルタにする (ユーザー決裁 2026-09-15)

### 経緯

H1 の実測で、**変更が 1 件も無い場合**の所要時間が次のようになった
([`TASK_H1.md`](TASK_H1.md) §9)。

| 操作 | ファイル数 | 対象 | 実測 |
|---|---|---|---|
| `hsync` (全体) | 235 | 24.8 MB | 135.350 s |
| `hsync sys` | 6 | 4.9 MB | 25.810 s |

費用は読んだバイト数にほぼ比例する (実効 366〜380 KB/s、両側を読むので実 I/O は 2 倍)。
共有ライブラリを 1 本差し替えるたびに `hsync sys` で 26 秒を払うのは実用に耐えない。

Codex に改善案を相談した結果、**読まずに同一を証明するには「前回一致を確認した」
「コピー元がそのときと同じ」「宛先がその後書かれていない」の 3 条件が要る**と整理された
(不変な配備元 + カーネルの宛先変更追跡)。これは KAPI 追加とカーネル改修を伴う大きな作業で、
H4 が前提になる。

**ユーザー決裁**: 日時で判定する方式を採る。強制上書きはオプションとして残す。

### 決めたこと

計画書 §10 の「日時だけの高速スキップは初期版に入れない」を**本決裁で更新する**。
ただし日時は「省略の根拠」ではなく**前置フィルタ**として使う。

| 状態 | 動作 |
|---|---|
| サイズか日時が違う | **内容を比較**して、違えばコピー (H1 の確実さをそのまま適用) |
| サイズも日時も同じ | スキップ (`unchanged`) |
| **日時が不明または 0** | **内容を比較する** (証拠が無いことを同一の根拠にしない) |

この形なら、候補に挙がったものについては**バイト単位の確実さが残る**。
日時の粒度 (ext2 は秒) で取りこぼす心配も、候補に入った時点で消える。

### 見込み

`make deploy` が更新するのは通常数ファイル (直近の実行で 5 件)。日時で絞れば
読むのはその数ファイルだけになり、残りは `stat` のみ。
`hsync sys` は 26 秒 → 1 秒程度、全体同期は 135 秒 → 数秒程度になる見込み。

### 失うもの (明記する)

**「サイズが同じ、かつ日時も同じ、かつ中身が違う」場合だけ見逃す**。
現実に起きるのは、時刻を保存する書庫から古いビルドを戻したとき、`cp -p` で複製したとき、
ビルド系が時刻を引き継ぐとき、**同じ 1 秒の中で 2 回ビルドした**とき (ext2 は秒単位)。

2026-09-14 に踏んだ事例 (再ビルドした `libos32gui.shlib`) は**日時が変わるので捕捉できる**。
あれは「サイズだけを見た」ことによる取りこぼしだった。

### オプション

- `-f` / `--force` — 既存。比較を省いて無条件にコピー。保護と検証は省かない。
- **内容を必ず比較する選択肢を新設する** (仮称 `--verify`)。H1 の現挙動そのもので、
  確実さが要るときだけ費用を払う。日常は速く、疑わしいときだけ徹底する。

### この票の位置づけが変わる

H3 は「H1 の直後にやるとよいもの」ではなく、**H1 を実用にするための前提**である。
とくに**保存側 (`sys_set_mtime`) が無いと成立しない**点に注意する。
宛先の日時は現状「hsync がコピーした時刻」なので、コピー元の時刻を宛先へ書かない限り
**全ファイルが永遠に「変更あり」に見えて 1 件もスキップされない**。
取得側だけでは速くならない。

## 9. 実機受入 (2026-09-15)

配備: `make deploy` → NHD を実機側から取り込み (`nhd_deploy.py pull`) → `os32-cycle deploy`
(vmkernel 478977 B 一致)。B8 (`b32c34b`) と同時に配備した。

**取得**: `stat /host/sys/lib/libos32gui.shlib` が `mtime=1789448856` を返した。NP21/W は
`LastWriteTime` を返す実装で、FILETIME → Unix 秒の変換が実機で効いている。
コーダーが懸念した「時刻が 0 なら全件比較に落ちる」経路には入らない。

**速度** (ゲストの `time`、変更 0 件、1 回目は宛先の時刻を揃えるため全件を読む):

| 操作 | 1 回目 | 2 回目 | H1 のみ (§8) | 短縮 |
|---|---|---|---|---|
| `hsync sys` (6 本 4.9 MB) | 25.750 s (`metadata_updated=6`) | **0.260 s** | 25.810 s | 約 1/100 |
| `hsync` 全体 (233 本 24.8 MB) | 145.940 s (`metadata_updated=232`) | **2.870 s** | 135.350 s | 約 1/47 |

§8 の見込み (26 秒 → 1 秒程度、135 秒 → 数秒程度) を満たした。2 回目は `stat` だけで
本体を読んでいない。共有ライブラリ 1 本の差し替えごとに払う費用は 26 秒から 0.3 秒になった。

**確認済みの限界** (§8): サイズも日時も同じで中身が違う場合だけ見逃す。`--verify` で全件比較に戻せる。
