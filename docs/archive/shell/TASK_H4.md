## 0. 目的

**「古い配備元から新しい成果物へ戻してしまう」事故を検出する。**

内容の違いは H1 の内容比較で分かる。しかし**どちらが意図した版か**は分からない。
`make deploy` を忘れたまま `hsync` を打てば、ゲストの新しいファイルがホストの古いもので
上書きされる。これは「同期が成功した」ように見える。

H4 は配備元に**世代の名札**を置き、`hsync` がそれを読んで食い違いを報せる。

## 1. 確認した事実 (2026-09-16、`9742a6b`)

1. ホスト側の配備は `tools/hostdrv_deploy.py sync`。層ごとの `deploy.yaml` を
   `tools/deploy_manifests.py` がまとめ、`C:\os32` (WSL から `/mnt/c/os32`) へ写す。
2. 失敗の扱いは H2 の往復で直っており、**コピーの失敗は握り潰さない** (`state` が
   `'ok'` / `'protected'` / `'error'`、致命的な失敗は `sys.exit(1)`)。
   **マニフェストを書く場所はこの成功判定の後**にする。
3. `hsync` 側には既に理由コードと集計がある (H1 / H2)。**世代の照合はここに足す**。
4. CRC-32 のストリーム版 `lib/crc32_core.inc` はホストとゲストで同じ値を出すことを
   H1 で確認済み。マニフェストの CRC はこれで出す。
5. ゲストに JSON のパーサは無い。**行指向の平文**にする。
6. 版の識別に使えるもの: `git rev-parse --short HEAD`、作業ツリーの汚れ (`git status --porcelain`)、
   `build/out/kernel.map` の有無。**日時や SHA の大小で新旧を決めない** (計画 §7-1)。

## 2. 設計

### 2-1. マニフェストの形式 — 決裁 D1

**推奨 (a)**: `C:\os32\.deploy\manifest.txt` (行指向の平文、UTF-8、LF)。

```
format=1
build=9742a6b+dirty
generated=2026-09-16T21:45:19Z
count=198
---
bin/cat.bin 16428 3b7f2a10 1789520013
boot/vmkernel.lz4 481400 a41c0e55 1789520100
```

- 先頭は `key=value` の行、`---` の後が 1 行 1 ファイル。
- ファイルの行は **パス / サイズ / CRC-32 (8 桁 16 進、小文字) / mtime (Unix 秒)**。
  区切りは空白 1 つ。**パスに空白を含むファイルは配備対象に無い**ことを検査で固定する
  (在ったら配備側が拒否する)。
- `build` は `<短い SHA>` に、作業ツリーが汚れていれば `+dirty` を付ける。
  **これは「同じか違うか」を見るための名札で、順序を表さない**。
- パスは `C:\os32` からの相対。**絶対パスと `..` は書かない・読まない**。

(b) 案: JSON。ゲストにパーサが無く、書くだけで数百行の実装が要る。推奨しない。

### 2-2. 書く側 (`tools/hostdrv_deploy.py`)

- **全ファイルの配備が成功した後にだけ書く**。1 件でも `error` があれば書かない
  (既にあるマニフェストは**消す** — 古い名札が残ると「配備済み」と誤読される)。
- 書き方は **一時ファイル + 置き換え**。中途半端なマニフェストを読ませない。
- `--no-manifest` で抑止できるようにする (調査時に使う)。

### 2-3. 読む側 (`hsync`)

- 起動時に `/host/.deploy/manifest.txt` を読む。**無ければ今までどおり動く** (後方互換)。
- 読めたら **1 行目に世代を表示**する: `DEPLOY build=9742a6b+dirty count=198 generated=…`。
- **`--expect-build <ID>`**: 名札が違えば**1 件も書かずに**非ゼロ終了 (`reason=build_mismatch`)。
  一致の判定は文字列の完全一致。**大小を比べない**。
- 既定 (`--expect-build` 無し) は**表示だけ**して同期を続ける。
  **勝手に拒否しない** — 意図した巻き戻しもあるため (計画 §7-1)。
- マニフェストは**全件を先に検査**してから使う。1 件でも壊れていたら**名札ごと捨てる**:
  - **`--expect-build` を指定していないとき**は表示だけして同期を続ける
    (`DEPLOY manifest invalid: <理由>`)。名札の不備で作業が止まるのは本末転倒。
  - **`--expect-build` を指定して、範囲を絞っていない (全体同期) ときは断る**
    (`reason=manifest_invalid`、1 件も書かずに非ゼロ終了)。利用者は世代を確かめるつもりで
    指定している。**名札が読めないことを「一致」と扱わない**
    (往復 1 所見 2: 壊れた名札で保護が素通りすると、H4 が防ぐはずの事故がそのまま起きる)。
  - **範囲を絞った同期 (`hsync usr` のように引数がある) では表示だけにして続ける**
    (往復 2 所見 1)。名札はルートの世代を表すもので、絞った範囲の正しさを保証しない。
    ここで止めると「名札の不備で作業が止まる」形になり、本末転倒。
  捨てる条件:
  - 形式版が `1` でない / `---` が無い / `count` と行数が合わない
  - 重複するパス / 絶対パス / `..` を含むパス / 長すぎるパス (`NAME_CAP` 超)
  - サイズや CRC の桁が不正
- **マニフェストを信じて内容比較を省かない** (初期実装)。CRC が一致していても、
  宛先が同じである証明にはならない (計画 §7-1)。**永続 CRC キャッシュも作らない**。
- **集計の数え方** (往復 2 所見 2 で設計を訂正):
  `hsync` は**配備元を正として列挙する** (`sync_directory`)。名札にあるのに配備元に無いファイルは
  **列挙に現れないので、そのままでは数えられない**。数えるには名札を正とする走査が別に要る。
  - `manifest_extra=N` (名札に無いものを写した) は**今の列挙のまま数えられる**。各ファイルを
    写すときに名札の表を引けばよい。**初期実装はこれだけにする**。
  - `manifest_missing` (名札にあるのに配備元に無い) は**初期実装では出さない**。
    名札の全件を配備元に対して `stat` し直す走査が要り、128 件の列挙上限や `/sys` の既定除外と
    絡むので、**別票**にする。票にそう書く。
  - 名札を引く表は**メモリ上限がある**。`hsync` の既存の上限 (`MAX_FILES` 128 / `NAME_CAP` 64) と
    同じ考え方で、名札が大きすぎたら**名札ごと捨てる** (`manifest invalid: too many entries`)。
    実際の配備は約 200 件なので、上限は実測に合わせて決める (票では値を固定しない)。

### 2-3-1. 保証しないこと — 配備と名札の間の非原子性 (レビュー往復 1 所見 1)

**ファイル群のコピーと名札の更新は原子的ではない。** 全件のコピーが成功した後、名札を書く前に
ホストが落ちると、**配備元は新しいのに名札は古い (または無い)** 状態になる。
「一時ファイル + 置き換え」が守るのは**名札そのものの完全性**だけで、この隙間は埋まらない。

この状態で `--expect-build <新しい ID>` を打つと **`build_mismatch` で断られる**。
ファイルは新しいのに同期できない。**安全側の壊れ方**ではあるが、起こることとして書いておく。

復旧は `make deploy` をもう一度打つだけ (名札が書き直される)。
埋めるには配備の完了を示す別の印か世代別ディレクトリが要るので、**§2-4 の範囲外**とする。

### 2-4. しないこと (H4 の範囲外)

- **世代別ディレクトリ** (同期中に配備元が動かない仕組み)。本命だが別票。
  運用契約「同期中に `make deploy` しない」で代替する (計画 §7-1)。
- `kernel` / `shlib` / `apps` を**原子的に切り替える**保証。
- SHA-256 の併記。CRC-32 で足りる用途に限る。
- **`manifest_missing` の集計** (名札にあるのに配備元に無い)。名札を正とする走査が要る。別票。

### 7-1. 票に書かれていない判断 (PM の確認が要る)

1. **名札そのものが同期対象になる。** `/host/.deploy/manifest.txt` は列挙に
   現れるので `/.deploy/manifest.txt` へ写る。除外の規則は足していない
   (票が求めておらず、H1〜H3 の規則を変えない方針のため)。ただし
   **名札自身の写しは `manifest_extra` に数えない** — 名札は自分の CRC を
   自分に書けないので、数えるとまっさらなゲストで必ず 1 になり、本当の
   食い違いが埋もれる。
2. **`--no-manifest` と `--tag` の部分配備でも古い名札を消す。** 票は「1 件でも
   失敗したら消す」しか書いていないが、新しいファイル + 古い名札が残ると
   `--expect-build <古い ID>` が**一致**してしまい、この票が防ぐ事故が裏返る。
3. **~~名札が無い + `--expect-build` は絞り込みでも断る~~ → PM 決裁で訂正
   (2026-09-16)。** 初版は M12 の例外が「名札が壊れている」場合にだけ書かれて
   いるのを字義どおりに取ったが、M6c との非対称が筋の通らないものだった。
   **「確かめられない」ときの扱いは、名札が壊れていても無くても同じにする**:

   | 状況 | 全体同期 | 絞り込み |
   |---|---|---|
   | 読めて**不一致** | 断る (`build_mismatch`) | **断る** (protection の本体) |
   | **壊れている** | 断る (`manifest_invalid`) | 表示のみ・続行 |
   | **無い** | 断る (`manifest_absent`) | 表示のみ・続行 |

   根拠は往復 2 で確認した「名札はルートの世代を表すもので、絞った範囲の
   正しさを保証しない」— この理屈は壊れている場合と無い場合に等しく当たる。
   一方、読めて**不一致**と分かった場合は絞り込みでも断る:
   **「確かめた結果おかしい」と「確かめられない」は別**だから。
   語を分けたのは、`manifest_missing` (§2-4 の別票の集計名) と紛れないよう
   `manifest_absent` にした。
