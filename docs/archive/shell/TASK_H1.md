# TASK_H1 — hsync: 同サイズ更新の検出 (内容比較 + CRC 検証)

> 発行: PM (Claude Code / Fable 5.1) (2026-09-15) / 状態: **受入完了 (2026-09-15)**

- 正典: [`HSYNC_IMPROVEMENT_PLAN.md`](HSYNC_IMPROVEMENT_PLAN.md) — ユーザー起草。**設計判断はこの文書に従う**
- 段階: 計画 §8 の **H1**。H2 (一時ファイル・置換の安全化) / H3 (mtime) / H4 (manifest・世代) は別票

## 1. 背景

2026-09-15、`kernel/shlib.c` の修正 (`30018f1`) を配備した際、`hsync` が更新後の
`libos32gui.shlib` を **スキップ**した。旧版と新版のバイナリサイズが偶然一致したためで、
現行の同一判定が**サイズだけ**を見ていることが原因。利用者は古い shlib で起動した画面を見て
「修正が効いていない」と判断することになる。同種の取り違えは配備経路全体の信頼性を損なう。

`-f` / `--force` は既に存在するが、「いつ付ければよいか」を人間が知っている前提の回避策であり、
既定の判定が誤るという欠陥そのものは残る。

## 2. 範囲 (計画 §8 の H1 行)

> 同サイズ内容比較、ストリーム CRC ＋読戻し、dry-run、理由表示、stat 失敗の是正
> 対象: `hsync.c`、CRC 共通コア、HostDrv のエラー処理、`hsync.1`、ホスト試験
> 完了条件: 同サイズ・同時刻更新を検出し、I/O 失敗を成功にしない。直接上書きの制限は明記

**含めないもの** — 一時ファイルと置換の安全化 (H2)、mtime の取得・保存と `sys_set_mtime`
([`TASK_H3.md`](TASK_H3.md))、manifest と世代 (H4)、`--quick`、`--delete`、永続 CRC キャッシュ。

H1 で KAPI を触らないのは**方針ではなく着地順の都合**である。KAPI の追加は追記専用 ([ABI2]) で
安全側の操作であり、カーネルの能力を CPL=3 へ渡すのは通常手順 ([C3])。H3 を分けたのは
[ABI3] の `make clean` + `make external` というゲートに H1 を縛らないためと、FILETIME 変換の
境界検証が比較ロジックと別種だからで、**H3 は H1 の直後に実施する** (計画 §10 の推奨順どおり)。

## 3. 作業項目

| # | 内容 | 根拠 |
|---|---|---|
| 1 | 既定の同一判定を「サイズ + 内容のバイト比較」へ。保護判定と範囲判定を、内容を開く処理や mkdir より先に通す。比較用サイズは列挙結果に依存せず直前に取り直す。比較は固定バッファ 2 本 (既存 64KB を 32KB×2 に分割)。両側の short read 分割が違っても比較オフセットと有効長を揃える。比較中の I/O 失敗・予定サイズに達しない EOF は**エラー** (「同一」にしない) | §3.1 |
| 2 | ストリーム CRC-32 の共通コア。既存 `lib/crc32.c` の `crc32_calc()` と同じ CRC (反転多項式 `0xEDB88320`、内部初期値 `0xFFFFFFFF`、最後に `0xFFFFFFFF` を XOR)。未確定の内部状態を入出力する更新関数を用意し、最終 XOR は 1 回だけ。チャンクごとの完成 CRC を XOR して全体にしない。既存一括関数の戻り値・保存形式は変えない。**CRC のために KAPI を増やさない** | §4.1 |
| 3 | コピー検証。コピー元を読む際に CRC と総バイト数を求め、書込み後に宛先を**再オープンして読み**、**バイト数と CRC の両方**を照合。I/O 失敗・予定長不一致・CRC 不一致は成功件数に入れない。`vfs_sync()` の成功と読戻し一致を記録 | §4.2 |
| 4 | CLI: `-n` / `--dry-run` (読み取りと比較のみ。mkdir・一時ファイル・明示 sync をしない)、`-v` / `--verbose`。既存 `-f` / `--force` は維持 (比較だけ省略し、保護・型検査・コピー後検証は省略しない)。**未知オプションと複数 dir はエラー** (現行の「最後の引数で上書き」を解消)。パスを正規化してから範囲を決め、`..` 脱出・切り詰め・自己コピーを拒否。`sys` 除外は**全体同期のルート直下にだけ**適用する (`hsync usr` の `usr/sys` を誤除外しない) | §3.2 |
| 5 | 結果と理由: 集計を `copied / unchanged / excluded / protected / errors` に分け、失敗時は非ゼロ終了。理由は固定文字列 (`size_changed / content_changed / forced / verify_failed / source_changed / type_conflict`)。`/sys` の既定除外を先頭で明示。`-f` でも除外は解除しない。更新対象に応じて再起動・シェル再起動の要否を表示し、hsync 成功を稼働版の切替完了と扱わない。再起動は自動実行しない | §7.2 |
| 6 | `fs/hostdrvfs.c` の `hdrv_stat()` が Basic/Standard 情報の取得に失敗しても成功を返す経路を是正 (ゼロサイズを実在する空ファイルと誤認しない)。64bit `EndOfFile` を u32 へ黙って切り捨てず検出して拒否。**時刻の転記は H3 なので H1 ではやらない** | §2 / §4.3 |
| 7 | `docs/manpages/hsync.1` を実装に合わせる (全体同期の `/sys` 除外、設定 DB 保護、新オプション、H1 の限界) | §2 |

## 4. H1 の限界 (コード註と man に明記する)

H1 は**直接上書きのまま**なので、**検証失敗時に旧宛先を復元する保証は無い**。解消は H2。
同サイズ・同時刻に戻る変更の完全検出、コピー中の元ファイル変更の完全検出も H1 では保証しない
(不変な配備元は H4)。

## 7. 実装レビュー (Codex、2026-09-15、往復 1)

対象 `e43fcb8`。判定 **Request changes**、blocker 3 件。**3 件とも PM が独立に到達可能性を確認済み**。

| # | 指摘 | 確認した根拠 |
|---|---|---|
| B1 | バックスラッシュが `..` 脱出検査を通り抜ける | `hsp_normalize` は `/` だけを区切りとするので `..\other` は通常の 1 要素。`session_set_path` (`fs/hostdrvfs.c:150`) は `/`→`\` 変換のみで他は素通し。NP21/W の `hostdrvNT_getHostPath` (`hostdrvnt.c:368-390`) は `PathCanonicalizeW` の後 `wcsncmp` の**境界無し前方一致**なので `C:\os32-other` が `C:\os32` を前方一致して通る |
| B2 | `/host` の 1 要素分を深さ上限に数えていない | `HSP_MAX_DEPTH` = `VFS_MAX_PATH_DEPTH` = 32。`fs/vfs.c:97-106` は上限超過の要素を**黙って捨てる**。32 要素の dir → 同期元 33 要素 → 親を列挙し、未同期のまま `errors=0` / 終了コード 0 |
| B3 | ディレクトリ経路で既存宛先の型衝突を成功扱いにする | `ext2_find_entry` (`fs/ext2_dir.c:251`) は**型を問わず** `EXT2_ERR_EXIST`。`hsync.c:681` が無条件に受理して再帰。通常ファイル側の `type_conflict` 検査がディレクトリ側に無い |

非 blocker: ホスト試験の `u32` が LP64 で 64bit になる (`-m32` 無し)。CRC の値照合には使えるが
32bit の加算回り込みの根拠にはならない。

**別課題として切り出し**: B1 の根本原因の半分は NP21/W 側にある。`hostdrvNT_getHostPath` の
ルート検査が区切り境界を見ない前方一致なので、`C:\os32` をルートにすると `C:\os32-other` 以下が
**hsync 以外の経路でも**見える。OS32 側の修正 (`\` を含む要素の拒否) とは独立に、
エミュレータ側で `wcsncmp` の後に区切り文字の確認を足すべき。本票では扱わない。

### PM の判断の誤り (記録)

往復 3 の B5・B6 は、**PM が受け入れた判断が誤っていた**ために生じた。
`hdrv_list_dir` の件数上限をエラーにする変更について、コーダーは影響調査で `fs_is_dir` の
危険性を自ら挙げ、「現状は先頭 1000 件だけを黙ってコピーするので断る方が安全」と結論した。
PM はこれを受け入れたが、実際の帰結は**断るのではなく間違った場所への書き込み**だった。
また「影響が広すぎれば上限の修正だけ切り離せる」と備えていたが、`fs_is_dir` が
列挙の成否を型判定に使う以上、**途中失敗をエラーにする修正だけでも同じ退行が起きる**ので
その備えは役に立たなかった。コーダーが最初の報告で「`fs_is_dir` を `sys_stat` 優先に直すのが本筋」
と書いていたのを PM が別票候補として範囲外に置いたのも誤りで、任意の改善ではなく
この変更を成立させる必須条件だった。

### 往復数について

ROLES §5 の上限は 3 往復 + 追加 1 往復。本票は 5 往復を要した。4 回目以降を続けた根拠は、
同じ形の誤りが繰り返されたため**残存面を数え、閉じていることを確認した**こと
(`vfs_path_kind` の消費者はカーネル内に `vfs_open_internal` と `vfs_chdir` の 2 箇所だけで、
open の入口は `vfs_open` / `vfs_open_sqlite` がともに `vfs_open_internal` に集約される。
PM とコーダーが独立に確認)。往復 5 の B8 は H1 以前からの欠陥で本票の範囲外なので、
ここで打ち切って別票へ送る。

### 検出漏れの原因 (往復 4 で判明)

追加した試験が `vfs_path_kind` の**戻り値までしか見ておらず**、実物の `vfs_open_internal` を
通していなかった。ハーネスに `fs/vfs_fd.c` を取り込み実物の `vfs_open` を駆動するよう直した。
**判定関数の戻り値だけを試験しても、受け手が追従しているかは分からない。**

### 判明した制限 (H2 へ)

**宛先ディレクトリが無いと `io_error` になる**。`hsync <未作成のディレクトリ>` は、
明示 dir の宛先を作らないまま子ファイルを開こうとして失敗する。**H1 の退行ではなく
元の版からの制限** (`fdd777f` も `sys_mkdir` は列挙ループの中だけ) だが、理由の文字列が
実態と合っていない。「宛先が無い」と言うべき。H2 で明示 dir の宛先作成とあわせて直す。

### 性能 (A21、実測 2026-09-15)

エミュレータを再起動した冷えた状態で、ゲストのシェル組み込み `time` で計測した。
**いずれも変更が 1 件も無い場合**である。

| 操作 | ファイル数 | 対象 | 実測 |
|---|---|---|---|
| `hsync` (全体) | 235 | 24.8 MB | **135.350 s** |
| `hsync sys` | 6 | 4.9 MB | **25.810 s** |

両側を読むので実 I/O は対象の 2 倍。実効 366 KB/s と 380 KB/s で**ほぼ一致**するので、
費用は「読んだバイト数 ÷ 一定の帯域」でよく説明できる。ファイル数やメタデータではなく
**本体を読む量が支配的**である。H1 以前は 235 回の `stat` だけで、ほぼ即座だった。

`vfs_sync` をまとめる案は**この問題にはほぼ効かない** (Codex 相談、2026-09-15)。
変更が無いファイルは比較するだけで `vfs_sync` を呼んでいない。さらに
`ext2_write_stream()` が内部で `ext2_sync()` を呼び、メタデータに変更が無ければ早期に戻る。

**日常操作の `hsync sys` が 26 秒**になったことが実害である。共有ライブラリを 1 本
差し替えるたびにこれを払う。→ 対策は [`TASK_H3.md`](TASK_H3.md) の日時前置判定へ。
