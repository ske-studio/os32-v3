# アーカイブのポリシー — 要約してから移す

> 状態: **現行 (2026-11-18)** — ユーザー決定 (2026-11-17〜18)「記述を要約してまとめ、アーカイブ出来るものはアーカイブ」「要約にしてアーカイブするポリシーをドキュメント化」。規則の本体は [CONSTRAINTS](CONSTRAINTS.md) の [D4]。手順はスキル `.claude/skills/os32-archive/SKILL.md`、籠の一覧は `docs/archive/README.md`。

完了した票・役目を終えた設計を現行の棚から外す時の決まり。**移す前に、今も効いている中身を現行の文書に要約する。**
要約せずに移すと、[D4] (アーカイブは作業の根拠にしない) のために、試験の期待の出所や実装の約束を誰も読めなくなる。

## §1. 何を、いつ移すか

| 決まり | 中身 |
|---|---|
| A1 移す物 | 状態が 受入完了・完了記録・撤回 の票 (`docs/tasks/**/TASK_*.md`) と、その票の段の確定設計 (`docs/decisions/**`) で役目を終えた物。別系統の調査の快照、対象外の草案 |
| A2 移す時 | 状態を完了にする変更と同じ変更の中で移す。現行の棚に完了した票を置かない (`make check-docs-status` が止める。残す理由がある票は `tools/docs_status_exceptions.json` に理由を書く) |
| A3 残す物 | 未実施・未確認の受入が票の中にしか無い物 (持越しの台帳 `docs/tasks/DEFERRED_TESTS.md` の行だけで何を・なぜ・いつ確かめるかが読めるなら移してよい)。今も設計の根拠として引かれている決定 (分け方・方式の比較の結論) |
| A4 記録は直さない | 移した文書の本文は書き換えない (動かしてよいのはリンクだけ)。続きが要るなら新しい票を立てる |

## §2. 移す前に要約する物

その票・設計を**今の約束として**引いている所を全部挙げ、引かれている中身を現行の文書に書く。

| 引いている所 | 探し方 | 要約の後の形 |
|---|---|---|
| 検査の宣言の出所 (`tools/checks/*.py` の `basis`) | `git grep -n "<票の名前>" -- tools/checks` | basis を設計書のパスに替える (アーカイブを指す basis は `python3 tools/checks/run.py --lint` が止める) |
| 試験の覚え (`tools/tests/*_tdd.md`) の `票:`・`契約の正典は` | `git grep -ln "<票のパス>" -- 'tools/tests/*_tdd.md'` | 設計書のパスと節の名前に替える |
| 仕様・索引・ほかの票・スキル (`docs/`・`.claude/skills/`) | `git grep -n "<票の名前>" -- docs .claude ':!docs/archive'` | 仕様として引いている所は設計書か仕様の節へ。所在だけの言及は文字で `(アーカイブ: \`docs/archive/…\`)` |
| 持越しの台帳の行 | `git grep -n "<票の名前>" -- docs/tasks/DEFERRED_TESTS.md` | 行が票を開かずに読める形か確かめる。読めなければ、その節を先に仕様へ移す |
| ソースの註・道具の docstring | `git grep -n "<票のパス>" -- '*.c' '*.h' '*.inc' '*.asm' '*.py'` | 来歴の記録として残してよい (新しく足さない)。契約のヘッダは註も含めて ABI の世代のハッシュに入るので触らない |

要約の置き場: 実装の約束は `docs/design/<ソースと同じパス>.md` (1 機能 1 ファイル、[POLICY_DEV](POLICY_DEV.md) §9)。
同じ約束が既に仕様 (§1〜§10・KAPI_SPEC・manpages) に在る時は重ねず、その節を引き先にする。

## §3. 要約の書き方

| 決まり | 中身 | 起きた事 (2026-11-18 の 7 領域・票 50 本) |
|---|---|---|
| S1 **今のソースと照らして書く** | 票を写さない。試験が確かめている契約 (入出力・誤りコード・不変条件・境界値・順序) を特定し、ソースと試験のコードを読んで、今成り立つ形を書く | 7 領域の全部で、票が今のコードと違っていた (撤去済みの関数を説明する票、試験の期待と逆の表、移った置き場) |
| S2 食い違いは今のコードと試験が正 | 票・覚えと違う所は今の形を書き、違いを報告する。不具合の疑いは別に挙げる | 保護の一覧の漏れ 1 件と、古い註 2 件が見つかった |
| S3 粒度 | 票を開かなくても、試験の期待が正しいかを判断できる程度。経緯・往復の記録・日付の履歴・誰が決めたかは書かない (git と票に在る) | — |
| S4 確かめていない事は書かない | ソースで確かめた事だけを書く。ゲスト・実機でしか分からない事は「確かめていない」と報告し、設計書には書かない | 担当が「覚えを頼りに書いた」と申告した 1 本は、PM がソースと照らして関数名を 1 か所直した |
| S5 書式 | 冒頭は `# <ソースのパス> — 設計`、`> 状態: **現行 (日付)** — 出所: <票の名前> の契約を今のソースと照らして要約`、`ソース: \`<パス>\``。ソースは行番号でなく名前で指す。設計書にアーカイブのパスを書かない。設計書間の案内と根拠は POLICY_DEV §9-2 に従う | 文書の検査 (`docs-line-refs`・`docs-tree`) が止める |
| S6 覚えは記録 | 試験の覚えは記録の層 (L5)。付け替えるのは契約の出所の行。本文が今のコードと違う所は、今の形に直すか、当時の記録である旨を頭に 1 行で書く | — |

## §4. 移す順

1. 引いている所を挙げる (§2 の表)。
2. 要約を書き、引き先を替える。要約の分担は領域ごと (1 領域 = 票 5〜10 本・覚え 10 本前後が 1 人ぶん)。
3. 新しい設計書を索引 (置き場の `README.md`、無ければ `docs/design/README.md`) に足す。
4. `python3 tools/move_docs.py --into docs/archive/<籠> <票> … --dry-run` で書き換えを見てから、`--dry-run` を外して移す。
5. `python3 tools/doc_delink_archive.py --dry-run` で現行 → アーカイブのリンクを見て、文字に戻す。
6. `docs/archive/README.md` の籠の表と、`docs/INDEX.md` の行 (所在を文字で) を直す。
7. `python3 tools/ops/check_archive_refs.py --write-baseline` (来歴の註が増減した時)。
8. 検査: `CHECK_NO_NEEDS=1 make check-docs-links check-docs-orphans check-docs-status check-docs-tree check-docs-line-refs check-archive-refs check-tests-inventory MUTATE=0` と `python3 tools/checks/run.py --lint`。新しい文書は先に `git add -N` (追跡されていない文書は検査に入らない)。

## §5. 検査が見る事

| 検査 | 見る事 |
|---|---|
| `docs-status` | 進行中の票に完了の基準がある、完了した票が現行の棚に無い |
| `docs-tree` | 現行の文書からアーカイブへのリンクが 0、根拠の向きと索引からの到達が POLICY_DEV §9-2 に従う。個別の辺・文書と理由を指定した例外だけを認める |
| `docs-orphans` | 現行の文書が索引から辿れる |
| `archive-refs` | 試験の覚え・ソースの註・道具の Python がアーカイブの文書を指す件数が、ファイルごとの基準と同じ |
| `run.py --lint` | 検査の宣言の basis がアーカイブ・実在しない文書を指していない |

## §6. やらない事

- 要約せずに移す事。「仕様はアーカイブの票を読め」という状態を作らない。
- アーカイブのパスを消すだけの直し (出所の手がかりが消えるだけで、約束が現行に無い事は変わらない)。
- 移した文書の本文の書き換え、ソースの註の書き換え。
- 要約に、票の経緯・決定の往復・当時の数字を写す事。
