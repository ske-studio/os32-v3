# MGX フォーマット仕様

漫画専用モノクロ (グレースケール) 画像形式 **MGX** (ManGa eXchange) の仕様書。

- **エンコーダ**: `tools/img2mgx.py` (ホスト側のみ)
- **デコーダ**: `userland/lib/mgx/` (ゲスト側のみ)
- **ビューワ**: `apps/mgxview/mgxview.c`
- **展開ルーチン**: `lib/zlib/` (zlib 本体の inflate、無改変で取り込み)

---

## 1. 設計方針

### 1.1 なぜ VDP ではないのか

既存の `VDP` 形式 (`apps/vdpview/vdpview.c`) は PC-98 のスクリーンショット保存用で、
漫画には向かない。

| 問題 | 内容 |
|---|---|
| ホスト側エンコーダが無い | VDP を作れるのは `gfx_screenshot()` だけで、`tools/` に変換器が無い |
| PackBits RLE のみ | 線画・階調のどちらにもほとんど効かない |
| 256B の固定ヘッダ | VQ・アニメ・当たり判定など漫画に無関係なフィールドが大半 |
| 仕様が不整合 | VDP1 の packed 構造体と `vdpview.c` の読み出しオフセットが食い違っている |

### 1.2 ビット深度は可変 (bpp 1..4)

PC-98 の 640x400 グラフィック画面は 4 プレーン = 16 色。パレットは各チャンネル
0..15 のアナログ値なので、16 段のグレーランプを**誤差なく**作れる。

**格納するプレーン数は絵に合わせて 1..4 で変えられる。** 展開量も VRAM への
転送量も N/4 になるので、**ファイルサイズとデコード時間の両方が減る**。

| bpp | 階調 | 用途 |
|---|---|---|
| 4 | 16 | 連続階調をそのまま持つ。最大品質 |
| 3 | 8 | **既定の auto がほぼここに落ちる。** 16 階調と見分けがつかない |
| 2 | 4 | 平坦トーンの漫画として成立する |
| 1 | 2 | 線画のみ。網点で階調を表現する |

実機でのデコード時間 (同一画像 640x349 を bpp 1..4 で符号化して計測):

| bpp | プレーン | 展開後 | mgx | 展開時間 | 1 プレーンあたり |
|---|---|---|---|---|---|
| 1 | 1 | 27,920 B | 8,590 B | 180 ms | 180 ms |
| 2 | 2 | 55,840 B | 18,567 B | 390 ms | 195 ms |
| 3 | 3 | 83,760 B | 27,328 B | 540 ms | 180 ms |
| 4 | 4 | 111,680 B | 38,294 B | 740 ms | 185 ms |

**プレーン数にきれいに比例する (約 185 ms/プレーン)。** `inflateInit()` や
32KB 窓の確保といった固定コストは測定に現れない程度に小さい。
つまり bpp を 1 段下げると展開時間もちょうど 1 プレーン分減る。

計測は同一画像を bpp 1..4 で符号化した `B1..B4.MGX` を `/data/manga/bench/` に
置いて `mgx_test` を走らせると出る (無ければ省略)。データはリポジトリにも配布物にも
入れない (2026-09-30、ユーザー決定: 漫画の実データは持たない)。計り直すときは
任意の画像を `tools/img2mgx.py --bpp 1..4` で作って `hsync` で置く。

※ 圧縮率の違う**別画像**どうしで比べると固定コストがあるように見えるので注意。
   プレーン数と時間の関係を見るときは必ず同一画像で比べること。

**1bpp (2 値) だと連続階調が破綻する。** 中間調を網点の粗密でしか表現できないため、
グラデーションのある絵では画面のほぼ全面にドットが乗り「ノイズ」に見える。
bpp>=2 なら階調をそのまま持てるのでこの問題が消える。

### 1.3 圧縮は PNG と同じ deflate をそのまま使う

MGX の圧縮は PNG と同じ **deflate** で、独自の圧縮アルゴリズムは一切実装していない。

- ホスト側は Python 標準の `zlib` (と、あれば `zopfli`) をそのまま呼ぶ
- ゲスト側は zlib 本体の inflate を無改変で取り込んで使う (`lib/zlib/`)

### 1.4 PNG のスキャンラインフィルタ段は採用していない

PNG は deflate の前に行フィルタ (Sub/Up/Average/Paeth) を掛ける。これは
連続階調で 1 画素が複数バイトある場合に効く仕組みで、**ビットプレーン形式では逆効果**。
同じ走査線がそのまま繰り返されるため LZ77 が長いマッチとして拾えるのに、
XOR フィルタがその繰り返しを壊してしまう。

実測 (1bpp、実画像 3 枚 × ディザ 3 種、単位バイト):

| 条件 | 素の deflate | 行フィルタ + deflate |
|---|---|---|
| 640x360 cluster | **9,689** | 10,238 |
| 640x349 cluster | **14,269** | 15,504 |
| 640x349 cluster | **8,336** | 9,036 |
| 640x360 fs | **23,904** | 25,311 |

`Image.save('PNG')` (フィルタあり) が素の deflate に負けるのも同じ理由による。
縦周期を吸収する XOR_UP(N) や 2 次元フィルタも試したが、一貫して素の deflate が勝った。
よって MGX にフィルタ段は無く、デコーダもその分小さい。

### 1.5 検討して却下した圧縮強化 (実測記録)

「デコーダ側に固定テーブルを持たせて画像本体を小さくできないか」を検証した結果。

| 方式 | deflate 比 | デコーダに焼くもの |
|---|---|---|
| zlib プリセット辞書 32KB (他画像から作成) | **−0.03 〜 +0.05%** | 32KB |
| 同上 (自画像から作成 = 反則的な上限) | **±0%** | — |
| 固定ハフマン表 (`Z_FIXED`) | **+9 〜 +10%** | 表 |
| 文脈モデル + 固定確率表 (他画像で学習) | −19 〜 −27% | 約 15KB |
| 文脈モデル + 適応符号化 (JBIG2/MQ 相当) | **−34 〜 −39%** | 約 300B + RAM 8KB |

- **辞書は効かない。** 自画像から作った完璧な辞書ですら 0%。ペイロードが 111KB あり
  冗長性は画像内で局所的なので、deflate の 32KB 窓が既に全部拾っている。
  辞書が効くのは payload が小さいときだけ (先頭 2KB のみなら −2.1%)。
- **固定ハフマンは損。** 動的木の伝送コスト (データの 10% 未満) より
  汎用表を使う損失の方が大きい。
- **文脈モデルは −35% と大きく効くが、速度で不採用。**
  実機で MQ 二値算術復号を計測したところ、1 ページ分の 1,024,000 判定に
  **18,860 ms**。現行 inflate の 790 ms に対して 24 倍で、
  先読みがあっても読者の方が速いので実用外と判断した (2026-08-21)。
  CPU がずっと速い環境で再検討する場合はこの数値を出発点にすること。

## 2. ファイル構造

```
+-----------------------------+
|  ヘッダ 32 バイト            |
+-----------------------------+
|  ペイロード (data_size B)    |
+-----------------------------+
```

### 2.1 ヘッダ (48 バイト固定, リトルエンディアン)

| off | size | field | 内容 |
|---|---|---|---|
| 0x00 | 4 | `magic` | `"MGX1"` |
| 0x04 | 1 | `version` | 1 |
| 0x05 | 1 | `flags` | bit0: bpp=1 で「セットされたビットが墨」/ bit1: エンコーダが 90 度回転した |
| 0x06 | 2 | `width` | 1..640 |
| 0x08 | 2 | `height` | 1..400 |
| 0x0A | 1 | `codec` | 0 = STORED, 1 = ZLIB |
| 0x0B | 1 | `dither` | 0=none 1=cluster 2=bayer4 3=bayer8 4=fs (情報用) |
| 0x0C | 4 | `data_size` | ヘッダ直後のペイロード長 |
| 0x10 | 4 | `raw_size` | 展開後のサイズ = `pitch * height * bpp` |
| 0x14 | 1 | `bpp` | 1..4 = 格納プレーン数 |
| 0x15 | 1 | `npal` | 使用パレット数 = `1 << bpp` (2/4/8/16) |
| 0x16 | 10 | `reserved` | 0 |
| 0x20 | 16 | `palette[16]` | プレーン値 `i` を表示するグレー階調 (0..15) |

`pitch = (width + 7) / 8`

デコーダは `raw_size == pitch * height * bpp` と `npal == (1 << bpp)` を検査する。
ヘッダ内で自己矛盾する値を弾くことで、壊れたサイズでメモリを確保させない。

### 2.2 ペイロード

| codec | 内容 |
|---|---|
| 0 (STORED) | 展開後データそのまま (`data_size == raw_size`) |
| 1 (ZLIB) | **標準の zlib ストリーム (RFC1950)** |

ZLIB の場合、ペイロードは `zlib.compress()` の出力そのままである。したがって

- ホスト側のどんなツールでも `zlib.decompress(payload)` で中身を取り出せる
- 末尾 4 バイトの **Adler-32** がそのまま完全性検査に使える (独自 CRC は持たない)

ゲスト側は `[CMF][FLG]` の 2 バイトを検査してから、その後ろの生 deflate 部分を
`puff()` に渡し、展開後に Adler-32 を照合する。

圧縮後サイズが生データ以上になった場合、エンコーダは codec を STORED に落とす。

### 2.3 展開後のデータ配置

PC-98 のプレーンが**そのままの並びで連続**する。枚数は `bpp`。

```
plane 0 (pitch * height バイト)   ... 各画素の bit0
plane 1                            ... bit1        (bpp >= 2)
plane 2                            ... bit2        (bpp >= 3)
plane 3                            ... bit3        (bpp == 4)
```

この並びにしてあるので、ゲスト側は画素単位の変換をせずに
`gfx_fb.planes[p]` へ行単位でコピーするだけでよい。

転送先のプレーン `bpp..3` には触らない。画素値は `2^bpp` 未満なので上位プレーンは
0 であるべきで、画面クリアで既にそうなっている (余白の色 `mgx_paper_index()` も
`2^bpp` 未満)。

いずれも 1 画素 1 ビット、**MSB first** (バイトの最上位ビットが左端の画素)。
行は `pitch` バイト境界で始まり、行末の余りビットは 0。

### 2.4 パレット

ヘッダ末尾の 16 バイトが **プレーン値 -> グレー階調 (0..15)** の対応表そのもの。

先頭 `npal` = `2^bpp` 個が有効で、残りは 0。

| bpp | palette[] の中身 |
|---|---|
| 1 | `palette[0]` = 紙 (15), `palette[1]` = 墨 (0) |
| 2/3/4 | `2^bpp` 個。**均等とは限らない** — エンコーダが絵のヒストグラムに
合わせて 0..15 から最適な組を選ぶ (下記) |

並べ替え (下記 Gray 符号) はエンコーダが表に畳み込んで書くので、
**デコード側に階調の変換ロジックは無い**。`gfx_set_palette(i, t[i], t[i], t[i])` を
16 回回すだけで、bpp=1 と bpp=4 で処理も分かれない。

#### Gray 符号を使う理由

ビットプレーンに分けると、隣り合う階調でも複数のビットが同時に反転しうる
(例: 7 = 0111 と 8 = 1000 は全ビット反転)。これがプレーンごとに見たときの
細かいノイズになり deflate の効きを落とす。Gray 符号なら隣接階調は必ず
**1 ビットしか違わない**ので、各プレーンが滑らかになる。

エンコーダは `palette[g ^ (g >> 1)] = g` という表を書き、プレーンには
Gray 符号を格納する。線形版も併せて試して小さい方を採る
(絵によっては線形が勝つ)。

実測 (プレーン分離 + zlib):

| 画像 | 線形 | Gray 符号 |
|---|---|---|
| A | 46,004 | **44,777** |
| B | 75,298 | **71,900** |
| C | 46,520 | **38,890** |

#### パレット順序は Gray 符号が最適 — 頻度順にしてはいけない

「出現頻度の多い色から順に並べれば圧縮率が上がるのでは」という発想は
**この形式では逆効果**。実測 (3 画像、bayer8、16 階調):

| permutation | Gray 比 |
|---|---|
| linear (恒等) | +4 〜 +18% |
| **Gray 符号** | — |
| 頻度順 -> 0..15 | **+11 / +11 / +23%** |
| 頻度順 -> Gray | +14 / +7 / +23% |
| 隣接最適化 (山登り) | +0.3 / −0.2 / ±0% |
| ランダム 60 回リスタート最良 | +0.3 / −0.8 / +1.5% |

圧縮はパレット番号の**ビットプレーン**に対して働くので、効くのは
「色の出現頻度」ではなく「**空間的に隣接する画素間で何枚のプレーンの
ビットが反転するか**」。目的関数は

```
Σ (隣接画素ペア a,b) 共起回数[a][b] × popcount(π(a) ^ π(b))
```

で、これは階調グラフの **4 次元超立方体 Q4 への最小重み埋め込み**。
共起行列は |a−b|=1 のペアが支配的なので、パス 0–1–…–15 を Q4 に
埋め込む問題になり、**Gray 符号がその厳密解** (各ステップがちょうど 1 ビット)。
頻度順は隣接関係を完全に無視するため、隣接階調が超立方体上で遠くに散らばる。

60 回のランダムリスタート探索でも実 zlib サイズは 3 枚中 2 枚で悪化した。
**Gray 符号は実質最適で、ファイルに任意の置換表を持つ価値も無い**
(表を持つのは上記の単純化のためであって、圧縮率のためではない)。

#### 2 画素 1 バイト (packed 4bpp) にしない理由

packed 4bpp のほうが 10% ほど小さくなる (35,032 B vs 38,890 B) が、
128,000 バイトを 4 プレーンへ散らす変換が必要になる。386 では
これが展開そのものに匹敵するコストになるため、
**プレーン分離 + Gray 符号**を採った。

## 3. エンコーダ (ホスト側)

```
python3 tools/img2mgx.py input.png -o output.mgx [options]
```

| オプション | 既定 | 内容 |
|---|---|---|
| `-o PATH` | (必須) | 出力先。`--batch` 時は出力ディレクトリ |
| `--batch` | off | `input` を glob として扱い複数ページを一括変換 |
| `--bpp N` | `auto` | `auto`/1/2/3/4。格納プレーン数。小さいほどファイルもデコード時間も減る |
| `--auto-tone-error F` | 0.75 | `auto` の閾値 (階調誤差 RMS, 0..15 スケール) |
| `--max-size WxH` | `640x400` | 上限解像度 |
| `--dither MODE` | bpp により | `none`/`bayer4`/`bayer8`/`fs`/`cluster` (bpp=4 は `bayer8`、bpp=1 は `cluster`) |
| `--tone-cell N` | 8 | `cluster` の網点セルサイズ (4/6/8/10/12) |
| `--autocontrast PCT` | 2 | 量子化前のオートコントラスト cutoff% (0 で無効) |
| `--sharpen PCT` | 110 | 量子化前のアンシャープマスク強度% (0 で無効) |
| `--posterize N` | 3 | **bpp=1 のみ** 階調を N 段へ量子化 (0/1 で無効) |
| `--gamma G` | なし | 量子化前のガンマ補正 |
| `--threshold T` | 128 | `--dither none` かつ bpp=1 の閾値 |
| `--rotate90` | off | 90 度回転してから収める |
| `--no-resize` | off | 縮小しない (1bpp かつ上限内の入力のみ) |
| `--no-graycode` | off | bpp=4 で Gray 符号を使わない |
| `--stored` | off | 無圧縮で出力 (デバッグ用) |
| `--no-zopfli` | off | zopfli を使わず zlib -9 のみ |
| `--stats` | off | 統計を表示 |
| `--verify` | off | 書き出した `.mgx` を復号して元と一致するか検証 |
| `--dump-pgm [PATH]` | off | 復号結果を PGM で書き出す |

処理の流れ:

1. 入力が既に 1bpp かつ上限内なら **そのまま素通し** (bpp=1 に落とす)
2. それ以外は `convert('L')` → アスペクト保持 LANCZOS 縮小
   → オートコントラスト → ガンマ → アンシャープマスク → 量子化
3. bpp=4 は 16 階調へ量子化 → Gray 符号 → 4 プレーンへ展開
   bpp=1 は網点化 → 1 プレーンへ展開
4. `zlib` / `zopfli` で圧縮し、大きくなるようなら STORED に落とす

依存: Pillow, numpy (必須) / zopfli (任意、あれば 3〜5% 小さくなる)

### 3.1 前処理 (既定で有効)

原稿が低コントラスト (空が灰色など) だと階調が中央に寄って眠い絵になる。
量子化の前に

1. `--autocontrast 2` — ハイライトを白に、シャドウを黒に寄せる
2. `--sharpen 110` — アンシャープマスクで線画を立てる

を掛ける。平坦な白/黒が増えるので圧縮率もふつうは良くなる。どちらも `0` で無効。

### 3.2 ビット深度の自動選択 (`--bpp auto`)

**判定基準は「階調誤差 RMS」** — その階調数で表現したときに失われる階調分解能を
直接測る。0..15 から `2^bpp` 個の代表階調を選ぶ最適解を 1 次元 k-means の
動的計画法で厳密に求め (値が 16 個なので一瞬)、その重み付き RMS が
`--auto-tone-error` 以下になる最小の bpp を採る。

選ばれた代表階調はそのままパレット表に書かれるので、**均等配置より階調が
絵に合う** (実測: bpp=2 で PSNR +2.0〜+3.6 dB)。

#### 「実使用階調数を数える」方式は使えない

一見すると「ディザ無しで 16 階調にしたとき何階調使うか」を数えれば済みそうだが、
**前処理のアンシャープが平坦性を壊す**。完全に 4 階調の原稿でも、シャープを
かけた瞬間に 16 階調に散る。JPEG ノイズも同じ。階調誤差 RMS はノイズでは
大きく動かないので、この問題を受けない。

実測 (4 階調の原稿を JPEG 経由で読ませた場合の RMS と判定結果):

| 入力 | N=2 | N=4 | N=8 | N=16 | → bpp |
|---|---|---|---|---|---|
| 4 階調原稿 (無劣化) | 2.44 | **0.63** | 0.33 | 0.00 | 2 |
| 4 階調 → JPEG q95 + シャープ | 2.44 | **0.64** | 0.33 | 0.00 | 2 |
| 4 階調 → JPEG q85 + シャープ | 2.45 | **0.68** | 0.35 | 0.00 | 2 |
| 4 階調 → JPEG q75 + シャープ | 2.47 | **0.72** | 0.38 | 0.00 | 2 |
| 連続階調 (サンプル 3 枚) | 1.73〜2.48 | 0.89〜1.19 | **0.39〜0.60** | 0.00 | 3 |

既定の閾値 0.75 なら、JPEG q75 + シャープを通した 4 階調原稿でも正しく bpp=2 と
判定し、連続階調は bpp=3 になる。

### 3.3 階調を下げるときディザは必須

`--bpp` を下げるときは必ずレベル間をディザする (既定 `bayer8`)。
ディザ無しで丸めると、空などのゆるいグラデーションに**硬いバンド境界**が走り、
境界がざらついて非常に目立つ。ディザすると局所平均が保たれるので、
同じ階調数でもトーンとして成立する。

**この判断に PSNR は使えない。** 同じ bpp=2 でディザ版 15.7 dB / ディザ無し版
19.8 dB と数値は逆転するが、目視では明確にディザ版が良い。誤差がバンド境界に
集中して目立つか、拡散して見えないかを PSNR が捉えられないため
(ガウシアンぼかし後の PSNR でも同じく逆転した)。

### 3.4 ディザ (bpp>=2)

16 階調あるので網点は要らず、量子化誤差を散らすだけでよい。

| モード | 特徴 |
|---|---|
| `bayer8` (既定) | 8x8 順序ディザ。バンディングが消えて**かつ最小**になる |
| `none` | 単純量子化。空などのグラデーションにバンドが出ることがある |
| `bayer4` | 4x4。パターンが粗く、`bayer8` より大きい |
| `fs` | Floyd-Steinberg。最も滑らかだが 25〜40% 大きく、Python 実装なので遅い |

### 3.5 網点 (bpp=1)

| モード | 特徴 |
|---|---|
| `cluster` (既定) | **45 度**のクラスタドット。漫画のスクリーントーンと同じ角度 |
| `bayer4` / `bayer8` | 順序ディザ。レトロゲーム風 |
| `fs` | 誤差拡散。非周期ノイズなので 2〜3 倍大きい |
| `none` | 単純閾値。既に 2 値化された線画向け |

#### 45 度である理由

スポット関数 `f = cos(2pi x/n) + cos(2pi y/n)` の値の順位で閾値を割り当てると、
極大が **45 度格子上**に並ぶ。印刷の網点が伝統的に 45 度なのと同じ理由で、
格子が目に付きにくく絵の細部と干渉しにくい。

「中心からの距離」で順位を付けると 0 度の同心円ドットになり、絵の細部と
干渉してモアレ (見た目のノイズ) が出る。実装時にこれを踏んだので注意。
`(x-c+y-c)^2 + (x-c-y+c)^2 == (x-c)^2 + (y-c)^2` なので、距離を回転座標で
計算しても**回転にはならない**。

#### `--posterize` (bpp=1 のみ)

本物の漫画は「平坦なトーンを面に貼る」ものであって、連続的なグラデーションを
網点化したものではない。元絵の階調をそのまま網点化すると画面のほぼ全面に
濃度の違うドットが乗り続ける。先に段数を減らしておくと同じ面が 1 種類の
網点密度に揃うので、実際のトーン貼りに近づき、平坦部が増えるぶん圧縮率も上がる。

## 4. デコーダ (ゲスト側)

`userland/lib/mgx/` は gfx にも KernelAPI にも依存しない純デコーダで、
ファイル入出力とメモリ確保は呼び出し側の責務。

```c
int  mgx_parse_header(const u8 *buf, u32 len, MgxHeader *h);
int  mgx_pitch(const MgxHeader *h);
u32  mgx_plane_size(const MgxHeader *h);
int  mgx_paper_index(const MgxHeader *h, int invert);
int  mgx_decode(const MgxHeader *h, const u8 *payload, u32 payload_len,
                u8 *dst, u32 dst_cap);

/* 格納されている nplanes 枚をそのまま転送 (bpp=1..4 で共通) */
int  mgx_blit_planes(u8 *const planes[4], int dst_pitch, int dst_w, int dst_h,
                     int dx, int dy, const u8 *bitmap, u32 plane_size,
                     int nplanes, int width, int height);
```

| ファイル | text | 内容 |
|---|---|---|
| `userland/lib/mgx/mgx_decode.c` | 825 B | ヘッダ解析 / パレット表 / inflate 呼び出し |
| `userland/lib/mgx/mgx_blit.c` | 1,268 B | プレーン転送 (bpp=1..4 共通の 1 本) |
| `lib/zlib/` (inflate 一式) | 12,174 B | deflate 展開 |

エラーは全て負値で返り、破損データに対して `dst_cap` を超えて書き込むことはない
(KAPI にポインタ検証が無く外部プログラムも CPL=0 なので、デコーダ側で境界を見る)。

`dx` が 8 の倍数ならバイト単位でコピーされ、それ以外は隣接バイトから継ぎ足す
シフト経路を通る。転送先の `dst_w` / `dst_h` でクリップする。

### lib/zlib について

`lib/zlib/` は zlib 公式ソースのうち**展開に必要な最小構成だけ**を
無改変で取り込んだもの (Jean-loup Gailly and Mark Adler、zlib ライセンス)。
`inflate.c` / `inffast.c` / `inftrees.c` / `adler32.c` / `zutil.c` と対応ヘッダ。
deflate 側・gzip 入出力・crc32 は含まない。出所と方針は `lib/zlib/README.OS32`。

ビルドは `-DNO_GZIP -DZ_SOLO`。`Z_SOLO` を付けると zlib が malloc を直接
呼ばなくなるので、アロケータは `mgx_decode.c` が `z_stream` に渡している
(inflate が確保するのは状態構造体 約 7KB と 32KB の窓の 2 つだけ)。

zlib ライセンスの条項 2 は改変版にその旨の明示を求めているので、
手を入れる場合は `lib/zlib/README.OS32` に記録すること。

#### puff.c から乗り換えた経緯

当初は zlib contrib の参照実装 `puff.c` を使っていた (text 3,147 B + bss 744 B)。
これは「速度より小ささと明快さ」を優先した実装で、実機で計測したところ

| 実装 | 640x400 4bpp 1 ページ (115,200 B) の展開 | コード |
|---|---|---|
| `puff.c` | 3,080 ms | 3.9 KB |
| **zlib 本体の inflate** | **790 ms** | 12.2 KB |

**約 3.9 倍速い**。コードは +9KB 増えるが、1 ページ 3 秒は
ビューワの初回表示とコールドジャンプで体感に出るため乗り換えた。

## 5. ビューワ

```
exec mgxview [FILE.MGX] [-k] [-i]
```

- 引数なし: カレントディレクトリの `*.MGX` を名前順に並べて 1 冊として開く
- `FILE.MGX` 指定: そのファイルのあるディレクトリを開き、そのページから表示
- `-k`: 終了時に VRAM をクリアしない
- `-i`: 白黒反転

| キー | 動作 |
|---|---|
| `S` / `→` / SPACE | 次ページ |
| `A` / `←` | 前ページ |
| `F` / `TAB` | ファイラ (別のページ / ディレクトリを選ぶ) |
| `ESC` / `q` | 終了 |

### ファイラ

`F` / `TAB` で `libos32filer` のモーダル UI を開き、`.mgx` / `.MGX` だけを
フィルタして一覧する (拡張子照合は大文字小文字を無視)。ディレクトリを辿れるので、
別のフォルダの続きを開くこともできる。

- 選択されたファイルのディレクトリを新しい走査対象にして、ページ一覧を作り直す。
  **その際キャッシュは全部捨てる** (前のディレクトリのページなので)。
- `libos32filer` の色番号 (`FC_TITLE` = 2 など) は `libos32md` の `md_palette`
  (`userland/lib/md/md_render.c`) を前提にしているので、ファイラを出す間だけ
  そのパレットへ差し替える。値は `mgxview.c` が持っている
  (パレットのためだけに libos32md をリンクしないで済ませるため)。
  ファイラを閉じたあとは `draw_page()` が階調ランプへ戻す。
- 差し替えの前に画面を消す。前のページのビットが残っていると、
  違うパレットで表示されて化けるため。

パレットはページごとに設定する (bpp / palette モードが混在しうるため)。
階調の並べ替え (Gray 符号) はエンコーダがパレット表に畳み込んでいるので、
ビューワ側に変換ロジックは無い。

キー入力待ちの合間に、現在ページの前後へ交互に広げながら展開済みページを
先読みキャッシュする。`mem_alloc()` が尽きた時点で先読みは止まる。
キャッシュに載っているページへの移動はファイル I/O も展開も発生しない。
キャッシュが一杯の状態で範囲外へ移動した場合は、現在ページから最も遠い
キャッシュを捨てて空きを作る。

1 ページの展開後サイズは `pitch * height * bpp`。640x400 なら bpp=4 で 128,000、
bpp=3 で 96,000、bpp=2 で 64,000 バイト。`build/app.conf` の `apps/mgxview` は
ヒープ 2MB なので、bpp=3 なら 20 ページ前後を保持できる。

## 7. 制限

- 解像度は 640x400 以下。縦長の漫画ページは高さ 400 に合わせると約 285x400 になり、
  吹き出しの文字は判読が難しい。`--rotate90` で横向きに収めれば約 566x400 まで使える。
- 1 ファイル 1 ページ。複数ページは同一ディレクトリに置いてビューワ側でまとめる。
- 色は持たない (16 階調グレーのみ)。
- 展開には `raw_size` バイト (bpp=4 で最大 128,000、bpp=2 なら 64,000) の連続領域が必要。
