# プロジェクト制約 — 正典

> **このファイルが規則の唯一の正典。** `CLAUDE.md` には規則行だけを
> 置き、理由と詳細はここを参照する。ずれは `make check`
> (`tools/check_constraints.py`) が検出する。

規則には安定した ID を振ってある。参照側は **ID を必ず含める**こと。文言は
場所によって変えてよいが、ID が欠けていれば検査が落ちる。

規則を足す・消すときは、このファイルと参照側を同じコミットで直すこと。

## C / ABI

### [C1] C11 (GNU11) を内部実装の基準とする

**規則**: OS32 本体、ブート、ユーザーランドおよび SDK 実装は `-std=gnu11` でビルドする。公開 SDK ヘッダは従来の C89/GNU89 互換性を維持し、SQLite 系は専用規則で GNU89 を維持する。
内部実装では `//` コメント、ブロック途中および `for` 内の宣言、`_Static_assert`、内部の真偽値、指示付き初期化子、寿命が明確な複合リテラルを許可する。既存コードの一括書換えは求めない。
暗黙の関数宣言、暗黙 int、VLA を禁止する。自作コードの旧式関数定義を禁止し、既存 vendor コードの例外は明記する。T0 では匿名構造体／共用体、`restrict`、atomic、TLS、スレッド API を新規導入しない。
既存の公開型・構造体配置・呼出し規約を維持する。型の運用詳細は `POLICY_DEV.md` §2 に定める。[C2]〜[C4] は変更しない。

**理由**: コードベース全体が `-std=gnu11` でビルドされ、SQLite 系だけ gnu89。混在の切り分けは `check-c-dialect` が実際の旗で検査する。

**詳細**: `docs/POLICY_DEV.md` §2 (C11 の採用範囲の表 = [TASK_C11_MIGRATION](tasks/v3/TASK_C11_MIGRATION.md) §4)

### [C2] カーネル内の文字列操作は `lib/kstring.h`

**規則**: カーネル側では `kstrncpy` / `kstrncat` / `kstrlen` / `kstrcmp` を使う。
libc の同等品を呼ばない。

**理由**: カーネルは newlib とリンクされない。libc を呼ぶとリンクエラーか、
最悪リンクだけ通って実行時に壊れる。

**詳細**: `docs/POLICY_DEV.md` §2

### [C3] 外部公開関数は `kapi/` に `__cdecl` ラッパーを持つ

**規則**: KernelAPI として外部プログラムへ公開する関数は、必ず `kapi/` に
`__cdecl` ラッパーを作りスタック渡しでブリッジする。

**理由**: カーネル内部は System V i386 ABI。呼び出し規約が食い違うと
引数が化けるが、クラッシュせずに動いてしまうことがあり発見が遅れる。

**詳細**: `docs/POLICY_DEV.md` §2

### [C4] ハードコード定数を書かない

**規則**: 番地・サイズ・パスは定数定義の 3 層管理に従う。ソースに直接書かない。

**理由**: 同じ値が複数箇所に散ると、片方だけ変えたときに静かに壊れる。
バージョン文字列が `cmd_base.c` に直書きされ、タグと表示がずれていた前例がある。

**詳細**: `docs/POLICY_DEV.md` §2 (定数定義の 3 層管理)

### [C5] 物理番地とポインタの変換を集約する

**規則**: 恒等 supervisor 領域の物理番地からポインタへは `P2V` / `P2V_IO` を使う。
静的初期化子・マクロ定義など定数式が要る場所だけ `P2V_CONST` / `P2V_IO_CONST` を使う。
ページング前のアクセスは `P2V_BOOT` で示す。装置・PTE・CR3 にポインタを渡すときは `V2P`。
アプリ帯・lease 窓の仮想番地に `V2P` を使わず、AS / SURFACE から物理を求める。
V86 ゲスト線形・リンカ由来の仮想などの例外は `tools/check_p2v_allow.txt` に関数と理由で記録する。

**理由**: v3 の恒等写像 (D20) を保ったまま物理と仮想の意味を明示する。
`tools/check_p2v.py` が通常チェック・変更時チェックの両方で走査する。

**詳細**: `docs/tasks/v3/TASK_T1_LEDGER.md` §3-4・§4-6

## ハードウェア

### [HW1] EGC / GRCG / GDC 描画コマンドを使わない

**規則**: 全ピクセル操作は CPU による VRAM (`0xA8000`) 直接書き込み。
バックバッファに描いて `gfx_present()` → `gfx_present_dirty()` の経路のみ。

**理由**: PC-98 の 32bit 環境では、I/O ウェイトを待つより CPU で直接 VRAM を
操作した方が速い (逆転現象)。加えてエミュレータ互換性の問題がある。

**詳細**: `docs/POLICY_DEV.md` §3

### [HW2] DMA バッファは 64KB 境界をまたがない

**規則**: DMA 転送に使うバッファは 64KB 境界をまたがないよう配置する。

**理由**: PC-98 の DMAC は 64KB 単位でアドレスを扱う。またぐと転送が
先頭へ回り込み、無関係なメモリを壊す。

**詳細**: `docs/POLICY_DEV.md` §3

## KernelAPI (ABI)

### [ABI1] `sdk/kapi.json` が唯一の真実

**規則**: 生成物 (`kapi/kapi_generated.c`, `sdk/include/os32/os32_kapi_generated.h`,
`exec/exec_kapi_init.inc`, `sdk/rust/os32api/src/kapi_generated.rs`) を手編集しない。

**理由**: 次の生成で消える。消えたことに気づかないまま ABI がずれる。

**詳細**: `docs/KAPI_SPEC.md`

### [ABI2] エントリは末尾追加のみ

**規則**: 既存スロットの並べ替え・削除をしない。追加は必ず末尾。

**理由**: 配備済みバイナリは番号でエントリを引く。並びが変わると旧バイナリの
呼び出しが別関数へ飛び、`jmp $` で永久スピンして rshell ごと沈黙する。

**詳細**: `docs/KAPI_SPEC.md`

### [ABI3] KAPI 変更後は `make clean` → `make all`

**規則**: `kapi.json` の `version` と `KAPI_VERSION` を同時に上げ、フルリビルドする。
差分ビルドで済ませない。

**理由**: 古い `.o` が旧レイアウトの構造体を持ったまま残り、静かに壊れる。

**詳細**: `docs/KAPI_SPEC.md`

> **[ABI4] は解消済み (v2 M1-M3, 2026-09-03)。** 外部プログラムは既定で CPL=3
> (リング3) で走り、KAPI トランポリンの範囲検証 + フォールトガードにより、
> プログラムの不正ポインタはアプリを kill するだけでカーネルを破壊しない。
> かつて「KAPI にポインタ検証はない/呼ぶ側が防衛的に」という制約だったが、
> アーキテクチャで解決したため規則から外した。例外は shell (常駐・信頼) と
> `OS32X_FLAG_FORCE_CPL0` の CPL=0 プログラムのみ。詳細は
> `docs/archive/kernel_v2/PLAN.md` と `CLAUDE.md` Known Gotchas。

## 検証

### [V1] `make deploy` (HostDrv) だけでは検証にならない

**規則**: ライブラリやテストの変更は、NP21/W 停止 → NHD フル配備 → 再起動で検証する。

**理由**: PATH 解決は NHD の `/usr/bin` を優先する。HostDrv だけ更新しても
名前で起動すると**古いバイナリが黙って動き、合格に見える**。

**詳細**: `CLAUDE.md` Known Gotchas

### [V2] 起動対象のバイナリは自層の `deploy.yaml` に登録する

**規則**: `userland/deploy.yaml` / `apps/deploy.yaml` / `game/deploy.yaml` の
いずれか、所有する層のマニフェストに必ず載せる。

**理由**: 未登録のバイナリは NHD 上で stale 化する。KAPI レイアウトが変わると
[ABI2] と同じ経路で沈黙する。

**詳細**: `docs/08_build.md`

### [V3] リモート実行の curl タイムアウトを短くしない

**規則**: `/api/cmd` の `-m` は最低 15 秒、長時間動くプログラムは 60 秒以上。

**理由**: エミュレータは ~16MHz で遅い。途中で切るとシリアルが非同期状態になり、
以降のコマンドがすべて無応答になる。復旧には NP21/W の再起動が要る。

**詳細**: `docs/POLICY_DEBUG.md`

### [V4] 失敗と手順飛ばしはそのまま報告する

**規則**: テストが落ちた、手順を飛ばした、確認していない — いずれもそのまま書く。
成功したことにしない。

**理由**: 検証結果が信用できなければ、検証そのものに意味が無くなる。

## 破壊的操作

### [D1] NP21/W 起動中に NHD を配備しない

**規則**: **停止 → 配備 → 起動** の順を厳守する。

**理由**: ファイルロックでコピーがサイレントに失敗し、古いバイナリが動き続ける。

**詳細**: `docs/POLICY_DEBUG.md`

### [D2] 不可逆な操作は事前に承認を得る

**規則**: NHD / ディスクイメージ・マスターの上書き、`rm -rf`、`git reset --hard`、
`*.ini` (NP21/W 設定) の書き換えは、何をどう変えるか提示してから行う。
一度の承認は当該操作限りで、次回に引き継がれない。

**理由**: いずれも取り返しがつかない。`*.ini` はユーザーの環境設定でもある。

### [D3] 秘密情報を出力に含めない

**規則**: `.env` / API キー / パスワードの**内容**を出力しない。
参照が必要なら変数名だけ示す。
