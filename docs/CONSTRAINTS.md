# プロジェクト制約 — 正典

規則の正典。参照側との ID の一致は `make check-constraints` で検査する。

## C / ABI

### [C1] C11 (GNU11) を内部実装の基準とする

**規則**: 本体・ブート・ユーザーランド・SDK 実装は GNU11、公開 SDK ヘッダは C89/GNU89 互換、SQLite は GNU89。暗黙の宣言・暗黙 int・VLA・自作コードの旧式関数定義を禁止し、vendor の例外は明記する。匿名構造体・共用体、`restrict`、atomic、TLS、スレッド API は新規導入しない。公開型・構造体配置・呼出し規約を維持する。

**理由**: 実装の言語仕様を揃え、公開 ABI と既存コードの互換性を保つ。詳細は `docs/POLICY_DEV.md` §2。

### [C2] カーネルの文字列操作

**規則**: `lib/kstring.h` の `kstrncpy` / `kstrncat` / `kstrlen` / `kstrcmp` を使い、libc の同等品を呼ばない。

**理由**: カーネルは newlib とリンクされない。

### [C4] 定数の 3 層管理

**規則**: 番地・サイズ・パスは定数定義の 3 層管理に従い、ソースに直接書かない。

**理由**: 同じ値の更新漏れを防ぐ。詳細は `docs/POLICY_DEV.md` §2。

### [C5] 物理番地とポインタの変換

**規則**: 恒等 supervisor 領域の物理番地からポインタへは `P2V` / `P2V_IO`、定数式には `P2V_CONST` / `P2V_IO_CONST`、ページング前は `P2V_BOOT` を使う。装置・PTE・CR3 に渡すポインタは `V2P`、アプリ帯・lease 窓は AS / SURFACE から物理を求める。例外は `tools/check_p2v_allow.txt` に関数と理由を記録する。

**理由**: 物理と仮想の意味を明示し、検査できるようにする。

### [ABI] KernelAPI

**規則**: `sdk/kapi.json` が唯一の正であり、生成物を手編集しない。エントリは末尾に追加し、既存スロットを並べ替え・削除しない。変更時は版を上げ `make clean` → `make all` を実行する。外部公開関数の `__cdecl` ラッパーは生成器が作る。

**理由**: 生成物と版を揃え、既存バイナリのスロットと呼出し規約を守る。詳細は `docs/KAPI_SPEC.md`。

## ハードウェア

### [HW1] EGC / GRCG / GDC 描画コマンドを使わない

**規則**: EGC / GRCG / GDC の描画コマンドを使わず、バックバッファから `gfx_present()` → `gfx_present_dirty()` を通す。98 標準と PEGC は CPU で VRAM に書き、Cirrus は HAL のバックエンド内で自分の描画機能を使ってよい。

**理由**: 直接書き込みの性能とエミュレータ互換性を保つ。

### [HW2] DMA の 64KB 境界

**規則**: DMA バッファは 64KB 境界をまたがないよう配置する。

**理由**: DMAC のアドレスが回り込み、メモリを壊すため。

### [HW3] 新しいハードウェアの実装は、ライセンス上参照しやすい既存の実装資料を参照してから設計する

**規則**: (1) メーカーの資料を設計票に挙げる。
(2) BSD / MIT 等の既存実装を手本にし、設計票に file:line を示す (装置を介さない CPU 命令のみの場合は任意)。
(3) GPL のコードや構造を写さず、許諾で禁止されたリバースエンジニアリングをしない。

**理由**: 装置の実装上の癖を踏まえ、ライセンスを守る。手本の書き方は `os32-design-rally` を参照。

## 検証

`make check-manifests` は `deploy.yaml` を検査する。

### [V1] HostDrv だけでは検証にならない

**規則**: ライブラリやテストの変更は NP21/W 停止 → NHD フル配備 → 再起動で検証する。

**理由**: PATH は NHD の `/usr/bin` を優先し、古いバイナリが動きうる。

### [V3] リモート実行のタイムアウト

**規則**: `/api/cmd` の curl `-m` は最低 15 秒、長時間動くプログラムは 60 秒以上。

**理由**: 途中で切るとシリアルが非同期状態になる。

### [V4] 失敗と手順飛ばしの報告

**規則**: 失敗・手順飛ばし・未確認をそのまま報告し、成功したことにしない。

**理由**: 検証結果の信頼性を保つ。

## 破壊的操作

### [D1] NP21/W 起動中に NHD を配備しない

**規則**: 停止 → 配備 → 起動の順を守る。

**理由**: ファイルロックによる配備失敗を防ぐ。

`tools/nhd_deploy.py` が起動中の書き込みを拒む。

### [D2] 不可逆な操作は事前に承認を得る

**規則**: NHD / ディスクイメージ・マスターの上書き、`rm -rf`、`git reset --hard`、`*.ini` の書き換えは、内容を提示して操作ごとに承認を得る。

**理由**: 操作を取り消せず、設定はユーザーの環境に属する。

### [D3] 秘密情報を出力しない

**規則**: `.env` / API キー / パスワードの内容を出力しない。必要なら変数名だけ示す。

**理由**: 秘密情報の漏出を防ぐ。

### [D4] アーカイブの参照

**規則**: `docs/archive/` はユーザーの指示があるときだけ読む・引く。作業の根拠にせず、現行文書からリンクせず、試験・検査・受入の一覧も指さない。アーカイブの管理・リンク・文書の木を扱う機械的な道具は例外。

**理由**: 過去の記録は現行の約束と食い違いうる。
