## §1 登録と期待集合

候補コミット S の登録を列挙し、各検査の名前、組、環境、arch、対象条件、必要な像、変異の対応を P1-5 の登録から読む。移行直前・直後の名前集合の対称差が空であることを lint で確かめる。P0-3 の 814 は当時の母数であり、P5 の承認済み統廃合を経た実装時点で取り直す。

実行前に plan.json を保存する。リポジトリ、完全長 SHA、実行種別（途中／取り込み全件）、登録と計画の digest、期待する (検査名、対象構成、通常／変異) の組、各組の適用根拠と必要な変異 ID を含む。全件ではその版の全登録から計画を作る。runner が終了してから観測できた名前を分母にすると、ジョブ丸ごとの欠落を検出できない。

## §2 共通入口

新設する入口を `python3 -m tests.ci` とする案。サブコマンド plan は SHA と種別から計画を作り、run は計画と束の ID を受け、collect は計画と各束の結果を突き合わせる。手元でも同じ checkout・計画で同じ run と collect を呼ぶ。Make の個別目標は同じ入口へ名前を渡す薄い呼び出しにする。旧 run.py と gate.py に別々の実行手順を残さない。手元と CI の意味上の結果（名前・構成・状態・変異別判定）の差を検査する。

環境の導入、版と sha256 の検証、入力 digest によるキャッシュを環境別の設定を読む共通 action に集める。実行前に束に必要なツールを全点検し、不足一覧と影響する検査名を出す。不足した環境で実行するはずの検査は ERROR、終了値 2。他の束は続ける。

## §3 結果ファイル

各束は results.json に版、repo、S、plan digest、workflow/run ID・attempt、環境の版と digest を記録する。行のキーは §1 の組。各行に状態、理由、秒数、必要な像の digest、失敗ログ参照を持つ。部分試験が対象外でも親の名前・構成・部分試験名・理由を保存し、必須部分の省略を親 PASS で隠さない。

| 状態 | 必要な根拠と関門の扱い |
|---|---|
| PASS | 要求した実行が完了し全条件成立 |
| FAIL | 期待値不一致または生き残った変異。赤、終了値 1 |
| ERROR | ツール不足、起動不能、結果形式・証拠の不整合。赤、終了値 2 |
| NOT_RUN | 計画が要求した行または変異の実行が欠落。赤 |
| NOT_APPLICABLE | 登録の適用条件と構成を照合し対象外である根拠を保存。途中の選択で外しただけの検査を対象外にしない |
| DEFERRED | 承認済み延期台帳の ID、対象・期限または戻す条件、取り込み可否を照合。その範囲だけ台帳に従う |
| REUSED | 元の PASS の run・attempt・行を参照し、対象 SHA、検査条件、実行環境、必要な生成物、検査結果の 5 項を照合。元の結果 digest と出所を検証できる場合だけ有効 |

変異は親の名前と構成の下に ID ごとの実行結果を記録し、予定・実行・期待した理由で検出した数・生存・実行異常・未実行を別々に集計する。実行数は検出＋生存＋実行異常、予定数は実行＋未実行。再試行は採用 attempt 内で一意に数える。通常だけの実行には変異実行を要求したかも記録する。子が出す SKIP は発生箇所で理由を分類し、説明不能は ERROR とする。P0-4 の SKIP 123 行中 105 行は帰属不明、RED 書式 9,042 行には総括が混在し、P0-3 でも数が確定したのは 261/814 本だった。以後の件数は結果ファイルから計算する。

| 入力例 | 期待する結果 |
|---|---|
| 全件計画の abi-boundary の束が結果を返さない | 集計が名前付き NOT_RUN を補い取り込みを止める |
| abi-boundary の変異 1 個が期待した異常を検出せず終了 | その ID を生存、親を FAIL とし取り込みを止める |
| main 更新後に S の全件実行の同一 PASS を参照、5 項が一致 | REUSED と元行を表示。像 digest が異なれば再実行 |
| 検査と構成が有効な延期 ID に一致し、その台帳行が取り込み可 | DEFERRED と ID を表示して当該項目を許容。期限切れで実行もなければ NOT_RUN |

## §4 ジョブの生成

計画ジョブが登録から静的検査、ビルド・生成物、単体・結合、arch 別システム、検査品質（変異）の束と必要な環境を出す。各束は matrix として並列に実行する。配布像は計画後ただちに組み、実物を読む束だけがその生成を待つ。最後に常時起動する集計ジョブを置く。YAML は入口呼び出し、依存、環境と結果配送だけを担う。

変更前後の版に対し [所有の表の入口](../../build/ownership.md) の `python3 tools/ownership.py --revision REV -- PATH...` を使う。削除は旧版、改名は両版で問い合わせる。kind・target・public・images・images_complete を独立に読み、未知・照会失敗・不完全なら全件へ広げる。文書かどうかを決める check.yml の手書きパス、land_gate の文書例外、ppc_scope の一覧を新 YAML に写さない。途中の文書変更で PPC 対象なしと確定した場合、計画の 1 ジョブで決め、起動後に終了する PPC 21 ジョブを作らない。取り込み全件は別の種別である。

## §5 全件の集計

候補 S を明示して全件計画を作り、全適用検査と変異を実行する。途中の選択・別 SHA の緑で短縮しない。fail-fast を無効にし、各束も失敗を記録して次の検査へ進む。取消・環境準備の失敗時も取得できた証拠を回収する。collect は先に確定した全期待キーに外部結合し、欠落を NOT_RUN、重複・余分なキー・版や attempt の混在を ERROR とする。集計自体の欠落も取り込み不可。必須の赤があれば非ゼロ、ERROR を含めば 2 を優先する。

要約に状態別件数、失敗した名前と末尾、所要上位、束ごとの秒数を載せ、JSON と失敗ログを保存する。受入では異なる束の検査を 2 本故意に落とし、両名とログ、残りの実行、最終ジョブの赤を確認する。環境不足は別に実演する。

## §6 選択の影測定

P1-7b が所有・依存・登録の入力欄を確定する。P6-6 では同一 SHA の全件を走らせたまま、仮に選ぶ名前と外す名前、理由、不明で全件に倒した回を記録する。20 push 以上で外すはずの赤の名前・回数と、待ちを含む所要の削減見込みを出す。途中の選択を関門に反映するのは A6 の後。

**runner の範囲（A6 推奨）** は信頼済みリポジトリ・actor・ref の push 初回に限り、現行 build の許可済み x86 shard をセルフホストにする。他の環境・再実行は hosted。もう一案は全件 hosted。対象を広げる前に同じ SHA・環境条件で結果差と待ち時間を比べる。

## §7 変異の影測定

同一 SHA・束・環境で通常検査と変異実行の秒数を分け、変異 ID ごとに対象・検査・登録の版を記録する。§6 と同じ 20 push 以上について、仮の再実行条件を当てた時に外れる ID と実測の生存・異常を突き合わせる。条件の中身は A6 に渡す。

**所要の目標（A6 推奨）** は全件成功の統合 push で、最初の run 作成から最後の必須ジョブ完了までの中央値を 30 分以内とする。P0-4 の成功した統合 5 push は 1,773〜2,544 秒、中央値 1,984 秒。全 20 push 中の最長は 2,999 秒、ジョブの待ち中央値は 11 秒、最大 1,671 秒だった。途中と全件、待ちと実行を分けて同じ定義で報告し、短縮のために検査を落とさない。

## §8 成果物

像ごとに repo・完全長 SHA・構成・ビルド run/attempt・artifact ID・内容 sha256 を manifest に持つ。集計側が同じ像の digest と全件結果を結ぶ検証記録を追加し、受入担当が同じ digest に受入記録を追加する。取り込みと取得の両方でこの対応を検証する。

| 入力例 | 状態と利用条件 |
|---|---|
| S の像 H が生成完了、全件結果待ち | BUILT。ci_fetch で実機調査用に取得可。正式取り込みは停止 |
| 同じ S・H の必須全件と変異が関門を通過 | VERIFIED。land_gate が正式取り込みを許可 |
| VERIFIED の S・H に必要なゲスト・実機受入の証跡が全部そろう | ACCEPTED。受入を要する配布に使用可。取り込み時にも同じ VERIFIED の証跡を確認 |

## §9 並走と撤去対象

10 回以上、同じ SHA・構成・変異条件で旧 check/build と新全件を走らせる。名前集合の旧⊆新と承認済み統廃合の差分、検査単位の成否、変異、所要を対応付け、差ごとに原因と再実行を記録する。旧ログで帰属不能な項は不明として保存し、個別再実行で補う。未説明の差がある回は一致に数えない。比較で結果差 0 を確認し、並走中は旧の全期待ジョブと新の両方の緑を要求する。前後の表を [gate.md](gate.md) に残す。

P7-1 の撤去候補は下表の 17 部品（旧ジョブ ID を workflow ごとに 1、独立入口と action は各 1）。workflow ファイル自体と関連試験はこの数の外。役割の継承先を先に確認する。

| 現行部品 | 件数 | 継承先 |
|---|---:|---|
| check.yml の static-check、ppc-layout-inventory、ppc-compile、ppc-toolchain-cache、ppc-qemu | 5 | §4 の登録別の束、環境キャッシュ |
| build.yml の artifacts、checks、warm-c-dialect | 3 | §4 の配布像・単体検査、共通のキャッシュ |

| gate.py の旧 run 入口、ppc_scope.py、reuse_success.py の workflow 単位の再利用 | 3 | §2 の実行、§4 の計画、§3 の結果単位の照合 |
| build-setup、gate-setup、ppc-setup、static-setup の独立 action | 4 | §2 の共通環境設定に導入・照合・キャッシュを移す |

land_gate.py と ci_fetch の利用側は新しい証跡を読む。cross の作成、所要計測、runner 比較、生成物同一性の機能は利用者を確認し、古いジョブ名だけで廃止を決めない。P7 で旧 workflow と専用試験を同時に片付け、登録・文書・外の呼び出し元で旧入口とジョブ名の参照が 0 になることを確認する。

## §10 切り替えと SHA の固定

A6 後、§6・§7 の実測で承認された途中 push の条件を有効にする。取り込みには文書だけの変更も含め、更新するコミット S 自身について §5 の全件と §8 の VERIFIED を要求する。現行 land_gate.py は通常は渡された SHA の run と attempt 内のジョブを調べるが、`--via V S` は V の全件に S の文書差分と static-check の成功を足せば通る。条件付きジョブの skipped も許容し、検査名ごとの実行や像の対応を証明しない。また判定後の main 更新は別操作である。

**GitHub の取り込み制御（A6 推奨）** は main の更新権限を専用の取り込み主体に限定し、検査済み S への fast-forward に固定する案。次の順で、判定と更新の間に main や統合枝が進んでも別の SHA を通さない。

1. 統合開始時の main の完全長 SHA を B、そこから作った候補を S として記録し、B が S の祖先であることを確認する。CI は S を直接 checkout する。
2. 更新主体は信頼する repo・workflow の S の全件 run/attempt、計画 digest、期待集合、集計結果、必須像の VERIFIED と sha256 を照合する。途中の緑・別 SHA・異なる像は拒む。
3. リモート main の旧値が B の時だけ、新値を記録済みの S にする条件付き ref 更新を行う。枝名の再解決・更新時の merge/rebase を行わない。競合なら新しい B から候補を作り直し全件を回す。通常の直接更新や検査を迂回する権限を閉じられることを A6 前に確認する。
4. P7-1 最初の取り込みで更新直後の main の SHA、全件 run の head_sha、VERIFIED manifest の SHA が全て S で、取得した像が同じ digest であることを実物で示す。B・S、run/attempt、更新記録、manifest を組にして残す。
