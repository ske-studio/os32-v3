## §0 最小 workflow と仮の関門

移動前の関門は現行 CI の全件 success。P3 の変更で旧 workflow 4 本を止め、候補 SHA を直接 checkout する新 workflow を入れる。x86 の make all と配布媒体の生成、PowerPC の 6 像のビルドを並列化し、独立したジョブは失敗後も続ける。各ジョブが必須ファイルの一覧と sha256 を出し、一致判定が P2-1 の道具で照合する。移動枝ではタグ v3-pre-restructure の保存物と比較し、差には Sep-Changes: の宣言と差ごとのレビューを要する。その後は同じ入力で再生成して比較する。ビルド破損・コンパイラ不足・必須ファイル欠落はそれぞれ赤とする。

仮の land_gate はこの票の変更だけを扱う。§8 の候補 S と ref 更新の手順を使い、S の最小 workflow の同一 attempt が完了・成功し、期待する全ジョブが success であることを確認する。さらに tools/ci_fetch.sh でその attempt の配布物を取得し、PC-98 の NP21/W と PowerPC の QEMU（起動用の像）が基点と同じ到達点まで進んだ記録を要する。受入担当は S、実際に起動した配布物の sha256、到達点、画面・ログの所在を残す。記録の欠落・別の像・取消は取り込み不可。P6-2 と P6-3 を同じ取り込みで有効にして初めて仮の関門を新 CI の全件 success に置き換える。

**PC-98 の起動（A1 推奨）** は CI が作った媒体を受入担当が NP21/W で起動して記録する方式。もう一案は専用 runner から NP21/W を起動する方式。後者は P4 の起動検査で同じ媒体の到達点を無人で採取でき、起動失敗・時間切れで赤になることを実証して採用する。自動化の可否は未確認。

## §1 新しい検査の登録

候補コミット S の登録を列挙し、各検査の名前、組、環境、arch、対象条件、必要な像、変異の対応を P1-5 の登録から読む。書き直した検査の正本は S の新登録とする。lint は仕様 §8 の登録欄と変異 ID の一意性を確認し、必須欄の欠落を拒む。

全件の plan.json には候補 SHA と、その版の登録が要求する検査名・構成・変異 ID を列挙する。各ジョブはこの表を分担し、集計は未提出の行にも名前を付けられる。

製品検査は協調切替で実際に起きる停止・破損・退行を対象とする。例えば切替を調べる時は、アプリが yield した後の動作を確かめる。

## §2 共通入口

新設する入口を `python3 -m tests.ci` とする案。サブコマンド plan は SHA と種別から計画を作り、run は計画と束の ID を受け、collect は全登録の検査・構成・必須変異 ID と結果を一度突き合わせる。計画から漏れた検査も含め、欠けた行を NOT_RUN、重複・余分な行や別 run/attempt の混入を ERROR とする。集計がなければ取り込めない。必須の赤があれば非ゼロ、ERROR を含めば 2 を優先する。

要約に状態別件数、失敗した名前と末尾、所要上位、束ごとの秒数を載せ、JSON と失敗ログを保存する。受入では異なる束の検査を 2 本故意に落とし、両名とログ、残りの実行、最終ジョブの赤を確認する。環境不足は別に実演する。

## §5 成果物

像ごとに repo・完全長 SHA・構成・ビルド run/attempt・artifact ID・内容 sha256 を manifest に持つ。集計側が同じ像の digest と全件結果を結ぶ検証記録を追加し、受入担当が同じ digest に受入記録を追加する。取り込みと取得の両方でこの対応を検証する。

| 入力例 | 状態と利用条件 |
|---|---|
| S の像 H が生成完了、全件結果待ち | BUILT。ci_fetch で実機調査用に取得可。正式取り込みは停止 |
| 同じ S・H の必須全件と変異が関門を通過 | VERIFIED。§8 の照合に通れば正式取り込み可 |
| VERIFIED の S・H に必要なゲスト・実機受入の証跡が全部そろう | ACCEPTED。受入を要する配布に使用可。取り込み時にも同じ VERIFIED の証跡を確認 |

## §6 全件の所要

途中の push も全件・変異込みで始める。全件所要が A1 の目標を越えた時だけ、20 push 以上で、仮に省いた検査・変異に赤が何回あったかと短縮できる所要を測り、A6 で途中の push の扱いを決める。

**runner の範囲（A1 推奨）** は信頼済みリポジトリ・actor・ref の push 初回に限り、許可した x86 ビルドをセルフホストにする。他の環境・再実行は hosted。もう一案は全件 hosted。対象を広げる前に同じ SHA・環境条件で結果差と待ち時間を比べる。

通常検査と変異にかかった秒数を分けて結果表に残す。

**所要の目標（A1 推奨）** は全件成功の統合 push で、最初の run 作成から最後の必須ジョブ完了までの中央値を 30 分以内とする。P0-4 の成功した統合 5 push は 1,773〜2,544 秒、中央値 1,984 秒。全 20 push 中の最長は 2,999 秒、ジョブの待ち中央値は 11 秒、最大 1,671 秒だった。途中と全件、待ちと実行を分けて同じ定義で報告し、短縮のために検査を落とさない。

## §7 旧経路の停止と撤去

P3 の移動で check・build・sep・selfhost-probe の起動を止める。新 CI は新登録だけを実行する。P7-4 では P0-4 の保存値と新 CI の所要・件数を [gate.md](gate.md) に記録する。

A7 後の P7-2 で片付ける旧部品は計 21。check・build・sep・selfhost-probe の全 13 ジョブ、旧実行入口 tools/checks/run.py と tools/ci/gate.py、ppc_scope.py、reuse_success.py、環境導入の 4 action（build-setup、gate-setup、ppc-setup、static-setup）が対象となる。land_gate.py と ci_fetch は新しい結果を読む。

## §8 取り込み SHA の固定

A6 後、§6 の実測で承認された途中 push の条件を有効にする。P6-2・P6-3 以降の取り込みには文書だけの変更も含め、更新するコミット S 自身について §4 の全件を要求し、P6-5 以降は §5 の VERIFIED も照合する。現行 land_gate.py は通常は渡された SHA の run と attempt 内のジョブを調べるが、`--via V S` は V の全件に S の文書差分と static-check の成功を足せば通る。条件付きジョブの skipped も許容し、検査名ごとの実行や像の対応を証明しない。また判定後の main 更新は別操作である。

**GitHub の取り込み制御（A1 推奨）** は main の更新権限を専用の取り込み主体に限定し、検査済み S への fast-forward に固定する案。次の順で、判定と更新の間に main や統合枝が進んでも別の SHA を通さない。

1. 統合開始時の main の完全長 SHA を B、そこから作った候補を S として記録し、B が S の祖先であることを確認する。CI は S を直接 checkout する。
2. 更新主体は候補 S の指定 workflow の同じ run/attempt が完了・成功したことを確認する。取消後も結果ファイルは残り得る。仮の関門では §0 の起動記録、切替後は §4 の集計、P6-5 以降はさらに §5 の VERIFIED を使う。
3. リモート main の旧値が B の時だけ、新値を記録済みの S にする条件付き ref 更新を行う。枝名の再解決・更新時の merge/rebase を行わない。競合なら新しい B から候補を作り直し全件を回す。通常の直接更新や検査を迂回する権限を閉じられることを A1 で確認する。
4. P7-1 最初の取り込みで更新直後の main の SHA、全件 run の head_sha、VERIFIED manifest の SHA が全て S で、取得した像が同じ digest であることを実物で示す。B・S、run/attempt、更新記録、manifest を組にして残す。正式配布の ACCEPTED も受入記録と照らして 1 回実証する。


## §9 A1 で示す簡略化

| 削った手順・検査 | 理由 |
|---|---|
| 取り込み時の期待集合の再計算 | §4 の集計が全登録から欠落を検出する。 |
| 複数箇所での attempt の成功確認 | §8 で一度確認すれば、取消後に残った結果での取り込みを防げる。 |
| 再利用元を何段もたどる照合 | 実行した PASS を直接参照できなければ、その検査を回せる。 |
| 目標超過前の選択の測定と変異専用の測定手順 | 当面は全件を回し、短縮が必要になった時に §6 の記録で判断できる。 |
| 旧ジョブごとの移管台帳 | P3 で旧 workflow をまとめて止め、P7 で旧入口と一緒に撤去する。 |
| 製品の並行・競合・多重実行試験 | OS32 で同時に走るアプリは 1 本で、切替点は park・yield・終了に限られる。 |
