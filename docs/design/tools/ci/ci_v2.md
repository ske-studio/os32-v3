## §0 最小 workflow と仮の関門

移動前の関門は現行 CI の全件 success。P3 の変更で旧 workflow 4 本を止め、候補 SHA を直接 checkout する新 workflow を入れる。x86 の make all と配布媒体の生成、PowerPC の 6 像のビルドを並列化し、独立したジョブは失敗後も続ける。PowerPC の各構成では、出力先の `PPCKERN.ELF` と `boot.iso` がともに非空の通常ファイルであることを求める。各ジョブが必須ファイルの一覧と sha256 を出す。移動枝では PM の機械で候補 SHA を組み、P2-1 でタグ v3-pre-restructure の保存物と比較する。差には Sep-Changes: の宣言と差ごとのレビューを要する。その後、同じ入力で再生成して比較するのは main に入れる候補 SHA だけとする。途中の push では再生成比較を省く。ビルド破損・コンパイラ不足・必須ファイル欠落はそれぞれ赤とする。

配布物の名前は現行のままとし、ノートと pc98emu は tools/ci_fetch.sh で候補 SHA の媒体を取得する。U21 の間は文書だけの変更も含め、取り込みごとに pc98emu が PC-98 の媒体を NP21/W で手動起動する。PowerPC の起動用の像は QEMU で確認する。記録には候補 SHA、媒体を出した run ID・attempt 番号、媒体の sha256、到達点、画面またはログの所在を書く。

仮の関門はこの票の変更だけを扱う。候補 SHA の指定 run の最新 attempt 自体が完了・成功し、同じ attempt のビルドが success で、PM の機械での生成物比較の記録（候補 SHA・基点 SHA・比較ログ・終了値 0・`SHA256SUMS` と `PRESENCE` それぞれの SHA-256）を取り込み判定に添え、基点と同じ到達点を確認した起動記録を §4 の条件で媒体に照合できれば通す。P6-2〜P6-4 を揃える取り込みで、同じ受入記録を入力とする §4 の全件集計に切り替える。

## §1 新しい検査の登録

候補コミット S の登録を列挙し、各検査の名前、組、環境、arch、対象条件、必要な像、変異の対応を P1-5 の登録から読む。書き直した検査の正本は S の新登録とする。lint は仕様 §8 の登録欄と変異 ID の一意性を確認し、必須欄の欠落を拒む。

全件の plan.json には候補 SHA・run ID・attempt 番号と、その版の登録が要求する検査名・構成・変異 ID を列挙する。文書を含むパスの分類は [P1-2 の所有の入口](../../build/ownership.md) に S を指定して取得する。workflow にパスの一覧を転記しない。各ジョブはこの表を分担し、集計は未提出の行にも名前を付けられる。

例えば、変更した全パスの所属が文書で像への依存が空なら、「製品入力の変更時」を対象条件とする検査とその変異は NOT_APPLICABLE。文書検査と常時必須の行は実行する。取り込み用のビルドと再生成比較は候補 SHA で毎回実行する。U21 の間は候補ごとに両機種を起動する。引き継ぎを再開した場合、文書だけの変更で媒体の sha256 が以前に受け入れた媒体と一致すれば、その起動記録を使える（U18、§4）。製品の入力の SHA を埋める案の採否は P6 の切り替えで決める。

製品検査の対象と書き方は P1-4 で定める。

## §2 共通入口

新設する入口を `python3 -m tests.infra.ci` とする案。サブコマンド plan は SHA と種別から計画を作り、run は計画と束の ID を受け、collect は全登録の検査・構成・必須変異 ID と結果を一度突き合わせる。計画から漏れた検査も含め、欠けた行を NOT_RUN、重複・余分な行や別 SHA・run の混入を ERROR とする。集計がなければ取り込めない。必須の赤があれば非ゼロ、ERROR を含めば 2 を優先する。

要約に状態別件数、失敗した名前と末尾、所要上位、束ごとの秒数を載せ、JSON と失敗ログを保存する。受入では異なる束の検査を 2 本故意に落とし、両名とログ、残りの実行、最終ジョブの赤を確認する。環境不足は別に実演する。

## §3 結果ファイル

各束は JSON に候補 SHA・run ID・attempt 番号を記し、検査名と構成ごとに状態、理由、所要秒、ログの所在を出す。P0-4 で帰属を取れなかった SKIP は、該当する検査名と構成の行で次のいずれかに判定する。

| 状態 | 判定根拠 |
|---|---|
| PASS | 対象の検査を実行し、期待値と一致した。 |
| FAIL | 実測が期待値に反した。失敗箇所をログに残す。 |
| ERROR | 必要な道具の欠落などで正常に判定できない。 |
| NOT_RUN | 必須の実行結果が欠けている。 |
| NOT_APPLICABLE | 登録の対象条件が構成に当てはまらない。該当条件を記す。 |
| DEFERRED | 承認済みの延期台帳 ID と取り込み条件を記す。 |
| REUSED | 同じ SHA・同じ環境の完了した成功実行の結果を使う状態。現段階では名前だけを定義し、照合の実装は §6 の A6 に送る。 |

変異には検査名・構成・変異 ID を付ける。検査ごとに宣言数、実行数、狙った異常を検出して赤になった数、変異の所要秒を出す。環境異常での終了は検出数に含めない。

## §4 全件の集計

集計ジョブは全ての束を needs に指定し、失敗時も各束の終了を待って collect を実行する。再実行時は全ジョブを回し直す。計画と各束の結果は attempt ごとの成果物に保存し、collect は今回の attempt の分だけを集計する。

取り込み候補では、pc98emu の手動起動記録を CI の外から受け取る。§0 の媒体の ID と sha256 を照合し、到達点を起動検査の行に反映する。PC-98 の記録には到達点とは別に起動 selftest の失敗数を整数の `selftest_fail` として記録し、0 を必須とする。U21 の間は文書だけの変更も PC-98 と PowerPC の起動記録を毎回取り直す。引き継ぎを再開した場合、文書だけの変更（§1）では、再配布時も、以前の起動記録の run/attempt が示す配布媒体と候補媒体の sha256 が一致すれば、その到達点と記録の所在を候補の集計に記す。それ以外は候補媒体の新しい起動記録を要する。

現行の PC-98 ビルドでは tools/gen_build_id.py が HEAD の短縮 SHA を os32_build_commit に書き、build/kernel.mk が build_id.o をリンクして vmkernel.lz4 を生成する。build/image.mk の FDD 媒体にもこのカーネルが入るため、文書コミットでも通常は媒体の sha256 が変わる。案として、配布ビルドの OS32_BUILD_COMMIT に直近の製品入力変更の SHA を指定し、候補 SHA は媒体の外の manifest に記録する。継承の判定には完成した媒体の sha256 を使う。

collect は §2 の照合を行い、通常検査の状態別件数と変異の件数を別表にする。必須の FAIL・ERROR・NOT_RUN、必須変異の欠け・未検出があれば赤。対象外は理由を残し、延期は台帳の取り込み条件を満たす時だけ許す。集計には候補 SHA・run ID・集計した attempt 番号を記す。

| 入力例 | 期待する判定 |
|---|---|
| 使用できる新規・継承の起動記録がない | 起動検査を NOT_RUN として取り込みを止める。 |
| 起動検査で期待する画面に届かない | FAIL とログを残し、他の束を最後まで集めて赤にする。 |
| 同じ SHA・環境の成功実行がある | 現段階では実行する。A6 で再利用を導入した場合だけ REUSED の候補。 |
| 実機検査に承認済み台帳 ID があり、今回の取り込みを許す条件に該当する | DEFERRED として別計上し、取り込みを許す。 |
| 文書だけを変更した取り込み候補 | 製品入力の変更が条件の検査・変異は NOT_APPLICABLE。文書検査と常時必須の全件が通り、両機種の新しい起動記録（引き継ぎ再開後は同一媒体の受入済み記録も可）が揃えば success。 |

## §5 成果物

配布ジョブは媒体名に `-a<attempt>` を付けて BUILT を公開する。検査ジョブは同じ run の同名の配布物を展開し、SHA256SUMS を照合する。全件集計と依存ジョブが成功した場合だけ、collect が集計 JSON を別の成果物 `verified-<SHA>-a<attempt>` として公開する。再実行は全ジョブを対象にする。以前の attempt の媒体や合格札は使えない。

ci_fetch の既定は VERIFIED 以上。`--allow-built` は実機調査向け。`--evidence JSON` では land_gate が両機種の起動記録を照合し、合格した媒体を ACCEPTED と表示する。受入記録は PM の証拠 JSON とログに保持する。

問い合わせ時に、媒体の manifest（SHA、構成、ビルド run/attempt、artifact ID、sha256）、§4 の集計、受入記録から次を導く。

| 入力例 | 問い合わせの答え |
|---|---|
| S の媒体がある | BUILT。集計前でも ci_fetch で取得できる。 |
| 同じ S の最新の全件集計が success | VERIFIED。§8 の取り込みに使える。 |
| S の媒体の sha256 を記した受入記録がある | ACCEPTED。その媒体の受入を確認できる。取り込みには §4 の success が要る。 |

## §6 全件の所要

途中の push も全件・変異込みで始める。全件所要が A1 の目標を越えた時だけ、20 push 以上で、仮に省いた検査・変異に赤が何回あったかと短縮できる所要を測り、A6 で承認された条件を途中の push に適用する。

**runner の範囲（A1 推奨）** は全件 hosted で始める。もう一案は信頼済み push の x86 ビルドだけをセルフホストで回す方式。同じ SHA のビルドを比べ、結果が一致し、待ち時間が短くなると確認できるまで分岐を保留する。

通常検査と変異にかかった秒数を分けて結果表に残す。

**所要の目標（A1 推奨）** は全件成功の統合 push で、最初の run 作成から最後の必須ジョブ完了までの中央値を 30 分以内とする。P0-4 の成功した統合 5 push は 1,773〜2,544 秒、中央値 1,984 秒。全 20 push 中の最長は 2,999 秒、ジョブの待ち中央値は 11 秒、最大 1,671 秒だった。途中と全件、待ちと実行を分けて同じ定義で報告し、短縮のために検査を落とさない。

## §7 旧経路の停止と撤去

P3 の移動で check・build・sep・selfhost-probe の起動を止める。新 CI は新登録だけを実行する。P7-4 では P0-4 の保存値と新 CI の所要・件数を [gate.md](gate.md) に記録する。

A7 後の P7-2 で片付ける旧部品は計 21。check・build・sep・selfhost-probe の全 13 ジョブ、旧実行入口 tools/checks/run.py と tools/ci/gate.py、ppc_scope.py、reuse_success.py、環境導入の 4 action（build-setup、gate-setup、ppc-setup、static-setup）が対象となる。land_gate.py と ci_fetch は新しい結果を読む。

## §8 取り込み SHA の固定

現行 land_gate.py の `--via V S` は、V の全件に S の文書差分と static-check の成功を足せば通る。新しい関門は文書だけでも S 自身を検査する。§1・§4 の対象外の行の実行時間は 0 分。取り込み候補にはビルド・一致・起動受入も要るため、CI の所要は §6 の全件と同じ中央値 30 分以内を目標とする。新 CI の文書変更の所要は未実測。pc98emu の記録待ちは別に計る。

取り込み時は候補 SHA である S の指定 run の最新 attempt が完了・成功したことを照合する。全件の成立は同じ attempt の collect が検査し、欠落や失敗があれば run が失敗する。

**GitHub の取り込み制御（A1 推奨）** は、判定を通った S をそのまま `git push origin <S>:main` で早送りする。main が先に分岐していれば push は拒否され、新しい候補を検査する。P7-1 で取り込み後の main と集計の SHA が一致し、取得した媒体の sha256 が受入記録に一致することを確かめる。

## §9 A1 で示す簡略化

| 削った手順・検査 | 理由 |
|---|---|
| 取り込み時の期待集合の再計算 | §4 の集計が全登録から欠落を検出する。 |
| 複数箇所での attempt の成功確認 | §8 で一度確認すれば、取消後に残った結果での取り込みを防げる。 |
| 再利用元を何段もたどる照合 | 実行した PASS を直接参照できなければ、その検査を回せる。 |
| 目標超過前の選択の測定と変異専用の測定手順 | 当面は全件を回し、短縮が必要になった時に §6 の記録で判断できる。 |
| 旧ジョブごとの移管台帳 | P3 で旧 workflow をまとめて止め、P7 で旧入口と一緒に撤去する。 |
| 製品の並行・競合・多重実行試験 | OS32 で同時に走るアプリは 1 本で、切替点は park・yield・終了に限られる。 |
| 起動記録の作成者の権限検証 | 開発者は PM 1 人であり、媒体の取り違えは run/attempt と sha256 の照合で検出できる。 |
| A6 前の REUSED の照合実装 | 全件を回す間は再利用する結果がない。 |
| 成果物の状態の保存・更新 | 媒体、集計、受入記録から問い合わせ時に導ける。 |
| 専用の取り込み主体と権限設定、B・S の組の保存 | PM が判定済みの SHA を指定して早送りする。 |
| 途中の push での再生成比較 | main に入れる候補で比較すれば、取り込み前に不一致を検出できる。 |

## §10 変更の所属による選択（U29）

途中の push と取り込み候補には同じ規則を使う。main の push は更新直前の SHA、枝は候補と origin/main の merge-base を基点とする。改名は旧名と新名の両方を照合し、削除など候補の所属表で確定できないパスは全件に広げる。複数の変更は必要な構成の和集合を取る。週に一度の main と手動実行は全件とする。

| 変更の所属 | 媒体・ビルド | 検査 |
|---|---|---|
| 共通カーネル・共通デバイス | PC-98 配布と PowerPC 6 像 | 両 CPU の層・HAL・KAPI・媒体・起動、所有 |
| CPU・機種固有 | 該当機種の媒体 | その CPU の構成と所有 |
| userland | PC-98 配布の programs。PowerPC 専用は同機種、共用ソースは両方 | PC-98 は Ring3・C 方言・配布物・再生成、PowerPC の利用はコンパイル登録を参照 |
| 文書 | PC-98 起動 FD と PowerMac core（U21） | 文書と、変更パスを入力とする検査 |
| 検査本体・関門 | 選んだ検査が実際に読む配布媒体 | 本体・登録入力の該当検査と登録・集計・取り込みの関門試験 |
| 公開口・固定契約・ABI、ビルド規則、workflow、登録、未知の影響 | PC-98 配布・6 像・programs・SDK | 全登録構成と変異 |

文書用 FD は packages.yaml の fd から必要な入力を列挙し、そこに載るコマンドだけを組む。PC-98 の通常配布では ISO と HostDrv が programs を必要とし、配布用カーネルも候補 SHA のものを使う。カーネル単独で省くのは独立した Ring3 検査と SDK ビルドで、媒体中の programs を過去の成果物から再利用するのは P6-6 の続きで扱う。共有ソースは Make の依存をたどり、PC-98 のユーザーランド ELF にも入れば Ring3 と C 方言を追加し、入力先が不明なら全件にする。

plan.json は基点、候補、run、attempt、変更パスの分類、媒体、選択した登録構成・変異と省略理由を記録する。集計は計画を再計算し、各ジョブの success / skipped と個別の結果を照合して VERIFIED を出す。取り込み時に現在の origin/main と候補から同じ選択を再計算し、計画と最新 attempt の VERIFIED 集計（終了値・実行識別・選択と省略理由・各行と変異の結果）、選択された機種の起動記録を照合する。文書だけでも両機種は今回の媒体で起動する。
