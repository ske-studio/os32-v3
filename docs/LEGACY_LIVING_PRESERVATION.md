# レガシー実機の動態保存と役割分離

> 状態: **草案 (2026-09-28)** — 設計思想の草案で、ロードマップ・実装契約ではない。位置は v3 本案 ([tasks/v3/V3_PLAN.md](tasks/v3/V3_PLAN.md) §1、2026-09-30) で決めた: v3 の目的の一文の「時代依存の仕事は Host Service に任せ、OS32 側の契約は小さく保つ」の出どころ。

> **OS64 の定義 (ユーザー決定 2026-09-30、語の定義はここ 1 か所)**: **OS64 は OS32 とは別の 64 ビット OS の構想**で、現代の機械で動く側に置く。
> OS32 の版ではなく、**v3 / v4 の範囲に入れない** (版数表にも載せない — [ROADMAP.md §0](ROADMAP.md))。Host Service の実装の名前でもない
> (Host Service は現代ホストで動くサービスで、そのホストの OS は問わない。OS64 はその候補の 1 つ)。
> OS32 の移植を 32 ビットに限る決定 ([tasks/portability/ARM_GAUGE.md §10](tasks/portability/ARM_GAUGE.md)「64 ビットは範囲外」) とは**別物として両立する** —
> OS32 を 64 ビットへ移すのではなく、64 ビット機には別の OS を考える。本文と [AUXILIARY_CORE_SERVICE.md](AUXILIARY_CORE_SERVICE.md) の「OS64」はこの意味で読む。

## 目的

OS32 / OS64 の目的は、古いコンピュータを現代コンピュータへ作り替えることではない。

レガシーハードウェアには、その世代のCPU、表示、音源、入力装置、バス、待ち時間、物理的な操作感など、実機で動かすこと自体に意味のある体験が存在する。OS32はその体験を残しながら、現代環境との接続に必要な処理だけを外部へ委譲する。

この方針を、単なる互換性維持ではなく **コンピュータの動態保存** のための設計原則として扱う。

## 判断基準: 「実機で行う意味があるか」

処理をレガシー側へ実装できるかどうかだけで配置を決めない。

第一の判断基準は、

> **その処理を実機で実行することが、その機械固有の体験・挙動・保存価値に寄与するか**

とする。

実機側へ残す候補:

- 当時のCPUで動くアプリケーション / ゲームロジック
- 実機のグラフィックハードウェアによる表示
- FM音源、PCM、MIDI等、その機械固有の音響経路
- キーボード、マウス、ゲームパッド等の実機入力
- FDD/HDD等、体験上意味のある実デバイス
- その世代固有のタイミング、バス帯域、制約が挙動へ影響する処理

現代ホストへ委譲する候補:

- TLSなど時代とともに更新されるネットワーク処理
- 現代的な動画・音声codec
- AI推論
- ストリーミング用エンコード
- 大容量ストレージ管理
- 現代サービス/APIとの接続
- レガシー実機で実行しても体験上の価値が増えない高負荷処理

例えばTLSを古いCPUへ移植すること自体は技術的挑戦になり得るが、それがPC-98等の機械固有の体験を増やさないなら、標準構成ではHost Serviceへ任せる。一方、実86音源を持つ機械では、音声生成を単に現代ホストのPCMへ置換せず、実機音源を利用すること自体に保存上の意味がある。

## レガシーを現代化しすぎない

新しい機能を利用できることと、レガシー側へ新しい機能を実装すべきことは同義ではない。

OS32側の役割を安定させ、時代とともに変化する処理はOS64 / Host Service側へ寄せる。

```text
Legacy machine / OS32
    |
    |  stable Host Service contract
    v
Modern host / OS64
    |
    +-- TLS / Internet services
    +-- AI
    +-- modern codecs
    +-- large storage
    +-- streaming
```

これにより、外部環境が変化してもレガシー側の変更を最小限にできる。

## 「結果」ではなく「体験」を保存する

エミュレータはソフトウェア、データ、論理的挙動の保存に重要であり、OS32でも積極的に利用する。

ただし実機保存とは目的が異なる。

実機では、

- 実際のCPU速度と待ち時間
- グラフィック回路と実表示
- 実音源
- バスやストレージの挙動
- 実際の入力装置
- ディスプレイや周辺機器との組み合わせ

まで含めたシステム全体を体験できる。

したがってOS32は、エミュレーションによる保存を否定せず、それとは別に **実機が実際に仕事をしている状態を維持する** ことを重視する。

## 動態保存

OS32 / OS64による保存は「電源が入る」「当時のソフトが起動する」だけを最終状態としない。

目標は、

> **レガシーコンピュータが、その固有性を失わず、現在の環境でも役割を持って稼働し続けること**

である。

現代ネットワークやサービスとの翻訳はホストが担当する。将来それらの仕様が変化した場合も、Host Service側を更新することでレガシー側を可能な限り固定する。

これはハードウェア保存、ソフトウェア保存、操作体験の保存に加えて、**現役性の保存** を狙うものである。

## Auxiliary Core Serviceとの関係

[AUXILIARY_CORE_SERVICE.md](AUXILIARY_CORE_SERVICE.md) の補助コア利用も、この原則に従う。

余剰コアが存在するからといってOS32を一般的なSMP OSへ変えるのではない。補助コアは、その実機内部で完結させることに意味があり、かつ固定機能として単純化できる仕事へ利用する。

一方、AIや現代codec等の高性能処理を補助コアへ無理に持ち込む必要はない。最新機に任せる方が適切な処理はHost Serviceへ委譲する。

ACSはHost Serviceの代替ではなく、**レガシー実機内部で余っている資源を、その機械の役割を壊さず活用する手段** と位置づける。

## 世代を越えた役割分担

この原則はPC-98だけに限定しない。

単一コアx86、マルチコアx86、ARM、ゲーム機、電子辞書等でも、

1. その機械で体験する意味のある仕事を特定する
2. その仕事は可能な限り実機側へ残す
3. 現代性だけを要求する処理は外部へ出す
4. 境界を安定したAPIとして維持する

という同じ判断を適用する。

これにより各世代のコンピュータを無理に同じ性能・機能へ揃えるのではなく、**各世代が得意な、割り切った仕事を持ったまま共存する**ことを目指す。

## 長期的な設計原則

技術の進歩によって「実装可能なこと」は増え続ける。しかしOS32 / OS64では、可能性そのものを機能追加の理由にしない。

- レガシー側の契約は小さく安定させる
- 時代依存部分は交換可能なホストへ置く
- 実機固有の価値を抽象化によって消さない
- 新しいハードウェアを古いハードウェアの代用品にするだけでなく、両者を協調させる
- 実機で行う意味のない高性能処理をレガシーへ強制しない

この境界を維持することを、OS32 / OS64の長期互換性と動態保存の基礎とする。
