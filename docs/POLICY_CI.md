# CI ポリシー — 作る時と、改修する時

> 状態: **現行 (2026-11-17)** — CI (GitHub Actions の workflow・composite action・CI から呼ぶ道具) を作る時と、既存の CI を直す時の決まりの正典。ユーザーの指示 (2026-11-17「ci 作成のポリシーと改修ポリシーをドキュメント化して」)。

対象は `.github/workflows/`・`.github/actions/`・`tools/ci/` と、検査の登録 (`tests/registry.toml`) を作る・直す人。
決まりの根拠になった既存の CI の欠点の実測 (F1〜F9) と、決まりどおりに組んだ手本の形は [design/tools/ci/gate.md](design/tools/ci/gate.md)。取り込みの手順 (どの結論で main に入れるか) は [ROLES §0「検査」](tasks/agents/ROLES.md)、検査の宣言の欄は [registry_v2.md](design/tools/checks/registry_v2.md) が正典で、ここには写さない。

結果の読み方・回し直し・CI が起動しない時の手順は、スキル `.claude/skills/os32-ci-read`。古い検査は関門ではない (P7 で消す)。参考に読むだけ。 停止前の所要の記録はスキル `.claude/skills/os32-ci-inventory`。

作り直し票の G1 は統合枝 wt/int-* の候補 SHA・指定 run の最新 attempt の選択計画に含まれる全件の集計（変異・同じ入力の再生成を含む）の成功と、同じ候補の計画で作る機種の起動受入（文書だけは両機種）を求める。旧 CI の R2・R3 は適用しない。早送り前に `python3 -B tools/ci/land_gate.py <SHA> --evidence <JSON>` を回す。[新 CI の関門](design/tools/ci/ci_v2.md#8-取り込み-sha-の固定)

## §1. 作る時の決まり

| # | 決まり | 理由・実例 |
|---|---|---|
| G1 | **関門にならない検査を作らない。** U29 に従い、**main に入れる SHA** も変更の所属で検査を選び、選んだ検査と変異の赤を取り込み前に止める。公開契約・ビルド規則・登録・workflow・所属不明は全件、週次と手動も全件。文書だけの候補も同じ関門を通す | 夜間の `full-check` は 2026-11-14〜17 の 4 回のうち 3 回が失敗し、その間も同じ SHA が毎回の CI を通って main に入った。変異の目印がずれた検査が 2 本、数日〜数週間そのままだった |
| G2 | **全部回して、全部挙げる。** 1 本落ちても残りを回す (`make -k`、行列は `fail-fast: false`)。ジョブを `needs` で鎖にするのは、前のジョブの成果物を実際に読む時だけ。結果の行が無い検査 (回っていない) は失敗に数える | 旧実行器は最初の失敗で止まった。11-17 は ppc-compile が 1 本目で落ち、後ろの ppc-qemu は実行されなかった |
| G3 | **結果は表で、ログは落ちた分だけ。** 検査ごとに 1 本のログ (`CHECK_LOG_DIR`)。画面とジョブの要約に出すのは、件数・落ちた検査の名前・その末尾・遅い検査だけ。成果物は結果の JSON と落ちた検査のログ。変異の「期待どおりの失敗」を共有のログに流さない | 11-17 の `full-check` の失敗ログは 1.4 GB・1,200 万行で、どの検査が落ちたかは grep しないと分からなかった |
| G4 | **何を回すかは登録から引く。** workflow の YAML に検査の名前・ソースのパスの一覧を書かない。検査の集合・シャードの割り方・要る環境は `tests/registry.toml` の登録から、arch ごとの対象は所有者集合 (`build/select.mk`) から引く | check.yml の static-check は `make check-<名>` を約 30 行手で並べ、`tools/ci/ppc_scope.py` は共通・PowerPC・x86 のパスの一覧を別に持っている。一覧が 2 つあると片方が古くなる |
| G5 | **用意は 1 か所。** 道具の導入は composite action にまとめ、ジョブには書かない。どのジョブも同じ環境にする。外から取る物は版と sha256 を固定し、キャッシュの鍵には入力のハッシュを入れる | `apt-get install … gcc-13 …` の行が check.yml と full-check.yml に 4 回、少しずつ違う中身で書かれている |
| G6 | **足りない道具は、検査を始める前に全部まとめて挙げて止める。** 環境の不足 (終了コード 2) と検査の失敗 (終了コード 1) を分ける。道具が無い検査を飛ばして通さない。SKIP の行がある検査は結果の表に挙げる | apt は update を 300 秒、install を 600 秒で打ち切り、TERM の 30 秒後も残るプロセスには KILL を送る。static-check は static-setup の最後に道具と Python モジュールの不足を summary に列挙し、終了コード 2 で止まる。クロスコンパイラの無いジョブでは PowerPC の検査が SKIP で通る。手元では `gcc-13` が無いと検査の途中で `FileNotFoundError` になり、変更が原因かどうかをログから読み分けることになった |
| G7 | **CI と手元で同じ入口。** workflow の `run:` は道具を 1 行で呼ぶだけにし、同じコマンドを手元で回せるようにする。合否の判定・集計・分岐を YAML の shell に書かない | `r1-fixture-host` は `make check-…` では通り、`run.py --run …` では `KeyError: 'BUILD_OUT'` で落ちる。入口が 2 つあると、片方でしか見つからない失敗が出る |
| G8 | **振る舞いを変えない変更は、生成物が基点と同じことを機械で確かめる。** 変わるのが正しい変更は、コミットの本文で宣言する (`Sep-Changes:`、[sep_identity.md](design/tools/ci/sep_identity.md)) | 移すだけの段のたびに、手元で 20〜40 分かけて組み比べていた |
| G9 | **CI の道具にも試験を付ける。** `tools/ci/` の道具は、判定の部分を純関数に分けて host の試験と変異を付け、検査として登録する。CI の判定が誤っていないことを CI 自身が確かめる | 判定の誤り (失敗を通す・回っていない検査を数えない) は、赤が出ないので誰も気付かない |
| G10 | **時間を割り、測り、見えるようにする。** 重い束はシャードで割る。検査ごとの秒を記録して、遅い検査を要約に出す。全部のジョブに `timeout-minutes`、同じ ref の古い実行は `concurrency` で打ち切る | `full-check` は 1 ジョブで 147 分かかり、どの検査が遅いかは成果物を開かないと分からなかった |
| G11 | **同じ入力からは同じ生成物。** 時刻・絶対パス・並びの揺れを生成物に入れない。入る物は G8 の比較から名前で外し、理由を書く | RAM root の ISO は同じ入力でも作るたびに 28 バイト変わる (今は比較から外している) |
| G12 | **入れる前に、赤が見えることを 1 回実演する。** 検査を 1 本わざと落とした枝で、残りが最後まで回ること・表と成果物に出ること・ジョブが失敗で終わることを確かめる。道具の無い環境で終了コード 2 になることも確かめる | 緑だけを見て入れた関門は、落ちた時に何が見えるかが分からない |
| G13 | **重い検査は中を並列にできるか検討する。** 検査を足す・変異や場合を足す時、独立に回せる繰り返し (変異ごとの組み直しと実行、場合ごとの実行) は `tools/tests/mutpar.py` の `run_ordered` に載せる (並べる数は `jobs()` が CPU から決める、出力の順は前と同じ)。直列に残すのは、`os.environ`・`sys.path`・カレントディレクトリ・元の木などを書き換える場合だけで、その理由を試験の中に 1 行書く。CI の実測で 300 秒を越える検査は、並列にしたか・できない理由を、検査の棚卸し (スキル `os32-ci-inventory`) の表に残す。並列にしたら、前後と直列 (`jobs=1`) で変異ごとの RED/SURVIVED が一致すること、CI の runner のメモリの上限を越えないことを確かめる | `gf5-host` は 217 本の変異を 1 本ずつ組み直して回し、CI で 13〜27 分、CPU は 1 スレッドだけだった (2026-11-19、ユーザーの指摘)。`run_ordered` に載せて手元の 8 並列で 1,029 秒 → 415 秒。300 秒を越える host の検査はほかに 17 本あった |


- **G14 検査の棚卸しはユーザーが決める** (ユーザー決定 2026-11-20「今後棚卸し内容は私が決めることにします」): CI から検査を外す・軽くする・戻すことは、PM が実測 (重い順の表・何を確かめているか・外した時に失う物) を出し、ユーザーが選ぶ。PM は自分で外さない。外した検査は持越し台帳 (docs/tasks/DEFERRED_TESTS.md) に戻す条件付きで書く。重みの作り直しと検査の中の並列化 (G13) は、検査の集合を変えないので PM が進めてよい。

## §2. 改修する時の決まり (既存の workflow を直す)

| # | 決まり | 理由・実例 |
|---|---|---|
| R1 | **欠点を実測で書いてから直す。** 実行履歴から、成功率・所要時間・ログの大きさ・飛ばされた検査を数え、どの決まり (G1〜G13) に反しているかを表にする。推測で直さない | [gate.md §1](design/tools/ci/gate.md) の表が雛形 (欠点・根拠の SHA と日付) |
| R2 | **手本を先に、別の workflow で動かす。** 既存の workflow は触らず、枝専用の workflow で新しい形を走らせて、時間と見つかる赤を測る。数字が出てから既存を替える | `sep` (`wt/sep-*` だけで起動) は check・build と並んで走る |
| R3 | **関門を弱めない。** 置き換えの前後で、回る検査の集合が減らないことを機械で確かめる (旧の workflow が回していた検査の名前 ⊆ 新しい形が回す名前)。新旧を並べて走らせる期間は、両方が緑の SHA だけを取り込む | 手で並べた一覧から登録の一覧に替える時に、落ちる検査が出やすい |
| R4 | **赤のまま関門にしない。** 新しい関門で初めて見える赤は、関門を有効にする前に直す。直すまで関門から外す検査は、名前・理由・直す票を 1 か所に挙げ、空になったらその表ごと消す | 変異込みを main に入れる SHA の関門にすると、main に溜まっていた赤 (2026-11-17 は 4 本) が最初の実行で全部出る |
| R5 | **1 つずつ替え、替えるたびに通す。** 1 コミットで替えるのは 1 つの workflow の 1 つのジョブまで。順は、用意 (G5) → 入口 (G7) → 一覧 (G4) → 表とログ (G2・G3) → 関門の強さ (G1)。各コミットは main の CI で 1 回通ってから次へ (同じ枝に積んでまとめて 1 回通すのは不可、ユーザー決定 2026-11-19 — 途中のコミットと revert の先が未検査になる。main への入れ方の順番は [PARALLEL_BRANCHES](tasks/agents/PARALLEL_BRANCHES.md) §3)。戻す時は `git revert` 1 回で戻る大きさにする | 用意と入口は検査の集合を変えないので先に替えられる。関門の強さは赤を消した後 |
| R6 | **workflow を読む物を同じ変更で直す。** workflow の本文を読む試験・道具 (`tools/tests/test_ci_stab.py`・`test_ci_split.py`・`ppc_ci.py`、`tools/gen_tests_inventory.py` は check.yml を読む、検査の `covers` に workflow のパスを持つ物) と、文書 ([08_build.md](08_build.md) §8-6、[TESTS.md](TESTS.md)) | workflow だけ直すと、その本文を目印にしている試験が変異込みで落ちる |
| R7 | **置き換えた物は同じ変更で消す。** 古いジョブ・道具・一覧・その試験を残さない。「旧」「互換」の名前で並べて残さない ([POLICY_DEV](POLICY_DEV.md) §9 の文書の決まりと同じ) | 残した古い経路は、誰も回さないまま壊れる |
| R8 | **前後の数字を残す。** 替える前と後の、所要時間 (ジョブごと・合計)・回った検査の数・見つかった赤を、その workflow の設計書に書く | 速くなったか・強くなったかを、次に直す人が数字で読める |

既存の workflow (check・build) をこの決まりに当てた対応表は [gate.md §4](design/tools/ci/gate.md)。

## §3. 入れる前の確かめ

新しい workflow・直した workflow・CI の道具を main に入れる前に、次を確かめて、その workflow の設計書に実行の SHA と一緒に書く。

| 確かめること | 決まり |
|---|---|
| 枝の上で実際に走らせ、全部のジョブの結論を読んだ (待ちの終了と取り込みを 1 本のコマンドに繋げない) | R2 |
| 1 本わざと落とした実行で、残りが回り、表・成果物・ジョブの結論に出た | G2・G3・G12 |
| 道具の無い環境で、検査を始めずに終了コード 2 で止まった | G6 |
| 回る検査の集合が、置き換える前より減っていない | R3 |
| CI の道具の試験と変異が通る。workflow の本文を読む試験を変異込みで回した | G9・R6 |
| 所要時間の前後を書いた | G10・R8 |
| 変更した契約を登録の sources と照合し、`python3 -B -m tests.infra.ci lint` と `python3 -B -m tests.infra.ci run --check <id> --mutate` を回した | R6 |
