# OS32 開発ポリシー

## §1. 基本方針

品質・可読性を優先し、学習と判断を記録し、動く最小単位を積み上げる。

### カーネル層の不具合は新機能より優先する

カーネル本体・VFS・FS・exec・ページング・KernelAPI・共有ライブラリの既知の不具合は、新機能より先に直す。アプリ固有の不具合は対象外。
発見したら票に起こし、着手中のものは試験が通る区切りまで進めてよい。通らなければ止めて先に直す。
未解消や範囲外のものは理由とともに残す。稀でもデータ破壊・型の取り違え・権限の飛び越えは優先する。
再現・切り分けに新機能側の道具が必要なら先に作り、完成後に不具合へ戻る。
役割とレビューは [ROLES](tasks/agents/ROLES.md) を参照。

## §2. コーディング規約

C の基準は [C1](CONSTRAINTS.md)、検査は `make check-c-dialect`。既存コードの言語機能・型を一括置換しない。
呼出し規約・文字列操作は [CONSTRAINTS.md](CONSTRAINTS.md)、アセンブラは [10_notes.md](10_notes.md) を参照。

### 数値演算は整数を第一選択にする (ユーザー決定)

カーネル本体・部品・ドライバとシステム部品は整数演算を使う。カーネル層はユーザーランドの数学ライブラリに依存せず、必要な道具を `lib/` に置く。ユーザーランドのシステム部品は同じ層の `os32_math` を先に使う。両層で必要になれば共有の置き場への移動を検討する。
浮動小数点が不可欠な場合は、整数では足りない理由と FPU の無い機体での扱いを示し、実装前にユーザーに確認する。アプリは対象外。

### ソースファイルの大きさ (ユーザー決定)

1 機能 1 ファイルを極力保ち、設計段階で関数・状態・共通部分のファイル割当てを表にする。既存の大きいファイルに足す機能も別ファイルに置く。共有の構造体や引数の束を増やすだけの場合は例外とし理由を書く。1 ファイルは 500 行程度を目安にする。大きいソースの分割は GeForce の実装後に行う (ユーザー指示)。
分割は手で写さず、コンパイラまたは ctags で関数範囲を取得し、対応表に従いスクリプトで切り出す。ビルドと関数ごとの機械語を比較し、差の理由を記録し、試験・許可リスト・変異の目印・検査の covers・ビルド登録を追従させる。移動は [SRC_MOVE.md](SRC_MOVE.md)。

### 定数定義の3層管理

| レイヤー | 定義場所 | 例 |
|---------|---------|-----|
| Shared Layer | `os32_kapi_shared.h` | KAPI構造体メンバ名、エラーコード |
| Subsystem Layer | 各サブシステムヘッダ (`vfs.h`, `pc98.h` 等) | `VFS_MAX_PATH`, `TVRAM_COLS` |
| Local Layer | 各モジュール内で定数化 | バッファオフセット等 |

1 つの意味に名前は 1 つ。番地・帯は `include/memmap.h` 等の正典を使う。NASM の C と共通の値は `.inc` に置き host 試験で一致を確かめる。kdebug・hwdev のヘッダは [hwdev の契約](design/hwdev/README.md) を参照。

## §7. リリースとバージョン管理

### バージョン番号の管理

| 定数 | 定義場所 | 用途 |
|------|---------|------|
| `SYS_VERSION` | `include/config.h` | OS全体のバージョン文字列 |
| `KAPI_VERSION` | `sdk/include/os32/os32_kapi_shared.h` | KernelAPI の互換性バージョン |

### リリースの手順 (v2.1 で行った形)

1. 版の区切りの条件をユーザーが決め、[decisions/VERSIONS.md §1](decisions/VERSIONS.md) に書く (版の対応の正典)。
2. `make clean` → `make all` → `make external` → `make check` (全部) が通ることを確かめ、rc を読む。
3. エミュレータと (実機が対象なら) 実機で条件を確かめ、判定を記録する (v2.1 は実機の回の CHECKLIST の末尾)。
4. **リリースノート `docs/RELEASE_vX.md`** (到達点・受け入れの条件・分かっている制限) を書き、
   **`CHANGELOG.md` に 3〜5 行の要約 + リリースノートへのリンク**、INDEX の「API・ガイド」節に載せる。
5. 取り込み先 (`main`) へ合流して Git タグ `vX.Y` を付け、push する。CI (GitHub Actions) の成果物が実機用の配布物になる
   ([08_build.md §8-6](08_build.md))。
6. タグを付けたリリースノートの本文は後から直さない。誤りが分かったら**訂正注記を足す** (版の記録を保つため)。

## §8. 文書の状態行 (語彙の正典)

`docs/tasks/` の票・計画・引き継ぎは先頭 12 行以内に `> 状態: **<語> (YYYY-MM-DD)** — <根拠や残件>` を持つ。`TASK_*.md`・`HANDOVER_*.md`・`CHECKLIST_*.md`・`*PLAN*.md` は必須。他は状態行があれば語彙に従う。古い行は `それまでの状態:` とする。検査は `make check-docs-status`。

<!-- status-vocab:begin -->
| 語 | 意味 |
|---|---|
| 確定 | 設計・契約の内容が確定。実装と受入の状態は対応する票で管理する |
| 計画 | 何をするか・順序を決めた段。設計票はまだ無い |
| 設計中 | 設計票を書いている・レビュー往復中、または設計が承認されて実装を待つ |
| 実装中 | 実装が進んでいる (一部着地を含む) |
| 受入待ち | 実装は着地した。受入条件の一部または全部が未実施 |
| 受入完了・実機確認待ち | エミュレータ (NP21/W) とホストの受入は済み、**実機での確認だけ**が残る (残る項目を行に書く) |
| 受入完了 | 受入条件をすべて満たした (満たさなかった項目は理由を書いて残件へ) |
| 撤回 | 取りやめた |
| 完了記録 | やり切った作業・実施済みの回・快照の記録。以後は更新しない |
| 草案 | 計画以前のアイデアや設計思想。ロードマップ・実装契約ではない |
| 現行 | 運用中の規約・台帳 (体制の文書など)。改訂しながら使い続ける |
<!-- status-vocab:end -->

## §9. 文書の書き方

正典は [INDEX.md](INDEX.md) の表で決め、古い記述を正典で直す。他の文書は要約とリンクにする。
仕様には現行の仕様、規約には現行の規則、票には設計・契約・受入条件、台帳には未完了、入口には案内を置く。

**2a. 設計書は 1 機能 1 ファイルでソースと同じ構造にする (ユーザー決定)。** `docs/design/<ソースと同じパス>.md` に置く。共通の取り決めは共通部分のソースの設計書に置き、他から参照する。既存の `docs/decisions/` の設計は移すまで現行。

現行・計画・過去を区別する。完了・撤回した票や記録は `tools/move_docs.py` で移す。
平易な日本語で 1 文に 1 つ書き、コードの根拠は `file:line`、文書間は節やリンクを使う。推測・未確認は [推]・[未]、日付は絶対日付で書く。
