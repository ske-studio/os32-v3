# OS32 開発ポリシー

## §1. 基本方針

品質・可読性を優先し、学習と判断を記録し、動く最小単位を積み上げる。

### カーネル層の不具合は新機能より優先する

カーネル本体・VFS・FS・exec・ページング・KernelAPI・共有ライブラリの既知の不具合は、新機能より先に直す。アプリ固有の不具合は対象外。
発見したら票に起こし、着手中のものは試験が通る区切りまで進めてよい。通らなければ止めて先に直す。
未解消や範囲外のものは理由とともに残す。稀でもデータ破壊・型の取り違え・権限の飛び越えは優先する。
再現・切り分けに新機能側の道具が必要なら先に作り、完成後に不具合へ戻る。
役割とレビューは [ROLES](tasks/agents/ROLES.md) を参照。

### HAL 中心期: 装置は HAL の口の実装として作る (ユーザー決定 2026-11-14)

「現在のGUIやCUIはドライバーが直接シェルやGUIに向かって入力している状態ですよね？なるべくHALに向かうようにしていきます」「アーキテクチャの拡張や新規デバイス対応はこのあたりで一度収めてHALを中心にしばらく据えようと思います」「今からでもやりましょう」「HALに乗せるべきデバイスに関しては開発を続けようと思います」(ユーザー 2026-11-14)。

- ドライバがシェル・GUI・アプリへ直接つながる経路を、HAL を通す形に直していく。順は入力 → 音 → 表示 (3D・動画の支援を含む)・ストレージの点検。
- HAL に乗せるべき機能を持つ装置 (GeForce の 3D・動画の支援、PowerPC の USB 入力の arch 依存の解消など) は続ける。**HAL の口を先に設計で決め、装置はその口の実装として作る**。
- HAL と関係の薄い新しい装置の対応と、アーキテクチャの拡張は着手しない。走っている物は区切りまで閉じる。
- 版 (v3・v4) の名前は計画の論点にしない (ユーザーが決める)。
- カーネル層の不具合を先に直す規則は、この期間も変わらない。

### 他のアーキテクチャへ移植するときは、ユーザーランドの libc に必ず newlib を使う (ユーザー決定 2026-11-16)

「他アーキテクチャ移植時に必ずnewlibcを使う様にドキュメント化」(2026-11-16)。発端は「sqlite ですが、newlibc が入ってないのでは？ newlibc に追加した x86 依存のアセンブラも移植して」(PowerPC のユーザーランドが libc なしで組まれていた)。

- ユーザーランドの C ライブラリは、どのアーキテクチャでも newlib nano にする。x86 と同じ版・同じ作り方にそろえる。
  - 版: `tools/ci/build_cross.sh` の NEWLIB_VER と SHA256。
  - configure: `--disable-newlib-supplied-syscalls --enable-newlib-nano-malloc --enable-newlib-nano-formatted-io` (理由は [08_build](08_build.md) の newlib の節)。
  - 改変しない: [THIRD_PARTY](../THIRD_PARTY.md) と `sdk/allocator/nano_inputs.json` の `patches: []`。
- 自前の小さな libc や、アプリごとの代用の関数で置き換えない。足りない関数があれば、newlib のものを使う形に直す。
- OS32 との境目は、x86 と同じ部品をアーキテクチャごとに用意する。
  - syscall の入口: `sdk/crt/syscalls.c` の KAPI の関数表 (`_read`・`_write`・`_sbrk` など)。
  - crt0: `sdk/crt/crt0.asm` に当たる物。
  - メモリの割り当て: `sdk/allocator` の nano の adapter (libc.a の malloc 系を `os32_private_*` に名前替えして `libos32nano.a` にまとめる方式)。
- アーキテクチャ依存のアセンブラ:
  - x86 の newlib には、OS32 が足したアセンブラは無い (無改変)。`lib/kstring_asm.asm` (memcpy・strlen など) と `lib/sqlite3/sqlite_stack.asm` はカーネル用で、newlib には入らない。
  - 移植先でカーネルの文字列操作や SQLite の別スタックが要るときは、カーネルの部品として移植する。PowerPC の `arch/ppc/setjmp.S` も同じ扱い。
- ユーザーランドの SQLite (`build/programs.mk` の単体版) は newlib をリンクする。カーネルの SQLite は newlib を使わない ([CONSTRAINTS](CONSTRAINTS.md) の「カーネルは newlib とリンクされない」)。
- 移植の設計の §1 で、newlib の入れ方 (版・multilib・浮動小数点の旗・syscalls.c と crt0 と allocator の adapter の置き場) を書く。互換の約束は [ARCH_COMPAT_CONTRACT](decisions/ARCH_COMPAT_CONTRACT.md) の AC-LIBC-1。

### 別のアーキテクチャで機能を作るときは、統合して作れるかを先に判断する (ユーザー決定 2026-11-14)

あるアーキテクチャだけで機能を作るとき、または他のアーキテクチャや本線にある役目を別の形で作るときは、設計の §1 で次の 3 点を判断して書く。
1. 同じ役目の機能・計画が、他のアーキテクチャや本線にあるか。票・確定設計・計画書 (例: [HOST_SERVICES_PLAN](tasks/network/HOST_SERVICES_PLAN.md)) を読んで確かめる。
2. あるなら、アーキテクチャに依る部分を HAL (`arch/`・`platform/` の口) に分けて、1 つの実装にするか。分けないなら、その理由を書く。
3. 既存の計画・確定設計の向き (プロトコル・tick・mount・exec など) と合うか。合わない設計にするときは、実装の前にユーザーに確かめる。

レビューの依頼にもこの 3 点を観点として入れる。
3 点の判断には、アーキ間の互換契約 [ARCH_COMPAT_CONTRACT](decisions/ARCH_COMPAT_CONTRACT.md) の該当 ID・能力の差・両アーキで回す共通の試験を添える。契約に無い約束が要るときは、先に契約へ項目を足す。
過去の例:
- PowerPC の LAN の操作口 PLN1 は、Host Services の計画を読まずに別の EtherType で作られ、後で link に統合し直すことになった。
- PowerPC の decrementer を物理 100Hz にした段 (B29) も、本線の物理 1kHz・論理 100Hz の設計と逆向きになった。

## §2. コーディング規約

C の基準は [C1](CONSTRAINTS.md)、検査は `make check-c-dialect`。既存コードの言語機能・型を一括置換しない。
呼出し規約・文字列操作は [CONSTRAINTS.md](CONSTRAINTS.md)、アセンブラは [10_notes.md](10_notes.md) を参照。

### 数値演算は整数を第一選択にする (ユーザー決定)

カーネル本体・部品・ドライバとシステム部品は整数演算を使う。カーネル層はユーザーランドの数学ライブラリに依存せず、必要な道具を `lib/` に置く。ユーザーランドのシステム部品は同じ層の `os32_math` を先に使う。両層で必要になれば共有の置き場への移動を検討する。
浮動小数点が不可欠な場合は、整数では足りない理由と FPU の無い機体での扱いを示し、実装前にユーザーに確認する。アプリは対象外。

### ソースファイルの大きさ (ユーザー決定)

1 機能 1 ファイルを極力保ち、設計段階で関数・状態・共通部分のファイル割当てを表にする。既存の大きいファイルに足す機能も別ファイルに置く。共有の構造体や引数の束を増やすだけの場合は例外とし理由を書く。1 ファイルは 500 行程度を目安にする。
分割は手で写さず、コンパイラまたは ctags で関数範囲を取得し、対応表に従いスクリプトで切り出す。ビルドと関数ごとの機械語を比較し、差の理由を記録し、試験・許可リスト・変異の目印・検査の covers・ビルド登録を追従させる。移動は [SRC_MOVE.md](SRC_MOVE.md)。

### 定数定義の3層管理

| レイヤー | 定義場所 | 例 |
|---------|---------|-----|
| Shared Layer | `os32_kapi_shared.h` | KAPI構造体メンバ名、エラーコード |
| Subsystem Layer | 各サブシステムヘッダ (`vfs.h`, `pc98.h` 等) | `VFS_MAX_PATH`, `TVRAM_COLS` |
| Local Layer | 各モジュール内で定数化 | バッファオフセット等 |

1 つの意味に名前は 1 つ。番地・帯は `include/memmap.h` (OS の配置)・`platform/<機種>/` の番地のヘッダ (PC-98 は `platform_boot_layout.h`) 等の正典を使う。NASM の C と共通の値は `.inc` に置き host 試験で一致を確かめる。kdebug・hwdev のヘッダは [hwdev の契約](design/hwdev/README.md) を参照。

### 試験の期待と製品の設計 (ユーザー決定 2026-11-15)

試験の期待は設計から決め、`CHECK` の `basis` に出所となる設計の ID を書く。
今の振る舞いの記録だけを残す試験は `kind='characterization'` とする。
これは現状の記録であり、設計が振る舞いを変えると決めたら期待を直してよい。
試験の都合で製品を変えず、設計に合わない試験は試験の側を差し替える。
欠陥を固定している試験は `pins` にその振る舞いを変える設計の ID を書き、その実装の段で期待を書き直す。

ホスト模型・QEMU・NP21/W 等の環境で出せない故障の型を `env_limit` に書き、
その試験の合格で保証できる範囲と、実機・別環境での受入を分ける。
CI は全部の検査を変異込みで回す。`full_only` で `make check-fast` と静的 CI から外すかは、試験の目的と環境の限界から決める。
欄の型と配置指定は `docs/TESTS.md` の「CHECK の宣言」を参照。

## §7. リリースとバージョン管理

### バージョン番号の管理

| 定数 | 定義場所 | 用途 |
|------|---------|------|
| `SYS_VERSION` | `include/config.h` | OS全体のバージョン文字列 |
| `KAPI_VERSION` | `sdk/include/os32/os32_kapi_shared.h` | KernelAPI の互換性バージョン |

### リリースの手順 (v2.1 で行った形)

1. 版の区切りの条件をユーザーが決め、[decisions/VERSIONS.md §1](decisions/VERSIONS.md) に書く (版の対応の正典)。
2. `make clean` → `make all` → `make external` → `make check` (全部) が通ることを確かめ、rc を読む。
3. エミュレータと (実機が対象なら) 実機で条件を確かめ、判定を記録する (v2.1 は実機の回の CHECKLIST の末尾)。
4. **リリースノート `docs/RELEASE_vX.md`** (到達点・受け入れの条件・分かっている制限) を書き、
   **`CHANGELOG.md` に 3〜5 行の要約 + リリースノートへのリンク**、INDEX の「API・ガイド」節に載せる。
5. 取り込み先 (`main`) へ合流して Git タグ `vX.Y` を付け、push する。CI (GitHub Actions) の成果物が実機用の配布物になる
   ([08_build.md §8-6](08_build.md))。
6. タグを付けたリリースノートの本文は後から直さない。誤りが分かったら**訂正注記を足す** (版の記録を保つため)。

## §8. 文書の状態行 (語彙の正典)

`docs/tasks/` の票・計画・引き継ぎは先頭 12 行以内に `> 状態: **<語> (YYYY-MM-DD)** — <根拠や残件>` を持つ。`TASK_*.md`・`HANDOVER_*.md`・`CHECKLIST_*.md`・`*PLAN*.md` は必須。他は状態行があれば語彙に従う。古い行は `それまでの状態:` とする。検査は `make check-docs-status`。

<!-- status-vocab:begin -->
| 語 | 意味 |
|---|---|
| 確定 | 設計・契約の内容が確定。実装と受入の状態は対応する票で管理する |
| 計画 | 何をするか・順序を決めた段。設計票はまだ無い |
| 設計中 | 設計票を書いている・レビュー往復中、または設計が承認されて実装を待つ |
| 実装中 | 実装が進んでいる (一部着地を含む) |
| 受入待ち | 実装は着地した。受入条件の一部または全部が未実施 |
| 受入完了・実機確認待ち | エミュレータ (NP21/W) とホストの受入は済み、**実機での確認だけ**が残る (残る項目を行に書く) |
| 受入完了 | 受入条件をすべて満たした (満たさなかった項目は理由を書いて残件へ) |
| 撤回 | 取りやめた |
| 完了記録 | やり切った作業・実施済みの回・快照の記録。以後は更新しない |
| 草案 | 計画以前のアイデアや設計思想。ロードマップ・実装契約ではない |
| 現行 | 運用中の規約・台帳 (体制の文書など)。改訂しながら使い続ける |
<!-- status-vocab:end -->

### 票の 2 つの決まり (2026-11-18)

- **完了の基準を最初に書く。** 進行中の票 (`TASK_*.md` で、状態が 計画・設計中・実装中・受入待ち・受入完了・実機確認待ち) は、先頭 20 行以内に `> 完了の基準: <測れる到達点>` の行を持つ。何が幾つになれば終わりかを、検査の名前や数で書く (例: 「`tools/check_layers.py` の違反が両方の像で 0」)。「段が全部通った」は基準にならない。**受入完了にするのは、この基準を満たした時だけ**。満たさずに残す物は、理由と渡し先 (票か 持越し台帳 (`docs/tasks/DEFERRED_TESTS.md`)) を書く。理由: 機種依存の分離は第 1〜5 段が全部受入完了だったが、共通のソースが機種のヘッダを読む辺は 118 本残っていた (各段の検査が通る事が受入で、到達点が決まっていなかった)。
- **完了した票は現行の棚に置かない。** 状態を 受入完了・完了記録・撤回 にする変更の中で、`tools/move_docs.py` で `docs/archive/` へ移す。その票の設計が今の仕様として引かれている時は、先に `docs/design/` へ要約を移す (決まりは [POLICY_ARCHIVE](POLICY_ARCHIVE.md)、手順はスキル `.claude/skills/os32-archive`)。
- 検査は `make check-docs-status`。例外は `tools/docs_status_exceptions.json` に書く: `no_criteria` (この決まりより前からある、基準の行が無い票。増やさない) と `done_in_place` (完了しても現行の棚に残す票と、その理由)。例外が要らなくなった票は一覧から外す (外さないと検査が落ちる)。

## §9. 文書の書き方

正典は [INDEX.md](INDEX.md) の表で決め、古い記述を正典で直す。他の文書は要約とリンクにする。
ユーザー決定 (2026-11-03): 「無効になった記述は注記でなく削除」「削除前の事実はgitで残る」。失効した本文は削除するか現行の内容に書き換え、取消線や訂正注記で残さない。

仕様には現行の仕様、規約には現行の規則、票には設計・契約・受入条件、台帳には未完了、入口には案内を置く。

**2a. 設計書は 1 機能 1 ファイルでソースと同じ構造にする (ユーザー決定)。** `docs/design/<ソースと同じパス>.md` に置く。共通の取り決めは共通部分のソースの設計書に置き、他から参照する。既存の `docs/decisions/` の設計は移すまで現行。

現行・計画・過去を区別する。完了・撤回した票や記録は `tools/move_docs.py` で移す。
平易な日本語で 1 文に 1 つ書き、コードの根拠は**パスと関数・マクロ・節の名前**で指し、文書間は節やリンクを使う。
**このリポジトリのソースを `パス:行番号` で指さない (ユーザー決定 2026-11-17)。** ソースが動くと行番号は黙ってずれ、読む側は気付けない。版を固定した外部の手本 (nouveau のコミット、BSD の固定版など) の `file:line` は書いてよい ([HW3])。設計の下書きとレビュー (`~/os32-tmp/run/` の作業中の文書) は対象外で、リポジトリへ写す時に名前の参照へ直す。`make check-docs-line-refs` が見つけたら落ちる (基準 `tools/doc_line_refs_baseline.json` は空)。ファイル名だけの形 (`kernel.c:521`) と続きの行番号 (`:98`・`同:98`) も、このリポジトリのソースには書かない (外部の同名のファイルと区別できないので、検査は数えない)。推測・未確認は [推]・[未]、日付は絶対日付で書く。

## §10. 設計の前提 (ユーザー決定の一覧)

設計・レビュー・依頼の前提になる決定を、今有効な形で 1 か所に並べる。依頼文とレビューの依頼には、関係する行を前提として書く。
決定が変わったら、行を書き換える (経緯は git)。PM の個人の memory には写さない — ここがほかのエージェントも読む正典 (書き方と memory の畳み直しはスキル `.claude/skills/os32-decision-fold`)。

| 前提 | 中身 | 設計・レビューでの使い方 | 決定 |
|---|---|---|---|
| 目的と上限 | PC-9801/9821 の実用性を示す。386 で成り立ち、Pentium 100MHz・32MB で「超快適」。設計の想定の上限は Pen4 1.2GHz・2GB まで。アプリ本体は 1MB で足りる | この枠を超える性能・機能は提案しない。足りない状況を想定した拡張をしない | 2026-09-04、2026-11-12 |
| 最終目標 | Win32 API と DirectX (Windows 2000 までのアプリ)。スレッドは擬似的に提供する。GPL/LGPL の互換層はユーザーランド ([L1]、[ROADMAP](ROADMAP.md)) | KAPI・exec・メモリの設計で、擬似スレッドと Win32 の下回りを塞がない。まだ着手しない | 2026-10-31 |
| シングルタスク・協調切替 | 同時に走るのは 1 本。切替はアプリ自身の park・yield・終了の時だけ | 並行実行・飢餓・番号の一周・悪意のある相手を前提にした仕組みを積まない。レビューの指摘は「協調の前提で起こり、実害 (破損・停止・退行・観測不能) があるか」で分け、PM が次の依頼へ流す前に濾す | 2026-10-09、2026-11-07 |
