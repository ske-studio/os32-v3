# OS32 開発ポリシー

OS32カーネルおよび外部プログラム開発における公式ポリシー。
コーディング規約、ビルド手順、バージョン管理、テスト、リリースに関する統一ルールを定める。

技術仕様・アーキテクチャの詳細は [DEVELOPMENT.md](DEVELOPMENT.md) を参照。
デバッグに関するポリシーは [POLICY_DEBUG.md](POLICY_DEBUG.md) を参照。

---

## §1. 基本方針

### 設計哲学

- **ホビープロジェクトとしての品質優先**: デッドラインよりも設計品質・コードの可読性を重視する。
- **学習と記録**: 過去のバグや設計判断は必ずドキュメントに残し、同じ問題を二度踏まないようにする。
- **段階的な進化**: 動作する最小単位を積み上げていく。大規模な書き直しよりも、小さな改善の積み重ねを好む。

### カーネル層の不具合は新機能より優先する

**カーネル層に不具合が分かっているあいだは、新機能の実装より先にそれを直す。**
ここで言うカーネル層とは、カーネル本体・VFS と各 FS ドライバ・exec とページング・
KernelAPI・共有ライブラリの読み込みを指す。アプリ 1 本の不具合はこれに当たらない。

理由は、**下の層の不具合が上の層の作業をすべて汚染する**こと。

- 誤った土台の上で作った新機能は、正しさを確かめたことにならない。試験が通っても、
  それは不具合の挙動に合わせて通っただけかもしれない。
- 不具合の発現が確率的・条件依存だと、**新機能の側の障害として何度も調査し直す**ことになる。
  2026-09-05 から 09-15 まで 10 日間生き延びた共有ライブラリの `.bss` 未初期化は、
  N4 (Host Services) の作業中に「N4 の退行」として切り分けを繰り返させた。
- 修正が後になるほど、その上に積んだコードの前提を作り直す範囲が広がる。

**適用の仕方**

- 分かった時点で票に起こし、**着手中の新機能より前に並べる**。着手済みのものは、
  切りの良いところ (試験が緑で着地できる状態) まで進めてから切り替えてよい。
  緑にできないなら、その場で止めて先に直す。
- **直せないもの・直さないと決めたものは、未解消として明記して残す。**
  黙って先へ進まない。範囲外と判断したなら、その理由も書く。
- 発現条件が稀でも、**影響がデータ破壊・型の取り違え・権限の飛び越えなら優先度は下がらない**。
  「滅多に起きない」は直さない理由にならない。
- 新機能の実装中に見つけたものも同じ。「ついでに直す」か「票にして先に直す」かを選び、
  **見なかったことにしない**。

**例外**: その不具合の再現・切り分けに新機能側の道具が要る場合は、道具を先に作ってよい。
ただし道具を作ったら不具合に戻る。道具の完成をもって不具合を後回しにしない。

### AI との協調開発

- AI エージェントで開発する。役割 (PM・コーダー・レビュアー・テスター) と起動・規約の正典は
  [tasks/agents/ROLES.md](tasks/agents/ROLES.md) §0 (現行の体制)。
- 生成したコードは独立したレビュアー (ROLES §5) が読み、ハードウェア制約・ABI・資源回収への違反を確かめる。
  決裁と実機の物理操作はユーザーが行う。
- AI 向けの指示書 (`CLAUDE.md` 等) はバージョン管理し、ルール変更時は指示書も同時に更新する (Docs as Code)。

## §2. コーディング規約

### C11 (GNU11) を内部実装の基準とする ([C1])

本体・ブート・userland・SDK の実装は `-std=gnu11` (`build/config.mk` の `C_STD`)。
**公開 SDK ヘッダ** (`sdk/include/os32/*.h`。`sdk/include/os32/os32_kapi_shared.h` を含む) は gnu89 と gnu11 の
両方から読めること (apps / game / `sdk/example/hello` は gnu89 のまま)。**SQLite 系**
(`lib/sqlite3/` と userland の SQLite 単体) は `C_STD_SQLITE` (gnu89)。旗の実際の効き方は
`make check-c-dialect` が確かめる。採用範囲の経緯は TASK_C11_MIGRATION (アーカイブ: `docs/archive/v3/TASK_C11_MIGRATION.md`) §4。

| 機能 | 内部実装での扱い | 既存コード |
|--------|-----|-----|
| ブロック途中の宣言、`for` 内宣言 | 許可 | 移動しない (スコープ・初期化時点が変わる) |
| `//` コメント | 許可 (公開 SDK ヘッダでは禁止) | `/* */` を書き換えない |
| `_Static_assert` | `STATIC_ASSERT(式, 識別子)` (`include/types.h`) 経由で使う | 呼び出しはそのまま |
| `<stdbool.h>` | **純粋な真偽値だけ**。エラー値・ビット集合・ABI の型には使わない | `int` を一括置換しない |
| `<stdint.h>` | 外部形式・新規の独立パーサー・移植コードで可。OS32 の API と共有構造体は `u8/u16/u32/i32` のまま、同じ API 内で型名を混在させない | `u32` を置換しない。SDK・KAPI・Rust FFI の型は変えない |
| 指示付き初期化子 | 内部のテーブルに可 | 一括変換しない (暗黙のゼロ初期化・条件付きメンバーの意味を保つ) |
| 複合リテラル | 寿命が明確な場合に可 | 代入列から一括変換しない |
| 暗黙の関数宣言・暗黙 int・VLA | **禁止** (`C_DIALECT_ERRORS` でエラー) | — |
| 旧式 (K&R) の関数定義 | 自作コードで禁止。vendor (`lib/zlib/` 等) は例外 | vendor は触らない |
| 匿名構造体・共用体、`restrict`、`_Atomic`、TLS、`<threads.h>` | T0 では新規導入しない (別設計) | — |
| 引数なしの `f()` | C11 でも `f(void)` と同義ではない。新規は `f(void)` と書く | 機械置換しない |

### 呼び出し規約

- **カーネル/外部プログラム**: System V i386 ABI (`-m32`)
- **KernelAPI**: 外部公開関数は必ず `kapi/` に `__cdecl` ラッパーを作成し、スタック渡しでブリッジする

### 文字列操作

カーネル内での文字列操作は `lib/kstring.h` の関数を優先して使用すること。

| 関数 | 用途 |
|------|------|
| `kstrncpy` | 安全な文字列コピー |
| `kstrncat` | バッファサイズを考慮した安全な文字列連結 |
| `kstrlen` | 文字列長取得 |
| `kstrcmp` / `kstrncmp` | 文字列比較 |

### アセンブラ

- NASM (`-f elf32` / ブートセクタは `-f bin`)。ローカルラベル `.loop:` は使ってよい
  (wasm 時代の制約は無い: [10_notes §10-11](10_notes.md))
- `boot_fat.asm` は `.8086`: 即値シフト不可 (`mov cl, N` / `shr ax, cl`)。IPL (`boot_hdd.asm`) の INT 1Bh は
  16 回 (上限の理由は未確認、[10_notes §10-2](10_notes.md))。
- FD の PM 遷移は `boot/loader_fat_new.asm` の `.load_done` → `pm_entry32`。
  `org 8000h` の同じバイナリに GDT と 16/32bit コードを置く。
  この遷移は分割禁止 (現行でも守る。旧版の理由「アドレス重なり」は現行実装では未確認)。

### 数値演算は整数を第一選択にする (ユーザー決定 2026-10-20)

- **カーネルレベルの機能は整数演算で実装する。** 対象は、カーネル本体・カーネル部品 (`.mod`)・ドライバと、
  カーネルや常駐 shell が呼ぶシステムの部品 (字形のラスタなど) である。
  使う道具は依存の向きを守って層ごとに選ぶ。
  - カーネル層 (カーネル本体・`.mod`・ドライバ): ユーザーランドのライブラリ (`os32_math`・libos32math) に依存しない。
    要る整数の道具 (固定小数点の掛け算・整数平方根など) はカーネル側の `lib/` に必要な分だけ置く。
  - ユーザーランドのシステムの部品 (font crate・gshell・libos32gui など): 同じ層の `userland/rust/os32_math`
    (C 版 libos32math) を先に使う。
  - 両方が同じ道具を要るようになったら、層に属さない共有の置き場へ移すかを、そのときに決める (重複させたままにしない)。
- **どうしても浮動小数点演算が要るときは、実装する前にユーザーに確認する。** 依頼・設計票には、
  なぜ整数では足りないのかと、FPU の無い機体での扱いを書いて示す。
- 理由: FPU の無い機体 (386・486SX) でも動くこと、x87 の状態の退避と復元 (FNSAVE/FRSTOR と guard) の
  費用と複雑さを持ち込まないこと。
- 既にある例外: 字形のラスタ (T7b-a2 の x87 guard) は整数化して x87 の保存・復元を撤去した
  (TASK_FONTPERF F5・F6、[T7 票 §4 の後](tasks/v3/TASK_T7_AND_FOLLOWUPS.md))。SQLite の double は台帳 NOFPU-1 で扱う。
  アプリ (ゲームなど) の浮動小数点は対象外。

### ソースファイルの大きさ (ユーザー決定 2026-10-28)

- **1 ファイルは 500 行程度までを目安にする**。新しく書く・大きく触るファイルが超えるなら、意味の切れ目 (状態と終端・バスのアクセス・計画の組立て・ログの送信など) で分ける。
- 理由: 実装者のモデルは**ソースを読むだけで文脈の窓を使い切る**。1,000 行を超えるファイルに触る段は terra では処理できず、sol か astra に出す (割当ては docs/tasks/agents/ROLES.md §0)。GeForce 4c で terra が止まった段は、どれも recover.c (2,200 行超) に触っていた。
- **大きいソースの分割は GeForce の実装 (4c の実機の回と本番の画面ドライバ) の後に行う** (ユーザー指示 2026-10-28)。振る舞いを変えない機械的な分割にし、分ける前後で関数ごとの機械語が同じことを objdump で確かめる。冗長な所 (同じ形の処理の繰り返し・使われない定義) はその機会に整える (段の分解は票 TASK_REDUNDANCY、docs/tasks/v3/)。2026-10-28 の時点で 1,000 行を超える .c: userland/system/hsync.c 3,039、exec/exec.c 2,534、kdebug/kselftest.c 2,495、kdebug/recover.c 2,374、mm/paging.c 1,696、drivers/block/fdc.c 1,345、kernel/v86/v86_bios.c 1,277、gfx/gfx_core.c 1,251、fs/ext2/ext2_dir.c 1,228、drivers/video/pc98/backend_pegc.c 1,215、drivers/block/loop_dev.c 1,177、kernel/ime/ime.c 1,159、exec/appslot.c 1,136、mm/pgalloc.c 1,098、drivers/net/ne2000/ne2000.c 1,057。分割の段は 1 ファイルずつ (sol か astra)、カーネル層 (paging・pgalloc・exec) は退行の危険が大きいので、ゲスト受入と組にする。
- **ファイルの置き場を変える (付け替え)**: 手順の正典は [SRC_MOVE.md](SRC_MOVE.md) (対応表 JSON と道具 `tools/move_files.py`、成果物のバイト比較、2026-10-30)。
- **分割の手段 (ユーザー指示 2026-10-29「肥大化したコードの分割手段としてドキュメント化」)**: 手で写さず、道具で切る。
  1. **関数の範囲はコンパイラに出させる** — `clang -Xclang -ast-dump=json` (実際のビルドと同じ `-D`・`-I` を渡す) で、関数ごとの開始・終了行を得る。マクロや条件コンパイルも実ビルドの解釈で扱える。ctags (`--fields=+ne`) でも可。clang-move (C++ のクラス向け)・coccinelle (意味の書換え向け) は分割には採らない。
  2. **人が決めるのは対応表だけ** — 「関数 (と static の変数・型・マクロ) → 移す先のファイル」。設計票や依頼に表として載せる。
  3. **切り出しは小さなスクリプト** — 対応表に従って行の範囲を移す。関数の直前のコメントは直前の空行まで含める。static のまま他のファイルから呼ばれるものは、共通の内部ヘッダに宣言を移す (公開はしない)。
  4. **確かめ** — コンパイルが通ることと、分ける前後で関数ごとの機械語が同じこと (objdump で比べる。static がファイルを跨いでインライン化が変わる関数は、差を一覧にして理由を書く)。
  5. **追従** — 実ソースを組む・文字で読む試験 (`grep -rln <元のファイル名> tools/tests`)、`tools/check_p2v_allow.txt` (file:function)、変異の目印 (一意に当たるか)、`tools/check_map.d` の対応表、ビルドの登録 (build/*.mk)。
  対応表と確かめの結果を残せば、レビューは中身の差分ではなく「対応表と機械語の一致」を見ればよい。

### 定数定義の3層管理

| レイヤー | 定義場所 | 例 |
|---------|---------|-----|
| Shared Layer | `os32_kapi_shared.h` | KAPI構造体メンバ名、エラーコード |
| Subsystem Layer | 各サブシステムヘッダ (`vfs.h`, `pc98.h` 等) | `VFS_MAX_PATH`, `TVRAM_COLS` |
| Local Layer | 各モジュール内で定数化 | バッファオフセット等 (ハードコードの `500` 等は禁止) |

- **1 つの意味に名前は 1 つ**。番地・帯は `include/memmap.h`、PC-98 の I/O と BIOS ワークは `include/pc98.h`、PCI は `drivers/pci/pci_decode.h`、Ethernet は `include/net_eth.h`、u32 の上限などの基本の値は `include/types.h`、kprintf のログ行の属性 `KLOG_ATTR` は `os32_kapi_shared.h`、GeForce の回復処理は `kdebug/recover.h` が正典。別の名前で同じ値を定義せず、正典の名前を使う (2026-10-25、票 TASK_MAGIC_NUM)。
- NASM の `.asm` は C のヘッダを読めないので、`arch/x86/kernel/cpu_flags.inc` に同じ値を置き、host 試験 (`check-double-fault-host`) で C 側との一致を固定する。GAS の `.S` は cpp を通るので `include/cpu.h` を読む (C の部分は `#ifndef __ASSEMBLER__`)。
- kdebug・hwdev が読むヘッダには **enum を足さず `#define` で書く** — `tools/gen_hwdev_contract.py` が DWARF の列挙子を契約に数えるので、enum を足すと HWDEV の契約の CRC が変わる。

## §3. ハードウェア制約

**規則と理由の正典は [CONSTRAINTS.md](CONSTRAINTS.md)** — [HW1] (EGC / GRCG / GDC の描画コマンドを使わず、HAL 経由で描画)、[HW2] (DMA 64KB 境界)、[HW3] (新しいハードウェアは BSD 系など参照しやすい既存の実装と資料を先に見る) を参照。ここには実装上の補足だけを置く。

- `disk.c` の DMA バッファは BSS 配置により 64KB 境界またぎを回避している ([HW2])。
- [HW3] の参照先の例: FreeBSD の `sys/dev/<装置>/` (BSD-2-Clause)、NetBSD の `sys/dev/ic/`・`sys/dev/pci/`。GeForce (NV4x) の手本は nouveau (MIT、`~/os32-tmp/refs/geforce6200/nouveau/` の `nvkm/subdev/devinit/`・`drivers/gpu/drm/nouveau/dispnv04/`) と envytools の rnndb (MIT)。メーカーの資料は `docs/hw/` のミラー (著作権物、コミットしない)。取ってきたソースは `~/os32-tmp/ref/<OS>-<版>/` に置き、リポジトリには入れない。

## §4. ビルドとデプロイ

### Makefile 構成

Makefile は `build/` ディレクトリに分割された `.mk` ファイルで構成されている:

| ファイル | 内容 |
|---------|------|
| `Makefile` | ルート (include + 主要ターゲット) |
| `build/config.mk` | ツールチェーン、フラグ、パス定義 |
| `build/kernel.mk` | カーネル + SQLite ビルドルール |
| `build/libs.mk` | 全ユーザー空間ライブラリ (テンプレートマクロ) |
| `build/programs.mk` | 外部プログラムビルドルール |
| `build/boot.mk` | ブートローダー |
| `build/deploy.mk` | デプロイターゲット |
| `build/image.mk` | D88/ISO イメージ生成 |
| `build/app.conf` | OS32Xヘッダ設定 (APIバージョン/ヒープサイズ) |

### 基本ルール

**ターゲット一覧の正典は [08_build.md](08_build.md#ビルドターゲット) にある。**
ここには方針だけを書く。一覧を二重に持つと必ず片方が腐る (実際 `dp-` の
廃止時に 3 箇所が取り残された)。

```bash
make all       # 全体
make clean     # KernelAPI 構造体を変えたら clean → all が必須
```

> ⚠️ **重要**: `os32_kapi_shared.h` / `os32_kapi_generated.h` / `kapi.json` を変更した場合は、必ず `make clean` → `make all` を実行すること。古い `syscalls.o` が残ると ABI 不整合で `malloc` が全て ENOMEM で失敗する。

### KernelAPI 拡張手順

[KAPI_SPEC.md §3-1](KAPI_SPEC.md) が正典 (末尾追記 / 版番号 2 箇所 / 再生成 /
`make clean` → `make all`)。ここには複製しない。

### 新規プログラム追加手順

1. `build/programs.mk` にソース定義とリンクルールを追加（テンプレートマクロ `DEFINE_TEST` / `DEFINE_GFX_APP` を活用）
2. `build/app.conf` に APIバージョンとヒープサイズを追加
3. 自層の `deploy.yaml` (`userland/` / `apps/` / `game/`) にデプロイ先パスを追加

### デプロイ方式

3 経路の使い分けもツールの詳細も [08_build.md §8-4](08_build.md#配備3経路) が正典。要点だけ:

| 目的 | コマンド | 備考 |
|---|---|---|
| ユーザランド変更 | `make deploy` (HostDrv) / `make hotdeploy FILE=...` | 再起動不要。ただし PATH は NHD の `/usr/bin` を優先するので、これだけでは検証にならない ([V1]) |
| カーネル / `/sys` 変更 | `make deploy-kernel` | HostDrv 同期 + NHD 全体書き込み。**NP21/W を止めてから** ([D1])、起動後に `ver` / kselftest で到達確認 |
| ローダ変更 | `make deploy-boot` | NHD ブート領域 (LBA 2〜17) |

(2026-09-05 訂正: 以前ここにあった「deploy-kernel = ブート領域書き込み」「NHD フル
デプロイはレガシー」は誤り。NHD 全体書き込みが現行の標準経路。)

### デプロイパスの整合性

`deploy.yaml` のゲストパスと `config.h` の `SYS_*` 定数は**必ず一致**させること。

| ビルド成果物 | ゲストパス | 設定元 |
|-------------|-----------|--------|
| `userland/shell.bin` | `/sys/shell.bin` | `config.h: SYS_SHELL_BIN` |
| `build/out/vmkernel.lz4` | `/boot/vmkernel.lz4` | `deploy.yaml: filesystem.files` |
| `boot/loader_hdd.bin` | (NHDブート領域 LBA 2-17) | `deploy.yaml: boot.loader` |
| `build/out/unicode.bin` | `/sys/unicode.bin` | `config.h: SYS_UNICODE_BIN` |

不一致はサイレントに古いバイナリが使われ続ける致命的な問題を引き起こす。

> **配備後は実行バイナリへの反映を確かめること ([V1])。** PATH は NHD の `/usr/bin` を優先するため、
> HostDrv だけ更新しても古いバイナリで合格に見える。配備経路は
> [08_build.md §8-4](08_build.md#配備3経路)、反映確認は [POLICY_DEBUG.md §2](POLICY_DEBUG.md) に従う。

### コマンド実行ルール (WSL環境)

- **`&&` でのコマンド連結は禁止**。必ず1コマンドずつ逐次実行すること。
- WSL から `/mnt/c/` (Windows側ファイルシステム) へのアクセスは遅延が大きいため、`&&` で連結するとタイムアウトの原因になる。

## §5. Git コミットポリシー

> 本セクションは旧 `GIT_POLICY.md` の内容を統合したものです (同ファイルは削除済み)。

### マイクロコミットの徹底

OS・低レイヤー開発においては、後からの `git bisect` や原因調査が容易であることが命綱となる。

- **禁止事項**: AI と一緒に大量のコードをリファクタリングして、テストや複数機能が混ざったまま「一括コミット」すること。
- **推奨単位**: 「KAPIの関数を1つ追加した」「ページングの不具合を1つ修正した」「1つのファイルをリファクタリングした」という論理的な最小単位で必ず `git commit` を行う。
- **背景**: PC-98 特有の挙動不良（画面のドット異常、謎のハングアップなど）が発生した際に、どの変更で壊れたのかを追跡できるようにするため。

### Conventional Commits

コミットメッセージは以下のプレフィックスを使用する:

| プレフィックス | 用途 |
|--------------|------|
| `feat:` | 新機能の追加 |
| `fix:` | バグ修正 |
| `refactor:` | 動作を変えずにコードの構造を改善 |
| `docs:` | ドキュメントの修正 |
| `test:` | 追加テスト |

**メッセージ例:**
```
refactor(exec): 外部プログラムローダーのハードコードを排除

VFSの仕様に基づき、固定のバッファサイズ(0x4000など)を利用していた
一時的な実装を削除し、動的割り当てとOS32_MAX_PATHを利用するように修正。
```

### 多段の検証 (ベアメタル特有)

ホストで回せるものは `make check` (ホスト TDD と変異試験、3 段は [08_build.md §8-4](08_build.md)) と CI
(GitHub Actions の本体ビルド、§8-6) に載せる。それでも**ゲストの挙動はエミュレータ (NP21/W) と実機でしか確かめられない**。

- ビルドと `make check` が通ったことを合格としない ([V4])。ゲストで要る確認はスキル `os32-build-verify` が選ぶ。
- NP21/W が模擬しないもの (シリアルの速度、2.4576MHz 系のクロック、FDC のシーク時間、画面モードの ROM の手順など) は
  実機で確かめる ([POLICY_DEBUG.md §4-49〜§4-62](POLICY_DEBUG.md))。
- レビュー (独立レビュアー、ROLES §5) は「ハードウェア制約 (EGC 使用禁止、BDA の上書きなど) に違反していないか」を必ず観点に入れる。

### AI との協調時の Git 操作 (エージェントの実行環境による)

これは**エージェントの実行環境から来る制約**であって、リポジトリの規則ではない。
リポジトリを `/mnt/c/` 側に置いて WSL から Windows ファイルシステムへ Git を叩く構成では、
`git add` / `git commit` / `git push` の I/O 遅延が大きく、エージェントのターミナルツールが
ハングまたはタイムアウトする。同じ理由で `&&` によるコマンド連結も避ける。

- **その構成のエージェント** は Git の変更操作を自分で実行せず、
  `git add` / `git commit` を `bash` コードブロックで提示してユーザーに実行してもらう
  (読み取りの `git status` / `git diff` は対象外)。以前この構成で動いていた Hermes は撤収済み
  (最上位プロンプトは `SOUL.md` (非公開・リポジトリ外、`.gitignore`) §3.2、効力なし)。
- **Linux ファイルシステム側 (`/home/...`) で動くエージェント**には当てはまらない。
  そちらは通常どおり実行してよく、許可の範囲は各エージェントの設定
  (Claude Code なら `.claude/settings.json` / `settings.local.json`) が決める。

いずれの場合も、コミットの単位とメッセージ形式は上記のルールに従う。

## §6. テストと品質保証

### 基本的な検証フロー

ビルドと配備は [08_build.md §8-4](08_build.md#配備3経路)、バイナリの反映確認は
[POLICY_DEBUG.md §2](POLICY_DEBUG.md) に従う。反映を確かめてから変更対象の機能を試験し、
期待した動作と既存機能への影響を確認する。未実行の試験は合格に含めず、報告で明示する ([V4])。
実機での更新・検証手順は [08_build.md §8-6](08_build.md) を参照する。
配備と検証の自動化は `os32-cycle`、ホットデプロイの設計と制限は `docs/archive/hotdeploy/DESIGN.md` を参照する。

### シリアルコンソール経由のリモートテスト

- NP21/W 内蔵のデバッグ HTTP API を通じてコマンドを送信し、結果を自動取得できる。
- `curl -X POST http://127.0.0.1:8025/api/cmd --data-binary "コマンド"` で実行可能。
- 画面テキストの取得: `curl -s http://127.0.0.1:8025/api/tvram`
- スクリーンショットの取得: `curl -s http://127.0.0.1:8025/api/screenshot`

### 実機の試験の作り (2026-10-29 の反省会、ユーザー決定)

GeForce 4c の実機の回 (読み返せないビットで 3 回止まり、4 回目で映像) から。詳細と段の分け方の案は票 TASK_GF_STAGES (docs/tasks/realhw/)。

- 実機の初回は**記録だけ**で流し、食い違いを 1 回で洗い出してから照合を締める。必須の確かめは設計で列挙したものだけ。
- 外す・変えるものは**実行時に渡す** (引数かファイル)。ビルドの入れ直しを避ける。
- やり直しの単位を小さく: 試験は**段ごとの小さなバイナリ + 共通部分 (読み書き・記録・戻す処理) の include**。試験のソースも段ごとに分け、全体の hash・行数を 1 か所で固定しない (1 つの段の直しが無関係の試験まで落とさない)。
- 道具の判定の誤りが**戻す操作を止めない**。台本の判定は道具の側に持たせ、シェルの grep で判定しない。

### テスト対象の優先度

| 優先度 | 対象 | 理由 |
|--------|------|------|
| 最高 | ブートシーケンス | 失敗するとシステム全体が起動しない |
| 高 | KernelAPI 変更 | ABI 不整合が全プログラムに波及する |
| 高 | ファイルシステム | データ破壊のリスクがある |
| 中 | シェルコマンド | ユーザー操作に直結する |
| 低 | ドキュメント変更 | 動作への影響なし |

## §7. リリースとバージョン管理

### バージョン番号の管理

| 定数 | 定義場所 | 用途 |
|------|---------|------|
| `SYS_VERSION` | `include/config.h` | OS全体のバージョン文字列 |
| `KAPI_VERSION` | `sdk/include/os32/os32_kapi_shared.h` | KernelAPI の互換性バージョン |

### リリースの手順 (v2.1 で行った形)

1. 版の区切りの条件をユーザーが決め、[decisions/VERSIONS.md §1](decisions/VERSIONS.md) に書く (版の対応の正典)。
2. `make clean` → `make all` → `make external` → `make check` (全部) が通ることを確かめ、rc を読む。
3. エミュレータと (実機が対象なら) 実機で条件を確かめ、判定を記録する (v2.1 は実機の回の CHECKLIST の末尾)。
4. **リリースノート `docs/RELEASE_vX.md`** (到達点・受け入れの条件・分かっている制限) を書き、
   **`CHANGELOG.md` に 3〜5 行の要約 + リリースノートへのリンク**、INDEX の「API・ガイド」節に載せる。
5. 取り込み先 (`main`) へ合流して Git タグ `vX.Y` を付け、push する。CI (GitHub Actions) の成果物が実機用の配布物になる
   ([08_build.md §8-6](08_build.md))。
6. タグを付けたリリースノートの本文は後から直さない。誤りが分かったら**訂正注記を足す** (版の記録を保つため)。

## §8. 文書の状態行 (語彙の正典)

`docs/tasks/` の票・計画・引き継ぎは、冒頭 (先頭 12 行以内) に **状態行** を 1 本持つ。
書き方は `> 状態: **<語> (YYYY-MM-DD)** — <根拠や残件>` (前に `> 発行: … / ` が付いてもよい)。
**語は下の表のどれかで始める**。`TASK_*.md`・`HANDOVER_*.md`・`CHECKLIST_*.md`・`*PLAN*.md` は状態行が必須、
それ以外は状態行があれば語彙を守る。状態が変わったら行を書き直し、古い行を残すなら `それまでの状態:` と書く
(検査は `状態:` の直前が行頭・`> `・`/ ` のときだけを状態行とみなす)。

検査は `make check-docs-status` (`tools/check_docs_status.py`、`make check` の列に入っている)。検査器の試験は `make check-docs-status-host` (記録 [docs_status_tdd.md](../tools/tests/docs_status_tdd.md))。
語彙はこの表から読むので、**語を足す・消すときはこの表だけを直す**。`docs/archive/` は検査しない (移したあと本文を書き換えない)。

<!-- status-vocab:begin -->
| 語 | 意味 |
|---|---|
| 確定 | 設計・契約の内容が確定。実装と受入の状態は対応する票で管理する |
| 計画 | 何をするか・順序を決めた段。設計票はまだ無い |
| 設計中 | 設計票を書いている・レビュー往復中、または設計が承認されて実装を待つ |
| 実装中 | 実装が進んでいる (一部着地を含む) |
| 受入待ち | 実装は着地した。受入条件の一部または全部が未実施 |
| 受入完了・実機確認待ち | エミュレータ (NP21/W) とホストの受入は済み、**実機での確認だけ**が残る (残る項目を行に書く) |
| 受入完了 | 受入条件をすべて満たした (満たさなかった項目は理由を書いて残件へ) |
| 撤回 | 取りやめた |
| 完了記録 | やり切った作業・実施済みの回・快照の記録。以後は更新しない |
| 草案 | 計画以前のアイデアや設計思想。ロードマップ・実装契約ではない |
| 現行 | 運用中の規約・台帳 (体制の文書など)。改訂しながら使い続ける |
<!-- status-vocab:end -->

「受入完了・実機確認待ち」は 2026-09-29 に足した (v2.1 の棚卸しで、エミュレータでは受け入れたが実機の確認が残る票が
4 本あり、「受入完了」とも「受入待ち」とも書けなかったため)。

## §9. 文書の書き方

散らばっていた決まり (INDEX の正典表・§8・CLAUDE.md・ROLES §0・反省会 2026-10-14 の冗長化) を 1 か所に集めたもの。
人も AI も間違えるので、細かい規則を足すより、迷ったときに戻る目安として使う。正典表が節の役割を指定していれば、そちらを優先する。

**1. 正典は 1 か所。** 事実ごとの更新先は [INDEX.md](INDEX.md) 冒頭の表が決める。他の文書は要約とリンクにし、
番地・数値・手順・進捗を独立に写さない (写すと必ず食い違う。2026-09-05 の診断で 6 件)。正典表が認めた要約・照合つきの写し (README・INDEX の KAPI 版番号など) は除く。

**2. 文書の種類ごとに置くもの。**

| 種類 | 例 | 置くもの | 置かないもの |
|---|---|---|---|
| 仕様 | `01_`〜`10_`、KAPI_SPEC | 今の仕様。誤読を防ぐのに要る短い背景 (旧い値を今に当てはめない注意など) | 作業の日誌 (いつ何をしたか)。経緯は HISTORY・CASE_STUDIES・archive・POLICY_DEBUG §4 |
| 規約 | POLICY_*、CONSTRAINTS、ROLES | 今の規則と、短い理由 | 長い経緯 (落とし穴の記録は POLICY_DEBUG §4 が正典) |
| 票 | `docs/tasks/` | 設計の本文・契約・受入条件。作業の記録は 1 段 10 行以内 (決定・未確認・持越し・証拠の所在) | 実行のログ・出力の貼り付け。受入の結果は合否 1 語 + 証拠のパス (ROLES §0「記録」)。版の連鎖参照 (確定版は本文を持つ) |
| 台帳 | DEFERRED_TESTS | 未完了の行だけ | 終わった行 (閉鎖台帳へ移す) |
| 入口 | CLAUDE.md・AGENTS.md・README・INDEX・HANDOVER | 指示・参照・案内用の要約 | 技術の本文 (HANDOVER は 50 行以内・上書き) |

**3. 現行・計画・過去を分ける。** 文書の冒頭か状態行で、今の仕様か、計画か、ある日のスナップショットかが分かるようにする (§8、INDEX)。
仕様の中の計画の値を、今の値と取り違えさせない。

**4. 終わった文書は archive へ。** 完了・撤回した票や記録は `docs/archive/` へ移し (`tools/move_docs.py`)、移したあと本文を書き換えない。

**5. 書き方。** 平易な日本語で、1 文に 1 つのことを書く。コードを根拠にするときは `file:line`、文書どうしは節やリンクでよい。
推測や未確認のことには [推] [未] を付ける (確かなことに毎回 [確] は要らない)。日付は絶対日付 (YYYY-MM-DD)。
同じ文書の中で同じことを独立に書き直さない (案内用の要約と詳細の節は可)。

**6. 古い記述に気づいたら、その場で正典を直す。** 別の所に正しいことを書き足して、古い記述を残さない。
