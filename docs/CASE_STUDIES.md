## 1. 資料どうしが食い違ったときの決着 — 別の量との整合で決める

シリアルのクロックで、同じ資料集の 2 か所が逆のことを書いていた (8MHz 系と 5/10MHz 系のどちらが 1.9968MHz か)。PC-9800 Bible と
非公式の調査資料 (UNDOCUMENTED) の間でも、キーボード 8251 のハンドシェイク線の極性で「リトライ 1: 有効」という機能名の書き方と「信号レベル (HIGH / LOW)」の書き方が
食い違っていた。実機でキーボードが一切効かなかった件では、機能名のほうの解釈で書いていたコマンド語を**原因候補 (本命)** とし、信号レベルの記述に合わせた —
沈黙する機構そのものは資料では証明できず、実機での打鍵は未確認のまま、観測の口を同時に入れた。どちらが新しいか、どちらが詳しいかでは決められなかった。

**学んだこと**: 表が食い違ったら、**同じ資料の別の量との整合** (ここでは「4 分周すると一致する」という分周関係) で決める。極性は**信号レベルで書いてある記述**を採り、
機能名 (「有効」「リトライ」) の記述は根拠にしない。別実装 (FreeBSD、エミュレータのソース) で裏を取る。それでも決まらない値 (機種依存で、しかも読者指摘で逆の可能性が併記されているもの) は
**自動では触らず、実機で確かめてから明示的に呼ぶ口**を用意する。「Bible と UNDOCUMENTED が矛盾したら UNDOCUMENTED」という一律の規則より、この決め方のほうが強い。

出典: `docs/POLICY_DEBUG.md` §4-50 (シリアルのクロック)、§4-57 (8251 のコマンド語)、§4-59 (8255 ポート C)。

## 2. エミュレータで確認済みが実機で通らない — 模擬していない量を「確認済み」と書かない

実機 (PC-9821Ra266) の初日、FD 起動が `root panic` で止まった。原因は 3 つあり、どれも NP21/W では出ない: FDC の IRQ 待ちが「エミュレータで困らない値」で実機のシークに足りない /
DMA の 1MB 制限のビットを落としていない (エミュレータは値を保存するだけで DMA が見ない) / FRY (準備完了) を立てていない。その前後にも同じ型が続いた: シリアルの高い速度は 8253 の整数分周で割り切れず
実機ではずれていた (エミュレータは通信速度を模擬しない)、PIT の分周がクロック決め打ちで、もう一方のクロックの機種では tick が速かった (エミュレータは片方のクロックしか無い)、
キーボード 8251 の DTR / RTS はエミュレータが見ない。(`io_wait()` の連打で FD の読みが古くなる件は NP21/W の上で再現した別の事例で、実機は未確認・原因未特定 — 実機固有の列には入れない。)

**学んだこと**: **エミュレータが模擬していない量は「確認済み」と書かない**。何を模擬していないかはエミュレータのソースで確かめられる (シーク時間、通信速度、クロックの種類、ハンドシェイク線、DMA の制限)。
時間の上限は「エミュレータで困らない値」ではなく**機構の最悪値から導いてコメントに根拠を書く**。「NP21/W で〜を抑制」という理由の定数は、実機の前に必ず疑う (`grep -rn NP21 drivers/`)。
機種で 2 通りある値を定数で持ったら、**判定する側と使う側の順序**まで見る (判定器はあったのに、使う側より後に呼ばれていた)。実機でしか分からない値には**観測の口** (`kbdstat`、起動ログ) を同時に入れる。

出典: `docs/POLICY_DEBUG.md` §4-47〜§4-57 (§4-49 シリアル、§4-51 FDC、§4-53 FRY、§4-54 PIT、§4-55 io_wait、§4-56 volatile、§4-57 8251)、`docs/archive/realhw_v21/TASK_FDC_REALHW.md`。

## 3. 画面モードの正典は実機 ROM が流す列 — 見えない画面の受け入れ条件を作る

実機で PEGC 640x480 へ入ると桁がずれ、NP21/W では正しく出ていた。モード設定の値の一部はエミュレータの BIOS 実装から写したもので、残りは起動時の BIOS の状態に依存していた。
実機の ROM が同じモードへ入るときに流す I/O の列を、V86 の監視で全部記録する道具を作って比べると、エミュレータの BIOS では出ない違いが十数か所並んだ (省いていた初期化、
設定していなかったレジスタ、毎回書いて落としていたビット)。直しは「入り・戻りの順序と値を実機 ROM の記録に合わせる」。ただし実機の前に居られないまま版を締める必要があり、
受け入れは**画面を見ない 3 条件**にした: (A) 実物のソースが出す OUT 列が ROM の記録と一致するホスト試験 (意図的な違いは理由付きの除外表、未解明の差分は除外表に明記)、(B) エミュレータの回帰、(C) 実機でレジスタの読み戻しを
シリアルで採る。

**学んだこと**: エミュレータの BIOS は「エミュレータの上で辻褄が合う値」で、実機の手順の写しではない。**実機のハードウェアへ書く列の正典は実機の ROM が流す列**で、取れるなら取ってから合わせる。
目で見られない条件で受け入れるときは、「一致する」ことを機械で照合できる形 (記録との突き合わせ + 除外表) にし、**未解明の差分を除外表に名指しで残す** — 崩れが残ったとき最初に疑う場所が決まる。
「v3 を遅らせないために画面を見ない条件で締める」はユーザー決定で、その代わり残件 (目視) を票に明記した。

出典: `docs/tasks/realhw/TASK_PEGC480_REALHW.md` §3・§5、`docs/POLICY_DEBUG.md` §4-62、`docs/RELEASE_v2.1.md` §2-1。

## 4. メモリマップの 3 者討論 — 意見書 → 反論と合成 → 最終案 → レビュー往復 → 決裁

v3 のメモリマップは、PM が 1 人で案を書いて Codex に見せる形では収束しなかった (v1 の「番地の付け直し」は往復 1 で反例 9 件)。ユーザーの指示で**3 者討論**にした: 議題 (材料と事実と「意見書に書く 5 項目」) →
ラウンド 1 は Fable と Codex が**独立に**意見書 (問題点・案・推奨) → ユーザーの回答 1 (8MB 機の位置づけ、互換の扱い、快適の基準) → ラウンド 2 は互いの案への反論と合成、一致点と争点の整理、ユーザーへの問い →
ユーザーの回答 2 → 最終案 v1 → Codex 往復 (P1/P2/P3 の判定) → v2 → 往復 → v3 → ユーザー判断 5 点 → Approve。PM は進行と取り次ぎだけで、判断はしない。討論の原本は一時ファイルで、要る内容は票に写した。

**学んだこと**: 設計の分岐が大きいときは、**先に事実を揃え** (実機の RAM 量、PCI の BAR 帯、エミュレータの構成、決定済みの制約)、**独立した 2 者に意見書を書かせてから突き合わせる**。
一致点は決定に昇格させ、争点だけをユーザーに問う (7 点、5 点と減らしていく)。「反論と合成」のラウンドで相手の案の反例を挙げるのは、自分の案を守るためではなく争点を絞るため。
最終案は Codex の往復で P1 (到達可能な反例) が消えるまで直し、ユーザーの判断が要る点は**番号を振って明示**する。決定は D1〜D36 のように番号で票に残し、後の決定は「D7 → D35」のように改訂として書く。

出典: `docs/tasks/v3/TASK_MEMMAP_V3.md` §0・§11 (ラウンドごとの要点)、`docs/archive/v3/V3_PLAN_DRAFT.md` §7。

## 5. 設計票を Codex と突き合わせる型 — 汎用機構を足すと指摘が集中する

実機のドライバ (内蔵 Trident) の設計票は、実装なしのまま Codex の設計レビューを 5 回受けて Approve になった。1 回目は P1 が 3 つ (「書き込みなし」と「全ダンプ」が両立しない、復帰経路が未設計、
窓の写像が既存 API と接続できない)。往復ごとに、資料に**あること**と**無いこと**を分け (「9682 は資料に記述なし」と v1 の断定を撤回)、参照実装 (FreeBSD → X.Org のドライバ) は「アドレス・幅・手順の出典」としては認めるが
「この機種で届く根拠」には数えない、と線を引いた。その前の結線の土台の票では 12 往復かかり、途中で PM が足した「IRQ0 が tick ごとに残件を回収する汎用機構」に指摘が集中 (予算・飢餓・再開位置・無進捗判定)、
機構ごと取り下げて driver 側のフックに戻したら収束した。

**学んだこと**: ドライバの設計は**実装の前に**独立レビューと突き合わせる (実機でしか動かないものは特に)。**設計票に新しい汎用機構を足すときは、既存の型で足りないかを先に問う**。
資料は「あること / 無いこと / 推定」を分けて書き、無いことを断定で埋めない。参照実装は出典の種類 (手順の根拠か、到達性の根拠か) を区別する。往復は「指摘の集合」で数え、依頼文には**網羅性**
(到達可能な欠陥を一度に全部、経路ごとの見た / 見ていない、次の往復で新領域を出すなら今回なぜ見えなかったか) を要求する。所見は鵜呑みにせず反例の到達可能性を自分で確かめ、誤検出はレビュー記録側を直す。
規定の 3 往復で決着しなければ争点を整理してユーザーへ — ユーザーは「あと 3」「解決まで」と段階的に許可した。

出典: `docs/tasks/realhw/TASK_TRIDENT_DRIVER.md` §8、`docs/tasks/v3/TASK_HAL_WIRING.md` (往復記録)、`docs/tasks/agents/ROLES.md` §3・§5。

## 6. 文書運用 — 正典を 1 か所、状態行の語彙、生成される文書

同じ事実を 2 か所で独立に更新する構造は必ず食い違う。外部の診断で 6 件 (メモリのギャップの記述、KAPI 手順の 4 か所、配備コマンドの誤説明、進捗、関数数、脱出キー) が見つかり、
「情報単位ごとに正典 1 か所、他は要約 + 参照」に切り替えた。AI アシスタントの入口 (CLAUDE.md) は 558 行 (`21cd48e9`、09-05) から段階的に (373 行を経て) 162 行 (`b57eec3d`、09-09) へ痩せ、手順はスキルへ、障害の経緯は教訓集へ。
9 月中旬の棚卸しでは、票の状態行が語彙の外 (「実装済み」「方針確定」「修正済み」…) で読み手ごとに意味が違う、索引に載せ忘れた票が 31 本、試験の一覧が手で書かれて古い、が見つかった。
状態行は語彙表 (計画 / 設計中 / 実装中 / 受入待ち / 受入完了 / 撤回 / 完了記録 / 草案 / 現行) から選び、検査器は語を持たず表から読む。試験一覧・メモリ地図は生成し、鮮度を `make check` が照合する。
リンク切れと孤児 (索引から辿れない文書) も `make check` の列に入れ、完了した票は archive へ移して参照を機械で書き換える。

**学んだこと**: **更新先を 1 つに決める表を索引の冒頭に置く**。変わりやすい数値・手順・進捗は複製せず、正典から生成できるものは生成する。状態は**語彙表の語**で書き、検査器に語彙を持たせない
(語を足すときは表だけ直す)。「書いてあるのに辿れない」は無いのと同じなので、孤児検査を回す。**運用規約はインシデントごとに 1 行足す構造にしない** — 14KB に膨れたオーケストレーションのプロンプトが慎重さの過剰と中断癖を強化していた。
規約は 3 行に固定し、増える分は既存行の書き換えで吸収する。

出典: `docs/INDEX.md` 冒頭の正典表、`docs/POLICY_DEV.md` §8 (状態行の語彙)、`tools/check_docs_status.py` / `check_docs_orphans.py` / `check_docs_links.py` の docstring、`docs/archive/agents/RETROSPECTIVE_2026-09-09.md` §4、`docs/archive/README.md`。

## 7. 変異試験 — 実物を書き換えない写しの木、変えた所だけ変異

変異試験は最初「実物のソースを書き換えて戻す」作りだった。`make check` を時間切れで打ち切ると変異が当たったままソースに残り、次の実行が「目印が無い」で落ち、打ち切り直後に `git add -A` すると壊したコードが
コミットに入る (一度は運だけで助かった)。並列にもできない (同じソースを奪い合って壊れ方が再現しない)。16 コアで `-j` を一度も指定しておらず `make check` は 15 分以上かかっていた。
全部を「一時ディレクトリの写しの木に変異を当てる」作りに移し、番人 (`check_tree_unchanged.py`) を残し、検査を 3 段にした: `check-fast` (変異なし、約 40 秒) / `check-changed` (変えたファイルに関係する検査だけ変異、対応表は静的に照合) /
`check` (全部)。重い変異は「最初に落ちたケースで打ち切る」(RED は 1 件で決まる)。

**学んだこと**: **試験が実物のソースを書き換える作りにしない**。打ち切り・並列・偶発のどれでも壊れる。変異は「その試験が見ているソースを変えたとき」にしか意味が無いので、変えた所だけ変異する段を持ち、
コーダーの完了条件はその段の rc=0、全部の変異は着地で 1 回。並列段の時間上限は単独の実測ではなく同時実行の負荷で決める。`make check` を打ち切ったら、コミットの前に `git status` と `git diff --stat` を見る。

出典: `docs/POLICY_DEBUG.md` §4-40・§4-41、`docs/archive/tools/TASK_CHECK_MUT_PARALLEL.md`、`docs/08_build.md` §8-4 (検査の 3 段)。

## 8. 資源回収は所有者タグで — 終了段の分だけ回収し、親へ戻るときは状態を復元する

プログラム終了時の自動回収が、FD とパイプを**所有者に関係なく全部**回収していた。常駐の FEP 辞書の DB 接続が、`ime on` を実行した一時プログラムの終了で閉じられて候補がゼロになる /
パイプの 1 段目の終了でシェルのパイプバッファが解放されて 2 段目が固まる / 子から戻るときにヒープを再初期化して親の先頭ブロックを壊す。
直しは、資源にネスト段の**所有者タグ**を付けて終了段の分だけ回収し、カーネル常駐の資源は保護フラグで除外し、親へ戻るときは初期化ではなく**保存した状態の復元**にする。
2 つのヒープ (libc の sbrk と OS の exec_heap) が同じ番地から始まって互いを上書きした件も同じ時期で、帯を分けて解決した。

**学んだこと**: 「終了時に全部片付ける」は、ネストする実行モデル (子が親の資源を見る、常駐が資源を持つ) では必ず親の資源を壊す。**回収は所有者で選ぶ**、**常駐の資源は明示的に保護する**、
**親へ戻るときは init ではなく restore**。ヒープが 2 系統あるなら番地の帯を分け、帯の重なり・逆転は地図の生成と検査 (`make check`) で機械的に見る。

出典: `docs/POLICY_DEBUG.md` §4-15・§4-16、`docs/09_exec.md` (資源の所有者)、`docs/10_notes.md` §10-9。

## 9. 配備の成否を文言で判断しない — 到達確認は実物の照合で ([V4])

「修正が効かない」調査を 3 回空転させた最初の例は、エミュレータが開いたままの NHD への配備が黙って無効になっていた件。その後も形を変えて続いた: 作業イメージが `/tmp` にあり消えても exit 0 /
NHD が満杯で `cp` の ENOSPC が出力の途中に 1 行流れ、最後は「完了! 183 ファイル」「Done!」で exit 0 (ディスク上のカーネルは切り詰められて壊れ、ゲストは古いカーネルで動き続ける) / `hsync` が HostDrv の古いファイルで NHD を上書きし数世代前に戻る /
GUI の受入台本が CUI のまま `RESULT: OK` を出していた。

**学んだこと**: **「配備完了」の文言を信じない**。到達確認は実物の照合で行う — ゲストの `ls -l` と手元のサイズ、起動時の自己試験の合否を**新しい**シンボル表の番地で読む (古い番地で読んだ値や初期化前の 0 を合格にしない)、
起動ログのビルド識別子 (Commit / CRC) と `ver` を突き合わせる。配備の道具にはその照合を組み込み、素通りする経路 (直接 `make deploy-nhd`) を無くす。受入の台本は「目的の状態に入れたか」を合否に入れる。
失敗と飛ばした段は起きたとおりに報告し、未検証を合格と書かない ([V4])。デバッグの最初の一手は「バイナリが新しいか」の排除で、これはプロジェクト開始以来もっとも時間を浪費した問題だった。

出典: `docs/POLICY_DEBUG.md` §2 (反映確認のチェックリスト)、§4-8・§4-17・§4-29・§4-33、`docs/CONSTRAINTS.md` [V1]・[V4]。

## 10. ドラッグ枠の残像 — 損傷の申告漏れは「描いた側」ではなく「壊された側」に返す

窓をドラッグして他の窓の上を通すと、途中位置の枠の線が下の窓のクライアント面に残った (2 バックエンドで再現)。枠はバックバッファへ実線で描き、消去は WM が持つ下地とクロームの合成だけで、
**枠が横切った窓へ Paint (再描画の要求) を返していなかった**。WM はクライアント面の中身を持たないので、跡はアプリに描き直させる以外に消せない。同じ形で、前面を替えたとき旧前面のタイトルが
アクティブ色のまま残る件 (新しい前面の外形しか損傷にしていない) も見つかった。直しは「上書きした範囲を、上書きされた窓の損傷に足す」の一般形で、試験は画素の見張り色で
「クライアント面が Paint 無しに書き替わっていないか」を機械で見る形にした (修正箇所と重なり順の統一は出典のコミット)。

**学んだこと**: 損傷 (damage) モデルでは、**何かを上書きした側が、上書きされた側の損傷を申告する**責任を持つ。「自分で消したから済んだ」は、自分が中身を持たない面 (アプリのクライアント面) では成り立たない。
状態の変化 (前面の交代) は**旧と新の両方**を損傷にする。受け入れは目視ではなく、画素の見張り色で「Paint 無しに変わっていないか」を機械で見る。最初はリリースノートの「既知の制限」に書いて締めるつもりだったが、
同じ日に直せたのは損傷モデルが票 (契約) に書いてあり、どこに責任があるかを議論せずに済んだから。
