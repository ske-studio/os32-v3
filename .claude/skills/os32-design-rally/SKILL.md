# os32-design-rally — 設計の往復と確定

役の割り当ての正典は [ROLES §0](../../../docs/tasks/agents/ROLES.md) と [HANDOVER](../../../docs/tasks/agents/HANDOVER_2026-10-09.md) §2
(2026-10-20 からの一時体制: 起草 = Fable (`model: fable`, general-purpose)、レビュー = Opus (`reviewer` subagent))。
**レビューは PM が代行しない。3 往復で決着しない争点はユーザーへ。**

## 1. 置き場

`~/os32-tmp/run/<名>/` に `DESIGN.r1.md` → `REVIEW.r1.md` (PM がレビューの返答を写す) → `DESIGN.r2.md` … → `DESIGN.final.md`。
票は `docs/tasks/…/TASK_<名>.md` に「§0 ユーザー決定」と「§1 詳細設計 (確定)」の要約だけを書き、全文はこの置き場を指す。

## 2. 起草の依頼 (トークン節約が最優先)

```
あなたは OS32 (PC-9821 用 32bit OS、/home/hight/os32-v3) の設計者です。<何の> 実装可能な粒度の詳細設計を 1 枚書いてください。
トークン節約が最優先: 下に挙げた所だけ読み、実コードは grep で行を絞る (全文読みはしない)。
前提 (議論しない): シングルタスク・協調切替。9801 互換は考えない。整数演算が第一選択 (POLICY_DEV §2)。CLAUDE.md の [C1]〜[D3]。<決定済みの事項>。
読む所: <票の行範囲>、<関係する確定設計>、実コード (grep で): <関数・ファイル名>
書く物: ~/os32-tmp/run/<名>/DESIGN.r1.md (日本語、<150〜250> 行以内、表と箇条書き中心)。章立て:
1. 実物の確認 (票の前提と実コードの食い違いを file:line で)
2〜. <中身: 構造・関数の形・手順・誤りコード・置き場>
n-2. ファイルごとの変更一覧 (新規/変更、おおよその行数)
n-1. 受入の各項目 → 試験 (host / ゲスト) と変異 1 行ずつ、段の分け方 (半日〜1 日、並列の可否、回す検査)
n. 未決 (ユーザー判断が要るものだけ、推奨付き)
返答本文は「書いた / 未決の数 / 実物との食い違いの数」の 3 行だけ。
```

## 3. レビューの依頼

```
OS32 の設計票 ~/os32-tmp/run/<名>/DESIGN.r1.md (<中身>、<起草者> 起草) をレビューしてください。設計ラリー第 1 回 (最大 3 回)。読み取りだけ。
前提 (指摘しない): シングルタスク・協調切替、9801 互換なし、過剰防御・マルチタスク前提は不要。<決定済みの事項と確定設計の所在>。
見てほしい点: (1) §1 の食い違いが実コードと合うか (file:line) (2) 実装者がこの文書だけで迷わず書ける粒度か (3) <この設計固有の危険: 回収・世代・固まる・ABI など> (4) 未決の推奨の妥当性とユーザー判断が本当に要るか (5) 段分けと試験・変異の対応。
書式: 指摘ごとに「重さ (P1 実装を誤らせる / P2 欠け / P3 軽微)・節・何が問題か・直し案 1 行」。全体 50 行以内。最後に「r2 が要るか」1 行と、未決の振り分け (ユーザー / PM)。
```

## 4. 往復

1. レビューの返答を `REVIEW.rN.md` に写す (要旨で可、ID と file:line は残す)。
2. 起草者には**同じ文脈に SendMessage** で差分だけ頼む (新しく起こさない — 読み直しのトークンを使わない):
   「REVIEW.rN.md を反映した DESIGN.r(N+1).md を書いて。rN からの差分だけ直し、関係する行以外は読み直さない。冒頭に『rN→r(N+1) の変更』を ID ごと 1 行、反論は末尾に 1 行ずつ。返答は『書いた / 反論の数』の 2 行」。
3. レビュアーにも同じ文脈で「第 N 回の指摘が直ったかと、直しで新しく生じた誤りだけに絞って、20〜30 行以内、最後に『確定してよいか』」。
4. **条件付きの承認で残りが数行なら、PM が直して `DESIGN.final.md` にする** (新しい往復を回さない)。
   直した点は final の末尾に「確定 (日付、誰の第 N 回、PM が反映)」として ID ごとに 1 行。
5. 実装に出した後に分かった決定・送り項目は、final の末尾に節を足して追記する (例「S1 の取り込みで決めたこと」)。

## 5. 未決の扱い

- 推奨は基本的に承認 (memory)。**ユーザーに上げるのは**: 仕様の分岐、スコープの拡大、物理操作、ライセンス・法的な判断、決定済みの方針を覆すもの。それ以外は PM が推奨どおりに決めて final と票に「PM 決定」と書く。
- ユーザーの決定は量の意味ごと原文で依頼に書く (memory)。

## 6. 確定の後

- 票の §1 に要約 (段の表・入口・PM 決定・全文の所在)、`docs/INDEX.md` から辿れるようにし、`make check-docs-links check-docs-orphans check-docs-status MUTATE=0`。
- 実装の依頼は os32-delegate、取り込みは os32-land。
