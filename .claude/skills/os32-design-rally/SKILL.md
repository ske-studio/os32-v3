# os32-design-rally — 設計の往復と確定

役の割り当ては [ROLES §0](../../../docs/tasks/agents/ROLES.md) を参照。**起草は astra** (`gpt-6.2-astra` を codex で、`~/os32-tmp/bin/codex_run.sh <名> gpt-6.2-astra <主の作業木> <PACK>`、書き込みは codex_run.sh に渡した段の名前のディレクトリ ~/os32-tmp/run/<段の名>/ の中だけ (sandbox の範囲。r2 以降を別の段の名で起こす時は、そのディレクトリに書かせて PM が往復の置き場に写す)、リポジトリは読むだけ — 2026-11-20 夕から、前は Fable、ユーザー決定「fable が枯渇してきたので」)、**レビューは sol** (`gpt-6.2-sol` を codex の read-only で。実装の astra と別のモデルにするため。PM が自分で代わりに読まない) (ユーザー決定 2026-11-19、Opus → astra → sol と決め直した最後)。下の §2 の依頼の型はそのまま起草者 (astra) に渡す (書く先は ~/os32-tmp/run/<名>/)。§3 のレビューの依頼は sol に渡し、§4 の往復は前回のレビューの返答と差分を添えて sol を起こし直す (codex は文脈を持ち越さない)。

## 1. 置き場

- **往復の版** (`DESIGN.r1.md` → `REVIEW.r1.md` (PM がレビューの返答を写す) → `DESIGN.r2.md` …、起草者のログ) は `~/os32-tmp/run/<名>/` に置く。リポジトリには入れない。
- **確定版の置き場 (2026-10-30 から)**: 設計書は 1 機能 1 ファイルで、`docs/design/<ソースと同じパス>.md` に写す (POLICY_DEV §9 の 2a)。往復の版 (DESIGN.r1 …) は 1 本でよいが、確定したらソースファイルごとの設計書に分けて写す。既存の `docs/decisions/` の形は移すまでの経過措置。
- **確定版はリポジトリに入れる**: `DESIGN.final.md` と、確定の後の追記 (ADDENDUM・設計者が決めたこと・送り項目) を `docs/decisions/<領域>/<名>_DESIGN.md` などに写す (層 L3 決定、2026-10-22 に `docs/tasks/<領域>/design/` から移した。冒頭に出所の 1 行と状態行 `> 状態: **現行 (日付)** — …`、中身は変えず、リポジトリ内の文書への参照だけリンクに直す)。**決定の文書がリンクしてよいのは L1〜L3 だけ** — 票 (`docs/tasks/`) は「段の状態は票 TASK_<名> が持つ」のように名前を文字で書き、リンクは票 → 決定の向きに張る (`python3 -B -m tests.infra.ci run --check docs_navigation` の決定→票)。**確定の後に追記したら、同じ取り込みでリポジトリの写しも更新する** (実装者・設計者には写しの方を直接直させてよい)。
  理由 (2026-10-21、ユーザーの指摘): 戻す処理と GeForce 4a の確定設計と追記が ~/os32-tmp にしか無く、票に戻っていなかった。
- 票の先頭 (状態行の次) に `> 完了の基準: <測れる到達点>` を書く — 何が幾つになれば終わりかを検査の名前や数で (POLICY_DEV §8、`python3 -B -m tests.infra.ci run --check docs_status` が見る)。起草の依頼にも「完了の基準の案」を章に入れる。
- 票は `docs/tasks/…/TASK_<名>.md` に「§0 ユーザー決定」と「§1 詳細設計 (確定)」の要約だけを書き、全文は `docs/decisions/` の写しへリンクする (例: [TASK_REALHW_RECOVER](../../../docs/tasks/realhw/TASK_REALHW_RECOVER.md) §6)。

[HW3] の手本は名前・版・ファイル・行範囲を記し、各レジスタ・手順の順序と前提を示す。
外れる箇所は理由を、手本に無い箇所はその旨と資料・観測の根拠を記す。
資料と実装が食い違う場合は両方を書き、実機で確かめる点にする。
GPL は資料と BSD 系で確かめられない挙動を知るためだけに使い、その旨を記す。

## 2. 起草の依頼 (トークン節約が最優先)

```
あなたは OS32 (PC-9821 用 32bit OS、/home/hight/os32-v3) の設計者です。<何の> 実装可能な粒度の詳細設計を 1 枚書いてください。
トークン節約が最優先: 下に挙げた所だけ読み、実コードは grep で行を絞る (全文読みはしない)。
前提 (議論しない): シングルタスク・協調切替。9801 互換は考えない。整数演算が第一選択 (POLICY_DEV §2)。CLAUDE.md の [C1]〜[D3]。<決定済みの事項>。
<ハードウェアの設計のとき> 手本: <BSD/MIT の既存の実装> を手本にする ([HW3])。書く各レジスタ・各手順について、手本のどの関数がどの順・どの前提の状態で行うかを file:line で示し、OS32 の列をそれに沿わせる。外れる所は理由を 1 行ずつ、手本に無いことは無いと明記して根拠を書く。
読む所: <票の行範囲>、<関係する確定設計>、実コード (grep で): <関数・ファイル名>
書く物: ~/os32-tmp/run/<名>/DESIGN.r1.md (日本語、<150〜250> 行以内、表と箇条書き中心)。章立て:
1. 実物の確認 (票の前提と実コードの食い違いを file:line で)。**設計に書く関数・マクロ・型は全部、実コードで実在と型を確かめて file:line を付ける (新設する物は「新設」と書く)**。**別の機種 (PowerPC など) の設計は「x86 との比べ」の節を持つ: x86 で同じ役目の物 (実行の形・シェルの枠・番号の振り方・資源の持ち方・起動の順・番地) を実コードで並べ、違いがあれば x86 に揃える段を先に置く。違いを残すのは物理の制約がある時だけで、[ARCH_COMPAT_CONTRACT §9](../../../docs/decisions/ARCH_COMPAT_CONTRACT.md) の一覧に書く (新しい 2 重は作らない、既にある違いにはわざわざ手を付けない) (POLICY_DEV §10「x86 に揃える」、ユーザー決定 2026-11-20)**。**別のアーキテクチャの機能・他のアーキテクチャや本線と同じ役目の機能なら、統合の判断 3 点 (POLICY_DEV §1「別のアーキテクチャで機能を作るとき」: 既存の機能・計画の有無、HAL で 1 つの実装にするか、計画の向きと合うか) をここに書く**
2〜. <中身: 構造・関数の形・手順・誤りコード・置き場>。**部品の境目 (他の部品・既存の型とつなぐ関数・構造体・通信の形式・誰が状態を持つか) はコード断片で書く** — 「何をするか」だけで止めない
   **部品の大きさの見積もり** (どの像・部品に入るか、増える KB、起動 FD・MINIMAL・kdebug.bin の上限に触れるか)
n-2. ファイルごとの変更一覧 (新規/変更、おおよその行数)。**1 機能 1 ファイル** (POLICY_DEV §2、ユーザー決定 2026-10-30) — 機能ごとのファイルの割り当てを表にし、段を「1 ファイル = 1 段 = 1 実装者」で並列に出せる形にする。**本線と PowerPC にまたがる段は、境目の関数の宣言 (名前・引数・戻り値・誤りの返し方・呼ぶ順) を確定設計に書く** — 書式の記録だけでは実装者が合わせ目で止まる (2026-11-20、module の L1)。**新しいファイルは、作る段でビルドの一覧に登録する** (x86 の像に入る最小の登録を同じ段に。像ごとの選択の広げは別の段でよい) — 登録だけを後の段に分けると、作る段のリンクが通らず実装者が止まる (2026-11-20 に 3 回: 7a の M3・M5、シェルの寄せの D1〜D3)。既存の大きいファイルに足す機能は別のファイル (`<元の名前>_<機能>.inc` か別の .c) に置き場を作る。分けない所は理由 (共有の構造体・引数の束が要る) を書く
n-1. 受入の各項目 → 試験 (host / ゲスト) と変異 1 行ずつ、段の分け方 (半日〜1 日、並列の可否、回す検査)
n-1b. **触る既存の検査と固定の一覧** (ユーザー提案 2026-11-20「計画書段階で検査項目を記載」): 段ごとに、変えるファイルを組む・読む既存の検査と、その追従が要る物を表にする — 登録の spec・sources・mutations と検査本体の入力を照合する。表の行は依頼の完了条件にそのまま写す
n. 未決 (ユーザー判断が要るものだけ、推奨付き)
返答本文は「書いた / 未決の数 / 実物との食い違いの数」の 3 行だけ。
```

- 2026-10-21 の反省 (ユーザー承認): 戻す処理と 4a の設計で、境目の形が無いために実装者 (sol) が「設計の欠け」で 6 回止まり、追記の往復が r4 と補完 2 回まで延びた。T3 では戻す処理が kdebug.bin に入って起動 FD の空きが下限を割った。上の 2 点 (境目のコード断片・大きさの見積もり) を起草の依頼に必ず入れる。追記で欠けを埋める往復も 3 回の上限に数え、超えたらユーザーに相談する。

- **PM が依頼に書く前提には file:line を付ける** (ユーザー決定 2026-11-20): 「〜は〜になっている」「〜は無い」と書く時は、PM が実コードを開いて確かめた位置を添える。確かめていない物は「未確認」と書いて、起草者に確かめさせる。ユーザーへの説明も同じ。
  理由: 2026-11-20、PM が記憶で書いた前提 (x86 の ID 1 は常駐のシェル) と、PM が書き足した条件の出口の抜けで、説明の訂正と実装者の止まり (段 7a の M5) が起きた。

## 3. レビューの依頼

```
OS32 の設計票 ~/os32-tmp/run/<名>/DESIGN.r1.md (<中身>、<起草者> 起草) をレビューしてください。設計ラリー第 1 回 (最大 3 回)。読み取りだけ。
前提 (指摘しない): シングルタスク・協調切替、9801 互換なし、過剰防御・マルチタスク前提は不要。<決定済みの事項と確定設計の所在>。
見てほしい点: (1) §1 の食い違いが実コードと合うか (file:line) (2) 実装者がこの文書だけで迷わず書ける粒度か (3) <この設計固有の危険: 回収・世代・固まる・ABI など> (4) 未決の推奨の妥当性とユーザー判断が本当に要るか (5) 段分けと試験・変異の対応 (6) 別のアーキテクチャの機能なら、統合の判断 (POLICY_DEV §1) が計画書・他のアーキテクチャの実装と合うか。 (7) 別の機種の設計なら、x86 との比べの節が実コードと合い、x86 と違う形を機種の境目で吸収していないか (POLICY_DEV §10「x86 に揃える」)
書式: 指摘ごとに「重さ (P1 実装を誤らせる / P2 欠け / P3 軽微)・節・何が問題か・直し案 1 行」。全体 50 行以内。最後に「r2 が要るか」1 行と、未決の振り分け (ユーザー / PM)。
```

## 4. 往復

1. レビューの返答を `REVIEW.rN.md` に写す (要旨で可、ID と file:line は残す)。
2. 起草者には**同じ文脈に SendMessage** で差分だけ頼む (新しく起こさない — 読み直しのトークンを使わない):
   「REVIEW.rN.md を反映した DESIGN.r(N+1).md を書いて。rN からの差分だけ直し、関係する行以外は読み直さない。冒頭に『rN→r(N+1) の変更』を ID ごと 1 行、反論は末尾に 1 行ずつ。返答は『書いた / 反論の数』の 2 行」。
3. レビュアーにも同じ文脈で「第 N 回の指摘が直ったかと、直しで新しく生じた誤りだけに絞って、20〜30 行以内、最後に『確定してよいか』」。
4. **条件付きの承認で残りが数行なら、PM が直して `DESIGN.final.md` にする** (新しい往復を回さない)。
   直した点は final の末尾に「確定 (日付、誰の第 N 回、PM が反映)」として ID ごとに 1 行。
5. 実装に出した後に分かった決定・送り項目は、final の末尾に節を足して追記する (例「S1 の取り込みで決めたこと」)。追記はリポジトリの写し (`docs/decisions/<領域>/`) にも同じ取り込みで入れる (§1)。

## 5. 未決の扱い

- 推奨は基本的に承認 (memory)。**ユーザーに上げるのは**: 仕様の分岐、スコープの拡大、物理操作、ライセンス・法的な判断、決定済みの方針を覆すもの。それ以外は PM が推奨どおりに決めて final と票に「PM 決定」と書く。
- ユーザーの決定は量の意味ごと原文で依頼に書く (memory)。

## 6. 確定の後

- **リポジトリへ写す時、このリポジトリのソースの `file:line` は「パス + 関数・マクロ・節の名前」に直す** (POLICY_DEV §9、ユーザー決定 2026-11-17。`python3 -B -m tests.infra.ci run --check docs_source_refs` が増加を止める)。下書きとレビューの往復 (~/os32-tmp/run/) では file:line のままでよい。版を固定した外部の手本の file:line は写しにも残す。

- **粒度ごとに分けて写す — 試行中** (ユーザー指示 2026-10-22: 冗長にならないように。**正式に取り入れるかはユーザーが後で評価して決める** — 試した文書: HWDEV の 4 本 (docs/tasks/realhw/TASK_HWDEV.md と docs/decisions/realhw/HWDEV_DESIGN・HWDEV_CORE_API・DEVICE_STATES) とこれから分ける分。評価の観点の案: 冗長さが減ったか、欲しい情報が 1 か所で見つかるか、リンクを辿る手間、更新のときの直し漏れ。評価までは新しい確定版に当て、既存の写しは無理に分け直さない): 1 枚の final をそのまま写さず、(1) 判断と状態 = 票 (`TASK_<名>.md`: 決定・段の表・状態行・送り項目の所在、短く)、(2) 構造 = `docs/decisions/<領域>/<名>_DESIGN.md` (分け方・方式の比較の結論・移し方)、(3) 参照の表 = `docs/decisions/<領域>/<名>_<API|TABLE>.md` (関数の一覧・ABI・構造体・番号)、(4) 他の設計からも引く要件 = 共通の文書 (例 `docs/decisions/realhw/DEVICE_STATES.md`) に分ける。同じことを 2 か所に書かず、片方はリンクで指す。既存の写しに同じ内容があれば重複させずにそちらへ寄せる。
- `DESIGN.final.md` を `docs/decisions/<領域>/` に写す (§1 の形)。以後の追記 (設計者の決定・送り項目) もそのたびに写しへ入れ、写しと ~/os32-tmp の final がずれたら写しを正とする。
- 票の §1 に要約 (段の表・入口・PM 決定・全文の所在 = `docs/decisions/` の写しへのリンク)、`docs/INDEX.md` から票が辿れるようにし (写しは票から辿れれば孤児にならない)、`python3 -B -m tests.infra.ci run --check <id>`。
- 実装の依頼は os32-delegate、取り込みは os32-land。
