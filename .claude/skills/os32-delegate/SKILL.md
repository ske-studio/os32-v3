# os32-delegate — 実装の依頼とレビューの依頼

役の割り当ては [ROLES §0](../../../docs/tasks/agents/ROLES.md) を参照。

## 1. 作業木

```bash
cd /home/hight/os32-v3
git worktree add -q -b wt/<名> ~/wt/os32-v3/<名> <基点の SHA>
~/os32-tmp/bin/seed_fonts.sh ~/wt/os32-v3/<名>   # assets/fonts/ を全部 (IPAex・Inconsolata・JF-Dot、gitignore)。codex のサンドボックスはネットに出られず (DNS 不可)、無いと make all がフォントの取得で rc=2 (2026-11-04、gf4-fxc・fxd)
```

- 触るファイルが重ならない段は並列で出す。重なるなら順に (先の段を取り込んでから次を作る)。
- **依頼の大きさ**: 1 回の依頼は ROLES §0「段の大きさ」の 1 段 (半日〜1 日) まで。Tx でまとめるときも codex の timeout (7100 秒 ≈ 2 時間) に収まる量にする (2026-10-23、B1+B2 の 8 時間を 1 回に出して止めた反省)。
- 依頼より前に、設計の「送り項目」(前の段のレビューで後へ回した指摘) を確定設計の末尾に書いておく。確定設計の所在はリポジトリの写し `docs/decisions/<領域>/` (os32-design-rally §1)。~/os32-tmp/run/ の final だけに書かない。

- **手本がある移植** (コンパイルを全部の実装の後に) は [PORT_FLOW.md](../../../docs/tasks/agents/PORT_FLOW.md) の §3 (設計の段の点検) と §4 (依頼に必ず書くこと) を依頼に入れる。

## 2. 実装の依頼の型

```
あなたは OS32 (PC-9821 用 32bit OS) の実装者です。作業木 /home/hight/wt/os32-v3/<名> (branch wt/<名>) だけで作業し、main は触らない。push・merge はしない。コミットは PM が行う。<NP21/W は触らない | NP21/W はあなた専用 (他に使う人はいない)>。
前提: シングルタスク・協調切替。9801 互換は考えない。CLAUDE.md の [C1]〜[D4] を守る (**[D4] `docs/archive/` は読まない・根拠にしない (ユーザーの指示があるときだけ)**、<関係する規則: [C2] kstr*、[C4] 定数の置き場、[ABI]、[V4] 未確認を合格と書かない、[D1] deploy-kernel/boot・ini 編集・NP21/W の停止起動はしない>)。
仕事: 確定設計 <所在> の §6 の段 **<段> だけ** (<中身>)。読む所: <節の番号と末尾の送り項目>。<他の段・他の実装者が触るファイル> には触らない。**設計に書いていない実装が要ったら、その部分は作らずに止めて、報告の「設計の欠け」に何が足りないかを書く** (PM が設計者に設計を埋めさせてから続きを頼む)。小さな判断 (名前・置き場・試験の形) は「未決」に書いて進めてよい。
完了条件: ROLES §0「検査」に従う。手本がある移植は PORT_FLOW の例外に従う。基点 <SHA>、触った像 <対象>、主な候補検査 <検査名と runner>、足した・触った試験 <対象>。CROSS_DIR=/home/hight/opt/cross を明示 (作業木に .env は無い)、ログは ~/os32-tmp/run/<名>/、合格に数えるのは最後の変更より後のログだけ。並列の試験が Inconsolata の .part を取り合って落ちたら単独で再実行し報告に書く。
返答本文に報告 (25〜35 行以内: 変更ファイル、試験と変異の結果ログの所在、設計からの逸脱、未決)。
```

- **完了条件はメインストリームもサブストリームも同じ** ([PARALLEL_BRANCHES](../../../docs/tasks/agents/PARALLEL_BRANCHES.md) §3、ユーザー決定 2026-11-05): 依頼には「make all と触った・足した試験の直接の実行と --mutate・lint だけ、`check-changed` は回さない」と書く。PM が `wt/<名前>` を push して GitHub の CI (check・build) の緑で取り込む。
- **名前の置き換え・式の書き換えを含む段** (2026-10-25、票 TASK_MAGIC_NUM で取り込みの検査に 6 本落ちた): 変異の置換の目印 (試験の中の元の式の文字列) が壊れても MUTATE=0 では見つからない。完了条件に「最後に `python3 ~/os32-tmp/bin/stale_anchor.py <基点>` を作業木で回し (試験の文字列のうち、基点では変えたファイルにあり今は無いものを挙げる)、目印なら直して、その試験を MUTATE=1 で 1 回回し RED の数が基点と同じこと」を足す。機械語を変えない段は、変える前後の ELF の `objdump -d` を比べる (`~/os32-tmp/run/magic/objcompare.py` が雛形)。
- 足した・触った試験の変異の実行条件は [ROLES §0「検査」](../../../docs/tasks/agents/ROLES.md) に従う。
- **試験に補助ヘッダ・include を足す段** (2026-10-27、TASK_DEP_DIR の D2・D3 の取り込みで 2 回): 完了条件に「新しく include や補助ヘッダを足した試験は、変異の段の写し (一時ディレクトリに書くソース) からもそのヘッダが見えることを grep で確かめる」と書く。`MUTATE=0` の候補検査では変異の写しを組まないので見つからず、PM の取り込みの検査 (変異込み) で初めて落ちる。
- KAPI を触る段: スキル os32-kapi-add に従い、`make clean` → `make all` を完了条件に足す。
- ゲスト受入を含める段: 配備はスキル run-os32 (作業木の成果物)、GUI は run-os32、カーネルの入れ替えは hsync + emu_reset、
  rshell 中の ESC は rshell を閉じる (閉じたら emu_key で `rshell` + RETURN)、MCP の emu_gui_launch / consink は本体の ELF を引くので
  `OS32_KERNEL_ELF` / `OS32_GSHELL_ELF` で作業木の ELF を渡す、証拠は `~/os32-tmp/evidence/<日付>/<名>/RESULT.md` (項目ごとに 合格/不合格/未確認、PNG を自分で開いて見る)。
- **設計の欠けが報告されたら** (ユーザー指示 2026-10-21): PM が実装を決めずに、設計者 (通常は astra) に確定設計の追記として埋めさせ (os32-design-rally の差分依頼の形)、必要ならレビュアーに短く見せてから、同じ実装者に続きを頼む。
- **設計者に実装させる段** (ユーザー承認 2026-10-21): 部品の境目が多く欠けが出やすい段 (戻す処理 realhw_recover と GeForce 4a の残りの段など) は、最初から設計者の astra に実装させる。依頼に「設計に書いていない実装が要ったら、設計者として確定設計の趣旨に沿って決め、確定設計 (依頼で指定した `docs/design/` の該当設計書、移行前は `docs/decisions/`) の末尾に『<段> の実装で設計者が決めたこと』として 1 件 1 行で書いて実装する。確定本文・ユーザー決定を覆すものだけ止めて報告」と書く。astra の実装なので、後片付けは Opus、レビューは別の Opus (ROLES §0)。決めたことはそのレビューで一緒に見る。
- 実装者が報告ファイルを書けないことがある → PM が返答本文から `~/os32-tmp/run/<名>/report.md` に要約して写す (レビュアーに渡すため)。

## 2-1. 起動と見張り (PM・機能 PM 共通、2026-11-05)

```bash
~/os32-tmp/bin/codex_run.sh <段> <モデル> <作業木> ~/os32-tmp/run/<段>/PACK.md   # すぐ戻る。ログは run/<段>/impl.log、最後の行が rc=N
~/os32-tmp/bin/watch_new.sh <段>/impl.log [<別の段>/impl.log ...]                  # 別の Bash 呼び出しで run_in_background
```

- `watch_new.sh` は、段が終わった (最後の行が `rc=`)・10 分ログが伸びない・混雑・15 分の見回り のどれかで知らせる。知らせが来たら中身を見て (途中は `~/os32-tmp/bin/progress.sh`)、まだ走る段があれば張り直す。
- 自前の待ちを書かない。理由 (2026-11-04〜05): nohup で切り離した codex は終わっても知らせが来ず 2 時間半気づかなかった、ログの `rc=` を grep して試験の出力の `rc=0` と取り違えた、`grep '[c]odex exec'` が起動した Bash の `bash -c` の行に一致してすぐ終わる番号を待った (2 回)、`pgrep -f` が自分に一致した。
- 依頼は `<<'EOT'` (引用符つき) の heredoc でファイルに書いてから渡す (バッククォートがシェルに解釈されて依頼が欠けた)。`--add-dir` は書き込みも許すので、codex_run.sh が渡す run の置き場と check-slots のほかは足さない。
- 機能 PM (サブエージェント) の依頼にも、この 2 行の使い方をそのまま書く。
- 手元の検査の枠 (`check_slot.sh`) は使わない。取り込みの検査は GitHub の CI (ユーザー決定 2026-11-05)。

## 3. PM が報告で見る点

- 完了条件のログが最後の変更より後か。逸脱と未決のうち、PM が決めるもの (推奨で決めて設計の末尾に記録) とユーザーに上げるもの。
- ROLES §4-1 (差し替え定義の追従・改名と許可リスト・対応表・--mutate の正常の段・乱数・int main・マージの重複)。
- ゲストの証拠の PNG は PM も開いて見る (読めた = 合格ではない)。

## 4. レビューの依頼の型

```
OS32 (/home/hight/os32-v3) の <書き手> 実装 <段> を読み取りだけでレビューしてください。対象 `git -C /home/hight/wt/os32-v3/<名> diff <基点>..HEAD` (<生成物・試験は流し見>)。設計は <所在> (<節>)、報告 ~/os32-tmp/run/<名>/report.md (逸脱 N 件・未決 M 件)。トークン節約: <中心に読むファイル>。試験は回さない。
前提 (指摘しない): シングルタスク、9801 互換なし、過剰防御は不要。<範囲外の段>。
見る点: (1)〜(6) <この段で壊れやすい所: 回帰・境界・回収・世代・ABI・x87 など>、逸脱それぞれの可否。
返答は 15〜20 行以内: 判定 (取り込み可 / 要修正)、指摘は「重さ・file:line・何が起きるか・直し方 1 行」。
```

- 「要修正」でも直しが数行なら PM が作業木で直して試験を回し、その直しを書き手と別のモデルに見せる (小さい差分のまとめレビュー)。
- 軽い指摘で次の段に回すものは、確定設計 (`docs/decisions/<領域>/` の写し) の末尾に「<段> の取り込みで <次の段> へ送る項目」として書き、同じ取り込みでコミットする。票の送り項目の表 (例 [TASK_REALHW_RECOVER](../../../docs/tasks/realhw/TASK_REALHW_RECOVER.md) §4) にも 1 行足す。
- 取り込みは os32-land。
