# OS32 ビルド・反映確認・検証

パスは OS32 リポジトリルート基準。サブディレクトリからは
`git rev-parse --show-toplevel` で確認する。
未読なら `CLAUDE.md`、`docs/CONSTRAINTS.md`、`docs/DEVELOPMENT.md` の該当行を読む。
ビルド・配備手順は `docs/08_build.md`、反映確認は `docs/POLICY_DEBUG.md` §2、
ABI 変更は `docs/KAPI_SPEC.md` を正典とする。同一セッションの既読内容は再利用する。

## 変更から検証範囲を選ぶ

最初に依頼範囲、`git status --short`、対象差分を確認する。
既存のユーザー変更や submodule の作業を上書きしない。
今回の変更と結びつく検証を選び、対象・判定条件を短く伝えて実行する。

| 変更 | 選ぶビルド・チェック | 実行検証 |
|---|---|---|
| カーネル・ドライバ | `make kernel` と `make check` | 新カーネルの起動、kselftest、対象機能と関連デバイス |
| ユーザーランド | 既存の個別ターゲット、必要なら `make programs`、`make check` | 対象ゲストプログラム。ライブラリ変更なら再リンクした利用側も確認 |
| KAPI / ABI | `docs/KAPI_SPEC.md` の生成・版更新手順と clean/full build | 旧成果物混在を排除し、呼出し側・SDK・該当 submodule を検証 |
| ブート | `build/boot.mk` の該当ターゲットと必要なカーネル | 対象媒体から起動する試験。ブート領域の配備は別途範囲確認 |
| 文書・スキルのみ | 参照・形式・`git diff --check`、必要な専用 validator、`make check` | ゲスト実行は通常不要。スキル検証のためにNHD配備しない |

正確なターゲット名は `build/*.mk` / `Makefile` で確認し、ファイル名から推測しない。
ツールチェーンがない場合は `INSTALL.md` / `build/config.mk` と照合する。
ホスト GCC をクロスコンパイラの代わりに黙って使わない。
ビルドログは終了コードと最初の有意な失敗を保存し、`tail` の成功をビルド成功にしない。
ABI が変わっていない通常の変更で、習慣的に `make clean` を実行しない。

プリミティブを変更した場合の kselftest 追加要件は `CLAUDE.md` を確認する。
ユーザーランドの newlib を使うテストはカーネルの kstring/kmalloc 検証を代替しない。

## 配備は成果物を確定してから

ビルドのみ、文書のみ、調査のみの依頼ならそこで必要な検証を完了する。
配備が範囲内なら、先にビルドを通し、成果物・配備先・起動対象を確定する。
必要な承認は現在の依頼と既存承認を確認し、未承認の実際の操作の直前に求める。
このスキル自体は `.ini` やディスクイメージへの書込み許可を与えない。
制約 [D1]〜[D3] の適用時は正典に従い、対象と理由を具体的に示す。

配備レシピは `build/deploy.mk` と `docs/08_build.md` で確認する。
`deploy-kernel` もカーネルだけのコピーとは限らず、同期・prune の範囲まで確認する。
`os32-cycle` 等の個人用補助コマンドは利用可能か調べ、なければリポジトリの道具を使う。

- ユーザーランドの短い反復は `make deploy` (ホスト → `C:\os32`) → ゲストで `hsync`。
  再起動は要らない。`hsync` は既定で `/sys` を外す (稼働中の常駐シェルと共有ライブラリ)。
  入れ替えるときだけ `hsync sys` と明示する。
  起動中の常駐プログラムは、ディスク上の更新だけで実行中コードが置き換わるとは考えない。
  **ホットデプロイ (物理末尾 256KB の窓) は 2026-09-09 に撤去した。**
- NHD 配備は NP21/W の**プロセス終了を確認**してから実行し、その後起動する。
  `emu_pause`、breakpoint 停止、HTTP 無応答は終了の証拠にならない。
  `np21w_ctl.py` が止めるのは `NP21W_DIR` の exe と ExecutablePath が一致するプロセスだけ
  (別の場所の NP21/W や名前が似ているだけのものは「対象外」と表示して触らない)。
  別の NP21/W が同じイメージを開いていれば、起動前のロック待ちが名指しで止まる。
- 停止と起動は `tools/np21w_ctl.py` で行う (`docs/POLICY_DEBUG.md` §5)。
  `stop` は `/api/quit` (save=0) で止めてその pid が消えるまで待つ (API が無い・古いフォークの
  ときだけ exe 一致のものを強制終了)。`start --ini <name> [--fd <name>] --wait-ready` は
  媒体 (ini の HDD/CD/FDD/SCSI と `--fd`) が続けて 5 秒開けるのを起動の直前まで確かめてから起動し、
  `/api/instance` の pid と exe の一致とプロセスの 10 秒生存まで確かめる。
  ダイアログで止まっていればその本文を出して失敗する。
  `taskkill` → `Start-Process` を手で続けて打たない — ロックで起動が途中で止まる (§4-60)。
  ini は書き換えない。FD は ini ではなく `--fd` で渡す。
  旧 `tools/np21w_restart.py` は ini の `FDD1FILE` を書き換えるので使わない ([D2])。
- 配備コマンドの終了コードだけで合格にしない。作業イメージ、コピー先、
  ゲストの起動媒体と実行ファイルが一致していることを確認する。

## 起動したバイナリを確認する

`docs/POLICY_DEBUG.md` §2 と `docs/CONSTRAINTS.md` [V1]〜[V4] に従う。
ゲストの `ver`、対応するビルド成果物と配備先のサイズ・ハッシュ、必要なら
新しい `build/out/kernel.map` に対応する実行メモリを使って確認する。
タイムスタンプ・サイズだけでは同一性が十分でない場合はハッシュや対象コードも比較する。

`make deploy` の HostDrv 同期だけでは NHD の `/usr/bin` を更新した証拠にならない。
外部バイナリは所有層の `deploy.yaml`、`build/app.conf`、ゲスト実行パスを照合する。
ライブラリ・テスト変更の最終検証は正典の NHD 配備条件に従い、HostDrv + hsync の結果と区別する。
カーネル起動時は完了後の `kselftest_pass` / `kselftest_fail` と期待項目を確認する。
初期化前のゼロ値や、古い map で読んだ値を成功と判定しない。

## ゲスト試験と報告

接続済みの MCP があれば実際のツール定義に従う。
未接続なら `tools/np21w_mcp/np21w_client.py` と `server.py` を参照して
既存 HTTP API を使う。接続追加・エミュレータ設定変更を暗黙に行わない。
行コマンドは `emu_cmd`、対話入力は `emu_key`、文字画面は `emu_tvram` を使い分ける。
長時間試験は [V3] と現行クライアントの timeout を確認する。
timeout 後は状態を読み、同じコマンドがまだ動いていないか確認してから再試行する。

元の不具合または新機能の合格条件を実行し、変更の影響がある回帰を確認する。
必要な検証が通った後の無目的な全テスト再実行は行わない。
エミュレータでの成功と実カード・実機での成功を区別する。

結果には以下を必要な範囲で含める:

- ビルドした対象と結果、関係する警告・失敗。
- 配備した成果物・ゲストパスと、反映を確認した証拠。
- 実行した試験と実際の結果。未実施なら理由と残作業。

未配備を「動作確認済み」、エミュレータ未接続を「試験成功」と表現しない。
失敗時は最初の有意なエラーと、ビルド・配備・起動・機能のどこで止まったかを示す。
恒久的な文書更新先は `docs/INDEX.md` から選び、検証手順を別文書へ複製しない。
