## sentinel・20 回・ネスト

NP21/W 64MB の同じ起動・入力・画面構成で、CUI shell と GUI gshell の端末から
次の 6 命令をそれぞれ実行する。GUI はほかのアプリを閉じ、出力する端末を先に
開いて安定させる。各命令の最初の MemStat を基準に全20回を比較し、途中の
pool/owner/heap 増加を新しい基準へ取り込み直さない。
各命令の20回の直前と、最外の fixture が終了して prompt に戻った直後に、
CUI は `mem` の `diag: sbrk_used=...`、GUI は CTRL+GRPH+F10 の serial
`OS32: resident sbrk_used=...` を採る。同じ常駐 shell / gshell のまま、
各命令について前後の `sbrk_used` (B) を記録し、`後 == 前` を必要とする。
増えていれば FAIL、一致しない場合も合格にしない。6命令をまとめた前後だけで
代用せず、途中で shell/gshell の再ロードや CUI/GUI 切替を挟まない。
これは子から見えない常駐 sbrk の比較であり、fixture の `usage=PASS` や
`resident_heap_used` (常駐 exec_heap)、`sbrk_peak` の比較で代用しない。

```text
layout_cycle_test exit
layout_cycle_test fault
layout_cycle_test stop
layout_cycle_test nested-exit
layout_cycle_test nested-fault
layout_cycle_test nested-stop
```

`exit` は同じバイナリの `--leaf` (両 heap を確保したまま正常終了)、`fault` は
既存の `faulttest ud`、`stop` は既存の `faulttest loop` を子として使う。
STOP は **各回の** `faulttest: looping (CTRL+STOP to kill)` を待ってから一度だけ
CTRL+STOP を押す/注入する。20 回必要。時間切れや別の終了方法で代用しない。
`nested-*` は親→同じ fixture の `--once` 親→上記の子、最大 app ID 4 の形。
正常・fault・STOP の終了種別と code を照合するので、起動失敗も PASS にならない。

各親は BSS/stack/libc malloc/KAPI mem_alloc の異なるパターンを保持する。
各復帰で `sentinel=PASS usage=PASS` が20行、最後に
`layout_cycle_test: PASS n/n`、終了コード0を必要とする。
`nested-*` の内部親の1回分の出力だけで合格にしない。最外の
`begin ... nested=1 rounds=20` から cycle=20 と最終集計までを保存する。
`usage` 行は pool の free pages、親 owner pages、親 exec heap、常駐 exec_heap、kheap。
ほかに親 extents、leftover pages、lease 数の増分も FAIL にする。
一時的な GUI の初回確保で FAIL した場合もその記録を残し、原因を調べる。

## CUI / GUI 復帰・採取

1. CUI の6命令後に `mem`、`gui`。GUI で6命令を実行し、
   CTRL+GRPH+F10 で serial の `OS32: resident ...` / `OS32: diag ...` と slot 行を保存。
   端末入力・描画が続くことを確認する。
2. GUI を通常の終了操作で閉じ CUI に戻り、`mem` と `layout_cycle_test exit` を再実行。
   `gui` で再入場し、端末で `layout_cycle_test nested-fault`、診断キー、通常終了、
   `mem` をもう一度採る。各状態で prompt/入力/描画が復帰したことと PASS を保存する。
3. CUI の `mem` の追加行 `sbrk_used/sbrk_peak/sbrk_capacity/exec_peak/exec_capacity` は B 単位。
   `sbrk_used` は aligned `_end` から現在の break までの増分
   (`primary_arena.brk - primary_arena.initial`、未初期化なら0) をそのまま表示する。
   `sbrk_peak` はその最大増分 (free/負方向 sbrk 後も減らない)、
   exec_peak は既存 `resident_heap_peak` (allocator の used、ヘッダ等込み)。
   sbrk は **shell/gshell をロードするたび0に戻る**ので、切替前に必ず採る。
   exec_peak と H-5 の4指標は起動以来の最大で、両 shell の合成最大。
   sbrk_peak < sbrk_capacity、exec_peak < exec_capacity (現行256KiB)、
   kstack < 16KiB、shell_stack < 40KiB、kheap_peak < KHEAP_SIZE を別々に確認する。
4. H-5 の同条件比較は票§0の Ra266 64MB・86ba40c の
   LAN hsync + GUI 往復と同じ構成・入力・起動条件で採る。
   基準は kstack=3544 / shell_stack=20440 / kheap_peak=45176 / resident_peak=131656 B。
   当 worktree に基準の evidence ディレクトリは無いため、PM は元記録の
   正確な操作列・KDEBUG・画像/フォント/画面/経路を確認して再現し、記録に添付する。
   NP21/W の値や異なる操作・KDEBUG・構成の値は参考値とする。
   `resident_peak` を sbrk peak と読み替えない。

## PT snapshot の監査

同じ配備版の `build/out/kernel.elf` / `memmap_layout.h` / `include/memmap.h` を使う。
既存の emulator 読取口で `MEM_FIXED_BOOT_PT_BASE` から連続
`MEM_FIXED_BOOT_PT_COUNT` 枚を各4096 B読み、それぞれ `{"hex":"..."}` として
任意の専用ディスクディレクトリに `pt0.json`〜`pt7.json` を保存する。
この番号は PDE 0〜7 に対応する。採取中はゲストの操作を止める。

```sh
python3 tools/memmap_audit_live.py /path/to/captured-pts --root /path/to/deployed-tree
```

正常時は食い違い0件・rc=0。shell 末尾の stack まで含む現在の全帯を確認する。
kernel BSS の KAPI trampoline 1頁の USER 属性は ELF の symbol から区別する。
guard の PRESENT 化・shell の USER 化・欠落 PT は FAIL。旧 scratch の固定パスを
使わない。実際の AS と master の一致は既存の kernel audit/host 試験も照合する。
